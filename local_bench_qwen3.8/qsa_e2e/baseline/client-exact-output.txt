## Design and Performance of a Distributed Database

A **distributed database** stores data across multiple machines, often in different locations, while presenting a unified logical database to applications. Its goals are to improve **scalability**, **availability**, **fault tolerance**, and **geographic locality**, while managing the costs of network latency, partial failures, and consistency tradeoffs.

A good distributed database design balances:

- **Consistency**: Are all replicas seeing the same data?
- **Availability**: Can the system respond despite failures?
- **Partition tolerance**: Can the system continue operating when network partitions occur?
- **Latency**: How fast are reads and writes?
- **Throughput**: How many operations can the system handle?
- **Durability**: Are committed writes preserved after failures?
- **Operational complexity**: How hard is the system to run and debug?

---

# 1. Core Design Concepts

## 1.1 Data Distribution

Distributed databases distribute data using one or more of the following techniques:

### Sharding / Partitioning

Data is divided into smaller pieces called **shards** or **partitions**.

Common partitioning strategies:

| Strategy | Description | Pros | Cons |
|---|---|---|---|
| Range partitioning | Data split by key ranges, e.g., user IDs 1–1000 | Efficient range queries | Hotspots possible |
| Hash partitioning | Hash key to determine shard | Even distribution | Poor range queries |
| Directory partitioning | Lookup table maps keys to shards | Flexible | Lookup table can become bottleneck |
| Consistent hashing | Nodes and keys placed on hash ring | Easier rebalancing | More complex |
| Composite partitioning | Shard by one key, sort by another | Good for locality | Requires careful key design |

Example:

```text
Shard A: user_id 0–999
Shard B: user_id 1000–1999
Shard C: user_id 2000–2999
```

Sharding improves scalability because different shards can be served by different machines.

---

### Replication

Each shard may have multiple copies called **replicas**.

Example:

```text
Shard A:
  Leader in us-east
  Follower in us-west
  Follower in eu-central
```

Replication improves:

- Availability
- Fault tolerance
- Read scalability
- Geographic locality

But it introduces complexity around consistency and conflict resolution.

---

## 1.2 Architecture Patterns

### Shared-Nothing Architecture

Each node has its own CPU, memory, and storage.

This is common in modern distributed databases because it scales horizontally.

Example:

```text
Node 1: Shard 1
Node 2: Shard 2
Node 3: Shard 3
Node 4: Shard 4
```

Benefits:

- Linear scaling potential
- No shared disk bottleneck
- Failure isolation

Challenges:

- Rebalancing
- Cross-node transactions
- Distributed query execution

---

### Leader-Follower Architecture

One replica is the **leader** or **primary** and handles writes.

Followers replicate the leader’s log and may serve reads.

```text
Write -> Leader -> Replication log -> Followers
Read  -> Leader or Followers
```

Benefits:

- Simple consistency model
- Easy conflict resolution
- Widely used

Challenges:

- Leader becomes a bottleneck
- Leader failure requires election
- Followers may lag

---

### Multi-Leader Architecture

Multiple nodes can accept writes for the same data.

```text
Client A -> Leader 1 -> Replicate -> Leader 2
Client B -> Leader 2 -> Replicate -> Leader 1
```

Benefits:

- Better write availability
- Useful for multi-region deployments
- Can reduce latency for geographically distributed clients

Challenges:

- Conflict resolution
- Causal consistency complexity
- Harder to guarantee strong consistency

---

### Leaderless Architecture

Any replica can accept writes.

Examples include Dynamo-style systems.

```text
Client -> Replica 1
Client -> Replica 2
Client -> Replica 3
```

Benefits:

- High availability
- Low write latency
- No single leader bottleneck

Challenges:

- Conflict resolution
- Weak consistency unless carefully designed
- Requires quorum or vector clocks

---

# 2. Consistency Models

Distributed databases must choose a consistency model.

## 2.1 Strong Consistency

All reads see the most recent committed write.

Example:

```text
Write x = 10 succeeds
Read x returns 10 from any replica
```

Strong consistency is required for systems where correctness depends on exact state, such as:

- Financial balances
- Inventory reservation
- Locking systems
- Configuration management

Implementation often uses consensus protocols such as:

- Raft
- Paxos
- Zab

---

## 2.2 Eventual Consistency

Replicas may temporarily diverge but eventually converge.

Example:

```text
Write x = 10 succeeds in region A
Read x in region B may still return 9 briefly
```

Benefits:

- High availability
- Low latency
- Better partition tolerance

Risks:

- Stale reads
- Write conflicts
- Harder application reasoning

---

## 2.3 Causal Consistency

Writes that are causally related are seen in order.

Example:

```text
Alice writes comment
Alice replies to comment
Bob must see reply only after seeing original comment
```

Causal consistency is stronger than eventual consistency but weaker than linearizability.

---

## 2.4 Read Your Writes Consistency

A client sees its own writes.

Example:

```text
Client writes x = 10
Client reads x
Client sees 10
```

This is useful for user-facing applications.

---

## 2.5 Monotonic Read Consistency

A client never sees older data after seeing newer data.

Example:

```text
Read returns x = 10
Later read cannot return x = 9
```

---

## 2.6 Monotonic Write Consistency

Writes are applied in the order the client issued them.

Example:

```text
Client writes x = 1
Client writes x = 2
Replicas apply x = 1 before x = 2
```

---

# 3. CAP and PACELC

## CAP Theorem

In the presence of a network partition, a distributed system can choose either:

- **Consistency**
- **Availability**

It cannot guarantee both.

```text
CP: Consistency + Partition tolerance
AP: Availability + Partition tolerance
```

Examples:

| System Type | CAP Choice | Behavior |
|---|---|---|
| Strongly consistent database | CP | Rejects writes/reads during partition |
| Highly available key-value store | AP | Allows stale reads or conflicts |

---

## PACELC

PACELC extends CAP by considering latency when there is no partition.

```text
If Partition: choose Availability or Consistency
Else: choose Latency or Consistency
```

This is important because even without failures, systems must choose between:

- Low latency
- Strong consistency

Example:

```text
Write to local region: low latency
Write to global quorum: higher latency but stronger consistency
```

---

# 4. Replication

Replication is one of the most important mechanisms in distributed databases.

## 4.1 Why Replicate?

Replication provides:

1. **Fault tolerance**
   - If one node fails, another can take over.

2. **High availability**
   - Clients can continue reading or writing.

3. **Read scalability**
   - Multiple replicas can serve reads.

4. **Geographic locality**
   - Users can access nearby replicas.

5. **Disaster recovery**
   - Data survives regional failures.

---

## 4.2 Synchronous Replication

The leader waits for followers to acknowledge before committing.

```text
Client -> Leader
Leader -> Follower 1
Leader -> Follower 2
Leader waits for acknowledgments
Leader commits
Leader -> Client success
```

Benefits:

- Strong durability
- Followers are up to date
- Failover can avoid data loss

Costs:

- Higher write latency
- Slower failover if follower is unreachable
- Network distance matters

Example:

```text
Write latency = max(network latency to followers)
```

---

## 4.3 Asynchronous Replication

The leader commits locally and replicates in the background.

```text
Client -> Leader
Leader commits
Leader -> Client success
Leader -> Followers asynchronously
```

Benefits:

- Low write latency
- High throughput
- Tolerates slow followers

Costs:

- Followers may lag
- Failover may lose recent writes
- Reads from followers may be stale

---

## 4.4 Semi-Synchronous Replication

The leader waits for at least one follower to acknowledge, but not necessarily all followers.

```text
Leader commits after one follower confirms
```

This balances durability and latency.

---

## 4.5 Quorum Replication

Writes and reads require agreement from a subset of replicas.

If there are `N` replicas:

```text
Write requires W acknowledgments
Read requires R acknowledgments
```

If:

```text
W + R > N
```

then reads and writes overlap, providing strong consistency.

Example:

```text
N = 3
W = 2
R = 2
```

A write must succeed on 2 replicas.

A read checks 2 replicas.

Because `2 + 2 > 3`, at least one replica must have the latest write.

---

## 4.6 Replication Protocols

### Raft

Raft is a consensus protocol designed for understandability.

Key concepts:

- Leader election
- Log replication
- Safety guarantees

A leader appends entries to its log and sends them to followers.

```text
Leader log:
[1][2][3][4]

Follower log:
[1][2][3]
```

The leader sends entry 4.

Once a majority acknowledges, the entry is committed.

Raft is used in systems such as:

- etcd
- CockroachDB
- TiKV
- MongoDB replica sets

---

### Paxos

Paxos is a family of consensus protocols.

It is powerful but historically harder to understand and implement.

Used in systems such as:

- Google Chubby
- Apache Cassandra lightweight transactions
- Some HBase components

---

### Zab

Zab is used by Apache ZooKeeper.

It provides atomic broadcast and is used for coordination.

---

## 4.7 Replication and Performance

Replication affects performance in several ways.

### Write Amplification

Each write may be sent to multiple replicas.

```text
1 client write = N replica writes
```

This increases network and disk load.

---

### Read Scalability

Reads can be distributed across replicas.

```text
Read traffic can be served by multiple followers
```

This can greatly improve read throughput.

---

### Latency

Synchronous replication increases write latency.

```text
Local write: 1 ms
Cross-region synchronous write: 50–150 ms
```

Asynchronous replication reduces latency but weakens durability guarantees.

---

### Failover Time

If the leader fails, followers must detect failure and elect a new leader.

Failover time depends on:

- Heartbeat timeout
- Election protocol
- Network conditions
- Log catch-up requirements

---

## 4.8 Conflict Resolution

In multi-leader or leaderless systems, concurrent writes can conflict.

Example:

```text
Region A writes x = 1
Region B writes x = 2
```

Possible strategies:

| Strategy | Description |
|---|---|
| Last write wins | Use timestamp; latest timestamp wins |
| Vector clocks | Track causality |
| CRDTs | Mergeable data types |
| Application-level resolution | Application decides |
| Deterministic merge | Custom merge logic |

CRDT examples:

- Counters
- Sets
- Maps
- Registers

CRDTs allow automatic merging without consensus in some cases.

---

# 5. Indexing in Distributed Databases

Indexing is still essential in distributed databases, but it becomes more complex because data and indexes may be distributed across nodes.

## 5.1 Purpose of Indexes

Indexes speed up queries by avoiding full scans.

Example:

```sql
SELECT * FROM users WHERE email = 'alice@example.com';
```

Without an index:

```text
Scan all rows
```

With an index:

```text
Lookup email index -> find row pointer -> fetch row
```

---

## 5.2 Local Indexes

Each shard maintains its own index.

```text
Shard 1: index for shard 1 data
Shard 2: index for shard 2 data
Shard 3: index for shard 3 data
```

Benefits:

- Simple
- Low coordination
- Good for queries filtered by shard key

Example:

```sql
SELECT * FROM users
WHERE user_id = 123;
```

If `user_id` is the shard key, the database can route directly to one shard.

---

## 5.3 Global Indexes

A global index spans all shards.

```text
Global index maps email -> shard
```

Example:

```sql
SELECT * FROM users
WHERE email = 'alice@example.com';
```

The global index tells the system which shard contains Alice.

Benefits:

- Supports queries on non-shard keys
- Avoids scatter-gather queries

Costs:

- Index updates may require cross-shard coordination
- Global indexes can become bottlenecks
- Rebalancing is more complex

---

## 5.4 Scatter-Gather Queries

If no useful index exists, the database may query all shards.

```text
Query -> Shard 1
Query -> Shard 2
Query -> Shard 3
Query -> Shard 4
Merge results
```

This is called a **scatter-gather** query.

Performance:

- Works for small clusters
- Becomes expensive at scale
- Latency is determined by slowest shard
- Throughput decreases as shard count grows

---

## 5.5 Index Types in Distributed Systems

### B-Tree Indexes

Common for equality and range queries.

Useful for:

```sql
WHERE id = 100
WHERE created_at > '2024-01-01'
```

---

### Hash Indexes

Good for equality lookups.

```sql
WHERE key = 'abc'
```

Poor for range queries.

---

### LSM Trees

Log-Structured Merge Trees are common in distributed key-value stores.

Examples:

- Cassandra
- RocksDB
- HBase
- LevelDB

Writes are appended to a memtable and later flushed to sorted SSTables.

Benefits:

- High write throughput
- Good for append-heavy workloads

Costs:

- Compaction overhead
- Read amplification
- Background resource usage

---

### Secondary Indexes

Secondary indexes are indexes on non-primary columns.

Example:

```sql
CREATE INDEX idx_email ON users(email);
```

In distributed databases, secondary indexes can be:

- Local
- Global
- Partitioned
- Replicated

---

### Inverted Indexes

Used for full-text search.

Example:

```text
term -> list of documents
```

Useful for:

```sql
WHERE text MATCH 'distributed database'
```

In distributed search systems, inverted indexes are often sharded across nodes.

---

### Geospatial Indexes

Used for location queries.

Example:

```sql
WHERE ST_Distance(location, point) < 1000
```

Common structures:

- R-tree
- Quadtree
- Geohash
- S2 cells

---

## 5.6 Index Maintenance and Performance

Indexes improve reads but slow writes.

Each write may update:

- Base table
- Primary index
- Secondary indexes
- Global indexes
- Replication log

Write cost:

```text
Write cost = base write + index updates + replication + logging
```

In distributed systems, global index updates may require:

- Cross-node RPC
- Distributed transactions
- Consensus coordination

This can significantly increase latency.

---

## 5.7 Index Design Guidelines

Good distributed index design considers:

1. **Query patterns**
   - Index columns used in `WHERE`, `JOIN`, `ORDER BY`, `GROUP BY`.

2. **Shard key alignment**
   - Queries filtered by shard key are fastest.

3. **Cardinality**
   - High-cardinality columns are often better index candidates.

4. **Write volume**
   - Too many indexes slow writes.

5. **Hotspots**
   - Avoid indexes that concentrate writes on one shard.

6. **Covering indexes**
   - Include enough columns to avoid fetching base rows.

Example:

```sql
CREATE INDEX idx_user_email ON users(email, name);
```

This may answer:

```sql
SELECT email, name FROM users WHERE email = 'alice@example.com';
```

without accessing the base table.

# 6. Transactions in Distributed Databases

A transaction is a logical unit of work that must satisfy **ACID** properties.

## 6.1 ACID Properties

### Atomicity

All operations in a transaction succeed or none do.

```text
Transfer $100 from A to B
Debit A
Credit B
```

If credit fails, debit must be undone.

---

### Consistency

The database moves from one valid state to another.

Example:

```text
Total money before = Total money after
```

---

### Isolation

Concurrent transactions do not interfere incorrectly.

Common isolation levels:

| Isolation Level | Description |
|---|---|
| Read Uncommitted | Can read uncommitted data |
| Read Committed | Reads only committed data |
| Repeatable Read | Same query returns same result during transaction |
| Serializable | Transactions behave as if executed one at a time |

---

### Durability

Committed data survives failures.

Durability is usually achieved through:

- Write-ahead logging
- Replication
- Checkpoints
- Backups

---

## 6.2 Distributed Transactions

A distributed transaction touches multiple nodes or shards.

Example:

```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

If account 1 and account 2 are on different shards, this is a distributed transaction.

---

## 6.3 Two-Phase Commit, 2PC

Two-Phase Commit is a classic protocol for distributed atomic commit.

### Phase 1: Prepare

Coordinator asks all participants:

```text
Can you commit?
```

Participants respond:

```text
Yes
No
```

### Phase 2: Commit or Abort

If all participants say yes:

```text
Coordinator sends COMMIT
```

If any participant says no:

```text
Coordinator sends ABORT
```

Example:

```text
Coordinator -> Shard A: prepare?
Coordinator -> Shard B: prepare?

Shard A: yes
Shard B: yes

Coordinator -> Shard A: commit
Coordinator -> Shard B: commit
```

---

## 6.4 Problems with 2PC

2PC provides atomicity but has drawbacks.

### Blocking

If the coordinator fails after participants prepare, participants may block.

```text
Shard A prepared
Shard B prepared
Coordinator crashes
```

Participants may not know whether to commit or abort.

---

### Latency

2PC requires multiple round trips.

```text
Prepare round trip
Commit round trip
```

This increases transaction latency.

---

### Availability

If a participant is unavailable, the transaction may fail or block.

This conflicts with high availability goals.

---

## 6.5 Three-Phase Commit, 3PC

Three-Phase Commit attempts to reduce blocking.

Phases:

1. Can commit?
2. Pre-commit
3. Commit

However, 3PC still cannot solve all failure scenarios and is rarely used in practice.

---

## 6.6 Consensus-Based Transactions

Modern distributed databases often use consensus protocols like Raft or Paxos instead of traditional 2PC.

Example:

```text
Transaction log entry replicated to majority
Once majority acknowledges, transaction is committed
```

This provides:

- Atomic commit
- Fault tolerance
- Leader-based coordination

Examples:

- CockroachDB
- TiDB
- Spanner
- FoundationDB

---

## 6.7 Spanner and TrueTime

Google Spanner provides external consistency using:

- Synchronous replication
- Paxos
- TrueTime API

TrueTime uses GPS and atomic clocks to bound clock uncertainty.

Spanner can wait for the maximum possible timestamp uncertainty before committing, ensuring globally ordered transactions.

This is powerful but complex and expensive.

---

## 6.8 Optimistic Concurrency Control

Optimistic concurrency assumes conflicts are rare.

A transaction:

1. Reads data
2. Tracks versions
3. At commit, checks whether versions changed
4. Aborts if conflict detected

Example:

```text
Transaction reads row version 5
Transaction writes row version 6
Commit checks current version
If current version is still 5, commit succeeds
If current version changed, abort
```

Benefits:

- Low locking overhead
- Good for read-heavy workloads

Costs:

- High abort rate under contention
- Requires retries

---

## 6.9 Pessimistic Concurrency Control

Pessimistic concurrency locks data before writing.

Example:

```text
Transaction locks row
Transaction updates row
Transaction commits
Lock released
```

Benefits:

- Prevents conflicts
- Good for high-contention workloads

Costs:

- Lock waits
- Deadlocks
- Reduced throughput

---

## 6.10 Snapshot Isolation

Snapshot isolation allows transactions to read from a consistent snapshot.

```text
Transaction sees database state as of start time
```

Writers do not block readers.

However, snapshot isolation can allow anomalies such as write skew.

Example:

```text
Two doctors on call
Each checks if at least one doctor is on call
Each decides to go on vacation
Both succeed
No doctor remains
```

Serializable isolation prevents this.

---

## 6.11 Serializable Isolation

Serializable isolation guarantees that concurrent transactions produce the same result as some serial execution.

Implementation methods:

- Two-phase locking
- Serializable snapshot isolation
- Optimistic validation
- Predicate locking
- MVCC with conflict detection

Serializable isolation is the strongest isolation level but can reduce performance.

---

## 6.12 Transaction Performance Considerations

Distributed transaction performance depends on:

### Number of Participants

More shards means more coordination.

```text
1 shard transaction: fast
3 shard transaction: slower
10 shard transaction: much slower
```

---

### Network Latency

Cross-region transactions are expensive.

```text
Same data center: 0.1–1 ms
Same region: 1–10 ms
Cross-region: 50–200 ms
```

---

### Contention

Hot rows cause lock waits or aborts.

Example:

```text
Inventory item with only 10 units
Thousands of concurrent purchases
```

This creates severe contention.

---

### Transaction Size

Large transactions are harder to coordinate and more likely to conflict.

Best practice:

```text
Keep transactions short
Avoid cross-region transactions
Batch carefully
```

---

### Retry Logic

Optimistic systems require retries.

Applications must handle:

```text
Transaction aborted due to conflict
Retry transaction
```

---

# 7. Recovery in Distributed Databases

Recovery ensures that committed transactions survive failures and that the database returns to a consistent state.

## 7.1 Failure Types

Distributed databases must handle:

### Node Failure

A single machine crashes.

### Disk Failure

Storage becomes unavailable or corrupted.

### Network Partition

Nodes cannot communicate.

### Region Failure

An entire data center becomes unavailable.

### Software Failure

A bug causes incorrect behavior.

### Human Error

Accidental deletion or misconfiguration.

---

## 7.2 Write-Ahead Logging

Write-ahead logging, WAL, is fundamental to recovery.

Before modifying data, the database writes a log record to durable storage.

```text
1. Write log record
2. Flush log to disk
3. Modify data
```

Log records may include:

```text
Transaction ID
Before image
After image
Commit record
Abort record
```

Benefits:

- Crash recovery
- Rollback
- Replication
- Point-in-time recovery

---

## 7.3 Checkpointing

A checkpoint records the state of the database at a point in time.

```text
Checkpoint:
  All dirty pages flushed
  Log position recorded
```

During recovery, the database can start from the last checkpoint instead of replaying the entire log.

Example:

```text
Log:
[1][2][3][checkpoint][4][5][6]

Recovery starts from checkpoint
```

---

## 7.4 Crash Recovery

After a crash, the database uses the log to restore state.

### Undo

Undo transactions that were not committed.

```text
If transaction did not commit, reverse its changes
```

### Redo

Redo transactions that were committed but whose changes may not have reached disk.

```text
If transaction committed, ensure changes are applied
```

Example:

```text
T1 committed
T2 not committed

Recovery:
Redo T1
Undo T2
```

---

## 7.5 Replication-Based Recovery

Replication provides redundancy.

If a leader fails:

```text
Follower becomes leader
```

The new leader must ensure:

- It has the latest committed data
- It does not resurrect lost writes
- It does not violate consensus safety

Consensus protocols help ensure that only a node with the most up-to-date log can become leader.

---

## 7.6 Leader Election

When a leader fails, followers elect a new leader.

Example using Raft:

```text
Follower becomes candidate
Candidate requests votes
Candidate with majority becomes leader
```

Election timeout should be randomized to avoid split votes.

```text
Timeout = random(150ms, 300ms)
```

---

## 7.7 Fencing

Fencing prevents an old leader from continuing to serve writes after a new leader is elected.

Example:

```text
Old leader thinks it is still leader
New leader is elected
Old leader sends write
```

Fencing tokens or epochs prevent this:

```text
Old leader token = 10
New leader token = 11
Replica rejects token 10
```

---

## 7.8 Point-in-Time Recovery

Point-in-time recovery restores the database to a specific moment.

Example:

```text
Restore backup from 02:00
Replay WAL from 02:00 to 03:45
```

Useful for:

- Accidental deletion
- Corrupted data
- Bad migration
- Security incident

---

## 7.9 Backups

Backups are essential for disaster recovery.

Types:

### Full Backup

Complete copy of the database.

```text
Backup entire database
```

Pros:

- Simple restore

Cons:

- Large storage
- Slow

---

### Incremental Backup

Only changes since last backup.

```text
Full backup
Incremental backup
Incremental backup
```

Pros:

- Smaller storage

Cons:

- Restore requires multiple files

---

### Differential Backup

Changes since last full backup.

Pros:

- Faster restore than incremental

Cons:

- Larger than incremental

---

### Continuous Backup

Backups are taken continuously or near-continuously.

Example:

```text
WAL archiving
```

---

## 7.10 Backup Consistency

Backups must be transactionally consistent.

A naive file copy may capture inconsistent state.

Example:

```text
Copy table A
Transaction commits
Copy table B
```

The backup may contain inconsistent data.

Solutions:

- Locking
- Snapshots
- Write quiescing
- Log-based consistent backups
- Database-native backup tools

---

## 7.11 Recovery Objectives

Databases define recovery objectives:

### RPO, Recovery Point Objective

Maximum acceptable data loss.

Example:

```text
RPO = 5 minutes
```

Means the system can lose at most 5 minutes of data.

---

### RTO, Recovery Time Objective

Maximum acceptable downtime.

Example:

```text
RTO = 15 minutes
```

Means the system must be restored within 15 minutes.

---

## 7.12 Recovery in Multi-Region Systems

Multi-region recovery must handle:

- Regional outage
- Network partition
- Clock skew
- Conflicting writes
- Failover and failback

Example:

```text
Primary region fails
Secondary region promoted
Clients redirected
Primary region rejoins
Data reconciled
```

Failback is often harder than failover because the failed region may have stale or conflicting data.

---

# 8. Performance of Distributed Databases

Performance depends on architecture, workload, and consistency requirements.

## 8.1 Key Performance Metrics

### Latency

Time to complete an operation.

```text
p50 latency
p95 latency
p99 latency
```

Tail latency is especially important in distributed systems.

Example:

```text
Average latency = 10 ms
p99 latency = 200 ms
```

The p99 may dominate user experience.

---

### Throughput

Number of operations per second.

```text
reads/sec
writes/sec
transactions/sec
```

---

### Scalability

How performance changes as nodes are added.

Ideal:

```text
Double nodes -> double throughput
```

Real systems face:

- Coordination overhead
- Hotspots
- Network bottlenecks
- Shared metadata limits

---

### Availability

Percentage of time the system can serve requests.

```text
99.9% = 8.76 hours downtime/year
99.99% = 52.6 minutes downtime/year
99.999% = 5.26 minutes downtime/year
```

---

### Durability

Probability that committed data survives failure.

---

## 8.2 Factors Affecting Performance

### Network Latency

Distributed databases are network-bound.

```text
Local disk: 0.1–1 ms
Same rack: 0.1–0.5 ms
Same data center: 0.5–2 ms
Same region: 1–10 ms
Cross-region: 50–200 ms
```

Cross-region synchronous replication can be expensive.

---

### Disk I/O

SSDs improve performance, but distributed systems still depend on:

- Write amplification
- Compaction
- Log flushing
- Index maintenance

---

### CPU

Serialization, compression, encryption, query planning, and consensus all consume CPU.

---

### Memory

Caches improve performance:

- Block cache
- Row cache
- Query cache
- Index cache

But cache invalidation across nodes is complex.

---

### Data Skew

Hot partitions limit scalability.

Example:

```text
One user has 100 million events
```

If all events are on one shard, that shard becomes a bottleneck.

---

### Query Complexity

Distributed joins are expensive.

Example:

```sql
SELECT *
FROM orders
JOIN customers ON orders.customer_id = customers.id
WHERE customers.region = 'EU';
```

If `orders` and `customers` are sharded differently, the database may need to move large amounts of data.

---

## 8.3 Performance Optimization Techniques

### Co-locate Related Data

Place related data on the same shard.

Example:

```text
Shard key = customer_id
Orders and customers for same customer are on same shard
```

This reduces cross-shard transactions and joins.

---

### Use Appropriate Shard Keys

Good shard keys:

- Distribute load evenly
- Match query patterns
- Avoid hotspots

Bad shard keys:

- Sequential IDs
- Low-cardinality columns
- Frequently updated single rows

---

### Cache Reads

Use caches for hot data.

Example:

```text
Redis cache in front of database
```

But cache consistency must be managed.

---

### Batch Writes

Batching reduces network round trips.

Example:

```text
1000 individual writes
vs
1 batch of 1000 writes
```

---

### Use Local Reads When Possible

Read from nearby replicas if consistency requirements allow.

```text
User in Europe reads from European replica
```

---

### Avoid Cross-Region Transactions

Cross-region transactions are slow.

Better patterns:

- Local transactions
- Asynchronous replication
- Eventual consistency
- Idempotent operations
- Conflict-free data types

---

### Use Indexes Carefully

Indexes improve reads but increase write cost.

In distributed systems, global indexes can be especially expensive.

---

### Monitor Tail Latency

Average latency can hide problems.

Track:

```text
p50
p90
p95
p99
p999
```

---

## 8.4 Performance Tradeoffs

| Design Choice | Benefit | Cost |
|---|---|---|
| Synchronous replication | Strong durability | Higher latency |
| Asynchronous replication | Low latency | Possible data loss |
| Strong consistency | Correctness | Lower availability |
| Eventual consistency | Availability | Stale reads |
| Global indexes | Flexible queries | Write overhead |
| Sharding | Scalability | Complex transactions |
| Multi-leader | Write availability | Conflict resolution |
| Serializable isolation | Strong correctness | Lower throughput |

---

# 9. Example: Designing a Distributed Database

Suppose we design a distributed database for a global e-commerce application.

## Requirements

- High availability
- Low latency for users worldwide
- Strong consistency for payments
- Eventual consistency acceptable for product browsing
- Support for transactions

## Design

### Data Partitioning

Partition users and orders by `customer_id`.

```text
Shard key = customer_id
```

This co-locates customer data and orders.

---

### Replication

Use three replicas per shard.

```text
Leader in customer region
Follower in nearby region
Follower in disaster recovery region
```

For payments:

```text
Synchronous replication to at least one follower
```

For product catalog:

```text
Asynchronous replication
```

---

### Transactions

Payment transactions use:

```text
Serializable isolation
Consensus-based commit
```

Product browsing uses:

```text
Read-your-writes or eventual consistency
```

---

### Indexing

Use local indexes for queries filtered by `customer_id`.

Use global indexes for:

```sql
WHERE email = ?
WHERE order_number = ?
```

But monitor write overhead.

---

### Recovery

Use:

- WAL
- Checkpoints
- Continuous backups
- Point-in-time recovery
- Automated failover
- Fencing tokens

---

# 10. Common Pitfalls

## 10.1 Poor Shard Key Choice

Bad:

```text
Shard by country
```

Problem:

```text
One country may have most traffic
```

Better:

```text
Shard by customer_id
```

## 10.2 Too Many Global Indexes

Each write may update many global indexes.

This can cause:

- High write latency
- Cross-shard transactions
- Hot index shards

## 10.3 Cross-Region Transactions

Cross-region transactions can be slow and fragile.

Avoid unless necessary.

## 10.4 Ignoring Tail Latency

A system may look healthy on average but have terrible p99 latency.

## 10.5 Assuming Network Reliability

Networks partition.

Design for partial failure.

## 10.6 Weak Recovery Testing

Backups are useless if not tested.

Regularly test:

- Restore
- Failover
- Point-in-time recovery
- Region outage

# 11. Summary

A distributed database is designed to scale across multiple machines while managing consistency, availability, and failure.

## Replication

Replication provides fault tolerance, availability, and read scalability.

Key choices:

- Synchronous vs asynchronous
- Leader-follower vs multi-leader vs leaderless
- Quorum reads and writes
- Consensus protocols such as Raft or Paxos
- Conflict resolution in multi-leader systems

---

## Indexing

Indexing remains critical but becomes more complex in distributed systems.

Key choices:

- Local vs global indexes
- Shard-key-aligned indexes
- LSM trees for write-heavy systems
- Avoiding scatter-gather queries
- Balancing read speed against write overhead

---

## Transactions

Distributed transactions must coordinate across nodes.

Key mechanisms:

- Two-phase commit
- Consensus-based commit
- Optimistic concurrency control
- Pessimistic concurrency control
- Snapshot isolation
- Serializable isolation

Performance depends heavily on participant count, network latency, contention, and isolation level.

---

## Recovery

Recovery ensures durability and consistency after failures.

Key mechanisms:

- Write-ahead logging
- Checkpoints
- Undo/redo recovery
- Leader election
- Fencing
- Backups
- Point-in-time recovery
- RPO and RTO planning

---

## Performance

Distributed database performance is dominated by:

- Network latency
- Coordination overhead
- Replication strategy
- Index maintenance
- Data skew
- Transaction complexity
- Failure handling

The best design depends on the workload.

For example:

```text
Payment system:
  Strong consistency
  Serializable transactions
  Synchronous replication
  Careful recovery

Analytics system:
  Eventual consistency
  Batch writes
  Sharded storage
  High throughput

Global user profile system:
  Multi-region replication
  Low latency reads
  Conflict resolution
  Read-your-writes consistency
```

In short, a distributed database is not just a database copied across machines. It is a carefully engineered system that balances **data placement**, **replication**, **consistency**, **transaction coordination**, **indexing**, and **recovery** to meet performance and reliability goals.

A **distributed database** is a database whose data is stored on multiple computers, often in different locations, but it behaves like one logical database to the application.

Its main goals are:

- **Scalability**: handle more data and traffic by adding machines.
- **Availability**: keep working when some machines fail.
- **Fault tolerance**: survive crashes, disk failures, or network problems.
- **Low latency**: serve users from nearby locations.
- **Consistency**: ensure data is correct and reliable.

The main challenge is that network communication is slow and unreliable, so the system must decide how to balance **consistency**, **availability**, and **performance**.

---

## 1. Design of a Distributed Database

A distributed database usually uses two main techniques:

### A. Sharding

The data is split into smaller pieces called **shards**.

Example:

```text
Shard 1: users 1–1000
Shard 2: users 1001–2000
Shard 3: users 2001–3000
```

Each shard can live on a different machine.

This helps scalability because different machines can handle different parts of the workload.

---

### B. Replication

Each shard can have multiple copies called **replicas**.

Example:

```text
Shard 1:
  Leader in New York
  Follower in London
  Follower in Singapore
```

Replication helps with:

- Fault tolerance
- High availability
- Faster reads
- Disaster recovery

---

## 2. Replication

**Replication** means copying data across multiple nodes.

### Synchronous Replication

The leader waits for followers to confirm before saying the write succeeded.

```text
Client writes
Leader writes
Leader waits for follower confirmation
Leader commits
```

Benefits:

- Strong durability
- Followers are up to date
- Less risk of data loss

Costs:

- Higher write latency
- Slower if followers are far away

---

### Asynchronous Replication

The leader commits locally and copies data in the background.

```text
Client writes
Leader commits
Leader returns success
Leader later copies to followers
```

Benefits:

- Faster writes
- Better performance

Costs:

- Followers may lag
- Recent writes may be lost if leader crashes
- Reads from followers may be stale

---

### Quorum Replication

A write succeeds if enough replicas acknowledge it.

Example:

```text
N = 3 replicas
W = 2 writes required
R = 2 reads required
```

If:

```text
W + R > N
```

then reads and writes overlap, giving stronger consistency.

Example:

```text
3 replicas
Write must succeed on 2
Read checks 2
```

At least one replica must have the latest data.

---

## 3. Indexing

An **index** is a data structure that helps the database find data quickly.

Example:

```sql
SELECT * FROM users WHERE email = 'alice@example.com';
```

Without an index, the database may scan all rows.

With an index, it can jump directly to the matching row.

---

### Local Index

Each shard has its own index.

```text
Shard 1 has index for Shard 1 data
Shard 2 has index for Shard 2 data
```

Good when queries include the shard key.

Example:

```sql
SELECT * FROM users WHERE user_id = 123;
```

If `user_id` is the shard key, the database knows exactly which shard to query.

---

### Global Index

A global index spans all shards.

Example:

```text
email index maps email -> shard
```

Useful for queries like:

```sql
SELECT * FROM users WHERE email = 'alice@example.com';
```

Benefits:

- Supports queries on non-shard columns

Costs:

- More complex
- Slower writes
- May require cross-shard coordination

---

### Scatter-Gather Query

If there is no useful index, the database may query all shards.

```text
Query -> Shard 1
Query -> Shard 2
Query -> Shard 3
Merge results
```

This can be slow and expensive at large scale.

---

## 4. Transactions

A **transaction** is a group of operations that must either all succeed or all fail.

Example:

```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

This transfers money from account 1 to account 2.

If one update fails, the whole transaction should fail.

---

### ACID Properties

Distributed transactions usually try to support ACID:

#### Atomicity

All or nothing.

```text
Either both updates happen, or neither happens.
```

#### Consistency

The database remains in a valid state.

```text
Total money before = total money after.
```

#### Isolation

Concurrent transactions do not interfere badly.

#### Durability

Once committed, data survives failures.

---

### Two-Phase Commit

A classic way to coordinate distributed transactions is **Two-Phase Commit**, or 2PC.

#### Phase 1: Prepare

The coordinator asks all participants:

```text
Can you commit?
```

Each participant answers yes or no.

#### Phase 2: Commit or Abort

If everyone says yes:

```text
Commit
```

If anyone says no:

```text
Abort
```

Example:

```text
Coordinator asks Shard A: prepare?
Coordinator asks Shard B: prepare?

Shard A: yes
Shard B: yes

Coordinator tells Shard A: commit
Coordinator tells Shard B: commit
```

---

### Problems with 2PC

2PC can be slow because it requires multiple network round trips.

It can also block if the coordinator crashes after participants have prepared.

Example:

```text
Shard A prepared
Shard B prepared
Coordinator crashes
```

Now the shards may not know whether to commit or abort.

---

### Modern Approach

Many modern distributed databases use consensus protocols like **Raft** or **Paxos** instead of traditional 2PC.

A transaction log entry is replicated to a majority of nodes.

```text
Write log entry
Replicate to majority
Majority acknowledges
Commit
```

This gives atomicity and fault tolerance.

---

## 5. Recovery

**Recovery** means restoring the database after failures.

Failures can include:

- Node crash
- Disk failure
- Network partition
- Region outage
- Software bug
- Human error

---

### Write-Ahead Logging

Before changing data, the database writes a log record to disk.

```text
1. Write log record
2. Flush log to disk
3. Modify data
```

This helps recovery after a crash.

---

### Undo and Redo

After a crash, the database uses the log.

#### Undo

Reverse transactions that did not commit.

```text
If transaction did not finish, undo its changes.
```

#### Redo

Reapply transactions that committed but may not have reached disk.

```text
If transaction committed, make sure its changes are present.
```

Example:

```text
T1 committed
T2 not committed

Recovery:
Redo T1
Undo T2
```

---

### Checkpointing

A checkpoint records the database state at a point in time.

```text
Checkpoint
```

During recovery, the database can start from the last checkpoint instead of replaying the entire log.

---

### Leader Election

If the leader fails, followers choose a new leader.

Example using Raft:

```text
Follower becomes candidate
Candidate asks other nodes for votes
Candidate with majority becomes leader
```

---

### Fencing

Fencing prevents an old leader from continuing to write after a new leader is elected.

Example:

```text
Old leader token = 10
New leader token = 11
Replica rejects old token 10
```

This prevents split-brain problems.

---

### Backups

Backups are needed for disaster recovery.

Types include:

- Full backup
- Incremental backup
- Differential backup
- Continuous WAL backup

A backup must be consistent, meaning it should not capture half-finished transactions.

---

## 6. Performance

Performance depends on several factors.

### Network Latency

Distributed databases are often limited by network speed.

Approximate latency:

```text
Local disk:       0.1–1 ms
Same data center: 0.5–2 ms
Same region:      1–10 ms
Cross-region:     50–200 ms
```

Cross-region synchronous replication can be slow.

---

### Write Amplification

If data is replicated to 3 nodes, one client write may become 3 writes.

```text
1 client write = 3 replica writes
```

This increases network and disk load.

---

### Read Scalability

Replicas can serve reads.

```text
Many reads can be handled by many followers
```

This improves read throughput.

---

### Hotspots

If one shard receives most of the traffic, it becomes a bottleneck.

Example:

```text
One popular product has most orders
```

If all orders for that product are on one shard, that shard becomes overloaded.

---

### Transaction Cost

Distributed transactions are slower than local transactions.

```text
1 shard transaction: fast
3 shard transaction: slower
10 shard transaction: much slower
```

Cross-region transactions are especially expensive.

---

## 7. Main Tradeoffs

| Choice | Benefit | Cost |
|---|---|---|
| Synchronous replication | Strong durability | Higher latency |
| Asynchronous replication | Faster writes | Possible data loss |
| Strong consistency | Correct data | Lower availability |
| Eventual consistency | High availability | Stale reads |
| Sharding | Scalability | Complex transactions |
| Global indexes | Flexible queries | Slower writes |
| Multi-leader | Write availability | Conflict resolution |
| Serializable isolation | Strong correctness | Lower throughput |

---

## Simple Summary

A distributed database stores data across multiple machines.

- **Replication** copies data for availability and fault tolerance.
- **Indexing** speeds up queries but can become complex across shards.
- **Transactions** ensure groups of operations succeed or fail together, but distributed transactions require coordination.
- **Recovery** uses logs, checkpoints, backups, leader election, and consensus to restore the database after failures.

The main design challenge is choosing the right balance between:

```text
Consistency
Availability
Latency
Throughput
Durability
```

A payment system may need strong consistency and synchronous replication.  
A social media feed may prefer low latency and eventual consistency.  
An analytics system may prioritize high throughput and batch writes.
