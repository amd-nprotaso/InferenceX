## Design and Performance of a Distributed Database

A **distributed database** stores data across multiple independent machines or sites while presenting a single logical database to users and applications. Its design must balance **scalability, availability, consistency, latency, throughput, fault tolerance, and recovery**. The main design areas are **data distribution, replication, indexing, transactions, and recovery**. Each choice affects performance directly.

---

## 1. Core Design Goals

A distributed database is usually designed to achieve:

1. **Scalability**
   - Scale out by adding nodes.
   - Distribute storage, compute, and network load.

2. **Availability**
   - Continue operating despite node or network failures.
   - Use replication and failover.

3. **Fault tolerance**
   - Survive disk, node, rack, zone, or region failures.
   - Recover without data loss where required.

4. **Performance**
   - Reduce network latency by placing data near users.
   - Parallelize queries across nodes.
   - Balance hot and cold data.

5. **Transparency**
   - Users should not need to know where data is stored.
   - The system should hide fragmentation, replication, and location details.

6. **Consistency control**
   - Provide strong consistency when needed.
   - Allow weaker consistency for higher availability or lower latency.

---

## 2. Data Distribution and Partitioning

Before discussing replication, indexing, transactions, and recovery, it is important to understand how data is distributed.

### Partitioning Strategies

#### Hash Partitioning

Data is assigned to nodes using a hash of the partition key.

Example:

```text
node = hash(customer_id) % number_of_nodes
```

**Advantages**

- Even data distribution.
- Good for uniform workloads.
- Simple routing.

**Disadvantages**

- Poor range queries.
- Rebalancing can be expensive.
- Hot keys can still overload one node.

#### Range Partitioning

Data is divided by ranges of a key.

Example:

```text
Node 1: customer_id 1–10,000,000
Node 2: customer_id 10,000,001–20,000,000
```

**Advantages**

- Efficient range scans.
- Good locality for related data.

**Disadvantages**

- Skew is common.
- Hot ranges can overload nodes.
- Rebalancing requires moving contiguous ranges.

#### Directory or Lookup Partitioning

A directory maps keys to nodes.

**Advantages**

- Flexible placement.
- Can move data without changing hash functions.

**Disadvantages**

- Directory lookup adds latency.
- Directory itself must be highly available.

### Partition Key Design

The partition key is one of the most important performance decisions.

Good partition keys:

- Distribute writes evenly.
- Keep related data together.
- Minimize cross-partition transactions.
- Avoid hotspots.

Bad partition keys:

- Timestamps that always write to the latest partition.
- Low-cardinality fields such as country or status.
- Keys that cause most transactions to touch many partitions.

---

## 3. Replication

Replication stores copies of data on multiple nodes. It improves availability, durability, and read performance, but it introduces consistency and latency tradeoffs.

---

### 3.1 Why Replicate?

Replication is used for:

1. **High availability**
   - If one node fails, another can serve requests.

2. **Durability**
   - Data survives disk or node failure.

3. **Read scaling**
   - Reads can be served from replicas.

4. **Geographic locality**
   - Users read from nearby replicas.

5. **Disaster recovery**
   - Remote replicas can survive regional failures.

---

### 3.2 Replication Models

#### Leader-Follower Replication

One node is the leader. It accepts writes and sends changes to followers.

**Write path**

```text
Client → Leader → Followers
```

**Read path**

```text
Client → Leader or Follower
```

**Advantages**

- Simple conflict resolution.
- Strong consistency is easier if reads go to the leader.
- Widely used in relational databases and many distributed systems.

**Disadvantages**

- Leader can become a bottleneck.
- Leader failure requires election.
- Followers may lag.

---

#### Multi-Leader Replication

Multiple nodes accept writes and replicate changes to each other.

**Advantages**

- Better write availability.
- Useful for geographically distributed deployments.
- Can reduce write latency by accepting writes locally.

**Disadvantages**

- Conflict resolution is required.
- Strong consistency is harder.
- More complex failure handling.

Common conflict resolution methods:

- Last-write-wins using timestamps.
- Vector clocks.
- Application-level merge logic.
- CRDTs, such as counters, sets, or maps.

---

#### Leaderless Replication

Any replica can accept writes. The system uses quorum rules to determine consistency.

**Advantages**

- High availability.
- No single leader bottleneck.
- Good for some NoSQL workloads.

**Disadvantages**

- Conflict resolution is complex.
- Read-your-writes consistency may require special handling.
- Tail latency can be high if some replicas are slow.

---

### 3.3 Synchronous vs Asynchronous Replication

#### Synchronous Replication

The leader waits for replicas to acknowledge before confirming the write.

```text
Client → Leader
Leader → Replica
Replica acknowledges
Leader confirms to client
```

**Advantages**

- Strong durability.
- Low risk of data loss if leader fails.
- Easier to provide strong consistency.

**Disadvantages**

- Higher write latency.
- Write throughput depends on slowest required replica.
- Network failures can block writes.

---

#### Asynchronous Replication

The leader confirms the write before replicas acknowledge.

```text
Client → Leader
Leader confirms to client
Leader sends to replicas later
```

**Advantages**

- Lower write latency.
- Higher throughput.
- Better tolerance of network delays.

**Disadvantages**

- Replicas may lag.
- Leader failure can lose recent writes.
- Reads from followers may be stale.

---

#### Semi-Synchronous Replication

The leader waits for at least one replica to acknowledge, but not necessarily all replicas.

This is a compromise between durability and latency.

---

### 3.4 Quorum Replication

In leaderless systems, consistency is often controlled by quorum rules.

Let:

```text
N = number of replicas
W = number of replicas that must acknowledge a write
R = number of replicas that must be read
```

A common rule is:

```text
R + W > N
```

This ensures that reads and writes overlap, so a read should see the latest committed write.

Example:

```text
N = 3
W = 2
R = 2
```

Because:

```text
2 + 2 > 3
```

the system can provide strong consistency for many operations.

**Performance tradeoff**

- Higher `W` improves write durability but increases write latency.
- Higher `R` improves read consistency but increases read latency.
- Lower `W` and `R` improve performance but weaken consistency.

---

### 3.5 Replication and Performance

Replication affects performance in several ways.

#### Write Amplification

If data is replicated to three nodes, a single logical write may become three physical writes.

```text
1 client write → 3 replica writes
```

This increases disk I/O and network traffic.

#### Network Latency

Synchronous replication across regions can add significant latency.

Example:

```text
US leader → Europe follower
```

Round-trip latency may be 100–200 ms or more.

#### Tail Latency

If the system waits for the slowest replica, occasional slow nodes can increase tail latency.

Techniques to reduce tail latency:

- Hedge requests.
- Use quorum instead of all replicas.
- Use local synchronous replication and asynchronous cross-region replication.
- Use fast local disks and network.

#### Read Scaling

Replicas can serve reads, increasing read throughput.

However, if reads require strong consistency, they may need to go to the leader or use quorum reads, reducing the benefit.

---

## 4. Indexing in Distributed Databases

Indexes improve query performance but are harder to manage in distributed systems because index entries may be spread across many nodes.

---

### 4.1 Types of Indexes

Common index types include:

1. **Primary or clustered index**
   - Determines physical data layout.

2. **Secondary index**
   - Index on non-primary columns.

3. **Covering index**
   - Contains all columns needed by a query.

4. **Composite index**
   - Index on multiple columns.

5. **Full-text index**
   - For text search.

6. **Geospatial index**
   - For location queries.

7. **Vector index**
   - For similarity search.

---

### 4.2 Local vs Global Indexes

#### Local Index

Each partition has its own index.

Example:

```text
Partition 1 has index for its data
Partition 2 has index for its data
```

**Advantages**

- Index updates are local.
- Better write locality.
- Easier rebalancing.
- Less cross-node coordination.

**Disadvantages**

- Queries may need to search many partitions.
- Scatter-gather queries can be expensive.
- Global uniqueness is harder to enforce.

---

#### Global Index

The index is maintained separately from the data partitions.

Example:

```text
email → customer_id
```

The index may be stored on different nodes from the customer data.

**Advantages**

- Efficient lookup by non-partition key.
- Can enforce global uniqueness.
- Good for queries that do not know the partition key.

**Disadvantages**

- Index updates may require distributed transactions.
- Global index can become a bottleneck.
- Rebalancing is more complex.
- Network traffic increases.

---

#### Partitioned Global Index

A global index is itself partitioned.

This reduces the bottleneck problem but still requires coordination.

---

### 4.3 Index Maintenance and Performance

When data is inserted, updated, or deleted, indexes must be updated.

#### Synchronous Index Update

The write is not considered complete until the index is updated.

**Advantages**

- Index is always consistent.
- Reads can trust the index.

**Disadvantages**

- Higher write latency.
- More distributed coordination.
- Index failures can block writes.

#### Asynchronous Index Update

The primary data is written first, and the index is updated later.

**Advantages**

- Lower write latency.
- Higher throughput.

**Disadvantages**

- Index may be stale.
- Queries may miss recent data.
- Requires reconciliation or repair processes.

---

### 4.4 Query Routing and Indexes

A distributed query optimizer must decide how to execute a query.

Example query:

```sql
SELECT *
FROM orders
WHERE customer_id = 123;
```

If `customer_id` is the partition key, the query can be routed directly to one partition.

Example query:

```sql
SELECT *
FROM orders
WHERE status = 'pending';
```

If `status` is not the partition key, the system may need to:

1. Use a global secondary index.
2. Scan all partitions.
3. Use a materialized view.
4. Use a search index.

Performance depends heavily on whether the query can be routed to a small number of partitions.

---

### 4.5 Index Performance Problems

#### Hot Index Partitions

If many writes update the same index range, one index partition can become overloaded.

Example:

```text
status = 'active'
```

If most rows are active, the index entry for `active` becomes hot.

#### Scatter-Gather Fan-Out

If a query must contact many partitions, latency increases.

Example:

```text
100 partitions × 5 ms network latency = 500 ms worst-case fan-out
```

#### Index Size

Large indexes consume memory and disk.

If the index does not fit in memory, query latency increases.

#### Rebalancing

Moving data requires moving index entries too.

This can cause temporary performance degradation.

---

## 5. Transactions in Distributed Databases

A distributed transaction may involve multiple partitions or nodes. This makes concurrency control and atomic commit more complex.

---

### 5.1 ACID in Distributed Systems

Distributed databases often aim to preserve ACID properties:

#### Atomicity

All parts of a transaction succeed or fail together.

#### Consistency

The database moves from one valid state to another.

#### Isolation

Concurrent transactions do not interfere incorrectly.

#### Durability

Committed transactions survive failures.

In distributed systems, atomicity and isolation are especially difficult because participants may fail independently.

---

### 5.2 Isolation Levels

Common isolation levels include:

1. **Read uncommitted**
   - May read dirty data.
   - Fastest but unsafe.

2. **Read committed**
   - Reads only committed data.
   - May see non-repeatable reads.

3. **Repeatable read**
   - Same query returns same result within transaction.
   - May see phantom rows.

4. **Serializable**
   - Transactions behave as if executed one at a time.
   - Strongest isolation.
   - Highest coordination cost.

Distributed databases may provide different isolation levels depending on the workload.

---

### 5.3 Concurrency Control

#### Locking

Transactions lock data items to prevent conflicts.

**Pessimistic locking**

- Locks are acquired before writing.
- Good for high contention.
- Can reduce throughput.

**Optimistic locking**

- Transactions proceed without locks.
- Conflicts are detected at commit time.
- Good for low contention.
- Can cause retries under high contention.

#### MVCC

Multi-version concurrency control keeps multiple versions of data.

Readers see a consistent snapshot.

Writers create new versions.

**Advantages**

- Readers do not block writers.
- Writers do not block readers.
- Good for analytical and mixed workloads.

**Disadvantages**

- Requires garbage collection of old versions.
- Can increase storage and memory usage.
- Long-running transactions can cause bloat.

---

### 5.4 Two-Phase Commit

The classic protocol for distributed atomic commit is **Two-Phase Commit**, or 2PC.

Participants:

- Coordinator
- One or more participants

#### Phase 1: Prepare

Coordinator asks all participants:

```text
Can you commit?
```

Each participant writes a prepare record to stable storage and replies yes or no.

#### Phase 2: Commit or Abort

If all participants vote yes, coordinator sends commit.

If any participant votes no, coordinator sends abort.

```text
Coordinator → Participants: prepare
Participants → Coordinator: yes/no
Coordinator → Participants: commit/abort
```

**Advantages**

- Provides atomic commit across nodes.
- Widely understood.

**Disadvantages**

- Coordinator can become a bottleneck.
- Blocking if coordinator fails after prepare.
- Participants may hold locks while waiting.
- High latency due to multiple round trips.

---

### 5.5 Three-Phase Commit

Three-Phase Commit, or 3PC, attempts to reduce blocking.

Phases:

1. Can commit?
2. Pre-commit?
3. Commit?

**Advantages**

- Less blocking than 2PC in some failure scenarios.

**Disadvantages**

- More complex.
- Still not safe under all network partitions.
- Rarely used in practice compared with consensus-based protocols.

---

### 5.6 Consensus-Based Commit

Modern distributed databases often use consensus protocols such as:

- Paxos
- Raft
- Multi-Paxos
- Raft-based commit protocols

These protocols can provide atomic commit and leader election with stronger fault tolerance.

They are often used to replicate transaction logs or coordinate metadata.

---

### 5.7 Distributed Deadlocks

A distributed transaction may lock resources on multiple nodes.

Example:

```text
Transaction A locks row on Node 1, wants row on Node 2
Transaction B locks row on Node 2, wants row on Node 1
```

This can create a deadlock.

Detection is harder because the wait-for graph is distributed.

Common approaches:

- Timeout-based detection.
- Global deadlock detector.
- Lock ordering.
- Avoiding cross-partition transactions.

---

### 5.8 Transaction Performance

Distributed transactions are slower than local transactions because of:

- Network round trips.
- Multiple log writes.
- Lock coordination.
- Commit protocol overhead.
- Participant failures and retries.

Performance improvements include:

- Keep transactions within one partition when possible.
- Use local transactions for most operations.
- Batch small transactions.
- Use group commit.
- Use optimistic concurrency control.
- Use idempotent operations.
- Use asynchronous workflows for long-running operations.
- Avoid distributed locks when possible.

---

### 5.9 Alternatives to Distributed Transactions

Many systems avoid strict distributed transactions for performance and availability reasons.

#### Sagas

A long-running transaction is broken into local transactions.

If a later step fails, compensating actions undo earlier steps.

Example:

```text
Reserve inventory
Charge payment
Ship order
```

If shipping fails:

```text
Cancel shipment
Refund payment
Release inventory
```

**Advantages**

- Better availability.
- No long-held locks.
- Good for microservices.

**Disadvantages**

- Intermediate states may be visible.
- Compensation logic is complex.

#### Eventual Consistency

Updates propagate asynchronously.

**Advantages**

- Low latency.
- High availability.
- Good for global systems.

**Disadvantages**

- Users may see stale data.
- Conflict resolution is required.
- Not suitable for all financial or inventory operations.

#### Idempotency

Operations can be safely retried.

Example:

```text
payment_id = abc123
```

If the client retries, the system does not charge twice.

This is important in distributed systems because network failures can cause ambiguous outcomes.

---

## 6. Recovery in Distributed Databases

Recovery ensures that committed data survives failures and that incomplete transactions are handled correctly.

---

### 6.1 Failure Types

Distributed databases must handle:

1. **Process failure**
   - Database process crashes.

2. **Node failure**
   - Machine dies.

3. **Disk failure**
   - Storage becomes unavailable.

4. **Network partition**
   - Nodes cannot communicate.

5. **Coordinator failure**
   - Transaction coordinator crashes.

6. **Site or region failure**
   - Entire data center becomes unavailable.

---

### 6.2 Write-Ahead Logging

A common recovery mechanism is **Write-Ahead Logging**, or WAL.

Before modifying data, the database writes a log record to stable storage.

Typical log record contains:

- Transaction ID
- Operation type
- Before image
- After image
- Timestamp or LSN

Rules:

1. Log record must be written before data page is written.
2. Commit record must be written before transaction is reported to client.
3. Log must be durable.

**Advantages**

- Fast writes because logs are sequential.
- Enables redo and undo.
- Supports point-in-time recovery.

**Disadvantages**

- Log volume can be large.
- Log replication adds network traffic.
- Recovery may require replaying many logs.

---

### 6.3 Checkpoints

A checkpoint records the state of the database and transaction table at a point in time.

During recovery, the system can start from the latest checkpoint instead of replaying all logs.

**Advantages**

- Faster recovery.
- Reduces log replay time.

**Disadvantages**

- Checkpointing consumes I/O and CPU.
- Too frequent checkpoints reduce throughput.
- Too infrequent checkpoints increase recovery time.

---

### 6.4 Recovery Process

A typical recovery process has three phases:

#### Analysis

Identify:

- Committed transactions.
- Transactions that were active at failure.
- Dirty pages that need redo.

#### Redo

Reapply changes from committed transactions that may not have reached disk.

#### Undo

Roll back changes from transactions that did not commit.

This is similar to ARIES-style recovery used in many database systems.

---

### 6.5 Distributed Transaction Recovery

Distributed recovery is harder because participants may fail independently.

Example:

```text
Coordinator sends prepare
Participant writes prepare record
Coordinator crashes
```

The participant may be stuck in a prepared state.

Recovery requires:

- Stable storage of prepare and commit records.
- Coordinator recovery.
- Participant recovery.
- Timeout handling.
- Possibly manual intervention.

Modern systems often use consensus protocols to avoid single-coordinator blocking.

---

### 6.6 Replication-Based Recovery

Replication is also a recovery mechanism.

If the leader fails, a follower can become the new leader.

Important issues:

#### Log Truncation

The new leader must not discard logs that contain committed data.

#### Fencing

Old leaders must be prevented from writing after being demoted.

This prevents split-brain corruption.

#### Leader Election

The system must choose a new leader safely.

Common protocols:

- Raft
- Paxos
- ZooKeeper-based coordination
- Database-specific consensus

#### RPO and RTO

Recovery Point Objective, RPO:

```text
Maximum acceptable data loss
```

Recovery Time Objective, RTO:

```text
Maximum acceptable downtime
```

Synchronous replication can provide low RPO.

Asynchronous replication may have higher RPO.

---

### 6.7 Snapshots and Backups

Distributed databases often use:

- Full snapshots
- Incremental backups
- Log shipping
- Point-in-time recovery

A snapshot captures a consistent state.

Logs allow recovery to a specific timestamp.

Example:

```text
Restore snapshot from 02:00
Replay logs from 02:00 to 09:59
```

This can recover from accidental deletes or application bugs.

---

### 6.8 Recovery Performance

Recovery performance depends on:

- Amount of log to replay.
- Checkpoint frequency.
- Disk throughput.
- Network bandwidth for log shipping.
- Size of database.
- Number of active transactions.
- Complexity of distributed commit state.

Frequent checkpoints improve recovery time but reduce throughput.

Large logs improve durability but increase recovery time.

---

## 7. Performance Considerations

Distributed database performance is determined by the interaction of many design choices.

---

### 7.1 Latency

Latency is affected by:

- Network distance.
- Number of nodes contacted.
- Replication mode.
- Transaction protocol.
- Lock contention.
- Index fan-out.
- Disk I/O.

Example:

```text
Local write: 1 ms
Synchronous cross-region write: 100 ms
```

---

### 7.2 Throughput

Throughput is affected by:

- Partitioning.
- Load balancing.
- Lock contention.
- Index maintenance.
- Replication overhead.
- CPU and disk capacity.

Good partitioning increases throughput by allowing parallel execution.

Poor partitioning creates hotspots.

---

### 7.3 Scalability

A distributed database should scale by adding nodes.

However, scalability is limited by:

- Shared metadata.
- Global indexes.
- Distributed transactions.
- Lock managers.
- Network bandwidth.
- Coordination protocols.

---

### 7.4 Availability

Availability is improved by:

- Replication.
- Failover.
- Quorum reads and writes.
- Multi-region deployment.
- Graceful degradation.

But availability may require weaker consistency.

---

### 7.5 Consistency

Strong consistency requires coordination.

Weaker consistency improves latency and availability.

CAP theorem says that during a network partition, a system must choose between:

- Consistency
- Availability

PACELC extends this:

- During partition: choose consistency or availability.
- Otherwise: choose latency or consistency.

---

## 8. Example Design

Consider a distributed relational database for an online store.

### Requirements

- High write throughput.
- Strong consistency for payments.
- Low read latency.
- Survive node and zone failures.
- Support global users.

### Design

#### Data Partitioning

Partition by `customer_id`.

```text
orders, payments, cart_items are colocated by customer_id
```

This keeps most customer transactions local.

#### Replication

Each partition is replicated using Raft.

- Three replicas per partition.
- Synchronous replication within region.
- Asynchronous replication to another region.

#### Indexing

- Local secondary indexes for customer queries.
- Global index for email lookup.
- Search index for product search.

#### Transactions

- Single-partition transactions use local MVCC and WAL.
- Cross-partition transactions use 2PC or consensus-based commit.
- Payment operations are idempotent.

#### Recovery

- WAL on each node.
- Periodic snapshots.
- Log shipping to object storage.
- Point-in-time recovery.
- Leader election using Raft.
- Fencing tokens prevent old leaders from writing.

### Performance Characteristics

- Customer transactions are fast because they are local.
- Email lookup may require global index access.
- Cross-region writes are slower due to asynchronous replication.
- Recovery is fast because snapshots limit log replay.
- Availability is high because replicas can take over.

---

## 9. Tradeoff Summary

| Design Area | Goal | Performance Benefit | Cost |
|---|---|---|---|
| Partitioning | Scalability | Parallelism, locality | Cross-partition transactions |
| Replication | Availability, durability | Read scaling, failover | Write amplification, latency |
| Synchronous replication | Strong durability | Low data loss | Higher write latency |
| Asynchronous replication | Low latency | Higher throughput | Stale reads, possible data loss |
| Local indexes | Write locality | Faster writes | Scatter-gather reads |
| Global indexes | Flexible queries | Faster non-key lookups | Distributed updates, bottleneck |
| 2PC | Atomic commit | Strong consistency | Blocking, latency |
| MVCC | Concurrency | Readers do not block writers | Version cleanup, storage |
| Checkpoints | Fast recovery | Less log replay | I/O overhead |
| WAL | Durability | Fast sequential writes | Log growth, recovery cost |

---

## 10. Practical Design Guidelines

1. **Choose partition keys carefully**
   - Avoid hotspots.
   - Keep related data together.

2. **Minimize cross-partition transactions**
   - They are slower and harder to recover.

3. **Use local indexes when possible**
   - They reduce distributed coordination.

4. **Use global indexes only when necessary**
   - They can become bottlenecks.

5. **Match replication mode to consistency requirements**
   - Synchronous for critical data.
   - Asynchronous for analytics or global reads.

6. **Use quorum rules deliberately**
   - `R + W > N` for strong consistency.
   - Lower values for performance.

7. **Design for failure**
   - Assume nodes, networks, and coordinators will fail.

8. **Make operations idempotent**
   - Retries are common in distributed systems.

9. **Monitor tail latency**
   - Distributed systems often fail due to slow nodes, not average nodes.

10. **Test recovery regularly**
   - Failover, restore, and point-in-time recovery should be practiced.

---

## Conclusion

The design of a distributed database is a set of tradeoffs among **consistency, availability, latency, throughput, and durability**.

- **Replication** improves availability and read performance but adds write latency and complexity.
- **Indexing** speeds up queries but can create distributed coordination bottlenecks.
- **Transactions** provide correctness but require expensive coordination across nodes.
- **Recovery** ensures durability and survivability but depends on logging, checkpointing, replication, and consensus.

A well-designed distributed database places data and indexes to maximize locality, uses replication and consensus to survive failures, limits distributed transactions, and tunes logging and recovery to meet performance and reliability goals.
