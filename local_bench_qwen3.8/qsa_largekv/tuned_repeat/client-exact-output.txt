## Design and Performance of a Distributed Database

A **distributed database** stores data across multiple machines, often in different locations, while presenting a unified logical database to applications. Its design must balance **scalability, availability, consistency, latency, throughput, fault tolerance, and operational complexity**.

The main design goals are:

1. **Scalability**  
   Handle more data and more requests by adding machines.

2. **Availability**  
   Continue operating despite node failures or network partitions.

3. **Consistency**  
   Ensure users see correct and predictable data.

4. **Performance**  
   Minimize latency and maximize throughput despite network communication.

5. **Fault tolerance**  
   Recover from crashes, disk failures, network partitions, and data corruption.

---

# 1. Core Design of a Distributed Database

A distributed database is usually built from several components:

## 1.1 Data Partitioning / Sharding

Data is divided across multiple nodes.

Common partitioning strategies:

### Range Partitioning

Data is divided by key ranges.

Example:

```text
Node A: user_id 1–1000
Node B: user_id 1001–2000
Node C: user_id 2001–3000
```

Advantages:

- Efficient range queries.
- Good locality for sequential access.

Disadvantages:

- Hotspots if one range receives most traffic.
- Rebalancing can be expensive.

---

### Hash Partitioning

A hash function determines the node.

Example:

```text
node = hash(user_id) % number_of_nodes
```

Advantages:

- Even data distribution.
- Good for load balancing.

Disadvantages:

- Poor range query performance.
- Rebalancing can require data movement.

---

### Directory-Based Partitioning

A metadata service maps keys to nodes.

Advantages:

- Flexible placement.
- Can optimize for locality and load.

Disadvantages:

- Directory can become a bottleneck.
- Requires careful metadata management.

---

## 1.2 Shared-Nothing Architecture

Most modern distributed databases use a **shared-nothing** design.

Each node has its own:

- CPU
- Memory
- Disk
- Network connection

Nodes communicate through messages.

Advantages:

- Horizontal scalability.
- No shared disk bottleneck.
- Easier to add nodes.

Disadvantages:

- Network latency becomes important.
- Distributed coordination is complex.

---

## 1.3 Consistency Models

Distributed databases must choose how strongly they guarantee consistency.

### Strong Consistency

All reads see the most recent committed write.

Example:

```text
Write succeeds only when a majority of replicas acknowledge it.
Reads also require majority confirmation.
```

Advantages:

- Simpler application logic.
- No stale reads.

Disadvantages:

- Higher latency.
- Lower availability during failures.

---

### Eventual Consistency

Replicas may temporarily diverge but eventually converge.

Advantages:

- High availability.
- Low write latency.

Disadvantages:

- Applications may see stale data.
- Conflict resolution is required.

---

### Causal Consistency

Writes that are causally related are seen in the same order by all nodes.

Example:

```text
If write A causes write B,
then any node that sees B must also see A.
```

Advantages:

- Stronger than eventual consistency.
- Better availability than strong consistency.

Disadvantages:

- More complex implementation.

---

## 1.4 CAP and PACELC Considerations

Distributed databases often make tradeoffs described by **CAP**:

- **Consistency**
- **Availability**
- **Partition tolerance**

During a network partition, a system usually chooses either:

- **CP**: consistency and partition tolerance
- **AP**: availability and partition tolerance

In practice, many systems use **PACELC**:

- During partitions: choose availability or consistency.
- During normal operation: choose latency or consistency.

# 2. Replication

Replication stores copies of data on multiple nodes.

It improves:

- Availability
- Durability
- Read scalability
- Fault tolerance

But it introduces complexity:

- Synchronization
- Conflict resolution
- Write amplification
- Consistency tradeoffs

---

## 2.1 Replication Architectures

### Leader-Follower Replication

One node is the leader.

- Writes go to the leader.
- Followers replicate changes from the leader.
- Reads may go to followers.

Example:

```text
Client → Leader → Followers
```

Advantages:

- Simple write model.
- Easy conflict resolution.
- Strong consistency possible.

Disadvantages:

- Leader can become a bottleneck.
- Leader failure requires failover.
- Followers may lag.

---

### Leaderless Replication

Any node can accept writes.

Example:

```text
Client → Node A, Node B, Node C
```

Advantages:

- High availability.
- No single leader bottleneck.

Disadvantages:

- Conflict resolution required.
- Harder to guarantee strong consistency.
- Read repair and anti-entropy needed.

---

### Quorum-Based Replication

Writes and reads require agreement from a subset of replicas.

Let:

```text
N = total replicas
W = write quorum
R = read quorum
```

Strong consistency requires:

```text
W + R > N
```

Example:

```text
N = 3
W = 2
R = 2
```

A write succeeds if 2 replicas acknowledge.  
A read succeeds if 2 replicas respond.

Advantages:

- Configurable consistency.
- Tolerates some failures.

Disadvantages:

- Latency depends on slowest quorum member.
- Network partitions can block operations.

---

## 2.2 Synchronous vs Asynchronous Replication

### Synchronous Replication

The leader waits for followers to acknowledge before committing.

```text
Write → Leader → Followers → Ack → Commit
```

Advantages:

- Strong durability.
- Followers are up to date.

Disadvantages:

- Higher write latency.
- Availability reduced if follower fails.

---

### Asynchronous Replication

The leader commits locally and sends changes later.

```text
Write → Leader → Commit
Leader → Followers later
```

Advantages:

- Low write latency.
- High availability.

Disadvantages:

- Data loss possible if leader crashes.
- Stale reads possible.

---

### Semi-Synchronous Replication

The leader waits for at least one follower to acknowledge.

Advantages:

- Better durability than asynchronous.
- Lower latency than fully synchronous.

Disadvantages:

- Still depends on follower health.

---

## 2.3 Replication Performance Issues

Replication affects performance through:

### Write Amplification

Each write may be sent to multiple replicas.

Example:

```text
1 client write = 3 network writes
```

### Read Amplification

Some systems read multiple replicas to detect stale data.

### Network Latency

Cross-region replication can add tens or hundreds of milliseconds.

### Hotspots

If one partition receives most traffic, replication cannot fix the bottleneck.

### Rebalancing

Moving data between nodes can consume bandwidth and I/O.

---

## 2.4 Conflict Resolution

In leaderless or asynchronous systems, concurrent writes may conflict.

Common approaches:

### Last Write Wins

Uses timestamp.

```text
latest timestamp wins
```

Simple but can lose updates.

---

### Vector Clocks

Track causality between writes.

Example:

```text
Node A: version 3
Node B: version 2
```

Helps detect concurrent writes.

---

### CRDTs

Conflict-free Replicated Data Types automatically merge updates.

Examples:

- Counters
- Sets
- Registers

Advantages:

- Automatic convergence.

Disadvantages:

- Limited to specific data types.

---

### Application-Level Resolution

The application decides how to merge conflicts.

Example:

```text
merge shopping cart items
```

Advantages:

- Flexible.

Disadvantages:

- Complex application logic.

---

# 3. Indexing in Distributed Databases

Indexes speed up queries, but in distributed systems they are harder to design because data and indexes may be spread across nodes.

---

## 3.1 Local Indexes

Each partition maintains its own index.

Example:

```text
Partition A: index for users in A
Partition B: index for users in B
```

Advantages:

- Simple.
- Index updates are local.
- Good for queries that include the partition key.

Disadvantages:

- Queries without partition key must scan all partitions.
- Global uniqueness is difficult.

Example problem:

```sql
SELECT * FROM users WHERE email = 'alice@example.com';
```

If the table is partitioned by `user_id`, the database may need to query every partition.

---

## 3.2 Global Indexes

A global index is maintained separately from the main table partitions.

Example:

```text
email index → user_id → partition
```

Advantages:

- Efficient queries on non-partition keys.
- Can enforce global uniqueness.

Disadvantages:

- Index updates may require distributed transactions.
- Index can become a bottleneck.
- More complex failure handling.

---

## 3.3 Partitioned Global Indexes

A global index is itself partitioned.

Example:

```text
email hash determines index partition
```

Advantages:

- Scales better than a single global index.

Disadvantages:

- Still requires distributed coordination.
- Rebalancing is complex.

---

## 3.4 Covering Indexes

A covering index contains all fields needed by a query.

Example:

```text
Index: (email, user_id, name)
Query: SELECT user_id, name FROM users WHERE email = ?
```

Advantages:

- Avoids fetching the main table.
- Reduces network round trips.

Disadvantages:

- Larger index size.
- More write overhead.

---

## 3.5 Secondary Indexes

Secondary indexes are indexes on non-primary fields.

Example:

```text
Primary key: user_id
Secondary index: email
```

In distributed databases, secondary indexes can be:

### Local Secondary Index

Stored with the partition.

Good when queries include partition key.

---

### Global Secondary Index

Stored separately.

Good for queries on non-partition keys.

---

## 3.6 Index Maintenance Cost

Every write may update multiple indexes.

Example:

```text
Insert user:
- update primary table
- update email index
- update name index
- update status index
```

Performance impact:

- More disk I/O
- More network traffic
- More distributed coordination
- More write amplification

---

## 3.7 Query Routing

Distributed databases need to decide which nodes to query.

### Partition Key Known

Query can be routed directly.

```sql
SELECT * FROM users WHERE user_id = 42;
```

Fast.

---

### Partition Key Unknown

Query may need scatter-gather.

```sql
SELECT * FROM users WHERE email = 'alice@example.com';
```

Without a global index, the database may query all partitions.

---

### Scatter-Gather Queries

The coordinator sends the query to many nodes and merges results.

Advantages:

- Works without perfect partitioning.

Disadvantages:

- High latency.
- High fan-out.
- Can overload the cluster.

---

## 3.8 Indexing Performance Guidelines

Good distributed indexing design:

1. Choose partition keys that match common queries.
2. Avoid queries that require scanning all partitions.
3. Use covering indexes to reduce fetches.
4. Limit the number of secondary indexes.
5. Prefer local indexes when possible.
6. Use global indexes only when necessary.
7. Monitor index update latency.
8. Watch for hot index partitions.

---

# 4. Transactions in Distributed Databases

A transaction is a group of operations that should behave as a single logical unit.

Classic ACID properties:

- **Atomicity**
- **Consistency**
- **Isolation**
- **Durability**

In distributed databases, transactions may span multiple nodes.

Example:

```text
Transfer $100 from account A on Node 1 to account B on Node 2
```

This requires coordination.

---

## 4.1 Two-Phase Commit, 2PC

Two-phase commit is a classic distributed transaction protocol.

### Phase 1: Prepare

Coordinator asks participants:

```text
Can you commit?
```

Each participant locks resources and writes to log.

Participants respond:

```text
Yes or No
```

### Phase 2: Commit or Abort

If all participants vote yes:

```text
Coordinator sends commit
```

If any participant votes no:

```text
Coordinator sends abort
```

Advantages:

- Provides atomicity across nodes.
- Supports strong consistency.

Disadvantages:

- Blocking if coordinator fails.
- Participants may hold locks while waiting.
- High latency.
- Poor availability during failures.

---

## 4.2 Three-Phase Commit, 3PC

Three-phase commit tries to reduce blocking.

Phases:

1. Can commit?
2. Pre-commit
3. Commit

Advantages:

- Less blocking than 2PC in some cases.

Disadvantages:

- More complex.
- Still not safe under all network partitions.
- Rarely used in practice.

---

## 4.3 Distributed Locking

Transactions may need locks on multiple nodes.

Example:

```text
Lock account A on Node 1
Lock account B on Node 2
```

Problems:

- Deadlocks
- Lock timeouts
- Network delays
- Lock holder failure

Solutions:

- Wait-for graphs
- Timeout-based locks
- Lease-based locks
- Priority-based deadlock resolution

---

## 4.4 Optimistic Concurrency Control

Instead of locking during the transaction, the system checks for conflicts at commit time.

Steps:

1. Read data with version numbers.
2. Perform local work.
3. At commit, verify versions have not changed.
4. If changed, abort or retry.

Advantages:

- Low lock overhead.
- Good for low-conflict workloads.

Disadvantages:

- High retry rate under contention.
- Requires versioning.

---

## 4.5 MVCC

Multi-Version Concurrency Control stores multiple versions of data.

Readers see a snapshot.

Writers create new versions.

Advantages:

- Readers do not block writers.
- Writers do not block readers.
- Good for analytical and mixed workloads.

Disadvantages:

- Requires garbage collection of old versions.
- Snapshot isolation may still have write conflicts.

---

## 4.6 Isolation Levels

Distributed databases may support different isolation levels.

### Read Uncommitted

May read uncommitted data.

Fast but unsafe.

---

### Read Committed

Reads only committed data.

Common default.

---

### Repeatable Read

Same transaction sees same data repeatedly.

Prevents non-repeatable reads.

---

### Snapshot Isolation

Transaction sees a consistent snapshot.

Common in distributed systems.

---

### Serializable

Transactions behave as if executed one at a time.

Strongest isolation.

Advantages:

- Highest correctness.

Disadvantages:

- More conflicts.
- More retries.
- More coordination.

---

## 4.7 Distributed Transaction Performance

Distributed transactions are expensive because they require:

- Multiple network round trips
- Locks across nodes
- Coordination
- Failure handling
- Log flushing

Performance depends heavily on:

- Network latency
- Number of participants
- Lock contention
- Isolation level
- Failure rate
- Whether data is co-located

---

## 4.8 Co-Locating Data

A major performance optimization is to place related data on the same node.

Example:

```text
Account A and Account B are on the same node
```

Then the transaction can be local.

Advantages:

- Low latency.
- No distributed commit.
- Simpler failure handling.

Disadvantages:

- Hard to maintain as data grows.
- May create hotspots.

---

## 4.9 Sagas

For long-running workflows, distributed databases may use **sagas** instead of traditional transactions.

A saga is a sequence of local transactions with compensating actions.

Example:

```text
1. Reserve inventory
2. Charge payment
3. Ship order
```

If shipping fails:

```text
Compensate:
1. Refund payment
2. Release inventory
```

Advantages:

- Better for long-running operations.
- Avoids holding locks for long periods.

Disadvantages:

- Not atomic in the traditional sense.
- Requires compensation logic.
- May produce intermediate inconsistent states.

---

# 5. Recovery in Distributed Databases

Recovery ensures the database can survive failures and restore a consistent state.

Failures include:

- Node crash
- Disk failure
- Network partition
- Data corruption
- Operator error
- Region outage

---

## 5.1 Write-Ahead Logging, WAL

Before modifying data, the database writes changes to a durable log.

Typical order:

```text
1. Write log record
2. Flush log to disk
3. Modify data page
4. Commit transaction
```

Advantages:

- Enables crash recovery.
- Supports replication and point-in-time recovery.

Disadvantages:

- Log flushing can reduce throughput.
- Requires careful fsync and durability settings.

---

## 5.2 Checkpointing

Checkpointing periodically writes dirty pages to disk and records a consistent state.

Advantages:

- Reduces recovery time.
- Limits log replay.

Disadvantages:

- Checkpointing can cause I/O spikes.
- Too frequent checkpoints reduce performance.

---

## 5.3 Crash Recovery

After a crash, the database replays logs.

Typical process:

1. Find last checkpoint.
2. Replay committed transactions.
3. Undo incomplete transactions.
4. Restore consistent state.

Example:

```text
Committed transactions: redo
Uncommitted transactions: undo
```

---

## 5.4 Replicated Recovery

In distributed systems, recovery must consider multiple replicas.

### Leader Recovery

If a leader crashes:

1. Detect failure.
2. Elect new leader.
3. New leader must know the latest committed state.
4. Followers may need to discard uncommitted changes.

---

### Follower Recovery

If a follower crashes:

1. Restart follower.
2. Compare log with leader.
3. Fetch missing log entries.
4. Catch up.

---

### Quorum Recovery

In quorum-based systems, recovery may require majority agreement.

Example:

```text
3 replicas
2 healthy replicas can recover
```

If fewer than a quorum are available, the system may be unavailable.

---

## 5.5 Consensus Protocols

Modern distributed databases often use consensus protocols such as:

- **Paxos**
- **Raft**
- **Zab**

These protocols ensure that replicas agree on the order of operations.

Example:

```text
Replicas agree on log entry order
```

Advantages:

- Strong consistency.
- Safe leader election.
- Automatic failover.

Disadvantages:

- Requires majority availability.
- Latency depends on network.
- Complex implementation.

---

## 5.6 Snapshots and Backups

Databases periodically take snapshots.

A snapshot is a consistent copy of data at a point in time.

Advantages:

- Faster recovery than replaying huge logs.
- Useful for backups.
- Supports disaster recovery.

Disadvantages:

- Snapshots consume storage.
- Taking snapshots can impact performance.

---

## 5.7 Point-in-Time Recovery

Point-in-time recovery restores the database to a specific moment.

Example:

```text
Restore to 2026-06-01 10:30:00
```

Process:

1. Restore latest snapshot before target time.
2. Replay transaction logs up to target time.

Useful for:

- Accidental deletes
- Corrupted updates
- Application bugs

---

## 5.8 Handling Network Partitions

Network partitions are one of the hardest failure modes.

Example:

```text
Region A cannot talk to Region B
```

The system must decide:

- Stop writes in one region?
- Allow writes in both regions?
- Use quorum?
- Use leader election?

### CP Approach

If a quorum is unavailable, stop writes.

Advantages:

- Avoids conflicting writes.

Disadvantages:

- Reduced availability.

---

### AP Approach

Allow writes in both regions.

Advantages:

- High availability.

Disadvantages:

- Conflicts must be resolved later.

---

## 5.9 Recovery Performance

Recovery performance depends on:

- Log size
- Checkpoint frequency
- Amount of dirty data
- Network bandwidth
- Number of replicas
- Failure type
- Whether data is corrupted or lost

Good recovery design:

1. Frequent enough checkpoints.
2. Fast log replay.
3. Parallel recovery where possible.
4. Incremental backups.
5. Automated failover.
6. Tested recovery procedures.

---

# 6. Performance Considerations

Distributed database performance is dominated by:

## 6.1 Network Latency

Network communication is often slower than local disk or memory.

Example:

```text
Local memory: nanoseconds
Local SSD: microseconds
Same data center: milliseconds
Cross-region: tens to hundreds of milliseconds
```

Design implication:

- Minimize cross-node communication.
- Co-locate related data.
- Use batching.
- Cache hot data.

---

## 6.2 Round Trips

A distributed transaction may require multiple round trips.

Example:

```text
Prepare → Ack → Commit → Ack
```

Each round trip adds latency.

Optimizations:

- Reduce participants.
- Use local transactions when possible.
- Batch operations.
- Use optimistic concurrency.

---

## 6.3 Throughput vs Latency

Distributed systems often improve throughput by adding nodes, but latency may increase due to coordination.

Example:

```text
More replicas = higher durability but higher write latency
```

---

## 6.4 Hot Partitions

A hot partition occurs when one node receives disproportionate traffic.

Causes:

- Poor partition key
- Skewed data
- Time-series writes
- Popular entities

Solutions:

- Better partition keys
- Hashing
- Splitting hot partitions
- Caching
- Load balancing

---

## 6.5 Write Amplification

Writes may be amplified by:

- Replication
- Indexes
- Logs
- Compression
- Garbage collection

Example:

```text
1 logical write = 3 replicas × 2 indexes × log writes
```

This can reduce throughput.

---

## 6.6 Read Amplification

Reads may require:

- Multiple replicas
- Multiple partitions
- Index lookup plus table lookup
- Merge of multiple sorted runs

Optimizations:

- Covering indexes
- Caching
- Bloom filters
- Partition-aware queries

---

## 6.7 Garbage Collection

MVCC and LSM-tree storage engines create obsolete data.

Garbage collection can cause:

- CPU spikes
- I/O spikes
- Latency jitter

Good systems control GC concurrency and scheduling.

---

# 7. Design Tradeoffs

## 7.1 Strong Consistency vs Availability

Strong consistency requires coordination.

Example:

```text
Write requires majority acknowledgment
```

If majority is unavailable, writes fail.

---

## 7.2 Low Latency vs Durability

Fast writes may be buffered in memory.

Durable writes require log flushing and replication.

Example:

```text
Fast but unsafe:
write to memory and return

Safe but slower:
write to log, flush, replicate, return
```

---

## 7.3 Scalability vs Simplicity

Distributed systems can scale, but complexity increases.

Complexity appears in:

- Replication
- Transactions
- Indexing
- Recovery
- Monitoring
- Failure handling

---

## 7.4 Global Distribution vs Latency

Global replication improves availability and locality but increases coordination cost.

Example:

```text
Same-region write: 1 ms
Cross-region write: 100 ms
```

---

# 8. Example Design: Distributed Key-Value Store

Suppose we design a distributed key-value store.

## Data Model

```text
Key → Value
```

## Partitioning

Use hash partitioning:

```text
partition = hash(key) % N
```

## Replication

Each partition has 3 replicas.

Use Raft:

```text
Leader accepts writes
Followers replicate log
Majority commit required
```

## Indexing

Primary index is the key.

Secondary indexes are global and partitioned.

## Transactions

Single-key transactions are local.

Multi-key transactions use distributed locking or 2PC.

## Recovery

Use:

- Raft log
- Snapshots
- Checkpoints
- Automatic leader election
- Log replay

## Performance

Optimize by:

- Co-locating related keys
- Caching hot keys
- Batching writes
- Using local indexes
- Avoiding cross-region transactions

# 9. Example Design: Distributed Relational Database

A distributed relational database may use:

## Partitioning

Partition tables by tenant or customer ID.

Example:

```sql
PARTITION BY HASH(customer_id)
```

## Replication

Each partition has replicas in multiple availability zones.

## Indexing

Use local indexes for queries containing partition key.

Use global indexes for cross-partition queries.

## Transactions

Use distributed transactions for cross-partition updates.

Use co-location to reduce distributed transactions.

## Recovery

Use:

- WAL
- Snapshots
- Point-in-time recovery
- Automated failover
- Cross-region backups

# 11. Key Takeaways

A well-designed distributed database must make explicit tradeoffs.

## Replication

- Improves availability and durability.
- Increases write cost.
- Requires consistency strategy.
- Must handle conflicts and network partitions.

## Indexing

- Speeds up reads.
- Can become a distributed bottleneck.
- Global indexes are powerful but expensive.
- Partition-aware queries are usually fastest.

## Transactions

- Distributed transactions are complex and slow.
- Strong isolation requires coordination.
- Co-location and optimistic concurrency improve performance.
- Sagas are useful for long-running workflows.

## Recovery

- Logs and snapshots are essential.
- Consensus protocols enable safe failover.
- Recovery must handle partial failures and network partitions.
- Recovery procedures must be tested regularly.

---

## Final Conclusion

The design of a distributed database is fundamentally about managing **data distribution, coordination, and failure**.

Good performance comes from:

1. Choosing partition keys that match workload access patterns.
2. Replicating enough for durability and availability, but not too much.
3. Using indexes carefully to avoid distributed fan-out.
4. Minimizing distributed transactions through data co-location.
5. Using logs, snapshots, and consensus protocols for reliable recovery.
6. Monitoring latency, hotspots, replication lag, and recovery health.

A distributed database can provide high scalability and availability, but only if replication, indexing, transactions, and recovery are designed together with the expected workload and failure model in mind.
