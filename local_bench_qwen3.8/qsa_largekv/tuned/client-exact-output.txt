A distributed database stores data across multiple machines connected by a network, while presenting the appearance of a single logical database to applications. Its design and performance are shaped by tradeoffs among scalability, availability, consistency, latency, throughput, fault tolerance, and operational complexity.

Below is a structured explanation of distributed database design and performance, focusing on replication, indexing, transactions, and recovery.

---

## 1. Core Design Goals of a Distributed Database

A distributed database is designed to solve problems that a single-node database cannot easily handle:

### 1.1 Scalability

A distributed database can scale by adding more machines.

There are two main scaling approaches:

#### Vertical scaling

Add more CPU, memory, storage, or faster disks to one machine.

Advantages:

- Simple architecture.
- Easier transaction management.
- Lower network overhead.

Disadvantages:

- Limited by hardware capacity.
- Expensive at large scale.
- Single point of failure.

#### Horizontal scaling

Add more machines and distribute data across them.

Advantages:

- Can scale to very large workloads.
- Better fault tolerance.
- Can use commodity hardware.

Disadvantages:

- More complex design.
- Network latency becomes important.
- Distributed transactions and consistency are harder.

Most modern distributed databases use horizontal scaling.

---

### 1.2 Availability

Availability means the system can continue serving requests despite failures.

A distributed database improves availability by:

- Replicating data across multiple nodes.
- Detecting failed nodes.
- Electing new leaders.
- Routing requests to healthy replicas.
- Allowing reads from replicas.
- Continuing writes when a quorum of nodes is available.

Availability is closely related to consistency. A system that remains available during network partitions may have to relax strong consistency.

---

### 1.3 Consistency

Consistency means that all nodes agree on the state of the data, or at least that clients observe a predictable ordering of updates.

Common consistency models include:

#### Strong consistency

All reads see the most recent committed write.

Example:

- A write to a bank account is visible to all subsequent reads immediately.

Advantages:

- Easier application reasoning.
- Safer for financial or inventory systems.

Disadvantages:

- Higher latency.
- Lower availability during network partitions.

#### Eventual consistency

Updates propagate to replicas over time. Reads may temporarily return stale data.

Example:

- A social media profile update may appear on some replicas immediately and on others later.

Advantages:

- High availability.
- Low write latency.
- Better partition tolerance.

Disadvantages:

- Applications must tolerate stale reads.
- Conflict resolution is more complex.

#### Causal consistency

Updates that are causally related are seen in the correct order.

Example:

- If a user creates a post and then comments on that post, other users should not see the comment before the post.

This is stronger than eventual consistency but weaker than linearizability.

---

### 1.4 Partition Tolerance

Partition tolerance means the system continues operating despite network failures that prevent some nodes from communicating.

The CAP theorem states that a distributed system cannot simultaneously guarantee all three of:

- Consistency
- Availability
- Partition tolerance

In practice, distributed databases usually choose between:

- CP: consistency and partition tolerance
- AP: availability and partition tolerance

However, many systems offer configurable consistency levels, allowing different tradeoffs for different workloads.

---

## 2. Data Distribution and Partitioning

A distributed database must decide how data is placed across nodes.

### 2.1 Sharding

Sharding divides data into smaller pieces called shards or partitions.

Each shard is stored on one or more nodes.

Common sharding strategies:

#### Range partitioning

Data is divided by ranges of a key.

Example:

```text
Shard 1: user_id 1–10,000
Shard 2: user_id 10,001–20,000
Shard 3: user_id 20,001–30,000
```

Advantages:

- Efficient range queries.
- Simple to understand.

Disadvantages:

- Hotspots can occur if one range receives disproportionate traffic.
- Rebalancing can be expensive.

#### Hash partitioning

A hash function determines the shard.

Example:

```text
shard = hash(user_id) % number_of_shards
```

Advantages:

- Even data distribution.
- Good for point lookups.

Disadvantages:

- Range queries require scanning multiple shards.
- Rebalancing can require data movement.

#### Directory-based partitioning

A lookup table maps keys to shards.

Advantages:

- Flexible placement.
- Can optimize for locality.

Disadvantages:

- Directory can become a bottleneck.
- Requires metadata management.

#### Consistent hashing

Used in many distributed systems to reduce data movement when nodes are added or removed.

Advantages:

- Better rebalancing behavior.
- Common in distributed caches and object stores.

Disadvantages:

- More complex than simple modulo hashing.
- May require virtual nodes to avoid imbalance.

---

### 2.2 Replication Factor

Each shard is usually replicated across multiple nodes.

Example:

```text
Shard A:
  Node 1: leader
  Node 2: follower
  Node 3: follower
```

A replication factor of 3 means each piece of data exists on three nodes.

Higher replication improves:

- Availability
- Durability
- Read scalability

But it increases:

- Storage cost
- Write amplification
- Synchronization overhead

---

## 3. Replication

Replication is one of the most important mechanisms in a distributed database. It copies data across multiple nodes to improve availability, durability, and performance.

---

## 3.1 Why Replicate Data?

Replication provides several benefits:

### Availability

If one node fails, another replica can serve requests.

### Durability

Data survives node failure if multiple copies exist.

### Read scalability

Reads can be served from multiple replicas.

### Locality

Data can be replicated closer to users to reduce latency.

### Disaster recovery

Replicas can be placed in different data centers or regions.

---

## 3.2 Replication Models

### 3.2.1 Leader-based replication

One node is the leader.

All writes go to the leader.

The leader sends changes to followers.

Reads may go to:

- Leader only
- Leader and followers
- Followers only, depending on consistency requirements

Example:

```text
Client write → Leader → Followers
Client read → Leader or follower
```

Advantages:

- Simple conflict resolution.
- Strong consistency is easier to implement.
- Widely used in production systems.

Disadvantages:

- Leader can become a bottleneck.
- Leader failure requires election.
- Followers may lag behind.

---

### 3.2.2 Multi-leader replication

Multiple nodes can accept writes.

Each leader replicates changes to other leaders.

Advantages:

- Better write availability.
- Useful for multi-region deployments.
- Can reduce write latency for geographically distributed clients.

Disadvantages:

- Conflict resolution is complex.
- Strong consistency is harder.
- Requires conflict detection and resolution strategies.

Conflict resolution methods include:

- Last write wins
- Vector clocks
- CRDTs
- Application-level merge logic
- Manual conflict resolution

---

### 3.2.3 Leaderless replication

Any node can accept writes.

Writes are sent to multiple replicas.

Reads may query multiple replicas and reconcile results.

Example:

```text
Write to 3 replicas
Read from 3 replicas
Choose latest version
```

Advantages:

- High availability.
- No single leader bottleneck.
- Good for partition-heavy environments.

Disadvantages:

- Weak consistency unless quorum rules are used.
- Complex conflict resolution.
- Harder to implement transactions.

---

## 3.3 Synchronous vs Asynchronous Replication

### Synchronous replication

The leader waits for replicas to acknowledge the write before returning success to the client.

Example:

```text
Client write → Leader
Leader writes locally
Leader sends to follower
Follower acknowledges
Leader returns success
```

Advantages:

- Strong durability.
- Followers are up to date.
- Failover can preserve committed writes.

Disadvantages:

- Higher write latency.
- If a follower is slow, the client waits.
- Availability may decrease if required replicas are unavailable.

---

### Asynchronous replication

The leader returns success before replicas acknowledge.

Example:

```text
Client write → Leader
Leader returns success
Leader sends to follower later
```

Advantages:

- Lower write latency.
- Better availability.
- Followers can be geographically distant.

Disadvantages:

- Committed writes may be lost if leader fails before replication.
- Followers may be stale.
- Failover may require data reconciliation.

---

### Semi-synchronous replication

The leader waits for at least one follower to acknowledge, but not necessarily all followers.

This is a compromise between synchronous and asynchronous replication.

---

## 3.4 Quorum Replication

Quorum replication uses majority rules to coordinate reads and writes.

Suppose there are `N` replicas.

A write succeeds if `W` replicas acknowledge.

A read succeeds if `R` replicas respond.

If:

```text
W + R > N
```

then reads and writes overlap, meaning a read should see the latest write.

Example:

```text
N = 3
W = 2
R = 2
```

A write must succeed on 2 replicas.

A read checks 2 replicas.

Because `2 + 2 > 3`, the read set and write set overlap.

Advantages:

- Configurable consistency.
- Tolerates some failures.
- Works well in leaderless systems.

Disadvantages:

- Latency depends on slowest required replica.
- Network partitions can block writes or reads.
- Requires careful configuration.

---

## 3.5 Replication and Performance

Replication affects performance in several ways.

### Write performance

Replication can slow writes because changes must be sent to multiple nodes.

Factors include:

- Number of replicas
- Synchronous vs asynchronous replication
- Network latency
- Disk speed
- Log flushing policy
- Leader election overhead

Synchronous replication across regions can significantly increase write latency.

---

### Read performance

Replication can improve read performance by allowing reads from multiple replicas.

However, reading from followers may return stale data unless the system provides strong consistency.

---

### Network cost

Replication consumes bandwidth.

High write throughput can create large replication traffic.

This is especially important in multi-region deployments.

---

### Failure handling

Replication improves fault tolerance, but failover can be expensive.

Leader election may require:

- Timeout detection
- Consensus protocol
- Log reconciliation
- Client redirection

Frequent leader changes can reduce performance.

---

## 4. Indexing in Distributed Databases

Indexing is critical for query performance, but distributed indexing is more complex than single-node indexing.

---

## 4.1 Purpose of Indexes

Indexes speed up queries by avoiding full table scans.

Common index types:

- B-tree indexes
- Hash indexes
- Bitmap indexes
- GiST/GIN indexes
- LSM-tree indexes
- Covering indexes
- Composite indexes
- Partial indexes

In a distributed database, indexes may be local or global.

---

## 4.2 Local Indexes

A local index is stored on the same node as the data it indexes.

Example:

```text
Shard 1:
  Table data
  Index for shard 1

Shard 2:
  Table data
  Index for shard 2
```

Advantages:

- Index updates are local.
- Lower network overhead.
- Easier to maintain during rebalancing.
- Good for queries that include the partition key.

Disadvantages:

- Queries without the partition key may need to scan all shards.
- Global uniqueness is harder to enforce.
- Secondary indexes may require scatter-gather queries.

Example problem:

```sql
SELECT *
FROM users
WHERE email = 'alice@example.com';
```

If the table is sharded by `user_id`, and the index on `email` is local, the database may need to query every shard.

---

## 4.3 Global Indexes

A global index spans multiple shards and maps values to shard locations.

Example:

```text
Global email index:
  alice@example.com → Shard 7
  bob@example.com   → Shard 3
```

Advantages:

- Efficient queries on non-shard keys.
- Avoids scatter-gather queries.
- Better for secondary lookups.

Disadvantages:

- Index updates may require distributed transactions.
- Global index can become a bottleneck.
- Rebalancing is more complex.
- Failure handling is harder.

---

## 4.4 Distributed Index Maintenance

When data changes, indexes must be updated.

In a distributed database, this can involve:

- Updating local indexes
- Updating global indexes
- Replicating index changes
- Coordinating across shards
- Handling partial failures

For example, inserting a row may require:

1. Writing the row to the correct shard.
2. Updating the local index on that shard.
3. Updating a global secondary index.
4. Replicating all changes to followers.
5. Confirming success to the client.

This increases write latency and complexity.

---

## 4.5 Indexing and Query Routing

A distributed query optimizer must decide:

- Which shards to query
- Which indexes to use
- Whether to push computation to nodes
- Whether to fetch intermediate results
- How to merge results

Example:

```sql
SELECT *
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 10;
```

If the table is sharded by `customer_id`, the query can go to one shard.

If the table is sharded by `order_id`, the query may need to scan many shards.

A good distributed index design aligns indexes with common query patterns and partition keys.

---

## 4.6 Indexing Performance Tradeoffs

### Read performance

Good indexes reduce:

- Disk I/O
- CPU usage
- Network transfer
- Query latency

Poor indexes can cause:

- Full scans
- Scatter-gather queries
- Large result sets
- Cross-shard joins

---

### Write performance

Indexes slow writes because each write may require multiple index updates.

In distributed systems, this cost is amplified by:

- Network round trips
- Replication
- Distributed transactions
- Locking or coordination

---

### Storage cost

Indexes consume additional storage.

In distributed databases, global indexes may require:

- Extra nodes
- Extra replication
- Extra metadata management

---

### Rebalancing cost

When shards move between nodes, indexes may need to be rebuilt or migrated.

This can be expensive.

---

## 5. Transactions in Distributed Databases

A transaction is a logical unit of work that must satisfy the ACID properties:

- Atomicity
- Consistency
- Isolation
- Durability

In a distributed database, transactions may touch multiple shards or nodes.

---

## 5.1 ACID in Distributed Systems

### Atomicity

All parts of a transaction succeed or all fail.

In a distributed transaction, this is difficult because one node may commit while another fails.

---

### Consistency

The database moves from one valid state to another.

Constraints may span multiple shards, making enforcement harder.

---

### Isolation

Concurrent transactions do not interfere incorrectly.

Distributed isolation requires coordination across nodes.

---

### Durability

Committed data survives failures.

Durability requires logging and replication.

---

## 5.2 Distributed Transaction Coordination

A distributed transaction may involve multiple participants.

Example:

```text
Transaction T:
  Update account A on Node 1
  Update account B on Node 2
```

The system must ensure both updates commit or both abort.

---

## 5.3 Two-Phase Commit

Two-phase commit, or 2PC, is a classic protocol for distributed transactions.

It has two phases:

### Phase 1: Prepare

The coordinator asks all participants:

```text
Can you commit?
```

Each participant:

- Locks resources
- Writes redo/undo logs
- Responds yes or no

### Phase 2: Commit or Abort

If all participants vote yes, the coordinator sends commit.

If any participant votes no, the coordinator sends abort.

Advantages:

- Provides atomic commit.
- Works with multiple participants.
- Widely understood.

Disadvantages:

- Blocking if coordinator fails.
- Participants may hold locks while waiting.
- High latency.
- Poor availability during failures.

---

## 5.4 Three-Phase Commit

Three-phase commit adds an extra phase to reduce blocking.

Phases:

1. Can commit?
2. Pre-commit?
3. Commit?

Advantages:

- Less blocking than 2PC in some failure scenarios.

Disadvantages:

- More complex.
- Still not fully non-blocking in all cases.
- Rarely used in practice.

---

## 5.5 Consensus-Based Transactions

Modern distributed databases often use consensus protocols such as:

- Paxos
- Raft
- Multi-Paxos
- Zab

These protocols help replicas agree on a log of operations.

They are used for:

- Leader election
- Replicated state machines
- Distributed commit
- Metadata management

Consensus provides strong consistency but can be expensive.

---

## 5.6 Isolation Levels

Distributed databases support various isolation levels.

### Read uncommitted

Transactions can see uncommitted changes.

Rarely used because of dirty reads.

### Read committed

Transactions see only committed data.

Prevents dirty reads.

### Repeatable read

A transaction sees the same data throughout its execution.

Prevents non-repeatable reads.

### Serializable

Transactions behave as if executed one at a time.

Strongest isolation.

Advantages:

- Easiest to reason about.
- Prevents anomalies.

Disadvantages:

- High coordination cost.
- More aborts.
- Lower throughput.

---

## 5.7 Distributed Deadlocks

Deadlocks can occur when transactions on different nodes wait for each other.

Example:

```text
Transaction 1 on Node A holds lock X and waits for lock Y
Transaction 2 on Node B holds lock Y and waits for lock X
```

Detection methods:

- Global wait-for graph
- Timeout-based detection
- Distributed deadlock detector

Resolution methods:

- Abort one transaction
- Retry transaction
- Use optimistic concurrency control

Deadlock detection is more expensive in distributed systems because lock information is spread across nodes.

---

## 5.8 Optimistic vs Pessimistic Concurrency Control

### Pessimistic concurrency control

Locks are acquired before writing.

Advantages:

- Prevents conflicts early.
- Useful for high-contention workloads.

Disadvantages:

- Locks can block transactions.
- Distributed locking is expensive.
- Deadlocks are possible.

---

### Optimistic concurrency control

Transactions execute without locks and validate at commit time.

Advantages:

- Better for low-contention workloads.
- Less blocking.
- Can improve throughput.

Disadvantages:

- More aborts under contention.
- Requires versioning or validation.
- May require retries.

---

## 5.9 MVCC in Distributed Databases

Multi-version concurrency control stores multiple versions of data.

Readers can see a consistent snapshot without blocking writers.

Advantages:

- Better concurrency.
- Reads do not block writes.
- Useful for analytical and mixed workloads.

Disadvantages:

- More storage.
- Garbage collection complexity.
- Snapshot isolation may still allow some anomalies.

In distributed systems, MVCC requires consistent timestamps across nodes.

This is often done using:

- Logical clocks
- Hybrid logical clocks
- TrueTime-like APIs
- Central timestamp servers

---

## 5.10 Transaction Performance

Distributed transactions are usually slower than local transactions.

Reasons include:

- Multiple network round trips
- Lock coordination
- Consensus overhead
- Replication
- Failure detection
- Retry costs

Performance can be improved by:

- Keeping transactions local when possible
- Designing shards to reduce cross-shard transactions
- Using batched writes
- Using asynchronous replication carefully
- Using optimistic concurrency
- Reducing transaction size
- Using idempotent operations
- Caching frequently accessed data

---

## 6. Recovery in Distributed Databases

Recovery means restoring the database to a correct state after failures.

Failures can include:

- Node crash
- Disk failure
- Network partition
- Data center outage
- Software bug
- Operator error
- Corrupted data

---

## 6.1 Logging

Logging is the foundation of recovery.

Common log types:

### Write-ahead logging

Changes are written to a log before modifying data pages.

This ensures that committed changes can be recovered after a crash.

### Redo log

Records changes that must be reapplied after recovery.

### Undo log

Records changes that must be rolled back if a transaction fails.

### Replication log

Records changes that must be sent to replicas.

---

## 6.2 Checkpointing

A checkpoint records the database state at a point in time.

During recovery, the system can start from the last checkpoint and replay logs after it.

Advantages:

- Faster recovery.
- Less log replay.

Disadvantages:

- Checkpointing consumes I/O.
- Too frequent checkpoints can reduce performance.
- Too infrequent checkpoints can slow recovery.

---

## 6.3 Crash Recovery

If a node crashes, recovery may involve:

1. Restarting the node.
2. Reading the last checkpoint.
3. Replaying redo logs.
4. Undoing incomplete transactions.
5. Rejoining the cluster.
6. Catching up with replicas or leader.

In a replicated system, a crashed follower may need to fetch missing log entries from the leader.

---

## 6.4 Leader Failure and Failover

In leader-based systems, if the leader fails, a new leader must be elected.

Failover steps may include:

1. Detect leader failure.
2. Elect a new leader.
3. Ensure the new leader has the latest committed data.
4. Redirect clients.
5. Resume writes.

Failover can be problematic if:

- The old leader had unreplicated writes.
- Network partitions cause split-brain.
- Multiple nodes believe they are leader.
- Clients are still connected to the old leader.

Consensus protocols help prevent split-brain by requiring a majority before a leader can act.

---

## 6.5 Network Partition Recovery

During a network partition, some nodes cannot communicate.

The system must decide:

- Which side can accept writes?
- Which side can serve reads?
- How to reconcile conflicting updates?
- When to reject requests?

CP systems may reject writes if a majority is unavailable.

AP systems may accept writes on both sides and reconcile later.

Recovery after partition may require:

- Conflict resolution
- Log reconciliation
- Version comparison
- Manual intervention
- Automated merge rules

---

## 6.6 Data Repair

Replicas can become inconsistent due to:

- Network failures
- Disk corruption
- Software bugs
- Partial writes
- Misconfigured replication

Repair mechanisms include:

- Anti-entropy processes
- Merkle trees
- Hash comparison
- Log-based repair
- Snapshot comparison
- Background reconciliation

Merkle trees are commonly used to compare large datasets efficiently.

---

## 6.7 Backup and Point-in-Time Recovery

Distributed databases often support:

- Full snapshots
- Incremental backups
- Log backups
- Point-in-time recovery
- Cross-region backups

Point-in-time recovery allows restoring the database to a specific moment.

Example:

```text
Restore database to 2026-01-01 10:00:00
```

This is useful for recovering from accidental deletes or application bugs.

---

## 6.8 Recovery Performance

Recovery performance depends on:

- Log size
- Checkpoint frequency
- Amount of data to replay
- Network bandwidth
- Disk throughput
- Number of replicas
- Consistency requirements

Fast recovery requires:

- Frequent checkpoints
- Efficient log formats
- Parallel replay
- Fast disks
- Good network connectivity
- Careful failure detection

---

## 7. Query Processing and Performance

Distributed databases must optimize queries across multiple nodes.

---

## 7.1 Query Routing

The system must determine which nodes hold the required data.

Example:

```sql
SELECT *
FROM users
WHERE user_id = 123;
```

If the table is sharded by `user_id`, the query can be routed directly to one shard.

If the query is:

```sql
SELECT *
FROM users
WHERE email = 'alice@example.com';
```

and there is no global index on `email`, the query may need to scan all shards.

---

## 7.2 Scatter-Gather Queries

A scatter-gather query sends the query to many nodes and merges results.

Example:

```sql
SELECT *
FROM logs
WHERE message LIKE '%error%'
ORDER BY timestamp DESC
LIMIT 100;
```

The query may be sent to all shards, each returns top results, and the coordinator merges them.

Advantages:

- Works when data is distributed.

Disadvantages:

- Can be expensive.
- May require large intermediate results.
- Latency depends on slowest shard.

---

## 7.3 Distributed Joins

Joins across shards are expensive.

Common strategies:

### Broadcast join

One small table is sent to all nodes.

Useful when one table is small.

### Partitioned join

Both tables are partitioned on the join key.

This allows local joins.

### Shuffle join

Data is redistributed across nodes by join key.

Expensive but flexible.

### Collocated join

Related data is stored on the same node.

Best performance, but requires careful schema design.

---

## 7.4 Query Optimization

A distributed query optimizer considers:

- Data distribution
- Index availability
- Network cost
- Node load
- Cardinality estimates
- Join order
- Aggregation pushdown
- Predicate pushdown
- Parallelism

Good optimization can reduce:

- Network transfer
- Disk I/O
- CPU usage
- Query latency

---

## 8. Performance Factors in Distributed Databases

The performance of a distributed database depends on many factors.

---

## 8.1 Network Latency

Network latency is often the dominant cost.

A local disk operation may take microseconds.

A cross-region network round trip may take tens or hundreds of milliseconds.

Operations that require multiple round trips can become slow.

Examples:

- Synchronous replication
- Two-phase commit
- Distributed locks
- Global index updates
- Leader election

---

## 8.2 Network Bandwidth

Large queries, replication, backups, and rebalancing can consume significant bandwidth.

High write throughput can create large replication traffic.

---

## 8.3 Disk Performance

Distributed databases still depend on local disk performance.

Important factors:

- SSD throughput
- IOPS
- Log flushing
- Page cache
- Compression
- Write amplification

LSM-tree-based databases can provide high write throughput but may have higher read amplification.

---

## 8.4 Concurrency Control

Concurrency control affects throughput and latency.

Pessimistic locking can reduce throughput under contention.

Optimistic concurrency can increase retries.

MVCC can improve concurrency but increases storage and cleanup costs.

---

## 8.5 Load Balancing

Uneven load can create hotspots.

Example:

```text
One shard receives 80% of traffic
```

This can happen due to:

- Poor partition keys
- Popular users
- Time-series data
- Range queries
- Skewed data distribution

Solutions:

- Better partition keys
- Consistent hashing
- Splitting hot shards
- Caching
- Read replicas
- Request routing

---

## 8.6 Caching

Caching improves performance by reducing disk and network access.

Common caches:

- Page cache
- Query result cache
- Row cache
- Key-value cache
- Metadata cache

Caching must be managed carefully to avoid stale reads.

---

## 8.7 Batch Processing

Batching can improve throughput.

Examples:

- Batch writes
- Batch index updates
- Batch replication
- Batch compaction
- Batch query execution

Batching reduces per-operation overhead but can increase latency.

---

## 9. Design Tradeoffs

Distributed database design is full of tradeoffs.

---

## 9.1 Consistency vs Availability

Strong consistency requires coordination.

High availability may require accepting stale reads or conflicting writes.

Example:

```text
Strong consistency:
  Write must be acknowledged by majority before success.

High availability:
  Write may succeed locally and replicate later.
```

---

## 9.2 Latency vs Durability

Waiting for multiple replicas improves durability but increases latency.

Returning success before replication improves latency but risks data loss.

---

## 9.3 Read Performance vs Write Performance

Replication and indexes can improve reads but slow writes.

A system optimized for reads may use many replicas and indexes.

A system optimized for writes may use fewer indexes and asynchronous replication.

---

## 9.4 Simplicity vs Scalability

Single-node databases are simpler.

Distributed databases are more scalable but harder to operate.

Complexity includes:

- Consensus
- Partitioning
- Rebalancing
- Monitoring
- Failure handling
- Upgrade coordination

## 9.5 Global Distribution vs Local Performance

Multi-region databases provide low latency for global users.

But cross-region coordination can be slow.

Design choices include:

- Regional leaders
- Multi-leader replication
- Conflict-free data types
- Eventually consistent reads
- Strong consistency only within a region

## 11. Practical Design Guidelines

When designing a distributed database, consider the following.

---

## 11.1 Choose a Partition Key Carefully

The partition key determines data distribution and query efficiency.

Good partition keys:

- Distribute load evenly
- Match common query patterns
- Avoid hotspots
- Keep related data together

Bad partition keys:

- Timestamps with monotonically increasing values
- Low-cardinality fields
- Fields that cause one shard to dominate traffic

---

## 11.2 Minimize Cross-Shard Transactions

Cross-shard transactions are expensive.

Design schemas so that frequently updated related data is colocated.

Example:

```text
Bad:
  Orders sharded by order_id
  Order items sharded by item_id

Better:
  Orders and order items sharded by order_id
```

---

## 11.3 Align Indexes with Query Patterns

Indexes should support the most important queries.

For distributed systems, prefer indexes that include the partition key.

Example:

```sql
CREATE INDEX idx_user_orders
ON orders (user_id, created_at DESC);
```

If the table is sharded by `user_id`, this index can be local and efficient.

---

## 11.4 Use Replication for Availability, Not Just Performance

Replication improves availability and durability.

But it also adds complexity.

Choose replication factor and consistency level based on business requirements.

---

## 11.5 Monitor Latency, Throughput, and Failure Events

Important metrics include:

- Query latency
- Write latency
- Replication lag
- Leader election frequency
- Network errors
- Disk utilization
- Cache hit rate
- Hot shard detection
- Transaction abort rate
- Recovery time

---

## 11.6 Test Failure Scenarios

Distributed databases must be tested under failure.

Examples:

- Kill a node
- Partition network
- Slow a disk
- Delay network packets
- Fill disk
- Restart leader
- Restore from backup
- Simulate data center outage

Failure testing reveals weaknesses in replication, recovery, and client behavior.

---

## 12. Summary

A distributed database is designed to provide scalability, availability, and fault tolerance by distributing data across multiple machines. Its performance depends heavily on how data is partitioned, replicated, indexed, and coordinated.

### Replication

Replication copies data across nodes to improve availability, durability, and read scalability. It can be synchronous, asynchronous, leader-based, multi-leader, or leaderless. Strong consistency usually requires coordination, which increases latency.

### Indexing

Indexes speed up queries but are more complex in distributed systems. Local indexes are efficient for queries that include the partition key. Global indexes support queries on non-shard keys but can require distributed coordination and become bottlenecks.

### Transactions

Distributed transactions must coordinate multiple nodes. Two-phase commit provides atomicity but can block. Consensus protocols such as Raft and Paxos provide stronger fault tolerance. Isolation levels, locking, MVCC, and deadlock detection all become more expensive across nodes.

### Recovery

Recovery relies on logging, checkpointing, replication, leader election, and data repair. Failures can cause stale replicas, lost writes, split-brain, or inconsistent partitions. Good recovery design requires careful consensus, backups, monitoring, and failure testing.

In short, distributed database design is a balance between consistency, availability, latency, throughput, and operational complexity. The best design depends on the workload, consistency requirements, geographic distribution, failure tolerance, and performance goals.
