## Distributed Database Design and Performance

A **distributed database** stores data across multiple machines, often across multiple data centers or cloud regions, while presenting a unified logical database to applications. Its design must balance **scalability, availability, consistency, latency, durability, and operational complexity**.

The main design areas are:

1. **Data distribution and partitioning**
2. **Replication**
3. **Indexing**
4. **Transactions**
5. **Recovery**

Performance depends heavily on how these mechanisms interact with network latency, failure handling, workload patterns, and consistency requirements.

---

# 1. Core Design Principles

A distributed database is usually built from several layers:

## 1.1 Data Distribution

Data is split across nodes using one or more strategies:

### Horizontal Partitioning / Sharding

Rows are divided across nodes based on a shard key.

Example:

```text
User ID 1–1000000 → Node A
User ID 1000001–2000000 → Node B
User ID 2000001–3000000 → Node C
```

Advantages:

- Scales write throughput
- Scales storage capacity
- Allows parallel query execution

Disadvantages:

- Cross-shard queries can be expensive
- Hot shards can form
- Rebalancing can be complex

Common shard keys:

- User ID
- Tenant ID
- Order ID
- Time bucket
- Hash of primary key

Good shard keys avoid hotspots and keep related data together.

---

### Vertical Partitioning

Different tables or columns are placed on different nodes.

Example:

```text
Node A: user profile data
Node B: order history
Node C: audit logs
```

This is useful when different data has different access patterns or performance requirements.

---

### Functional Partitioning

Different database services are separated:

- Query coordinator
- Storage nodes
- Index nodes
- Log nodes
- Transaction manager
- Metadata service

This improves scalability and fault isolation.

---

## 1.2 Consistency Models

Distributed databases must choose how strongly they guarantee consistency.

### Strong Consistency

All replicas agree on the latest value.

Example:

```text
Write succeeds only when a majority of replicas acknowledge it.
Read returns the latest committed value.
```

Used in systems requiring correctness, such as financial transactions.

Cost:

- Higher latency
- Lower availability during network partitions

---

### Eventual Consistency

Replicas may temporarily diverge but eventually converge.

Example:

```text
Write succeeds locally.
Other replicas receive updates asynchronously.
```

Used in global applications where low latency and high availability are more important than immediate consistency.

Cost:

- Stale reads
- Conflict resolution complexity

---

### Causal Consistency

Preserves cause-and-effect relationships.

Example:

```text
If write B depends on write A,
then any replica that sees B must also see A.
```

Useful for collaborative applications, social feeds, and multi-step workflows.

---

### Read-your-writes Consistency

A client sees its own writes immediately, even if other clients may see stale data.

Example:

```text
User updates profile.
User immediately reads profile.
User sees updated value.
```

This is often sufficient for many web applications.

---

## 1.3 CAP and PACELC

The **CAP theorem** says a distributed system can guarantee at most two of:

- **Consistency**
- **Availability**
- **Partition tolerance**

In practice, network partitions are unavoidable, so systems usually choose between consistency and availability during partitions.

**PACELC** extends this:

- During network partitions: choose **Availability** or **Consistency**
- During normal operation: choose **Latency** or **Consistency**

This is important for performance design.

Example:

```text
Strong consistency → higher latency
Low latency → weaker consistency
```

---

# 2. Replication

Replication stores copies of data on multiple nodes. It improves availability, durability, read scalability, and geographic locality.

---

## 2.1 Replication Strategies

### Leader-Based Replication

One node is the leader.

```text
Writes → Leader
Reads → Leader or followers
```

The leader accepts writes and sends changes to followers.

Advantages:

- Simple consistency model
- Easier transaction coordination
- Good for strong consistency

Disadvantages:

- Leader can become bottleneck
- Leader failure requires failover
- Cross-region writes can be slow

Common in:

- PostgreSQL with streaming replication
- MySQL replication
- MongoDB replica sets
- Many cloud SQL databases

---

### Multi-Leader Replication

Multiple nodes accept writes.

```text
Write → any leader
Replicas synchronize asynchronously
```

Advantages:

- Better write availability
- Better geographic latency
- Useful for offline or edge applications

Disadvantages:

- Conflict resolution required
- Harder to guarantee global consistency
- More complex operational behavior

Common in:

- Cassandra
- DynamoDB global tables
- CouchDB
- Some multi-region SQL databases

---

### Leaderless Replication

Any node can accept writes.

```text
Write → one or more replicas
Read → one or more replicas
```

Advantages:

- High availability
- No single leader bottleneck

Disadvantages:

- Complex consistency
- Requires quorum reads/writes
- Conflict resolution may be needed

Common in:

- Dynamo-style systems
- Cassandra
- Riak

---

## 2.2 Synchronous vs Asynchronous Replication

### Synchronous Replication

The write is acknowledged only after replicas confirm.

```text
Client → Leader
Leader → Replicas
Replicas acknowledge
Leader acknowledges client
```

Advantages:

- Strong durability
- Less data loss during failover

Disadvantages:

- Higher latency
- Availability depends on replica health

---

### Asynchronous Replication

The leader acknowledges the client before replicas confirm.

```text
Client → Leader
Leader acknowledges client
Leader sends updates to replicas later
```

Advantages:

- Lower latency
- Better availability

Disadvantages:

- Possible data loss if leader fails
- Followers may lag

---

### Semi-Synchronous Replication

The leader waits for at least one replica to acknowledge before responding.

This is a compromise between synchronous and asynchronous replication.

---

## 2.3 Quorum Replication

A common model in leaderless systems.

Let:

```text
N = number of replicas
W = number of replicas that must acknowledge a write
R = number of replicas consulted for a read
```

A common rule:

```text
W + R > N
```

Example:

```text
N = 3
W = 2
R = 2
```

This ensures reads and writes overlap, reducing the chance of stale reads.

Performance tradeoff:

```text
Higher W → stronger write consistency, higher write latency
Higher R → stronger read consistency, higher read latency
```

---

## 2.4 Replication Placement

Placement affects performance and availability.

### Same-Rack Replication

Fast network, but vulnerable to rack failure.

### Cross-Rack Replication

Better fault tolerance, moderate latency.

### Cross-Datacenter Replication

Protects against datacenter failure, but higher latency.

### Cross-Region Replication

Protects against regional failure, but significantly higher latency.

Design rule:

```text
Strong consistency across regions is expensive.
Asynchronous replication across regions is common.
```

---

## 2.5 Replication and Performance

Replication can improve performance by:

- Serving reads from nearby replicas
- Reducing load on primary nodes
- Allowing parallel reads
- Improving fault tolerance

But it can also hurt performance by:

- Increasing write amplification
- Increasing network traffic
- Adding replication lag
- Requiring conflict resolution
- Increasing storage cost

Important metrics:

```text
Replication lag
Replica health
Write amplification
Read latency by region
Stale read rate
Failover time
```

---

# 3. Indexing in Distributed Databases

Indexes speed up queries but create additional complexity in distributed systems.

---

## 3.1 Local Indexes

Each partition maintains its own index.

Example:

```text
Partition A: index for rows in A
Partition B: index for rows in B
```

Advantages:

- Simple
- Low coordination
- Good for queries that include the partition key

Disadvantages:

- Query without partition key must search many partitions
- Global uniqueness is harder

Example:

```sql
SELECT *
FROM orders
WHERE order_id = 123;
```

If `order_id` is the partition key, this can be fast.

But:

```sql
SELECT *
FROM orders
WHERE customer_id = 456;
```

If `customer_id` is not the partition key, the database may need to query many partitions.

---

## 3.2 Global Indexes

A global index spans all partitions.

Example:

```text
customer_id → partition location
```

Advantages:

- Fast queries on non-partition keys
- Better support for global uniqueness

Disadvantages:

- Index updates may require cross-partition coordination
- Global index can become a bottleneck
- More complex recovery and rebalancing

Example:

```sql
SELECT *
FROM orders
WHERE customer_id = 456;
```

A global index can route the query directly to the correct partition.

---

## 3.3 Partitioned Global Indexes

A global index is itself partitioned.

Example:

```text
Index partition 1: customer_id 1–10000
Index partition 2: customer_id 10001–20000
```

Advantages:

- Scales better than a single global index
- Reduces hotspot risk

Disadvantages:

- More complex
- May require multiple index partitions for range queries

---

## 3.4 Secondary Indexes

Secondary indexes support queries on non-primary attributes.

Example:

```sql
CREATE INDEX idx_email ON users(email);
```

In distributed databases, secondary indexes can be:

### Local Secondary Index

Stored with the partition.

Good when queries include the partition key.

### Global Secondary Index

Stored separately from the main table.

Good for queries that do not include the partition key.

Performance tradeoff:

```text
Global secondary index → faster reads, slower writes
Local secondary index → faster writes, limited query flexibility
```

---

## 3.5 Index Maintenance and Write Performance

Every write may update multiple indexes.

Example:

```text
Insert user row
Update primary key index
Update email index
Update phone index
Update location index
```

This increases write cost.

Performance considerations:

- More indexes → slower writes
- More indexes → more storage
- More indexes → more replication traffic
- More indexes → more recovery work

Best practice:

```text
Create indexes only for important query patterns.
Avoid over-indexing.
```

---

## 3.6 Distributed Index Types

### B-Tree Indexes

Good for:

- Equality
- Range queries
- Sorting

Example:

```sql
WHERE created_at BETWEEN '2024-01-01' AND '2024-01-31'
```

---

### Hash Indexes

Good for:

- Equality lookups
- Fast point queries

Not good for:

- Range queries
- Sorting

---

### Bitmap Indexes

Good for:

- Low-cardinality columns
- Analytics workloads

Example:

```text
status = active
status = inactive
```

Less common in high-write OLTP systems.

---

### Inverted Indexes

Good for:

- Full-text search
- Log search
- Document search

Example:

```text
word → list of documents
```

Often used in search engines and log databases.

---

### Spatial Indexes

Good for:

- Geographic queries
- Nearby search
- Map applications

Example:

```sql
WHERE ST_Distance(location, point) < 1000
```

---

### Vector Indexes

Good for:

- Similarity search
- Machine learning embeddings
- Recommendation systems

Example:

```text
Find nearest vectors to query vector
```

Common in modern AI applications.

---

## 3.7 Indexing and Query Routing

A distributed query engine may use indexes to decide which partitions to query.

Example:

```sql
SELECT *
FROM orders
WHERE customer_id = 456;
```

If the index says:

```text
customer_id 456 is in partition 7
```

The query can be sent only to partition 7.

This is called **partition pruning** or **query pruning**.

Performance benefit:

```text
Avoid scanning all partitions.
```

---

# 4. Transactions in Distributed Databases

A transaction is a group of operations that must behave as a single logical unit.

Classic properties are **ACID**:

- **Atomicity**
- **Consistency**
- **Isolation**
- **Durability**

In distributed databases, ACID is harder because data may be spread across multiple nodes.

---

## 4.1 Atomicity

Atomicity means all operations in a transaction succeed or none do.

Example:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

If one update fails, both must be undone.

In distributed systems, this requires coordination.

---

## 4.2 Consistency

Consistency means the database remains in a valid state according to rules.

Example:

```text
Total money before transfer = total money after transfer
```

Distributed databases enforce consistency through:

- Constraints
- Transactions
- Replication protocols
- Conflict resolution
- Validation rules

---

## 4.3 Isolation

Isolation controls how concurrent transactions interact.

Common isolation levels:

### Read Uncommitted

Can read uncommitted data.

Fast but unsafe.

---

### Read Committed

Reads only committed data.

Common default in many databases.

---

### Repeatable Read

A transaction sees the same values throughout its execution.

Prevents non-repeatable reads.

---

### Serializable

Transactions behave as if executed one after another.

Strongest isolation.

Cost:

- More locking
- More aborts
- Higher latency

---

## 4.4 Two-Phase Commit

Two-phase commit, or **2PC**, is a classic distributed transaction protocol.

### Phase 1: Prepare

Coordinator asks participants:

```text
Can you commit?
```

Each participant locks resources and replies yes or no.

### Phase 2: Commit or Abort

If all participants say yes:

```text
Coordinator sends commit
```

If any participant says no:

```text
Coordinator sends abort
```

Advantages:

- Atomic commit across nodes
- Strong consistency

Disadvantages:

- Coordinator can become bottleneck
- Participants may block while waiting
- Network failures can delay commit
- Poor availability during partitions

2PC is common in traditional distributed SQL databases but can be expensive.

---

## 4.5 Three-Phase Commit

Three-phase commit adds an extra phase to reduce blocking.

Phases:

1. Can commit?
2. Pre-commit
3. Commit

It improves availability compared with 2PC but is more complex and still not perfect.

---

## 4.6 Paxos and Raft

Modern distributed databases often use consensus protocols such as **Paxos** or **Raft**.

These protocols allow a group of nodes to agree on a sequence of operations.

Example:

```text
Replica group elects a leader
Leader proposes log entries
Majority acknowledges
Entry is committed
```

Uses:

- Replicated state machines
- Leader election
- Metadata management
- Distributed transactions
- Log replication

Advantages:

- Strong consistency
- Fault tolerance
- Better operational behavior than naive 2PC

Cost:

- Majority quorum required
- Cross-region latency can be high
- More complex implementation

---

## 4.7 Distributed Snapshots

Distributed databases often use snapshot isolation.

A transaction reads from a consistent snapshot.

Example:

```text
Transaction T starts at timestamp 100
T sees all data committed before timestamp 100
```

This avoids many locking problems.

Common in:

- PostgreSQL
- CockroachDB
- Google Spanner
- FoundationDB

---

## 4.8 Optimistic Concurrency Control

Optimistic concurrency assumes conflicts are rare.

A transaction:

1. Reads data
2. Performs work
3. Checks whether data changed
4. Commits if no conflict

Example:

```text
Read balance = 100
Update balance = 50
Check if balance still 100
If yes, commit
If no, abort
```

Advantages:

- Low locking overhead
- Good for read-heavy workloads

Disadvantages:

- High abort rate under contention
- Requires retry logic

---

## 4.9 Pessimistic Concurrency Control

Pessimistic concurrency locks data before modifying it.

Example:

```text
SELECT ... FOR UPDATE
```

Advantages:

- Prevents conflicts
- Simpler reasoning

Disadvantages:

- Lock contention
- Deadlocks
- Reduced throughput

---

## 4.10 Transaction Latency

Distributed transactions are slower because they involve multiple network round trips.

Example:

```text
Client → coordinator
Coordinator → partition A
Coordinator → partition B
Partition A → coordinator
Partition B → coordinator
Coordinator → client
```

Performance factors:

- Number of partitions touched
- Network latency
- Lock contention
- Replication factor
- Consistency level
- Transaction size
- Retry rate

Design rule:

```text
Keep transactions small.
Keep related data on the same partition when possible.
```

---

## 4.11 Hotspots

A hotspot occurs when many transactions access the same row or partition.

Example:

```text
Inventory item with only 100 units
Thousands of users trying to buy it
```

This can cause:

- Lock contention
- Transaction aborts
- Partition overload
- Poor throughput

Solutions:

- Split counters into multiple rows
- Use asynchronous reservation
- Use optimistic concurrency with retries
- Use sharded inventory
- Use queue-based processing

---

# 5. Recovery in Distributed Databases

Recovery means restoring the database after failures such as node crashes, disk failures, network partitions, or data corruption.

---

## 5.1 Failure Types

Distributed databases must handle:

### Node Failure

A single machine crashes.

### Disk Failure

Storage becomes unavailable or corrupted.

### Network Partition

Nodes cannot communicate.

### Datacenter Failure

An entire facility becomes unavailable.

### Region Failure

A cloud region fails.

### Software Bug

Bad upgrade or logic error corrupts data.

### Human Error

Accidental deletion or misconfiguration.

---

## 5.2 Write-Ahead Logging

A **write-ahead log**, or WAL, records changes before applying them to the main database.

Basic rule:

```text
Log the change before modifying data.
```

Example:

```text
1. Write log record: update account 1 balance to 100
2. Flush log to disk
3. Apply update to memory
4. Later flush data page to disk
```

If the node crashes, the log can be replayed to recover committed changes.

---

## 5.3 Checkpoints

A checkpoint records the database state at a point in time.

Example:

```text
Checkpoint at timestamp 1000
```

During recovery:

```text
Start from checkpoint
Replay WAL after checkpoint
```

This reduces recovery time.

---

## 5.4 Snapshots

A snapshot is a consistent copy of the database.

Example:

```text
Nightly snapshot of entire database
```

Snapshots are useful for:

- Backup
- Restore
- Testing
- Disaster recovery

In distributed databases, snapshots must be globally consistent if used for recovery.

---

## 5.5 Point-in-Time Recovery

Point-in-time recovery allows restoring to a specific moment.

Example:

```text
Restore database to 2024-06-01 10:15:00
```

This is useful after:

- Accidental deletion
- Bad deployment
- Data corruption

Implementation:

```text
Snapshot + WAL replay up to target time
```

---

## 5.6 Replication-Based Recovery

If one node fails, another replica can take over.

Example:

```text
Leader fails
Follower becomes leader
Clients reconnect
```

Recovery depends on:

- Replication lag
- Consistency model
- Failover policy
- Client retry behavior

Important issue:

```text
If replication is asynchronous, the new leader may be missing recent writes.
```

Stronger recovery requires synchronous or majority-based replication.

---

## 5.7 Quorum Recovery

In quorum systems, recovery requires a majority of replicas.

Example:

```text
N = 3
Majority = 2
```

If one node fails, the remaining two can continue.

If two nodes fail, the system may become unavailable.

---

## 5.8 Anti-Entropy and Repair

Replicas can diverge due to network partitions or bugs.

Anti-entropy processes compare replicas and repair differences.

Common methods:

### Merkle Trees

A hash tree summarizes data.

If hashes differ, the system compares subtrees to find differences.

Used in:

- Cassandra
- DynamoDB-style systems
- Some distributed key-value stores

Advantages:

- Efficient comparison
- Detects differences without comparing every row

Disadvantages:

- CPU overhead
- Complexity

---

### Gossip Protocols

Nodes periodically exchange state information.

Example:

```text
Node A tells Node B about recent changes
Node B tells Node C
```

Advantages:

- Decentralized
- Resilient

Disadvantages:

- Convergence may be slow
- Harder to reason about

---

## 5.9 Garbage Collection and Tombstones

Distributed databases often use tombstones to mark deleted data.

Example:

```text
Delete key K
Write tombstone for K
```

Tombstones are needed because replicas may not have seen the delete yet.

Problem:

```text
Too many tombstones slow reads and recovery.
```

Solutions:

- Compaction
- Garbage collection
- Time-to-live
- Periodic cleanup

---

## 5.10 Recovery Performance

Recovery performance depends on:

- Amount of log to replay
- Size of checkpoint
- Number of failed nodes
- Network bandwidth
- Disk speed
- Data size
- Index rebuild requirements
- Replication state

Fast recovery requires:

- Frequent checkpoints
- Fast log storage
- Parallel replay
- Incremental backups
- Warm standby replicas
- Automated failover

---

# 6. Performance Considerations

Distributed database performance is dominated by network behavior, data placement, and consistency choices.

---

## 6.1 Network Latency

Network latency is often the biggest performance factor.

Example:

```text
Same datacenter: 0.1–1 ms
Cross-region: 50–200 ms
Cross-continent: 100–300 ms
```

Strong consistency across regions can require multiple round trips.

Example:

```text
Write requires majority acknowledgment
Read requires latest value
```

This can make cross-region transactions slow.

Design rule:

```text
Place data close to users.
Use asynchronous replication for distant regions.
Use strong consistency only where necessary.
```

---

## 6.2 Throughput

Throughput depends on:

- Partitioning
- Replication factor
- Index count
- Transaction size
- Lock contention
- Network bandwidth
- Disk I/O
- CPU
- Query complexity

Increasing partitions can increase throughput, but only if workload is evenly distributed.

---

## 6.3 Read Performance

Read performance improves with:

- Local replicas
- Caching
- Partition pruning
- Efficient indexes
- Materialized views
- Denormalization
- Read replicas

Read performance suffers from:

- Cross-partition scans
- Global index lookups
- Stale replica reads
- Too many replicas consulted
- Large result sets

---

## 6.4 Write Performance

Write performance suffers from:

- Synchronous replication
- Many indexes
- Large transactions
- Cross-partition writes
- Lock contention
- Tombstone cleanup
- Log flushing
- Network latency

Write performance improves with:

- Local writes
- Asynchronous replication
- Fewer indexes
- Batch writes
- Partitioned writes
- Optimistic concurrency
- Efficient log storage

---

## 6.5 Query Performance

Distributed queries may involve:

1. Query parsing
2. Query planning
3. Partition pruning
4. Parallel execution
5. Data shuffling
6. Aggregation
7. Result merging

Performance problems occur when queries require:

- Full table scans
- Cross-partition joins
- Large data movement
- Many small network requests
- Poorly chosen indexes
- Skewed data distribution

Optimization techniques:

- Co-locate frequently joined data
- Use partition keys in queries
- Avoid `SELECT *`
- Use covering indexes
- Push filters down to storage nodes
- Use approximate queries when acceptable
- Cache hot results

---

## 6.6 Load Balancing

Load balancing distributes requests across nodes.

Important because distributed databases can have uneven load.

Example:

```text
One tenant has 80% of traffic
```

This creates a hot partition.

Solutions:

- Better shard keys
- Split hot partitions
- Use tenant-aware routing
- Add read replicas
- Use caching
- Rebalance data

---

## 6.7 Caching

Caching reduces database load.

Types:

### Application Cache

```text
Cache query results in application memory
```

### Distributed Cache

```text
Redis, Memcached
```

### Database Buffer Cache

```text
Cache data pages in database memory
```

### Query Result Cache

```text
Cache expensive analytical queries
```

Caching tradeoff:

```text
Faster reads, but possible stale data.
```

---

## 6.8 Denormalization

Denormalization stores redundant data to reduce joins.

Example:

```text
Instead of joining users and orders,
store user_name inside each order row.
```

Advantages:

- Faster reads
- Fewer distributed joins

Disadvantages:

- More storage
- More write complexity
- Update anomalies

Useful in read-heavy distributed systems.

---

## 6.9 Batch Processing

Batching improves throughput.

Example:

```text
Insert 1000 rows in one request
```

Instead of:

```text
Insert 1 row 1000 times
```

Batching reduces:

- Network round trips
- Log overhead
- Lock overhead
- Coordination overhead

But large batches can increase latency and memory usage.

---

# 7. Design Tradeoffs

## 7.1 Consistency vs Latency

Strong consistency requires coordination.

Example:

```text
Write must be acknowledged by majority
```

This increases latency.

Weak consistency allows faster local writes.

Example:

```text
Write acknowledged by one node
```

But reads may be stale.

---

## 7.2 Availability vs Consistency

During a network partition:

- Choose availability → accept stale data
- Choose consistency → reject some operations

Example:

```text
Bank transfer system may prefer consistency.
Social media feed may prefer availability.
```

---

## 7.3 Read Scalability vs Write Complexity

Replication improves read scalability.

But every write may need to update multiple replicas and indexes.

---

## 7.4 Global Queries vs Partition Locality

Global queries are convenient but expensive.

Partition-local queries are fast.

Design rule:

```text
Design schema so common queries are partition-local.
```

---

## 7.5 Indexing vs Write Cost

More indexes improve reads but slow writes.

Distributed databases amplify this because index updates may cross partitions.

---

## 7.6 Strong Transactions vs Scalability

Strong distributed transactions require coordination.

This limits scalability.

Many systems use:

- Smaller transactions
- Eventual consistency
- Idempotent operations
- Compensating transactions
- Message queues

---

# 8. Example Design Scenarios

## 8.1 Global E-Commerce Database

Requirements:

- High availability
- Low latency worldwide
- Product catalog reads
- Order transactions
- Inventory consistency

Design:

```text
Product catalog:
  Multi-region read replicas
  Eventual consistency acceptable

User profiles:
  Regional primary
  Read-your-writes consistency

Orders:
  Strong consistency
  Partition by customer or region
  Synchronous replication within region

Inventory:
  Hot inventory split into shards
  Optimistic concurrency
  Reservation queue
```

Performance focus:

- Keep catalog reads local
- Keep order transactions small
- Avoid global locks
- Use regional failover

---

## 8.2 Financial Transaction System

Requirements:

- Strong consistency
- No lost updates
- Auditability
- High durability

Design:

```text
Partition by account ID
Synchronous replication within region
Majority commit
Serializable or snapshot isolation
Strict transaction boundaries
WAL + snapshots + point-in-time recovery
```

Performance focus:

- Minimize cross-partition transactions
- Use local transactions when possible
- Monitor lock contention
- Use fast storage for logs

---

## 8.3 Analytics Warehouse

Requirements:

- Large scans
- Aggregations
- Historical data
- High throughput

Design:

```text
Columnar storage
Partition by date
Sort by common query columns
Materialized views
Parallel query execution
Object storage for cold data
```

Performance focus:

- Partition pruning
- Compression
- Vectorized execution
- Avoid row-by-row processing

## 8.4 Real-Time Chat Application

Requirements:

- Low latency
- High write throughput
- Message ordering
- Global availability

```text
Partition by conversation ID
Append-only message log
Causal consistency
Local writes
Asynchronous replication
TTL for old messages
```

Performance focus:

- Fast append writes
- Efficient message retrieval
- Avoid global locks
- Use local replicas

# Distributed Database Design and Performance

A **distributed database** stores data across multiple machines, racks, data centers, or cloud regions while presenting a unified logical database to applications.

Its design must balance:

- **Scalability**
- **Availability**
- **Consistency**
- **Latency**
- **Durability**
- **Fault tolerance**
- **Operational complexity**

Performance depends heavily on how data is partitioned, replicated, indexed, coordinated, and recovered.

---

## 1. Data Distribution

Distributed databases usually split data across nodes using **partitioning** or **sharding**.

### Horizontal Partitioning

Rows are divided across nodes.

Example:

```text
User ID 1–1000000     → Node A
User ID 1000001–2000000 → Node B
User ID 2000001–3000000 → Node C
```

Benefits:

- Scales storage
- Scales write throughput
- Enables parallel query execution

Risks:

- Hot partitions
- Expensive cross-partition queries
- Complex rebalancing

### Vertical Partitioning

Different tables or columns are stored on different nodes.

Example:

```text
Node A: user profile data
Node B: order history
Node C: audit logs
```

This is useful when data has different access patterns.

### Functional Partitioning

Different database roles are separated:

- Query coordinator
- Storage nodes
- Index nodes
- Transaction manager
- Metadata service

This improves scalability and fault isolation.

---

## 2. Replication

Replication stores copies of data on multiple nodes.

It improves:

- Availability
- Durability
- Read scalability
- Geographic locality
- Fault tolerance

But it also increases:

- Write overhead
- Network traffic
- Storage cost
- Coordination complexity

---

### Leader-Based Replication

One node is the leader.

```text
Writes → Leader
Reads → Leader or followers
```

Advantages:

- Simple consistency model
- Easier transaction coordination
- Good for strong consistency

Disadvantages:

- Leader can become a bottleneck
- Failover complexity
- Cross-region writes can be slow

Examples:

- PostgreSQL streaming replication
- MySQL replication
- MongoDB replica sets

---

### Multi-Leader Replication

Multiple nodes accept writes.

```text
Write → any leader
Replicas synchronize asynchronously
```

Advantages:

- Better write availability
- Lower regional latency
- Useful for global applications

Disadvantages:

- Conflict resolution required
- Harder to guarantee global consistency

Examples:

- DynamoDB global tables
- Cassandra
- CouchDB

---

### Leaderless Replication

Any node can accept writes.

```text
Write → one or more replicas
Read → one or more replicas
```

Advantages:

- High availability
- No single leader bottleneck

Disadvantages:

- Complex consistency
- Requires quorum reads and writes
- May need conflict resolution

Examples:

- Dynamo-style systems
- Cassandra
- Riak

---

### Synchronous vs Asynchronous Replication

#### Synchronous Replication

The write is acknowledged only after replicas confirm.

```text
Client → Leader
Leader → Replicas
Replicas acknowledge
Leader acknowledges client
```

Advantages:

- Strong durability
- Less data loss during failover

Disadvantages:

- Higher latency
- Availability depends on replica health

---

#### Asynchronous Replication

The leader acknowledges the client before replicas confirm.

```text
Client → Leader
Leader acknowledges client
Leader sends updates to replicas later
```

Advantages:

- Lower latency
- Better availability

Disadvantages:

- Possible data loss if leader fails
- Followers may lag

---

### Quorum Replication

A common model in leaderless systems.

Let:

```text
N = number of replicas
W = number of replicas required for a write
R = number of replicas consulted for a read
```

A common rule is:

```text
W + R > N
```

Example:

```text
N = 3
W = 2
R = 2
```

This ensures reads and writes overlap, reducing stale reads.

Performance tradeoff:

```text
Higher W → stronger write consistency, higher write latency
Higher R → stronger read consistency, higher read latency
```

---

## 3. Indexing

Indexes speed up queries but create additional complexity in distributed systems.

---

### Local Indexes

Each partition maintains its own index.

Example:

```text
Partition A: index for rows in A
Partition B: index for rows in B
```

Advantages:

- Simple
- Low coordination
- Fast for queries that include the partition key

Disadvantages:

- Queries without the partition key may scan many partitions
- Global uniqueness is harder

Example:

```sql
SELECT *
FROM orders
WHERE order_id = 123;
```

If `order_id` is the partition key, this can be fast.

But:

```sql
SELECT *
FROM orders
WHERE customer_id = 456;
```

If `customer_id` is not the partition key, the database may need to query many partitions.

---

### Global Indexes

A global index spans all partitions.

Example:

```text
customer_id → partition location
```

Advantages:

- Fast queries on non-partition keys
- Supports global uniqueness

Disadvantages:

- Index updates may require cross-partition coordination
- Can become a bottleneck
- More complex recovery and rebalancing

Example:

```sql
SELECT *
FROM orders
WHERE customer_id = 456;
```

A global index can route the query directly to the correct partition.

---

### Partitioned Global Indexes

A global index is itself partitioned.

Example:

```text
Index partition 1: customer_id 1–10000
Index partition 2: customer_id 10001–20000
```

Advantages:

- Scales better than a single global index
- Reduces hotspot risk

Disadvantages:

- More complex
- Range queries may touch multiple index partitions

---

### Secondary Indexes

Secondary indexes support queries on non-primary attributes.

Example:

```sql
CREATE INDEX idx_email ON users(email);
```

In distributed databases, secondary indexes can be:

#### Local Secondary Index

Stored with the partition.

Good when queries include the partition key.

#### Global Secondary Index

Stored separately from the main table.

Good for queries that do not include the partition key.

Performance tradeoff:

```text
Global secondary index → faster reads, slower writes
Local secondary index → faster writes, limited query flexibility
```

---

### Index Types

#### B-Tree Indexes

Good for:

- Equality
- Range queries
- Sorting

Example:

```sql
WHERE created_at BETWEEN '2024-01-01' AND '2024-01-31'
```

---

#### Hash Indexes

Good for:

- Equality lookups
- Fast point queries

Not good for:

- Range queries
- Sorting

---

#### Inverted Indexes

Good for:

- Full-text search
- Log search
- Document search

Example:

```text
word → list of documents
```

---

#### Spatial Indexes

Good for:

- Geographic queries
- Nearby search
- Map applications

Example:

```sql
WHERE ST_Distance(location, point) < 1000
```

---

#### Vector Indexes

Good for:

- Similarity search
- Machine learning embeddings
- Recommendation systems

Example:

```text
Find nearest vectors to query vector
```

---

### Indexing and Write Performance

Every write may update multiple indexes.

Example:

```text
Insert user row
Update primary key index
Update email index
Update phone index
Update location index
```

This increases write cost.

Performance considerations:

- More indexes → slower writes
- More indexes → more storage
- More indexes → more replication traffic
- More indexes → more recovery work

Best practice:

```text
Create indexes only for important query patterns.
Avoid over-indexing.
```

---

## 4. Transactions

A transaction is a group of operations that must behave as a single logical unit.

Classic properties are **ACID**:

- **Atomicity**
- **Consistency**
- **Isolation**
- **Durability**

In distributed databases, ACID is harder because data may be spread across multiple nodes.

---

### Atomicity

Atomicity means all operations in a transaction succeed or none do.

Example:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

If one update fails, both must be undone.

In distributed systems, this requires coordination.

---

### Consistency

Consistency means the database remains in a valid state according to rules.

Example:

```text
Total money before transfer = total money after transfer
```

Distributed databases enforce consistency through:

- Constraints
- Transactions
- Replication protocols
- Conflict resolution
- Validation rules

---

### Isolation

Isolation controls how concurrent transactions interact.

Common isolation levels:

#### Read Uncommitted

Can read uncommitted data.

Fast but unsafe.

---

#### Read Committed

Reads only committed data.

Common default in many databases.

---

#### Repeatable Read

A transaction sees the same values throughout its execution.

Prevents non-repeatable reads.

---

#### Serializable

Transactions behave as if executed one after another.

Strongest isolation.

Cost:

- More locking
- More aborts
- Higher latency

---

### Two-Phase Commit

Two-phase commit, or **2PC**, is a classic distributed transaction protocol.

#### Phase 1: Prepare

Coordinator asks participants:

```text
Can you commit?
```

Each participant locks resources and replies yes or no.

#### Phase 2: Commit or Abort

If all participants say yes:

```text
Coordinator sends commit
```

If any participant says no:

```text
Coordinator sends abort
```

Advantages:

- Atomic commit across nodes
- Strong consistency

Disadvantages:

- Coordinator can become bottleneck
- Participants may block while waiting
- Network failures can delay commit
- Poor availability during partitions

2PC is common in traditional distributed SQL databases but can be expensive.

---

### Three-Phase Commit

Three-phase commit adds an extra phase to reduce blocking.

Phases:

1. Can commit?
2. Pre-commit
3. Commit

It improves availability compared with 2PC but is more complex and still not perfect.

---

### Paxos and Raft

Modern distributed databases often use consensus protocols such as **Paxos** or **Raft**.

These protocols allow a group of nodes to agree on a sequence of operations.

Example:

```text
Replica group elects a leader
Leader proposes log entries
Majority acknowledges
Entry is committed
```

Uses:

- Replicated state machines
- Leader election
- Metadata management
- Distributed transactions
- Log replication

Advantages:

- Strong consistency
- Fault tolerance
- Better operational behavior than naive 2PC

Cost:

- Majority quorum required
- Cross-region latency can be high
- More complex implementation

---

### Distributed Snapshots

Distributed databases often use snapshot isolation.

A transaction reads from a consistent snapshot.

Example:

```text
Transaction T starts at timestamp 100
T sees all data committed before timestamp 100
```

This avoids many locking problems.

Common in:

- PostgreSQL
- CockroachDB
- Google Spanner
- FoundationDB

---

### Optimistic Concurrency Control

Optimistic concurrency assumes conflicts are rare.

A transaction:

1. Reads data
2. Performs work
3. Checks whether data changed
4. Commits if no conflict

Example:

```text
Read balance = 100
Update balance = 50
Check if balance still 100
If yes, commit
If no, abort
```

Advantages:

- Low locking overhead
- Good for read-heavy workloads

Disadvantages:

- High abort rate under contention
- Requires retry logic

---

### Pessimistic Concurrency Control

Pessimistic concurrency locks data before modifying it.

Example:

```text
SELECT ... FOR UPDATE
```

Advantages:

- Prevents conflicts
- Simpler reasoning

Disadvantages:

- Lock contention
- Deadlocks
- Reduced throughput

---

### Transaction Latency

Distributed transactions are slower because they involve multiple network round trips.

Example:

```text
Client → coordinator
Coordinator → partition A
Coordinator → partition B
Partition A → coordinator
Partition B → coordinator
Coordinator → client
```

Performance factors:

- Number of partitions touched
- Network latency
- Lock contention
- Replication factor
- Consistency level
- Transaction size
- Retry rate

Design rule:

```text
Keep transactions small.
Keep related data on the same partition when possible.
```

---

### Hotspots

A hotspot occurs when many transactions access the same row or partition.

Example:

```text
Inventory item with only 100 units
Thousands of users trying to buy it
```

This can cause:

- Lock contention
- Transaction aborts
- Partition overload
- Poor throughput

Solutions:

- Split counters into multiple rows
- Use asynchronous reservation
- Use optimistic concurrency with retries
- Use sharded inventory
- Use queue-based processing

---

## 5. Recovery

Recovery means restoring the database after failures such as node crashes, disk failures, network partitions, or data corruption.

---

### Failure Types

Distributed databases must handle:

#### Node Failure

A single machine crashes.

#### Disk Failure

Storage becomes unavailable or corrupted.

#### Network Partition

Nodes cannot communicate.

#### Datacenter Failure

An entire facility becomes unavailable.

#### Region Failure

A cloud region fails.

#### Software Bug

Bad upgrade or logic error corrupts data.

#### Human Error

Accidental deletion or misconfiguration.

---

### Write-Ahead Logging

A **write-ahead log**, or WAL, records changes before applying them to the main database.

Basic rule:

```text
Log the change before modifying data.
```

Example:

```text
1. Write log record: update account 1 balance to 100
2. Flush log to disk
3. Apply update to memory
4. Later flush data page to disk
```

If the node crashes, the log can be replayed to recover committed changes.

---

### Checkpoints

A checkpoint records the database state at a point in time.

Example:

```text
Checkpoint at timestamp 1000
```

During recovery:

```text
Start from checkpoint
Replay WAL after checkpoint
```

This reduces recovery time.

---

### Snapshots

A snapshot is a consistent copy of the database.

Example:

```text
Nightly snapshot of entire database
```

Snapshots are useful for:

- Backup
- Restore
- Testing
- Disaster recovery

In distributed databases, snapshots must be globally consistent if used for recovery.

---

### Point-in-Time Recovery

Point-in-time recovery allows restoring to a specific moment.

Example:

```text
Restore database to 2024-06-01 10:15:00
```

This is useful after:

- Accidental deletion
- Bad deployment
- Data corruption

Implementation:

```text
Snapshot + WAL replay up to target time
```

---

### Replication-Based Recovery

If one node fails, another replica can take over.

Example:

```text
Leader fails
Follower becomes leader
Clients reconnect
```

Recovery depends on:

- Replication lag
- Consistency model
- Failover policy
- Client retry behavior

Important issue:

```text
If replication is asynchronous, the new leader may be missing recent writes.
```

Stronger recovery requires synchronous or majority-based replication.

---

### Quorum Recovery

In quorum systems, recovery requires a majority of replicas.

Example:

```text
N = 3
Majority = 2
```

If one node fails, the remaining two can continue.

If two nodes fail, the system may become unavailable.

---

### Anti-Entropy and Repair

Replicas can diverge due to network partitions or bugs.

Anti-entropy processes compare replicas and repair differences.

Common methods:

#### Merkle Trees

A hash tree summarizes data.

If hashes differ, the system compares subtrees to find differences.

Used in:

- Cassandra
- DynamoDB-style systems
- Some distributed key-value stores

Advantages:

- Efficient comparison
- Detects differences without comparing every row

Disadvantages:

- CPU overhead
- Complexity

---

#### Gossip Protocols

Nodes periodically exchange state information.

Example:

```text
Node A tells Node B about recent changes
Node B tells Node C
```

Advantages:

- Decentralized
- Resilient

Disadvantages:

- Convergence may be slow
- Harder to reason about

---

### Garbage Collection and Tombstones

Distributed databases often use tombstones to mark deleted data.

Example:

```text
Delete key K
Write tombstone for K
```

Tombstones are needed because replicas may not have seen the delete yet.

Problem:

```text
Too many tombstones slow reads and recovery.
```

Solutions:

- Compaction
- Garbage collection
- Time-to-live
- Periodic cleanup

---

### Recovery Performance

Recovery performance depends on:

- Amount of log to replay
- Size of checkpoint
- Number of failed nodes
- Network bandwidth
- Disk speed
- Data size
- Index rebuild requirements
- Replication state

Fast recovery requires:

- Frequent checkpoints
- Fast log storage
- Parallel replay
- Incremental backups
- Warm standby replicas
- Automated failover

---

## 6. Performance Considerations

Distributed database performance is dominated by network behavior, data placement, and consistency choices.

---

### Network Latency

Network latency is often the biggest performance factor.

Example:

```text
Same datacenter: 0.1–1 ms
Cross-region: 50–200 ms
Cross-continent: 100–300 ms
```

Strong consistency across regions can require multiple round trips.

Example:

```text
Write requires majority acknowledgment
Read requires latest value
```

This can make cross-region transactions slow.

Design rule:

```text
Place data close to users.
Use asynchronous replication for distant regions.
Use strong consistency only where necessary.
```

---

### Throughput

Throughput depends on:

- Partitioning
- Replication factor
- Index count
- Transaction size
- Lock contention
- Network bandwidth
- Disk I/O
- CPU
- Query complexity

Increasing partitions can increase throughput, but only if workload is evenly distributed.

---

### Read Performance

Read performance improves with:

- Local replicas
- Caching
- Partition pruning
- Efficient indexes
- Materialized views
- Denormalization
- Read replicas

Read performance suffers from:

- Cross-partition scans
- Global index lookups
- Stale replica reads
- Too many replicas consulted
- Large result sets

---

### Write Performance

Write performance suffers from:

- Synchronous replication
- Many indexes
- Large transactions
- Cross-partition writes
- Lock contention
- Tombstone cleanup
- Log flushing
- Network latency

Write performance improves with:

- Local writes
- Asynchronous replication
- Fewer indexes
- Batch writes
- Partitioned writes
- Optimistic concurrency
- Efficient log storage

---

### Query Performance

Distributed queries may involve:

1. Query parsing
2. Query planning
3. Partition pruning
4. Parallel execution
5. Data shuffling
6. Aggregation
7. Result merging

Performance problems occur when queries require:

- Full table scans
- Cross-partition joins
- Large data movement
- Many small network requests
- Poorly chosen indexes
- Skewed data distribution

Optimization techniques:

- Co-locate frequently joined data
- Use partition keys in queries
- Avoid `SELECT *`
- Use covering indexes
- Push filters down to storage nodes
- Use approximate queries when acceptable
- Cache hot results

---

### Load Balancing

Load balancing distributes requests across nodes.

Important because distributed databases can have uneven load.

Example:

```text
One tenant has 80% of traffic
```

This creates a hot partition.

Solutions:

- Better shard keys
- Split hot partitions
- Use tenant-aware routing
- Add read replicas
- Use caching
- Rebalance data

---

### Caching

Caching reduces database load.

Types:

#### Application Cache

```text
Cache query results in application memory
```

#### Distributed Cache

```text
Redis, Memcached
```

#### Database Buffer Cache

```text
Cache data pages in database memory
```

#### Query Result Cache

```text
Cache expensive analytical queries
```

Caching tradeoff:

```text
Faster reads, but possible stale data.
```

---

### Denormalization

Denormalization stores redundant data to reduce joins.

Example:

```text
Instead of joining users and orders,
store user_name inside each order row.
```

Advantages:

- Faster reads
- Fewer distributed joins

Disadvantages:

- More storage
- More write complexity
- Update anomalies

Useful in read-heavy distributed systems.

---

### Batch Processing

Batching improves throughput.

Example:

```text
Insert 1000 rows in one request
```

Instead of:

```text
Insert 1 row 1000 times
```

Batching reduces:

- Network round trips
- Log overhead
- Lock overhead
- Coordination overhead

But large batches can increase latency and memory usage.

---

## 7. Design Tradeoffs

### Consistency vs Latency

Strong consistency requires coordination.

Example:

```text
Write must be acknowledged by majority
```

This increases latency.

Weak consistency allows faster local writes.

Example:

```text
Write acknowledged by one node
```

But reads may be stale.

---

### Availability vs Consistency

During a network partition:

- Choose availability → accept stale data
- Choose consistency → reject some operations

Example:

```text
Bank transfer system may prefer consistency.
Social media feed may prefer availability.
```

---

### Read Scalability vs Write Complexity

Replication improves read scalability.

But every write may need to update multiple replicas and indexes.

---

### Global Queries vs Partition Locality

Global queries are convenient but expensive.

Partition-local queries are fast.

Design rule:

```text
Design schema so common queries are partition-local.
```

---

### Indexing vs Write Cost

More indexes improve reads but slow writes.

Distributed databases amplify this because index updates may cross partitions.

---

### Strong Transactions vs Scalability

Strong distributed transactions require coordination.

This limits scalability.

Many systems use:

- Smaller transactions
- Eventual consistency
- Idempotent operations
- Compensating transactions
- Message queues

---

## 8. Example Design Scenarios

### Global E-Commerce Database

Requirements:

- High availability
- Low latency worldwide
- Product catalog reads
- Order transactions
- Inventory consistency

Design:

```text
Product catalog:
  Multi-region read replicas
  Eventual consistency acceptable

User profiles:
  Regional primary
  Read-your-writes consistency

Orders:
  Strong consistency
  Partition by customer or region
  Synchronous replication within region

Inventory:
  Hot inventory split into shards
  Optimistic concurrency
  Reservation queue
```

Performance focus:

- Keep catalog reads local
- Keep order transactions small
- Avoid global locks
- Use regional failover

---

### Financial Transaction System

Requirements:

- Strong consistency
- No lost updates
- Auditability
- High durability

Design:

```text
Partition by account ID
Synchronous replication within region
Majority commit
Serializable or snapshot isolation
Strict transaction boundaries
WAL + snapshots + point-in-time recovery
```

Performance focus:

- Minimize cross-partition transactions
- Use local transactions when possible
- Monitor lock contention
- Use fast storage for logs

---

### Analytics Warehouse

Requirements:

- Large scans
- Aggregations
- Historical data
- High throughput

Design:

```text
Columnar storage
Partition by date
Sort by common query columns
Materialized views
Parallel query execution
Object storage for cold data
```

Performance focus:

- Partition pruning
- Compression
- Vectorized execution
- Avoid row-by-row processing

---

### Real-Time Chat Application

Requirements:

- Low latency
- High write throughput
- Message ordering
- Global availability

Design:

```text
Partition by conversation ID
Append-only message log
Causal consistency
Local writes
Asynchronous replication
TTL for old messages
```

Performance focus:

- Fast append writes
- Efficient message retrieval
- Avoid global locks
- Use local replicas

---

```text
Query latency

Lock contention
Disk I/O
Network latency
Node health
Failover events

Cache hit rate
```

### Backups

Backups should be:

- Regular
- Tested
- Globally consistent if needed
- Stored separately from production
- Restorable to a specific point in time

---

### Upgrades

Distributed databases require careful upgrades:

- Rolling upgrades
- Compatibility testing
- Schema migrations
- Backward compatibility
- Rollback plan

---

### Rebalancing

Rebalancing moves data between nodes.

It can affect performance.

Best practices:

- Throttle rebalancing
- Monitor load
- Avoid rebalancing during peak traffic
- Use incremental data movement
- Validate consistency after rebalancing

---

### Failure Testing

Systems should be tested for:

- Node crash
- Disk failure
- Network partition
- Region failure
- Clock skew
- Slow disk
- Slow network
- Bad upgrade
- Accidental deletion

This is often called chaos engineering.

---

## Final Summary

A distributed database is designed to scale data, queries, and availability across multiple machines. Its performance depends on careful choices in data placement, replication, indexing, transactions, and recovery.

### Replication

Replication improves availability, durability, and read scalability.

Key choices:

- Leader-based vs multi-leader vs leaderless
- Synchronous vs asynchronous
- Quorum settings
- Regional placement
- Conflict resolution

Performance impact:

- More replicas → better availability and read scalability
- More replicas → more write overhead and latency

---

### Indexing

Indexes speed up reads but increase write cost and complexity.

Key choices:

- Local vs global indexes
- Partitioned indexes
- Secondary indexes
- Search, spatial, vector indexes
- Index maintenance strategy

Performance impact:

- Good indexes reduce query latency
- Too many indexes slow writes and recovery

---

### Transactions

Distributed transactions require coordination.

Key choices:

- Two-phase commit
- Consensus protocols like Raft or Paxos
- Snapshot isolation
- Optimistic vs pessimistic concurrency
- Transaction size and partition locality

Performance impact:

- Strong transactions increase latency
- Cross-partition transactions reduce scalability
- Hot partitions cause contention

---

### Recovery

Recovery handles failures and restores consistency.

Key mechanisms:

- Write-ahead logging
- Checkpoints
- Snapshots
- Point-in-time recovery
- Replica failover
- Anti-entropy repair
- Tombstone cleanup

Performance impact:

- Faster recovery requires frequent checkpoints and fast logs
- Asynchronous replication improves performance but risks data loss
- Strong replication improves recovery but increases latency

---

## Practical Design Rule

The best distributed database design depends on workload requirements.

A practical rule is:

```text
Use strong consistency only where correctness requires it.
Keep transactions small.
Keep related data on the same partition when possible.
Design shard keys to avoid hotspots.
Use indexes selectively.
Replicate data close to users.
Use asynchronous replication across distant regions.
Plan recovery before failures happen.
```

In short:

```text
Distributed database performance is mostly a problem of data placement, coordination cost, and failure handling.
```
