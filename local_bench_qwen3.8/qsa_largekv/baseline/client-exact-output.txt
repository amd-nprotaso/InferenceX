## Distributed Database Design and Performance

A **distributed database** stores data across multiple independent machines or sites connected by a network, while presenting users and applications with a unified logical database. Its design must balance **scalability, availability, consistency, latency, throughput, fault tolerance, and operational complexity**.

The main design areas are:

1. **Data distribution and partitioning**
2. **Replication**
3. **Indexing**
4. **Transactions**
5. **Recovery**

---

# 1. Overall Design of a Distributed Database

A distributed database is usually built from several components:

- **Nodes/servers**: machines that store and process data.
- **Network layer**: communication between nodes.
- **Storage engine**: local data structures such as B-trees, LSM trees, logs, or columnar stores.
- **Query processor**: parses, optimizes, and executes distributed queries.
- **Coordinator or leader**: may manage metadata, transactions, or replication.
- **Metadata/catalog service**: stores schema, partitioning, replication, and placement information.
- **Consensus or coordination service**: used for leader election, metadata consistency, and atomic commit.

## Common Architectures

### 1. Shared-nothing architecture

Each node owns a portion of the data and has its own CPU, memory, and disk.

Examples: Cassandra, DynamoDB, Google Spanner, CockroachDB, TiDB.

Advantages:

- Horizontal scalability.
- No shared disk bottleneck.
- Good fault isolation.

Challenges:

- Network communication becomes central.
- Data placement and rebalancing are complex.
- Distributed transactions are expensive.

---

### 2. Master/slave or leader/follower architecture

One node, the leader, accepts writes. Followers replicate the leader’s log.

Advantages:

- Simple consistency model.
- Easier transaction processing.
- Stronger consistency is easier to implement.

Challenges:

- Leader can become a bottleneck.
- Leader failure requires failover.
- Write throughput may be limited by leader capacity.

---

### 3. Multi-leader architecture

Multiple nodes accept writes, often in different regions.

Advantages:

- Better write availability.
- Lower write latency for geographically distributed users.

Challenges:

- Conflict resolution is required.
- Strong consistency becomes harder.
- Replication lag can cause anomalies.

---

### 4. Leaderless architecture

Any node can accept writes and reads, often using quorum protocols.

Examples: Dynamo-style systems.

Advantages:

- High availability.
- No single leader bottleneck.

Challenges:

- Weak or eventual consistency unless carefully controlled.
- Conflict resolution and read repair are complex.

---

# 2. Data Distribution and Partitioning

Distributed databases usually partition data across nodes. Partitioning is central to performance because it determines where data is stored and how queries are routed.

## Partitioning Strategies

### 1. Hash partitioning

Data is assigned by hashing a key:

```text
node = hash(key) mod number_of_nodes
```

Advantages:

- Even data distribution.
- Simple point lookups.

Disadvantages:

- Range queries are expensive.
- Rebalancing can move large amounts of data.
- Hot keys can still create hotspots.

---

### 2. Range partitioning

Data is assigned by key ranges:

```text
A–M on node 1
N–Z on node 2
```

Advantages:

- Efficient range scans.
- Locality for related keys.

Disadvantages:

- Hot ranges can overload one node.
- Rebalancing may be uneven.

---

### 3. Directory or lookup-based partitioning

A metadata service maps keys to nodes.

Advantages:

- Flexible placement.
- Can optimize for locality, load, or cost.

Disadvantages:

- Lookup service can become a bottleneck.
- Metadata must be highly available.

---

### 4. Consistent hashing

Nodes are placed on a hash ring, and keys are assigned to the next node clockwise.

Advantages:

- Fewer data movements when nodes join or leave.
- Good for distributed caches and key-value stores.

Disadvantages:

- Still needs virtual nodes to avoid imbalance.
- Range queries are not natural.

---

## Fragmentation Models

Distributed databases may use:

### Horizontal fragmentation

Rows are split across nodes.

Example:

```text
Node 1: users with ID 1–1,000,000
Node 2: users with ID 1,000,001–2,000,000
```

This is the most common model.

---

### Vertical fragmentation

Columns are split across nodes.

Example:

```text
Node 1: user_id, name, email
Node 2: user_id, address, preferences
```

Useful when different columns have different access patterns, but joins become expensive.

---

### Hybrid fragmentation

Combines horizontal and vertical fragmentation.

---

## Placement and Rebalancing

Data placement affects performance:

- **Locality**: related data should be placed together.
- **Load balance**: avoid hot partitions.
- **Fault tolerance**: replicas should be on different racks, zones, or regions.
- **Rebalancing**: moving data when nodes are added or removed must be gradual to avoid network storms.

Poor placement causes:

- Hot partitions.
- Cross-node joins.
- High network traffic.
- Uneven disk and CPU utilization.

---

# 3. Replication

Replication stores copies of data on multiple nodes. It improves availability, durability, and read performance, but introduces consistency and latency tradeoffs.

## Why Replicate?

Replication provides:

- **Fault tolerance**: if one node fails, another copy exists.
- **High availability**: reads and sometimes writes can continue during failures.
- **Read scalability**: multiple replicas can serve reads.
- **Geographic locality**: users can read from nearby replicas.
- **Durability**: data survives disk or machine failure.

---

## Replication Models

### 1. Synchronous replication

The leader writes locally and waits for replicas to acknowledge before returning success to the client.

```text
Client → Leader → Replica acknowledges → Client
```

Advantages:

- Strong durability.
- If the leader fails, no committed data is lost.
- Easier to provide linearizable reads.

Disadvantages:

- Higher write latency.
- Availability depends on replica availability.
- Network failures can block writes.

Used in systems requiring strong consistency, such as financial databases.

---

### 2. Asynchronous replication

The leader acknowledges the client after writing locally, then sends changes to replicas in the background.

```text
Client → Leader → Client
Leader → Replica later
```

Advantages:

- Low write latency.
- High write throughput.
- Tolerates replica failures.

Disadvantages:

- Committed data may be lost if the leader fails before replication.
- Stale reads are possible.
- Failover may lose recent writes.

Common in high-throughput systems where some data loss is acceptable.

---

### 3. Semi-synchronous replication

The leader waits for at least one replica to acknowledge receipt of the log, but not necessarily full application of the data.

Advantages:

- Better durability than fully asynchronous.
- Lower latency than fully synchronous.

Disadvantages:

- Still can lose data in some failure scenarios.
- More complex than simple synchronous or asynchronous modes.

---

### 4. Quorum replication

Writes and reads require agreement from a subset of replicas.

If there are `N` replicas:

```text
Write quorum: W
Read quorum: R
```

A common rule is:

```text
W + R > N
```

This ensures overlap between read and write sets, improving consistency.

Example:

```text
N = 3
W = 2
R = 2
```

Advantages:

- Tunable consistency.
- Can tolerate some node failures.
- No single leader required in leaderless designs.

Disadvantages:

- Complex conflict resolution.
- Tail latency can be high if one replica is slow.
- Strong consistency requires careful protocol design.

---

## Leader/Follower Replication

In leader/follower systems:

1. Client sends write to leader.
2. Leader appends to write-ahead log.
3. Followers replicate log.
4. Leader commits after required acknowledgments.
5. Followers apply changes.

Performance depends on:

- Network latency.
- Disk write speed.
- Log replication bandwidth.
- Number of required acknowledgments.
- Follower apply lag.

---

## Multi-Leader Replication

Multiple leaders accept writes.

Advantages:

- Better availability.
- Better latency for distributed users.

Challenges:

- Conflicts occur when two leaders update the same data.
- Conflict resolution may be:
  - Last-write-wins.
  - Vector clocks.
  - CRDTs.
  - Application-level merge logic.
- Strong consistency is difficult.

---

## Leaderless Replication

Any node can accept writes.

Advantages:

- High availability.
- No leader election bottleneck.

Challenges:

- Read repair and anti-entropy are required.
- Stale reads are common.
- Strong consistency requires quorums and careful versioning.

---

## Consistency Models

Replication design determines consistency.

### Strong consistency

All reads see the latest committed write.

Examples:

- Linearizability.
- Serializability.

Advantages:

- Simple application semantics.
- Safe for critical operations.

Costs:

- Higher latency.
- Lower availability during partitions.

---

### Eventual consistency

Replicas converge over time, but reads may be stale.

Advantages:

- High availability.
- Low latency.

Costs:

- Applications must tolerate stale data.
- Conflict resolution is required.

---

### Causal consistency

Writes that are causally related are seen in order.

Example:

If write B depends on write A, any node that sees B must also see A.

Advantages:

- Stronger than eventual consistency.
- More available than full linearizability.

Costs:

- Requires version vectors or causal metadata.

---

## Replication Performance Issues

### Write amplification

Each write may be:

- Logged locally.
- Sent to replicas.
- Applied to indexes.
- Compacted later.

This increases disk and network load.

---

### Read amplification

Reads may require:

- Multiple replicas.
- Tombstone filtering.
- Merge of multiple versions.
- Read repair.

---

### Tail latency

If a system waits for multiple replicas, the slowest replica can delay the request.

Mitigations:

- Hedged reads.
- Quorum reads.
- Fastest replica selection.
- Timeout-based fallback.

---

### Network partitions

During partitions, systems must choose:

- **Consistency**: reject writes to preserve correctness.
- **Availability**: accept writes and resolve conflicts later.

This is the CAP tradeoff.

---

# 4. Indexing in Distributed Databases

Indexes speed up queries, but in distributed systems they also affect data placement, write cost, and query routing.

## Local Indexes

Each partition maintains its own index.

Example:

```text
Partition 1: index for users in range A–M
Partition 2: index for users in range N–Z
```

Advantages:

- Index updates are local.
- Low network cost.
- Good for queries that target one partition.

Disadvantages:

- Queries across all partitions must scan many indexes.
- Global uniqueness constraints are hard.
- Range queries may require scatter-gather.

---

## Global Indexes

A global index maps values to partitions across the entire dataset.

Example:

```text
email = alice@example.com → partition 7
```

Advantages:

- Efficient lookup by non-partition key.
- Supports global uniqueness.
- Avoids scanning all partitions.

Disadvantages:

- Index updates may require cross-node transactions.
- Global index can become a bottleneck.
- Rebalancing requires index updates.

---

## Global Index Implementation

A global index can be stored:

1. **In a separate table**
2. **In a dedicated index service**
3. **Replicated across nodes**
4. **Partitioned by indexed value**

Example:

```text
Primary table partitioned by user_id
Secondary index partitioned by email
```

When inserting a user:

```text
Write user row to user_id partition
Write email index entry to email partition
```

This may require distributed transaction coordination.

---

## Index Types

### B-tree indexes

Good for:

- Point lookups.
- Range scans.
- Ordered access.

Common in traditional relational databases.

---

### LSM-tree indexes

Good for:

- High write throughput.
- Append-heavy workloads.

Used in systems like Cassandra, RocksDB, HBase.

Costs:

- Read amplification.
- Background compaction.
- Tombstone handling.

---

### Hash indexes

Good for:

- Exact-match lookups.

Poor for:

- Range queries.
- Ordered scans.

---

### Bitmap indexes

Good for:

- Low-cardinality columns.
- Analytical queries.

Poor for:

- High-update transactional workloads.

---

### Covering indexes

An index contains all columns needed by a query.

Advantages:

- Avoids fetching the base row.
- Reduces I/O.

Costs:

- Larger index size.
- More write overhead.

---

## Distributed Query Optimization

Distributed query optimizers must consider:

- Network latency.
- Data location.
- Partition pruning.
- Join placement.
- Index availability.
- Replication state.
- Skew.

Example:

```sql
SELECT *
FROM orders
WHERE customer_id = 123;
```

If `orders` is partitioned by `customer_id`, the query can go directly to one partition.

If `orders` is partitioned by `order_id`, the query may need to scan many partitions unless a secondary index exists.

---

## Indexing Performance Tradeoffs

### Write cost

Every index must be updated on insert, update, or delete.

In distributed systems, index updates may require:

- Cross-partition writes.
- Distributed transactions.
- Replication.
- Conflict handling.

---

### Read cost

Indexes can reduce reads, but distributed indexes may require:

- Index lookup on one node.
- Data fetch on another node.
- Multiple round trips.

---

### Skew

If many rows have the same indexed value, one index partition can become hot.

Example:

```text
status = "active"
```

If most rows are active, an index on `status` may overload one node.

---

### Rebalancing

When data moves between nodes, indexes must also move or be updated.

Poor rebalancing can cause:

- Temporary query failures.
- Stale index entries.
- High network load.
- Increased latency.

---

# 5. Transactions in Distributed Databases

A distributed transaction involves operations on multiple nodes. It must preserve ACID properties:

- **Atomicity**: all or nothing.
- **Consistency**: database remains valid.
- **Isolation**: concurrent transactions do not interfere incorrectly.
- **Durability**: committed changes survive failures.

Distributed transactions are harder because nodes can fail independently and network messages can be delayed or lost.

---

## Two-Phase Commit, 2PC

The classic protocol for atomic commit across nodes.

### Phase 1: Prepare

Coordinator asks all participants:

```text
Can you commit?
```

Each participant:

- Locks resources.
- Writes prepare record to log.
- Replies yes or no.

### Phase 2: Commit or Abort

If all participants vote yes:

```text
Coordinator sends commit
Participants commit
```

If any participant votes no:

```text
Coordinator sends abort
Participants abort
```

Advantages:

- Provides atomic commit.
- Works well for small, short transactions.

Disadvantages:

- Coordinator can become a bottleneck.
- Participants may block while waiting for coordinator.
- Network partitions can leave transactions in doubt.
- High latency due to multiple round trips.

---

## Three-Phase Commit, 3PC

Adds a pre-commit phase to reduce blocking.

Phases:

1. Can commit?
2. Pre-commit.
3. Commit.

Advantages:

- Reduces blocking compared to 2PC.

Disadvantages:

- Still not safe under all network partitions.
- More complex.
- Rarely used in practice.

---

## Consensus-Based Commit

Modern systems often use consensus protocols such as:

- Paxos.
- Raft.
- Multi-Paxos.
- Raft-based replicated state machines.

These provide:

- Leader election.
- Log replication.
- Fault tolerance.
- Strong consistency within a replicated group.

Examples:

- CockroachDB uses Raft.
- TiDB uses Raft.
- Spanner uses Paxos-like replication.

Consensus helps avoid split-brain and ensures replicas agree on committed data.

---

## Distributed Isolation Levels

### Read committed

A transaction sees only committed data.

Advantages:

- Lower locking overhead.

Disadvantages:

- Non-repeatable reads.
- May be insufficient for complex transactions.

---

### Repeatable read

A transaction sees the same data throughout its execution.

Advantages:

- Prevents non-repeatable reads.

Disadvantages:

- More locking or versioning.
- May still allow phantom reads depending on implementation.

---

### Snapshot isolation

Each transaction reads from a consistent snapshot.

Advantages:

- Good performance.
- Readers do not block writers.
- Common in MVCC systems.

Disadvantages:

- Write-write conflicts must be detected.
- Not always serializable.

---

### Serializable

Transactions behave as if executed one at a time.

Advantages:

- Strongest correctness.

Disadvantages:

- Higher latency.
- More aborts.
- More coordination.

Techniques:

- Strict two-phase locking.
- Serializable snapshot isolation, SSI.
- Predicate locking.
- Timestamp ordering.

---

## Concurrency Control

### Locking

Transactions lock data items.

Advantages:

- Simple correctness model.

Disadvantages:

- Locks across nodes are expensive.
- Deadlocks are harder to detect.
- Locks can reduce throughput.

---

### Optimistic concurrency control

Transactions execute without locks, then validate at commit.

Advantages:

- Good for low-contention workloads.

Disadvantages:

- High abort rates under contention.

---

### MVCC

Multi-version concurrency control keeps multiple versions of data.

Advantages:

- Readers do not block writers.
- Writers do not block readers.
- Good for distributed systems.

Disadvantages:

- Version cleanup is required.
- Long-running transactions can cause bloat.
- Snapshot reads may be stale depending on consistency model.

---

## Distributed Deadlock Detection

Deadlocks can occur across nodes.

Example:

```text
Transaction A on Node 1 waits for lock on Node 2
Transaction B on Node 2 waits for lock on Node 1
```

Solutions:

- Global wait-for graph.
- Timeout-based detection.
- Hierarchical deadlock detection.
- Avoidance through lock ordering.

Timeouts are common because global detection is expensive.

---

## Transaction Performance

Distributed transaction latency is dominated by:

- Network round trips.
- Number of participants.
- Lock contention.
- Replication acknowledgments.
- Consensus messages.
- Coordinator overhead.

A local transaction may take microseconds. A distributed transaction may take milliseconds or more.

---

## Reducing Transaction Cost

Common techniques:

### Partition-aware transactions

Keep transactions within one partition whenever possible.

Example:

```text
Transfer between accounts in same partition → local transaction
Transfer between accounts in different partitions → distributed transaction
```

---

### Batched commits

Combine multiple transactions into one log flush or consensus round.

---

### Idempotent operations

Allow safe retries after timeouts.

---

### Sagas

Break long transactions into smaller local transactions with compensating actions.

Example:

```text
Reserve inventory
Charge payment
Ship order
```

If shipping fails:

```text
Refund payment
Release inventory
```

Advantages:

- Better availability.
- Avoids long distributed locks.

Disadvantages:

- Not fully isolated.
- Application must handle partial states.

---

# 6. Recovery in Distributed Databases

Recovery ensures that committed transactions survive failures and uncommitted transactions are not visible.

## Failure Types

Distributed databases must handle:

- Node crash.
- Disk failure.
- Network partition.
- Clock skew.
- Slow or delayed messages.
- Partial message loss.
- Leader failure.
- Replica failure.
- Data corruption.
- Site failure.

---

## Write-Ahead Logging, WAL

A write-ahead log records changes before they are applied to the database.

Typical log records:

```text
BEGIN
UPDATE
COMMIT
ABORT
CHECKPOINT
```

Rules:

- Log record must be durable before the change is acknowledged.
- Committed transactions must be recoverable from the log.
- Uncommitted transactions must be undone.

---

## Recovery Process

After a crash:

1. Read stable log.
2. Identify committed transactions.
3. Redo committed changes.
4. Undo uncommitted changes.
5. Restore database to consistent state.

---

## Checkpointing

A checkpoint records the state of the database and log at a point in time.

Advantages:

- Faster recovery.
- Reduces log replay.

Disadvantages:

- Checkpointing consumes I/O and CPU.
- Too frequent checkpoints reduce throughput.
- Too infrequent checkpoints increase recovery time.

---

## Recovery in Replicated Systems

### Synchronous replication

If the leader fails, a follower can take over with little or no data loss.

Recovery steps:

1. Detect leader failure.
2. Elect new leader.
3. New leader replays log.
4. Clients reconnect.

---

### Asynchronous replication

Failover may lose recent writes.

Recovery may require:

- Choosing the most up-to-date replica.
- Reconciling divergent logs.
- Accepting data loss.
- Manual repair.

---

### Quorum recovery

A new leader or coordinator must contact a quorum of replicas to determine the latest committed state.

This prevents:

- Lost updates.
- Split-brain.
- Old leaders committing stale data.

---

## Handling In-Doubt Transactions

In 2PC, a participant may be prepared but not know whether the transaction committed.

Example:

```text
Participant voted YES
Coordinator crashed before sending final decision
```

The participant is in doubt.

Solutions:

- Coordinator recovery.
- Consult other participants.
- Timeout and abort.
- Consult replicas or consensus log.
- Manual intervention in rare cases.

---

## Fencing

When a leader is suspected dead, it may still be alive but partitioned.

Fencing prevents the old leader from continuing to write.

Methods:

- Epoch numbers.
- Lease tokens.
- Storage-level fencing.
- Consensus-based leader epochs.

Example:

```text
New leader has epoch 10
Old leader has epoch 9
Replicas reject writes from epoch 9
```

---

## Point-in-Time Recovery

Systems may support recovery to a specific timestamp.

Uses:

- Undo accidental deletes.
- Recover from application bugs.
- Audit compliance.

Implementation:

- Full backup.
- Continuous log archive.
- Replay logs up to target time.

---

## Backup and Restore

Backups can be:

- Full snapshots.
- Incremental backups.
- Log archives.
- Replicated snapshots.

Distributed backups must be consistent across partitions.

Options:

- Pause writes briefly.
- Use consistent snapshots.
- Use distributed transaction timestamps.
- Use MVCC snapshot boundaries.

---

# 7. Performance Considerations

Distributed database performance depends on many factors.

## Latency

Latency includes:

- Network round trip.
- Disk I/O.
- Lock waiting.
- Replication acknowledgment.
- Consensus messages.
- Query coordination.

Strong consistency usually increases latency.

---

## Throughput

Throughput depends on:

- Partitioning.
- Load balance.
- Index design.
- Transaction size.
- Replication mode.
- Hardware speed.
- Network bandwidth.

Poor partitioning can limit throughput even if hardware is powerful.

---

## Tail Latency

Distributed systems often suffer from high tail latency because a request may depend on multiple nodes.

If one node is slow, the whole request may be slow.

Mitigations:

- Hedged requests.
- Quorum reads.
- Fast replica selection.
- Timeout policies.
- Caching.
- Background compaction control.

---

## Network Bottlenecks

Network can dominate performance.

Common causes:

- Cross-partition joins.
- Global indexes.
- Distributed transactions.
- Rebalancing.
- Replication traffic.
- Backup traffic.

Design should minimize cross-node communication.

---

## Skew and Hotspots

Hot partitions occur when many requests target the same data.

Examples:

```text
Popular product
Accounting counter
Trending hashtag
```

Mitigations:

- Partition key design.
- Sub-partitioning.
- Caching.
- Counter sharding.
- Load-aware placement.

---

## Storage Engine Choice

### B-tree

Good for:

- OLTP.
- Range queries.
- Low write amplification.

### LSM-tree

Good for:

- High write throughput.
- Append-heavy workloads.

Costs:

- Compaction.
- Read amplification.
- Tombstones.

---

## Caching

Caching improves performance but complicates consistency.

Types:

- Client cache.
- Proxy cache.
- Server-side block cache.
- Query result cache.
- Materialized views.

Invalidation must be handled carefully in distributed systems.

---

## Query Optimization

Distributed optimizers should:

- Push filters to storage nodes.
- Prune partitions.
- Choose join strategies.
- Avoid unnecessary data movement.
- Use indexes.
- Consider replication lag.
- Account for network cost.

---

# 8. Design Tradeoffs

## Consistency vs Availability

Strong consistency requires coordination.

Availability requires accepting operations despite failures.

In a partition, a system may choose:

- **CP**: consistent and partition-tolerant.
- **AP**: available and partition-tolerant.

Many systems allow per-table or per-query consistency choices.

---

## Latency vs Durability

Synchronous replication improves durability but increases latency.

Asynchronous replication improves latency but risks data loss.

---

## Read Performance vs Write Performance

More indexes and replicas improve reads but slow writes.

Fewer indexes improve writes but slow reads.

---

## Strong Transactions vs Scalability

Distributed transactions provide correctness but reduce scalability.

Many large systems avoid distributed transactions by:

- Designing partitions around business entities.
- Using idempotency.
- Using sagas.
- Accepting eventual consistency.

---

## Simplicity vs Fault Tolerance

Simple leader/follower systems are easier to reason about.

Leaderless systems can be more available but harder to debug.

---

# 9. Example: Designing a Distributed Banking Database

Suppose we design a distributed account database.

## Data Model

```text
accounts(account_id, owner_id, balance, currency, version)
transactions(txn_id, from_account, to_account, amount, status)
```

## Partitioning

Partition by `account_id` using hash partitioning.

```text
account_id hash → partition
```

## Replication

Use leader/follower replication with Raft.

Each partition has:

- One leader.
- Two followers.

Writes require majority acknowledgment.

## Indexing

Primary index:

```text
account_id
```

Secondary index:

```text
owner_id
```

The secondary index is stored in a separate partitioned table.

## Transactions

A transfer between two accounts may involve two partitions.

Use distributed transaction protocol:

1. Lock or prepare both accounts.
2. Validate balances.
3. Commit atomically.
4. Release locks.

For high throughput, use optimistic concurrency control with version numbers.

## Recovery

Use WAL and Raft log.

If leader fails:

1. Followers detect failure.
2. New leader elected.
3. Committed log entries are applied.
4. Clients reconnect.

If a transaction is in doubt:

- Consult majority replicas.
- Determine commit status from consensus log.
- Commit or abort accordingly.

---

# 10. Summary

A distributed database is designed around data distribution, replication, indexing, transactions, and recovery.

## Replication

Replication improves availability and durability but creates consistency and latency tradeoffs.

Key choices:

- Synchronous vs asynchronous.
- Leader/follower vs multi-leader vs leaderless.
- Quorum size.
- Consistency model.
- Conflict resolution.

## Indexing

Indexes improve query performance but can become distributed bottlenecks.

Key choices:

- Local vs global indexes.
- Partition-aware indexing.
- Index update cost.
- Cross-partition query cost.
- Rebalancing impact.

## Transactions

Distributed transactions provide atomicity and isolation but are expensive.

Key choices:

- 2PC or consensus-based commit.
- Locking vs MVCC vs optimistic concurrency.
- Isolation level.
- Partition-aware transaction design.
- Sagas for long-running workflows.

## Recovery

Recovery must handle node failures, network partitions, and in-doubt transactions.

Key mechanisms:

- Write-ahead logging.
- Checkpointing.
- Replicated logs.
- Leader election.
- Fencing.
- Quorum recovery.
- Backups and point-in-time recovery.

## Performance

Performance is usually limited by:

- Network latency.
- Cross-partition operations.
- Replication acknowledgments.
- Lock contention.
- Hot partitions.
- Index maintenance.
- Consensus coordination.

The best distributed database design minimizes cross-node communication, chooses the weakest consistency model that is safe for the application, partitions data around natural access patterns, and uses replication and recovery mechanisms appropriate to the required durability and availability.
