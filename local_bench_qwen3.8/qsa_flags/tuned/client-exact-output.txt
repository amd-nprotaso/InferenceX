A distributed database is a database whose data and processing are spread across multiple machines, often in different locations, while appearing to clients as a single logical database. Its design is dominated by tradeoffs among **scalability, availability, consistency, latency, durability, and operational complexity**. The four areas you asked about—**replication, indexing, transactions, and recovery**—are central to both correctness and performance.

---

## 1. Design Goals of a Distributed Database

A distributed database is usually designed to achieve one or more of the following:

### 1.1 Scalability

The system should handle growth in:

- Data volume
- Number of clients
- Query throughput
- Write throughput
- Number of concurrent transactions

Scalability is achieved by distributing data and work across many nodes.

### 1.2 Availability

The system should continue serving requests despite failures of:

- Individual servers
- Disks
- Network links
- Data centers
- Entire regions

Availability is usually improved through replication and automatic failover.

### 1.3 Fault Tolerance

The database should survive partial failures without losing committed data or corrupting state.

This requires:

- Replicated logs
- Consensus protocols
- Checkpoints
- Backups
- Recovery procedures

### 1.4 Performance

Performance depends heavily on:

- Data placement
- Network latency
- Replication strategy
- Index design
- Transaction coordination
- Query execution
- Caching
- Load balancing

### 1.5 Consistency

Distributed databases must define what consistency clients can expect.

Common consistency models include:

| Model | Meaning |
|---|---|
| Strong consistency | All clients see the same data at the same time |
| Linearizability | Reads and writes appear to occur atomically at a single point in time |
| Sequential consistency | Operations appear in some globally consistent order |
| Causal consistency | Causally related operations are seen in order |
| Eventual consistency | Replicas converge over time, but may temporarily diverge |

The CAP theorem says that during a network partition, a distributed system must choose between **consistency** and **availability**. In practice, many systems offer configurable consistency levels.

---

## 2. Core Design Dimensions

Before discussing replication, indexing, transactions, and recovery, it helps to understand the main design choices.

---

### 2.1 Data Partitioning / Sharding

Data is divided into smaller units called partitions, shards, or tablets.

Common partitioning strategies:

#### Hash Partitioning

Each row is assigned to a shard using a hash of the partition key.

Example:

```text
shard = hash(customer_id) % number_of_shards
```

Advantages:

- Even data distribution
- Simple routing
- Good for high-cardinality keys

Disadvantages:

- Range queries are expensive
- Rebalancing can be complex
- Hot keys can still cause hotspots

#### Range Partitioning

Data is partitioned by ranges of a key.

Example:

```text
Shard 1: customer_id 0–9999
Shard 2: customer_id 10000–19999
```

Advantages:

- Efficient range scans
- Natural locality for ordered access patterns

Disadvantages:

- Hot ranges can occur
- Rebalancing may be needed
- Uneven load if ranges are skewed

#### Directory Partitioning

A lookup table maps keys to shards.

Advantages:

- Flexible placement
- Can move data easily

Disadvantages:

- Lookup service becomes critical
- Metadata can become a bottleneck

#### Geographic Partitioning

Data is placed based on user location or regulatory requirements.

Example:

```text
European users -> EU data center
US users -> US data center
```

Advantages:

- Low latency for local users
- Data residency compliance

Disadvantages:

- Cross-region transactions are expensive
- Complex operational management

---

### 2.2 Replication Factor

Each partition is usually stored on multiple nodes.

Example:

```text
Partition P1:
  Replica 1: Node A
  Replica 2: Node B
  Replica 3: Node C
```

Higher replication improves durability and availability but increases write cost and storage cost.

---

### 2.3 Consistency Model

The database must decide how reads and writes behave across replicas.

Examples:

- Write to leader, read from leader: strong consistency
- Write to leader, read from any replica: possible stale reads
- Quorum reads/writes: configurable consistency
- Eventual consistency: replicas converge asynchronously

---

### 2.4 Query Processing

Distributed queries may require:

- Scatter-gather execution
- Distributed joins
- Partial aggregation
- Query pushdown
- Parallel scans
- Result merging

Performance depends heavily on whether data needed by a query is colocated.

---

## 3. Replication

Replication means storing copies of data on multiple nodes.

It is used for:

- Fault tolerance
- High availability
- Read scalability
- Geographic locality
- Disaster recovery

But replication introduces complexity around consistency, latency, and conflict resolution.

---

## 3.1 Replication Architectures

### 3.1.1 Primary-Backup / Leader-Follower

One node is the leader or primary. It accepts writes.

Followers or replicas apply the leader’s log.

```text
Client -> Leader -> Follower 1
                 -> Follower 2
                 -> Follower 3
```

Advantages:

- Simple conflict resolution
- Easy to reason about correctness
- Common in many systems

Disadvantages:

- Leader can become a bottleneck
- Leader failure requires failover
- Followers may lag

---

### 3.1.2 Synchronous Replication

The leader waits for replicas to acknowledge the write before returning success to the client.

```text
Client -> Leader
Leader -> Replica 1
Leader -> Replica 2
Replicas ACK
Leader -> Client: success
```

Advantages:

- Strong durability
- No committed data loss if one replica fails
- Easier failover

Disadvantages:

- High write latency
- Sensitive to slow replicas
- Network failures can block writes

Performance impact:

```text
Write latency ≈ network RTT + disk fsync + coordination overhead
```

---

### 3.1.3 Asynchronous Replication

The leader acknowledges the client before replicas have applied the write.

```text
Client -> Leader
Leader -> Client: success
Leader -> Replicas asynchronously
```

Advantages:

- Low write latency
- Better throughput
- Tolerates slow replicas

Disadvantages:

- Possible data loss if leader fails
- Stale reads
- Failover may lose recent writes

This is common when performance is prioritized over strict durability.

---

### 3.1.4 Semi-Synchronous Replication

The leader waits for at least one replica to acknowledge receipt of the log, but not necessarily full application.

This is a compromise between synchronous and asynchronous replication.

---

### 3.1.5 Quorum Replication

Writes and reads require a majority of replicas.

If there are `N` replicas:

- Write requires `W` acknowledgments
- Read requires `R` responses

If:

```text
W + R > N
```

then reads and writes overlap, providing strong consistency.

Example:

```text
N = 3
W = 2
R = 2
```

A write must succeed on 2 replicas. A read checks 2 replicas. Since any two replicas overlap, the read sees the latest write.

Advantages:

- Configurable consistency
- Tolerates some replica failures
- No single leader required in some designs

Disadvantages:

- Complex conflict resolution
- Tail latency can be high
- Requires careful tuning

---

### 3.1.6 Leaderless Replication

Any replica can accept writes.

Examples include Dynamo-style systems.

Advantages:

- High availability
- No single leader bottleneck
- Good for write-heavy workloads

Disadvantages:

- Conflict resolution is complex
- May require application-level merge logic
- Harder to provide strong consistency

---

### 3.1.7 Multi-Master Replication

Multiple nodes can accept writes.

Advantages:

- High availability
- Useful for geographically distributed applications

Disadvantages:

- Conflict resolution is difficult
- Hard to maintain strong consistency
- Can produce surprising behavior

Conflict resolution strategies:

- Last-write-wins
- Vector clocks
- Version vectors
- CRDTs
- Application-defined merge rules

---

## 3.2 Replication Protocols

### 3.2.1 Primary-Based Replication

The leader serializes writes and sends them to followers.

This is common in systems like:

- MySQL replication
- PostgreSQL streaming replication
- MongoDB replica sets
- Many distributed SQL databases

The leader usually maintains a write-ahead log. Followers apply the log in order.

---

### 3.2.2 Consensus-Based Replication

Consensus protocols such as Raft or Paxos ensure that replicas agree on the order of operations.

This is important for:

- Leader election
- Log replication
- Failover safety
- Avoiding split-brain

In a consensus group:

- A leader is elected
- The leader proposes log entries
- A majority must accept the entries
- Committed entries are durable

Consensus provides strong consistency but can increase latency.

---

### 3.2.3 Chain Replication

Replicas are arranged in a chain.

```text
Head -> Middle -> Tail
```

Writes enter at the head and propagate to the tail. Reads may be served from any node depending on the design.

Advantages:

- Deterministic ordering
- Good throughput
- No majority quorum needed for every write

Disadvantages:

- Failure handling is complex
- Reconfiguration can be expensive

---

## 3.3 Replication and Performance

Replication affects performance in several ways.

### 3.3.1 Write Latency

Synchronous replication increases write latency because the leader must wait for acknowledgments.

```text
Synchronous write latency = local write + network RTT + replica fsync + coordination
```

Asynchronous replication reduces client-visible latency but increases risk.

---

### 3.3.2 Write Throughput

Replication can reduce throughput because each write must be propagated.

However, batching and parallel replication can improve throughput.

Example:

```text
Batch 1000 log entries
Send to replicas
Replicas apply in parallel
```

---

### 3.3.3 Read Latency

Reads can be served from local replicas, reducing latency.

This is useful for:

- Analytics
- Reporting
- Caching
- Read-heavy workloads

But stale reads may occur if replicas lag.

---

### 3.3.4 Tail Latency

If a system waits for multiple replicas, the slowest replica can dominate latency.

Example:

```text
Need 2 of 3 replicas
If one replica is slow, write may wait
```

Techniques to reduce tail latency:

- Hedged requests
- Quorum tuning
- Fast replicas
- Network optimization
- Batching
- Replication lag monitoring

---

### 3.3.5 Hotspots

If one partition receives disproportionate traffic, replication does not solve the problem.

Example:

```text
All writes go to customer_id = 1001
```

Solutions:

- Better partition keys
- Composite keys
- Hashing
- Load splitting
- Caching
- Pre-aggregation

---

## 4. Indexing in Distributed Databases

Indexes are data structures that speed up queries. In a distributed database, indexing is more complex because data is partitioned and replicated.

---

## 4.1 Local vs Global Indexes

### 4.1.1 Local Indexes

A local index is partitioned the same way as the base table.

Example:

```text
Table partitioned by customer_id
Index also partitioned by customer_id
```

Advantages:

- Writes are local to the partition
- No cross-partition coordination for index updates
- Easier to scale
- Good for partition-key queries

Disadvantages:

- Queries not using the partition key require scatter-gather
- Each partition must be searched

Example query:

```sql
SELECT *
FROM orders
WHERE customer_id = 123;
```

This can go directly to the correct partition.

But:

```sql
SELECT *
FROM orders
WHERE status = 'PENDING';
```

may require scanning all partitions.

---

### 4.1.2 Global Indexes

A global index is partitioned independently of the base table.

Example:

```text
Table partitioned by customer_id
Index partitioned by order_id
```

Advantages:

- Efficient queries on non-partition-key columns
- Avoids scatter-gather for indexed queries

Disadvantages:

- Writes may require cross-partition coordination
- Index maintenance can become a bottleneck
- More complex consistency

Example:

```sql
SELECT *
FROM orders
WHERE order_id = 98765;
```

A global index can route directly to the correct partition.

---

## 4.2 Index Types

### 4.2.1 B-Tree Indexes

B-trees are common for:

- Equality queries
- Range queries
- Sorted scans

In distributed systems, B-trees are often used per partition.

Advantages:

- Good for range queries
- Predictable performance
- Widely supported

Disadvantages:

- Random I/O can be expensive
- Write amplification
- Not always ideal for high-write workloads

---

### 4.2.2 LSM-Tree Indexes

Log-structured merge trees are used in systems optimized for high write throughput.

Examples:

- Cassandra
- RocksDB
- HBase
- Some distributed SQL engines

Writes are appended to a memtable and later flushed to disk in sorted files.

Advantages:

- High write throughput
- Sequential disk I/O
- Good for large-scale systems

Disadvantages:

- Read amplification
- Compaction overhead
- Background resource usage
- More complex tuning

---

### 4.2.3 Hash Indexes

Hash indexes are good for equality lookups.

Example:

```text
hash(key) -> value
```

Advantages:

- Very fast point lookups
- Low CPU overhead

Disadvantages:

- Poor range queries
- Collisions and rebalancing complexity
- Not suitable for ordered scans

---

### 4.2.4 Secondary Indexes

Secondary indexes are built on non-primary columns.

Example:

```sql
CREATE INDEX idx_status ON orders(status);
```

In distributed databases, secondary indexes can be:

- Local
- Global
- Asynchronous
- Transactional

---

### 4.2.5 Covering Indexes

A covering index contains all columns needed by a query.

Example:

```sql
CREATE INDEX idx_customer_status ON orders(customer_id, status, total);
```

Query:

```sql
SELECT status, total
FROM orders
WHERE customer_id = 123;
```

The database can answer the query using only the index.

Advantages:

- Avoids fetching base table rows
- Reduces I/O
- Improves latency

---

### 4.2.6 Full-Text, Spatial, and Vector Indexes

Modern distributed databases may support:

- Full-text search
- Geospatial queries
- Vector similarity search
- JSON indexes
- Time-series indexes

These indexes often require specialized engines or distributed search clusters.

---

## 4.3 Distributed Index Maintenance

When data changes, indexes must also change.

Example:

```sql
UPDATE orders
SET status = 'SHIPPED'
WHERE order_id = 98765;
```

This may require:

1. Update base table
2. Update primary index
3. Update secondary indexes
4. Replicate changes
5. Maintain transactional consistency

---

### 4.3.1 Transactional Index Updates

Indexes are updated atomically with the base table.

Advantages:

- Strong consistency
- No stale index entries

Disadvantages:

- More coordination
- Higher write latency
- More locking

---

### 4.3.2 Asynchronous Index Updates

Indexes are updated in the background.

Advantages:

- Faster writes
- Better scalability

Disadvantages:

- Indexes may be stale
- Queries may miss recent data
- Requires eventual consistency assumptions

---

### 4.3.3 Index Partitioning Strategies

Indexes can be partitioned by:

- Same key as base table
- Indexed column
- Hash of indexed column
- Range of indexed column
- Composite key

The choice affects query performance and write coordination.

---

## 4.4 Indexing and Performance

### 4.4.1 Read Performance

Good indexes reduce:

- Full scans
- Network fan-out
- Disk I/O
- CPU work

Bad indexes can increase:

- Write latency
- Storage cost
- Compaction cost
- Coordination overhead

---

### 4.4.2 Write Performance

Every index adds write cost.

If a table has 5 indexes, one insert may require:

```text
1 base table write
+ 5 index writes
+ replication of all changes
```

This is called write amplification.

---

### 4.4.3 Index Skew

If many rows have the same indexed value, the index can become hot.

Example:

```sql
status = 'PENDING'
```

If most orders are pending, an index on `status` may concentrate writes and reads.

Solutions:

- Composite indexes
- Partial indexes
- Partitioning by status
- Caching
- Materialized views

---

### 4.4.4 Scatter-Gather Cost

If a query cannot use a partitioned index efficiently, the database may query all partitions.

Example:

```sql
SELECT *
FROM orders
WHERE status = 'PENDING';
```

If there are 100 partitions, the query may fan out to 100 nodes.

This increases:

- Network traffic
- Coordination overhead
- Tail latency
- CPU usage

---

## 5. Transactions in Distributed Databases

A transaction is a logical unit of work that must satisfy ACID properties.

---

## 5.1 ACID in a Distributed Setting

### Atomicity

All operations in a transaction either succeed or fail.

In a distributed database, this is difficult because a transaction may touch multiple partitions or nodes.

---

### Consistency

The transaction must move the database from one valid state to another.

This includes constraints, schema rules, and application invariants.

---

### Isolation

Concurrent transactions must not interfere incorrectly.

Common isolation levels:

| Isolation Level | Description |
|---|---|
| Read Uncommitted | Can read uncommitted data |
| Read Committed | Reads only committed data |
| Repeatable Read | Same transaction sees consistent values |
| Snapshot Isolation | Transaction sees a consistent snapshot |
| Serializable | Equivalent to serial execution |

Distributed databases often provide snapshot isolation or serializable isolation, but serializable transactions are more expensive.

---

### Durability

Committed data must survive failures.

Durability usually requires:

- Write-ahead logging
- fsync
- Replication
- Checkpoints
- Backups

---

## 5.2 Distributed Transaction Coordination

A transaction that touches multiple partitions requires coordination.

Example:

```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

If account 1 and account 2 are on different nodes, the system must ensure both updates commit or neither commits.

---

## 5.3 Two-Phase Commit

Two-phase commit, or 2PC, is the classic protocol for distributed atomic commit.

### Phase 1: Prepare

Coordinator asks all participants:

```text
Can you commit?
```

Each participant:

- Locks resources
- Writes prepare record to log
- Responds yes or no

### Phase 2: Commit or Abort

If all participants vote yes:

```text
Coordinator sends COMMIT
```

If any participant votes no:

```text
Coordinator sends ABORT
```

Advantages:

- Atomic across multiple nodes
- Well understood

Disadvantages:

- High latency
- Coordinator can become bottleneck
- Blocking if coordinator fails
- Participants may hold locks while waiting

Performance impact:

```text
2PC latency = multiple network round trips + log fsync + lock coordination
```

---

## 5.4 Three-Phase Commit

Three-phase commit attempts to reduce blocking compared to 2PC.

Phases:

1. Can commit?
2. Pre-commit?
3. Commit?

It is more complex and still not perfect in asynchronous networks. Many systems prefer consensus-based commit protocols instead.

---

## 5.5 Consensus-Based Commit

Systems using Raft or Paxos can commit transactions through consensus.

Instead of a single coordinator, a replicated state machine decides the outcome.

Advantages:

- No single coordinator bottleneck
- Better fault tolerance
- Strong consistency

Disadvantages:

- More complex
- Higher latency
- Requires majority availability

---

## 5.6 Concurrency Control

Distributed databases need concurrency control to prevent anomalies.

---

### 5.6.1 Two-Phase Locking

Transactions acquire locks before accessing data.

Phases:

1. Growing phase: acquire locks
2. Shrinking phase: release locks

Advantages:

- Strong isolation
- Prevents many anomalies

Disadvantages:

- Lock contention
- Deadlocks
- Distributed lock management is expensive

---

### 5.6.2 Optimistic Concurrency Control

Transactions execute without locks and validate at commit time.

Advantages:

- Good for low-contention workloads
- Less blocking

Disadvantages:

- High abort rate under contention
- Validation overhead
- Complex conflict detection

---

### 5.6.3 MVCC

Multi-version concurrency control stores multiple versions of data.

Readers see snapshots, writers create new versions.

Advantages:

- Readers do not block writers
- Good for read-heavy workloads
- Supports snapshot isolation

Disadvantages:

- Version storage overhead
- Garbage collection
- Long-running transactions can cause bloat

---

### 5.6.4 Serializable Snapshot Isolation

SSI provides serializable isolation using snapshot reads plus conflict detection.

Advantages:

- Strong correctness
- Better than pessimistic locking in some workloads

Disadvantages:

- Higher overhead
- More aborts
- Complex implementation

---

## 5.7 Distributed Transactions and Performance

Distributed transactions are expensive because they involve:

- Multiple network round trips
- Multiple log writes
- Lock coordination
- Consensus or 2PC
- Failure handling
- Retry logic

Performance depends heavily on transaction scope.

---

### 5.7.1 Local Transactions

A transaction touches only one partition.

Example:

```sql
UPDATE accounts
SET balance = balance - 100
WHERE id = 1;
```

If `id = 1` is on one partition, this is fast.

---

### 5.7.2 Cross-Partition Transactions

A transaction touches multiple partitions.

Example:

```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

If `id = 1` and `id = 2` are on different partitions, coordination is required.

---

### 5.7.3 Cross-Region Transactions

If partitions are in different regions, latency can be tens or hundreds of milliseconds.

Example:

```text
US region -> EU region RTT = 100 ms
```

A transaction requiring multiple round trips can become very slow.

---

## 5.8 Strategies to Improve Transaction Performance

### 5.8.1 Colocate Related Data

Place frequently updated data together.

Example:

```text
Partition by customer_id
Store customer, orders, and order_items in same partition
```

This reduces cross-partition transactions.

---

### 5.8.2 Use Local Transactions When Possible

Design schemas so common transactions are local.

---

### 5.8.3 Batch Writes

Combine multiple operations into one commit.

Example:

```text
Instead of 1000 individual commits
Use 1 batch commit
```

This reduces log fsyncs and network round trips.

---

### 5.8.4 Use Idempotent Operations

Retries are common in distributed systems.

Idempotent operations can be safely retried.

Example:

```text
Set order status = SHIPPED
```

is idempotent.

But:

```text
balance = balance + 100
```

is not idempotent unless guarded by a unique transaction ID.

---

### 5.8.5 Use Sagas for Long-Running Workflows

Instead of one large distributed transaction, use a sequence of local transactions with compensating actions.

Example:

```text
1. Reserve inventory
2. Charge payment
3. Create shipment
```

If shipment fails:

```text
1. Cancel shipment
2. Refund payment
3. Release inventory
```

Sagas improve scalability but require careful business logic.

---

### 5.8.6 Reduce Lock Scope

Use short transactions and narrow locks.

Avoid:

```sql
BEGIN;
-- long application logic
-- network calls
-- user interaction
COMMIT;
```

---

## 6. Recovery in Distributed Databases

Recovery is the process of restoring the database to a correct state after failure.

Failures can include:

- Process crash
- Node crash
- Disk failure
- Network partition
- Data center outage
- Software bug
- Human error
- Data corruption

---

## 6.1 Durability Mechanisms

### 6.1.1 Write-Ahead Logging

Before modifying data, the database writes a log record to durable storage.

Typical order:

```text
1. Write log record
2. fsync log
3. Apply change to memory
4. Later flush data pages
```

This ensures that committed transactions can be recovered after a crash.

---

### 6.1.2 fsync

`fsync` forces operating system buffers to disk.

Without fsync, a crash may lose recent writes.

Performance tradeoff:

- Frequent fsync improves durability
- Frequent fsync reduces throughput

Techniques:

- Group commit
- Batch fsync
- Battery-backed write cache
- Async replication with durability tradeoffs

---

### 6.1.3 Checkpoints

A checkpoint records the database state at a point in time.

During recovery, the database can start from the last checkpoint and replay logs after it.

Advantages:

- Faster recovery
- Bounded log replay

Disadvantages:

- Checkpointing consumes I/O
- Can cause latency spikes

---

### 6.1.4 Snapshots

A snapshot is a consistent copy of the database.

Snapshots are used for:

- Backups
- Cloning
- Disaster recovery
- Testing
- Point-in-time recovery

---

## 6.2 Crash Recovery

After a crash, the database may need to redo or undo operations.

### Redo

Reapply committed transactions that were not yet written to data pages.

### Undo

Roll back uncommitted transactions that were partially applied.

Typical recovery:

```text
1. Load last checkpoint
2. Scan WAL from checkpoint
3. Redo committed transactions
4. Undo incomplete transactions
5. Restore consistency
```

---

## 6.3 Distributed Recovery

Distributed recovery is more complex because multiple nodes may fail independently.

---

### 6.3.1 Replica Recovery

If a follower crashes, it can recover by:

1. Loading local state
2. Reconnecting to leader
3. Receiving missing log entries
4. Applying log entries
5. Catching up

If the follower’s data is too old, it may need a snapshot restore.

---

### 6.3.2 Leader Failure

If the leader fails, the system must elect a new leader.

Requirements:

- New leader must have the most up-to-date committed log
- Old leader must not resume writing
- Clients must be redirected
- Split-brain must be avoided

Techniques:

- Consensus-based leader election
- Fencing tokens
- Lease mechanisms
- Quorum checks

---

### 6.3.3 Network Partition

If nodes cannot communicate, the system must decide whether to:

- Block writes to preserve consistency
- Allow writes and risk divergence
- Partition the system into independent groups

Consensus systems usually require a majority to make progress.

Example:

```text
3-node cluster
If 1 node is isolated, remaining 2 can elect leader
If 2 nodes are isolated, remaining 1 cannot elect leader
```

---

### 6.3.4 Split-Brain Prevention

Split-brain occurs when two nodes both believe they are leader.

This can cause conflicting writes.

Prevention methods:

- Quorum-based leader election
- Fencing tokens
- STONITH
- Lease-based leadership
- Consensus protocols

---

## 6.4 Backup and Restore

### 6.4.1 Full Backup

A complete copy of the database.

Advantages:

- Simple restore

Disadvantages:

- Large storage cost
- Long backup time

---

### 6.4.2 Incremental Backup

Backs up only changes since last backup.

Advantages:

- Faster
- Less storage

Disadvantages:

- Restore requires multiple backups
- More complex

---

### 6.4.3 Point-in-Time Recovery

The database can be restored to a specific time.

Example:

```text
Restore to 2026-01-01 10:00:00
```

This requires:

- Full backup
- Continuous log archive
- Replay logs up to target time

---

## 6.5 Recovery and Performance

Recovery affects performance in several ways.

### 6.5.1 Recovery Time

Long recovery times reduce availability.

Factors:

- Amount of log to replay
- Checkpoint frequency
- Snapshot size
- Network speed
- Disk throughput

---

### 6.5.2 Recovery Point Objective

RPO is the maximum acceptable data loss.

Example:

```text
RPO = 5 seconds
```

This means the system may lose up to 5 seconds of data after failure.

Achieving low RPO requires:

- Synchronous replication
- Frequent log flushing
- Fast failover

---

### 6.5.3 Recovery Time Objective

RTO is the maximum acceptable downtime.

Example:

```text
RTO = 30 seconds
```

This requires:

- Fast leader election
- Fast client redirection
- Fast log replay
- Automated failover

---

## 7. Performance Considerations

Distributed database performance is not just about raw CPU or disk speed. It is heavily affected by coordination and data placement.

---

## 7.1 Network Latency

Network latency is often the dominant cost.

Examples:

```text
Same rack: ~0.1 ms
Same data center: ~0.5–2 ms
Different regions: 50–200 ms
```

Operations requiring multiple round trips become expensive across regions.

---

## 7.2 Network Bandwidth

Large scans, joins, and replication can saturate network links.

Optimizations:

- Compression
- Columnar storage
- Query pushdown
- Partial aggregation
- Caching
- Colocating related data

---

## 7.3 Disk I/O

Databases are often I/O-bound.

Important factors:

- Random vs sequential I/O
- fsync frequency
- SSD vs HDD
- Log throughput
- Compaction
- Checkpointing

---

## 7.4 CPU

CPU is used for:

- Query parsing
- Optimization
- Compression
- Encryption
- Serialization
- Index maintenance
- Consensus logic

---

## 7.5 Lock Contention

Hot rows or hot partitions can serialize transactions.

Example:

```sql
UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 123;
```

If many transactions update the same product, they may wait on locks.

Solutions:

- Sharding inventory counts
- Batching updates
- Optimistic concurrency
- Queue-based processing
- Pre-reservation

---

## 7.6 Hot Partitions

A hot partition occurs when one shard receives disproportionate traffic.

Causes:

- Poor partition key
- Time-series data with monotonically increasing keys
- Popular entities
- Sequential IDs

Solutions:

- Hash partitioning
- Composite partition keys
- Salting
- Splitting hot ranges
- Caching
- Load balancing

---

## 7.7 Replication Lag

Replication lag affects read freshness.

Example:

```text
Write succeeds on leader
Read from follower returns old value
```

Monitoring replication lag is essential.

---

## 7.8 Tail Latency

Average latency may be acceptable, but tail latency can dominate user experience.

Causes:

- Slow replicas
- Garbage collection
- Compaction
- Lock waits
- Network jitter
- Checkpoints
- Leader election

Techniques:

- Hedged requests
- Batching
- Caching
- Fast replicas
- Isolation of background tasks
- Better partitioning

---

## 8. Design Tradeoffs

Distributed database design is a set of tradeoffs.

---

### 8.1 Consistency vs Availability

Strong consistency often requires coordination.

High availability often allows stale reads or partition tolerance.

---

### 8.2 Latency vs Durability

Fast writes may delay fsync or replication.

Durable writes may require synchronous fsync and replication.

---

### 8.3 Read Performance vs Write Performance

More indexes improve reads but slow writes.

---

### 8.4 Scalability vs Complexity

Sharding improves scalability but complicates transactions, joins, and operations.

---

### 8.4.1 Global Indexes vs Local Indexes

Global indexes improve non-key queries but increase write coordination.

Local indexes simplify writes but may require scatter-gather reads.

---

### 8.5 Synchronous vs Asynchronous Replication

Synchronous replication improves durability but increases latency.

Asynchronous replication improves performance but risks data loss.

---

## 9. Example: Designing a Distributed Order System

Suppose we design an order system.

Entities:

```text
customers
orders
order_items
payments
inventory
```

Common queries:

```sql
SELECT * FROM orders WHERE customer_id = 123;
SELECT * FROM order_items WHERE order_id = 987;
SELECT * FROM orders WHERE status = 'PENDING';
```

---

### 9.1 Partitioning

Partition by `customer_id`.

```text
customers.customer_id
orders.customer_id
order_items.customer_id
```

This colocates customer-related data.

Query:

```sql
SELECT *
FROM orders
WHERE customer_id = 123;
```

can be served from one partition.

---

### 9.2 Replication

Use three replicas per partition.

```text
Replica 1: leader
Replica 2: follower
Replica 3: follower
```

For strong consistency:

```text
W = 2
R = 2
```

or use consensus-based replication.

---

### 9.3 Indexing

Use local indexes for customer queries.

```sql
CREATE INDEX idx_customer_status
ON orders(customer_id, status);
```

For global queries:

```sql
SELECT *
FROM orders
WHERE order_id = 98765;
```

Use a global index partitioned by `order_id`.

---

### 9.4 Transactions

Order creation may touch:

```text
orders
order_items
inventory
payments
```

If these are colocated, the transaction can be local.

If not, use distributed transaction coordination or a saga.

---

### 9.5 Recovery

Use:

- WAL
- Checkpoints
- Snapshots
- Continuous log archiving
- Point-in-time recovery
- Automated failover

---

## 10. Practical Design Checklist

When designing a distributed database, ask:

### Data Placement

- What is the primary access pattern?
- What data is frequently joined or updated together?
- Can related data be colocated?
- Are there hot keys?
- Is range access important?

### Replication

- How many replicas are needed?
- Is replication synchronous or asynchronous?
- What consistency model is required?
- How are conflicts resolved?
- How is replication lag monitored?

### Indexing

- Are indexes local or global?
- Which queries need global indexes?
- How many indexes are acceptable?
- Are index updates transactional or asynchronous?
- Are there hot index ranges?

### Transactions

- Are transactions local or distributed?
- What isolation level is required?
- How are distributed commits coordinated?
- How are retries handled?
- Are operations idempotent?

### Recovery

- What is the RPO?
- What is the RTO?
- Are logs archived?
- Are snapshots consistent?
- How is leader election handled?
- How is split-brain prevented?

### Performance

- Where is the bottleneck?
- Is latency dominated by network, disk, CPU, or locks?
- Are tail latencies acceptable?
- Are background tasks isolated?
- Is caching effective?

---

## 11. Summary

A distributed database is designed around distributing data and computation across multiple nodes while preserving correctness and performance.

### Replication

Replication provides availability, durability, and read scalability. It introduces tradeoffs between latency, consistency, and data loss risk. Common approaches include leader-follower, quorum, leaderless, and consensus-based replication.

### Indexing

Indexes speed up queries but add write cost and coordination complexity. Local indexes are simpler and faster for partition-key queries. Global indexes support non-key queries but can require distributed coordination.

### Transactions

Distributed transactions require coordination across nodes. Two-phase commit, consensus-based commit, MVCC, locking, and optimistic concurrency control are common techniques. Performance improves when transactions are local, short, and colocated.

### Recovery

Recovery relies on write-ahead logging, checkpoints, snapshots, backups, and log replay. Distributed recovery must handle node failures, network partitions, leader election, split-brain prevention, and data repair.

The best distributed database design depends on the workload. A system optimized for global availability may accept eventual consistency. A system optimized for financial correctness may require strong consistency, synchronous replication, and serializable transactions. The key is to align data placement, replication, indexing, transaction semantics, and recovery mechanisms with the application’s correctness and performance requirements.
