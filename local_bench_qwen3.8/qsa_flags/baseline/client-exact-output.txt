## Distributed Database Design and Performance

A **distributed database** stores data across multiple machines connected by a network while presenting a unified database view to applications. Its design must balance **scalability, availability, consistency, durability, latency, and operational complexity**.

The main design dimensions are:

1. **Data distribution**: partitioning/sharding, replication, placement.
2. **Consistency model**: strong consistency, eventual consistency, causal consistency, etc.
3. **Query execution**: distributed query planning, joins, index usage.
4. **Transaction management**: distributed atomic commit, isolation, concurrency control.
5. **Recovery and fault tolerance**: logging, checkpoints, replication, leader election.

---

# 1. Core Design Principles

## 1.1 Transparency

A distributed database should ideally provide:

- **Location transparency**: users do not need to know where data is stored.
- **Replication transparency**: users do not need to know how many copies exist.
- **Fragmentation transparency**: users do not need to know how data is partitioned.
- **Concurrency transparency**: users do not need to know how locks or MVCC are implemented.

In practice, many modern systems expose some of these details to improve performance or consistency control.

---

## 1.2 Scalability

Distributed databases scale in two ways:

### Vertical scaling

Adding more CPU, memory, or storage to a single node.

### Horizontal scaling

Adding more nodes and distributing data across them.

Horizontal scaling is usually preferred for large systems, but it introduces complexity:

- Network latency.
- Distributed joins.
- Distributed transactions.
- Hot partitions.
- Data skew.
- Consistency overhead.

---

## 1.3 Availability and Fault Tolerance

Distributed databases are designed to survive failures:

- Disk failure.
- Node crash.
- Network partition.
- Datacenter outage.
- Region failure.

Availability is improved through:

- Replication.
- Failover.
- Leader election.
- Quorum protocols.
- Consensus algorithms such as Raft or Paxos.

---

## 1.4 Consistency

Distributed databases must decide how consistent reads and writes should be.

Common consistency models include:

| Model | Meaning |
|---|---|
| Strong consistency | All replicas agree on the latest value before a write is acknowledged. |
| Eventual consistency | Replicas may temporarily differ but converge over time. |
| Read-your-writes | A client sees its own writes. |
| Monotonic reads | Once a client sees a value, it never sees an older value. |
| Causal consistency | Writes that are causally related are seen in order. |
| Linearizability | Operations appear to occur atomically at a single point in time. |

The CAP theorem states that during a network partition, a system must choose between **consistency** and **availability**. In practice, many systems offer configurable consistency levels.

---

# 2. Data Distribution: Partitioning and Sharding

## 2.1 Partitioning

Partitioning divides data into smaller pieces.

### Horizontal partitioning

Rows are distributed across nodes.

Example:

```text
Node 1: customer_id 1–1,000,000
Node 2: customer_id 1,000,001–2,000,000
Node 3: customer_id 2,000,001–3,000,000
```

This is common in large OLTP systems.

### Vertical partitioning

Columns are separated.

Example:

```text
Node 1: customer_id, name, email
Node 2: customer_id, profile_image, preferences
```

This can reduce I/O for queries that only need certain columns.

---

## 2.2 Sharding Strategies

### Range-based sharding

Data is assigned by ranges.

```text
Shard A: user_id 0–999
Shard B: user_id 1000–1999
```

Advantages:

- Range queries are efficient.
- Easy to understand.

Disadvantages:

- Hotspots if one range is very active.
- Rebalancing can be complex.

---

### Hash-based sharding

A hash function determines the shard.

```text
shard = hash(user_id) % number_of_shards
```

Advantages:

- Better load distribution.
- Avoids range hotspots.

Disadvantages:

- Range queries may require scatter-gather.
- Rebalancing requires data movement.

---

### Directory-based sharding

A lookup table maps keys to shards.

Advantages:

- Flexible placement.
- Can move data easily.

Disadvantages:

- Directory lookup adds latency.
- Directory itself must be highly available.

---

## 2.3 Performance Impact of Sharding

Good sharding improves:

- Write throughput.
- Read throughput.
- Storage scalability.
- Locality.

Bad sharding causes:

- Hot partitions.
- Cross-shard joins.
- Distributed transactions.
- Uneven load.
- Poor cache utilization.

A common design goal is to place related data on the same shard.

Example:

```text
Shard by customer_id

Tables on same shard:
customers
orders
order_items
payments
```

This allows many transactions to remain local.

---

# 3. Replication

## 3.1 Purpose of Replication

Replication stores copies of data on multiple nodes.

It provides:

- High availability.
- Fault tolerance.
- Read scalability.
- Geographic locality.
- Disaster recovery.
- Faster reads near users.

---

## 3.2 Replication Architectures

### Leader-based replication

One node is the leader.

```text
Writes → Leader
Reads  → Leader or Followers
```

The leader accepts writes and sends changes to followers.

Advantages:

- Simple consistency model.
- Easy conflict resolution.
- Strong consistency possible.

Disadvantages:

- Leader can become a bottleneck.
- Leader failure requires failover.
- Followers may lag.

---

### Multi-leader replication

Multiple nodes accept writes.

```text
Writes → Leader A, Leader B, Leader C
```

Advantages:

- Better write availability.
- Useful for geographically distributed systems.

Disadvantages:

- Conflict resolution is required.
- Strong consistency is harder.
- More complex.

---

### Leaderless replication

Any replica can accept writes.

```text
Writes → Any replica
Reads  → Quorum of replicas
```

Advantages:

- High availability.
- No single leader bottleneck.

Disadvantages:

- Conflict resolution required.
- Harder to reason about consistency.
- May require vector clocks, CRDTs, or application-level merging.

---

## 3.3 Synchronous vs Asynchronous Replication

### Synchronous replication

A write is acknowledged only after replicas have stored it.

```text
Client → Leader
Leader → Follower
Follower acknowledges
Leader acknowledges client
```

Advantages:

- Low risk of data loss.
- Strong durability.

Disadvantages:

- Higher write latency.
- If a follower is slow, writes slow down.
- Availability may decrease during network partitions.

---

### Asynchronous replication

The leader acknowledges the client before replicas receive the write.

```text
Client → Leader
Leader acknowledges client
Leader later sends to follower
```

Advantages:

- Lower write latency.
- Better throughput.

Disadvantages:

- Follower may lose recent writes if leader crashes.
- Stale reads possible.

---

### Semi-synchronous replication

The leader waits for at least one follower to acknowledge receipt, but not necessarily durable storage.

This is a compromise between synchronous and asynchronous.

---

## 3.4 Quorum Replication

Quorum systems require a majority of replicas to agree.

If there are `N` replicas:

```text
Write quorum: W
Read quorum: R

If W + R > N, reads should see the latest write.
```

Example:

```text
N = 3
W = 2
R = 2

W + R = 4 > 3
```

Advantages:

- Tolerates some failures.
- Configurable consistency.

Disadvantages:

- More complex.
- Latency depends on slowest quorum member.
- Network partitions can block writes or reads.

---

## 3.5 Replication and Performance

Replication affects performance in several ways:

| Factor | Effect |
|---|---|
| Read scaling | More replicas can serve more reads. |
| Write cost | Each write may need to be copied to replicas. |
| Latency | Synchronous replication increases write latency. |
| Availability | More replicas improve fault tolerance. |
| Staleness | Asynchronous replication can cause stale reads. |
| Conflict handling | Multi-leader replication adds complexity. |
| Network traffic | Replication consumes bandwidth. |

---

## 3.6 Conflict Resolution

In multi-leader or leaderless systems, two nodes may update the same record concurrently.

Common strategies:

### Last-write-wins

The latest timestamp wins.

Simple but can lose updates.

---

### Vector clocks

Track causality between updates.

Helps detect concurrent writes.

---

### CRDTs

Conflict-free replicated data types automatically merge.

Examples:

- Counters.
- Sets.
- Maps.
- Sequences.

---

### Application-level merge

The application decides how to resolve conflicts.

Example:

```text
If two users edit the same document, show both versions and ask user to merge.
```

---

# 4. Indexing in Distributed Databases

## 4.1 Why Indexing Matters

Indexes speed up reads but add write overhead.

In a distributed database, indexing is more complex because data is spread across nodes.

---

## 4.2 Local Indexes

Each shard maintains indexes for its own data.

Example:

```text
Shard 1:
orders index on customer_id

Shard 2:
orders index on customer_id
```

Advantages:

- Fast local queries.
- Low coordination overhead.

Disadvantages:

- Cannot efficiently answer queries across all shards.
- Global uniqueness is harder.

---

## 4.3 Global Indexes

A global index maps values to shards.

Example:

```text
email → shard_id

alice@example.com → shard 3
bob@example.com   → shard 7
```

Advantages:

- Efficient lookup by non-shard key.
- Useful for unique constraints.

Disadvantages:

- Index updates may require cross-shard coordination.
- Global index can become a bottleneck.
- Must be replicated or partitioned carefully.

---

## 4.4 Partitioned Global Indexes

A global index is itself partitioned across nodes.

Example:

```text
Index shard A: email A–M
Index shard B: email N–Z
```

Advantages:

- Scales better than a single global index.
- Reduces hotspot risk.

Disadvantages:

- More complex.
- Range queries may touch multiple index shards.

---

## 4.5 Index Types

### B-tree indexes

Good for:

- Equality.
- Range queries.
- Sorted access.

Used in many traditional databases.

---

### Hash indexes

Good for:

- Equality lookups.

Not good for:

- Range queries.

---

### LSM-tree indexes

Log-structured merge trees are common in distributed key-value stores.

Advantages:

- High write throughput.
- Good for append-heavy workloads.

Disadvantages:

- Compaction overhead.
- Read amplification.
- More complex.

---

### Secondary indexes

Secondary indexes support queries on non-primary columns.

Example:

```text
Primary key: order_id
Secondary index: customer_id
```

In distributed systems, secondary indexes may be:

- Local to each shard.
- Global.
- Partitioned globally.

---

### Covering indexes

An index contains all columns needed by a query.

Example:

```sql
CREATE INDEX idx_customer_email ON customers(customer_id, email);
```

If the query only needs `customer_id` and `email`, the database can answer from the index without reading the table.

This reduces I/O and improves performance.

---

## 4.6 Distributed Query Execution

A distributed query may require:

1. Partition pruning.
2. Local index scans.
3. Scatter-gather.
4. Distributed joins.
5. Aggregation.
6. Sorting.

Example:

```sql
SELECT name
FROM customers
WHERE email = 'alice@example.com';
```

If `email` is not the shard key, the system may need to:

- Query a global index.
- Or scan all shards.

Scanning all shards is expensive.

---

## 4.7 Distributed Joins

Joins are one of the hardest performance problems.

### Colocated join

Both tables are partitioned by the same key.

```text
orders.customer_id
customers.customer_id
```

If both are sharded by `customer_id`, the join can be local.

This is very efficient.

---

### Broadcast join

One small table is copied to all nodes.

```text
Small table: countries
Large table: customers
```

Each node joins locally.

Good when one table is small.

---

### Shuffle join

Data is redistributed across nodes by join key.

```text
orders.customer_id
customers.customer_id
```

Both tables are shuffled so matching rows meet on the same node.

This can be expensive because it moves large amounts of data.

---

## 4.8 Indexing Performance Tradeoffs

| Benefit | Cost |
|---|---|
| Faster reads | Slower writes |
| Better query locality | More storage |
| Unique constraints | Coordination overhead |
| Reduced scans | Index maintenance |
| Covering indexes | Larger index size |
| Global indexes | Cross-shard updates |

A common design principle:

> Index what you query, but avoid indexes that cause excessive write amplification or cross-shard coordination.

---

# 5. Transactions in Distributed Databases

## 5.1 ACID in Distributed Systems

A transaction should provide:

### Atomicity

All changes happen or none happen.

### Consistency

The database moves from one valid state to another.

### Isolation

Concurrent transactions do not interfere incorrectly.

### Durability

Committed changes survive failures.

In distributed systems, atomicity and isolation are harder because data may be on multiple nodes.

---

## 5.2 Distributed Transactions

A transaction may touch multiple shards.

Example:

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE account_id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE account_id = 2;

COMMIT;
```

If account 1 and account 2 are on different shards, the transaction is distributed.

---

## 5.3 Two-Phase Commit

The classic protocol for distributed atomic commit is **Two-Phase Commit**, or 2PC.

### Phase 1: Prepare

Coordinator asks all participants:

```text
Are you ready to commit?
```

Each participant:

- Locks resources.
- Writes prepare record to log.
- Replies yes or no.

### Phase 2: Commit or Abort

If all participants say yes:

```text
Coordinator sends COMMIT
```

If any participant says no:

```text
Coordinator sends ABORT
```

---

## 5.4 2PC Advantages

- Provides atomic commit across nodes.
- Preserves ACID semantics.
- Well understood.

---

## 5.5 2PC Disadvantages

- Adds latency.
- Coordinator can become a bottleneck.
- Participants may block while waiting.
- If coordinator crashes, participants may be stuck.
- Poor availability during network partitions.

---

## 5.6 Three-Phase Commit

Three-phase commit tries to reduce blocking.

Phases:

1. Can commit?
2. Pre-commit.
3. Commit.

It improves availability in some failure cases but is more complex and still not perfect.

---

## 5.7 Consensus-Based Commit

Modern systems often use consensus protocols such as:

- Raft.
- Paxos.
- Multi-Paxos.
- Raft-based transaction logs.

These can provide:

- Leader election.
- Log replication.
- Atomic commit.
- Fault tolerance.

Example:

```text
Transaction log replicated to majority of nodes.
Commit is acknowledged after majority durable storage.
```

---

## 5.8 Isolation Levels

Distributed databases may support different isolation levels.

### Read uncommitted

May read dirty data.

Rarely used.

---

### Read committed

Reads only committed data.

Common default in many databases.

---

### Repeatable read

A transaction sees the same values repeatedly.

May prevent some anomalies.

---

### Snapshot isolation

Each transaction sees a consistent snapshot from the start of the transaction.

Advantages:

- Good performance.
- Readers do not block writers.

Disadvantages:

- Write skew anomalies possible.

---

### Serializable

Transactions behave as if executed one at a time.

Strongest isolation.

Harder to implement efficiently in distributed systems.

---

## 5.9 Concurrency Control

### Locking

Transactions lock rows or ranges.

Advantages:

- Simple.
- Strong isolation.

Disadvantages:

- Contention.
- Deadlocks.
- Poor scalability under high concurrency.

---

### Timestamp ordering

Each transaction gets a timestamp.

Conflicts are resolved by timestamp order.

---

### Optimistic concurrency control

Transactions execute without locks and validate at commit.

Advantages:

- Good when conflicts are rare.

Disadvantages:

- High abort rate under contention.

---

### MVCC

Multi-version concurrency control stores multiple versions of data.

Advantages:

- Readers do not block writers.
- Writers do not block readers.
- Good for snapshot isolation.

Disadvantages:

- More storage.
- Garbage collection needed.
- Complex in distributed systems.

---

## 5.10 Distributed Transaction Performance

Distributed transactions are expensive because they involve:

- Multiple network round trips.
- Lock coordination.
- Log flushing.
- Participant voting.
- Failure handling.

Performance improves when transactions are designed to be local.

Example:

```text
Bad:
Transaction touches 10 shards.

Good:
Transaction touches 1 shard.
```

Design techniques:

- Shard by tenant or customer.
- Co-locate related tables.
- Use local transactions when possible.
- Use idempotent operations.
- Use sagas for long-running workflows.
- Avoid distributed joins inside transactions.

---

## 5.11 Sagas

For long-running business processes, distributed ACID transactions may be too expensive.

A **saga** breaks a transaction into smaller local transactions with compensating actions.

Example:

```text
1. Reserve inventory
2. Charge payment
3. Create shipment

If shipment fails:
1. Cancel payment
2. Release inventory
```

Advantages:

- Better scalability.
- Better availability.
- Avoids long distributed locks.

Disadvantages:

- Intermediate states may be visible.
- Compensation logic is complex.
- Not equivalent to full ACID.

---

# 6. Recovery in Distributed Databases

## 6.1 Failure Types

Distributed databases must handle:

- Node crash.
- Disk failure.
- Network partition.
- Clock skew.
- Coordinator failure.
- Partial write failure.
- Replication lag.
- Data corruption.

---

## 6.2 Write-Ahead Logging

A write-ahead log records changes before they are applied to the database.

Rules:

1. Log record must be durable before the change is acknowledged.
2. Log record must be durable before the data page is written to disk.

This allows recovery after crash.

---

## 6.3 Redo and Undo

During recovery:

### Redo

Reapply committed changes that may not have reached the data files.

### Undo

Roll back uncommitted changes that may have partially reached the data files.

---

## 6.4 Checkpointing

A checkpoint records the database state at a point in time.

Advantages:

- Faster recovery.
- Less log replay.

Disadvantages:

- Checkpointing consumes I/O.
- Can cause latency spikes.

---

## 6.5 Distributed Recovery

In distributed systems, recovery must coordinate multiple nodes.

Example:

```text
Node A prepared transaction T.
Node B prepared transaction T.
Coordinator crashed.
```

Participants may not know whether to commit or abort.

This is called the **in-doubt transaction** problem.

---

## 6.6 Recovery in 2PC

2PC recovery requires careful logging.

Coordinator logs:

- Start.
- Prepare.
- Commit or abort decision.

Participants log:

- Prepare.
- Commit or abort.

If coordinator crashes:

- Participants may block.
- New coordinator may recover decision from logs.
- If decision is unknown, participants may remain in doubt.

---

## 6.7 Consensus-Based Recovery

Systems using Raft or Paxos recover by:

1. Electing a leader.
2. Replicating logs.
3. Replaying committed log entries.
4. Discarding uncommitted entries.

Example:

```text
Committed log entries are replayed.
Uncommitted entries are discarded.
```

This provides strong durability if a majority of nodes have the log.

---

## 6.8 Replication-Based Recovery

Replication helps recovery by providing copies.

Example:

```text
Primary crashes.
Follower becomes new leader.
New leader replays replicated log.
```

Important issues:

- Follower may be behind.
- Some writes may be lost if asynchronous.
- Fencing is needed to prevent split-brain.
- Old leader must not continue writing.

---

## 6.9 Snapshots and Backups

Distributed databases often use:

- Full snapshots.
- Incremental backups.
- Log shipping.
- Point-in-time recovery.

Example:

```text
Snapshot at 02:00
Logs from 02:00 to 10:00
Recover to 09:59
```

---

## 6.10 Recovery Performance

Recovery performance depends on:

| Factor | Effect |
|---|---|
| Log size | Larger logs mean slower recovery. |
| Checkpoint frequency | More checkpoints reduce recovery time. |
| fsync latency | Slower durable writes reduce throughput. |
| Replication lag | May delay failover. |
| Data size | Larger snapshots take longer to restore. |
| Network speed | Affects log shipping and failover. |
| Consensus protocol | Affects commit latency and recovery correctness. |

---

# 7. Performance Design Tradeoffs

## 7.1 Consistency vs Latency

Strong consistency requires coordination.

Example:

```text
Write must be replicated to majority before acknowledgment.
```

This increases latency.

Eventual consistency can reduce latency but may return stale data.

---

## 7.2 Availability vs Consistency

During a network partition:

- Strong consistency may reject writes.
- High availability may accept writes and later resolve conflicts.

This is the CAP tradeoff.

---

## 7.3 Read Performance vs Write Performance

More indexes and replicas improve reads but slow writes.

Example:

```text
10 replicas + 5 indexes = high write cost
```

---

## 7.4 Locality vs Load Balancing

Placing related data together improves performance but may create hotspots.

Example:

```text
Shard by customer_id:
Good locality.

Shard by hash(customer_id):
Better load balance.
```

---

## 7.5 Durability vs Throughput

Durable writes require fsync or majority replication.

This reduces throughput but improves safety.

---

# 8. Example Design: E-Commerce System

Suppose we design a distributed database for an e-commerce platform.

## Workload

- High read traffic.
- High write traffic.
- Orders, customers, inventory, payments.
- Need strong consistency for payments and inventory.
- Need high availability for product browsing.

## Design

### Sharding

Shard by `customer_id`.

Tables colocated:

```text
customers
orders
order_items
payments
```

This keeps most customer transactions local.

---

### Replication

Use leader-follower replication.

```text
Writes → leader
Strong reads → leader
Product browsing reads → followers
```

Use synchronous replication for payment data.

Use asynchronous replication for product catalog reads.

---

### Indexing

Local indexes:

```text
orders(customer_id)
payments(order_id)
```

Global index:

```text
email → customer_id → shard
```

This allows login by email without scanning all shards.

---

### Transactions

Order creation:

```sql
BEGIN;

INSERT INTO orders ...
INSERT INTO order_items ...
UPDATE inventory SET stock = stock - 1 ...
INSERT INTO payments ...

COMMIT;
```

If inventory is on a different shard, use a distributed transaction or a saga.

For payment, use strong consistency.

For product recommendations, use eventual consistency.

---

### Recovery

Use:

- Write-ahead logging.
- Checkpoints.
- Replicated logs.
- Leader election.
- Fencing.
- Point-in-time recovery.

If leader crashes:

1. Followers elect new leader.
2. New leader replays committed log.
3. Old leader is fenced.
4. Clients reconnect to new leader.

---

# 9. Summary

A distributed database is designed around several major tradeoffs.

## Replication

Replication improves availability and read scalability but adds write cost, latency, and consistency complexity.

Key choices:

- Synchronous vs asynchronous.
- Leader-based vs multi-leader vs leaderless.
- Quorum size.
- Conflict resolution.

---

## Indexing

Indexing improves query performance but increases write overhead and coordination complexity.

Key choices:

- Local vs global indexes.
- Partitioned indexes.
- Covering indexes.
- Shard key selection.
- Distributed join strategy.

---

## Transactions

Distributed transactions provide atomicity and isolation but are expensive.

Key choices:

- Two-phase commit.
- Consensus-based commit.
- Isolation level.
- Locking vs MVCC.
- Local transactions vs distributed transactions.
- Sagas for long-running workflows.

---

## Recovery

Recovery ensures durability and correctness after failures.

Key mechanisms:

- Write-ahead logging.
- Checkpoints.
- Redo and undo.
- Replicated logs.
- Leader election.
- Fencing.
- Snapshots and backups.

---

## Overall Design Principle

The best distributed database design depends on the workload.

For high-performance systems, the usual goals are:

1. Keep transactions local.
2. Co-locate related data.
3. Choose shard keys carefully.
4. Use replication to scale reads and improve availability.
5. Use strong consistency only where needed.
6. Use indexes that reduce cross-shard work.

## Distributed Database Design and Performance

A **distributed database** stores and manages data across multiple networked nodes to improve **scalability, availability, fault tolerance, and performance**. Its design must balance **consistency, latency, throughput, durability, and complexity**.

### 1. Replication

Replication stores copies of data on multiple nodes.

**Benefits:**
- Improves availability and fault tolerance.
- Supports disaster recovery.
- Reduces read latency by serving reads from nearby replicas.
- Increases read throughput.

**Tradeoffs:**
- Synchronous replication improves consistency but increases write latency.
- Asynchronous replication improves performance but may cause stale reads or data loss.
- Multi-leader replication improves availability but requires conflict resolution.

### 2. Indexing

Indexes speed up queries but add write overhead.

**Types:**
- **Local indexes**: maintained per shard; efficient for shard-local queries.
- **Global indexes**: map values to shards; useful for non-shard-key lookups.
- **Partitioned global indexes**: scale better than a single global index.

**Performance impact:**
- Good indexing reduces cross-shard scans.
- Poor indexing causes scatter-gather queries and distributed joins.
- Too many indexes slow writes and increase storage cost.

### 3. Transactions

Distributed transactions must ensure **ACID** properties across multiple nodes.

**Common mechanisms:**
- **Two-phase commit**: ensures atomic commit but adds latency and can block during failures.
- **Consensus protocols** such as Raft or Paxos: provide fault-tolerant commit and leader election.
- **MVCC**: improves concurrency by allowing readers not to block writers.

**Performance considerations:**
- Local transactions are faster than distributed transactions.
- Strong isolation increases coordination overhead.
- Sagas are often used for long-running workflows to avoid expensive distributed locks.

### 4. Recovery

Recovery ensures durability and correctness after failures.

**Key techniques:**
- **Write-ahead logging**: records changes before applying them.
- **Checkpoints**: reduce recovery time by limiting log replay.
- **Replicated logs**: allow failover to another node.
- **Leader election and fencing**: prevent split-brain scenarios.
- **Snapshots and backups**: support disaster recovery and point-in-time restoration.

### Overall Performance Tradeoff

Distributed database performance depends on balancing:

- **Consistency vs latency**
- **Availability vs consistency**
- **Read speed vs write cost**
- **Data locality vs load balancing**
- **Durability vs throughput**

A well-designed distributed database keeps transactions local, chooses shard keys carefully, uses replication strategically, indexes only what is needed, and implements robust logging and recovery mechanisms.

## Distributed Database Comparison

| System | Main Model | Replication | Indexing | Transactions | Recovery |
|---|---|---|---|---|---|
| **Cassandra** | Wide-column, peer-to-peer | Multi-datacenter replication, eventual consistency | Local secondary indexes, SASI, materialized views | Lightweight transactions, limited ACID | Hinted handoff, repair, snapshots |

## Practical Design: High-Traffic E-Commerce Database

### Requirements
- Millions of users
- High read and write traffic
- Strong consistency for payments and inventory
- High availability for product browsing
- Low latency for users in different regions

---

## 1. Data Partitioning

Shard by `customer_id`.

```text
Shard 1: customer_id 1–1,000,000
Shard 2: customer_id 1,000,001–2,000,000
Shard 3: customer_id 2,000,001–3,000,000
```

Colocate related tables:

```text
customers
orders
order_items
payments
```

This keeps most customer transactions local.

---

## 2. Replication

Use leader-follower replication.

```text
Writes → Leader
Strong reads → Leader
Product browsing reads → Followers
```

For payment data:

```text
Synchronous replication
```

For product catalog:

```text
Asynchronous replication
```

---

## 3. Indexing

Local indexes:

```sql
CREATE INDEX idx_orders_customer ON orders(customer_id);
CREATE INDEX idx_payments_order ON payments(order_id);
```

Global index for login:

```text
email → customer_id → shard
```

This avoids scanning all shards when a user logs in by email.

---

## 4. Transactions

Order creation:

```sql
BEGIN;

INSERT INTO orders ...
INSERT INTO order_items ...
UPDATE inventory SET stock = stock - 1 ...
INSERT INTO payments ...

COMMIT;
```

If inventory is on another shard, use:

- Distributed transaction, or
- Saga with compensation

Example saga:

```text
1. Reserve inventory
2. Charge payment
3. Create shipment

If shipment fails:
1. Cancel payment
2. Release inventory
```

---

## 5. Recovery

Use:

- Write-ahead logging
- Checkpoints
- Replicated logs
- Leader election
- Fencing
- Snapshots
- Point-in-time recovery

If leader fails:

```text
1. Detect failure
2. Elect new leader
3. Replay committed log
4. Fence old leader
5. Resume writes
```

---

## Performance Result

This design improves performance by:

- Keeping most transactions local
- Reducing cross-shard queries
- Scaling reads through replicas
- Protecting critical data with strong consistency
- Recovering quickly after failures
