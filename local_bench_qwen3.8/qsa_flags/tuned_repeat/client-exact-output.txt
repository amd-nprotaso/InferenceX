A distributed database stores data across multiple machines, sites, or regions while presenting a coherent database service to applications. Its design must balance **scalability, availability, consistency, latency, throughput, fault tolerance, and operational complexity**. The major design and performance concerns are **replication, indexing, transactions, and recovery**.

---

## 1. Overall Design of a Distributed Database

A distributed database is usually built around several core design decisions:

### 1.1 Data Distribution

Data is distributed across nodes using one or more strategies:

#### Fragmentation

Data is split into smaller pieces:

- **Horizontal fragmentation**: rows are partitioned by key range, hash, or list.
  - Example: users with IDs 0–999 on shard A, 1000–1999 on shard B.
- **Vertical fragmentation**: columns are split across nodes.
  - Example: profile data on one node, activity logs on another.
- **Derived fragmentation**: fragments are derived from joins or relationships.
  - Example: orders and customers colocated by customer ID.

#### Allocation

Fragments are placed on nodes:

- **Centralized**: all data on one node.
- **Partitioned**: each node stores a subset of data.
- **Replicated**: each node stores a copy of some or all data.
- **Hybrid**: some data is partitioned, some is replicated.

### 1.2 Transparency

A good distributed database hides complexity from users:

- **Location transparency**: users do not need to know where data is stored.
- **Fragmentation transparency**: users do not need to know how data is partitioned.
- **Replication transparency**: users do not need to know how many copies exist.
- **Failure transparency**: the system continues despite node failures.

### 1.3 Architecture Models

Common architectures include:

- **Shared-nothing**: each node has its own CPU, memory, and disk.
  - Common in sharded relational databases and many NoSQL systems.
- **Shared-disk**: nodes share storage but have separate compute.
  - Common in cloud databases with disaggregated storage.
- **Leader-follower**: one node accepts writes, followers replicate logs.
- **Leaderless**: any node can accept writes, using quorums or conflict resolution.
- **Consensus-based**: writes are committed through protocols such as Raft or Paxos.

### 1.4 Consistency Models

Distributed databases choose consistency guarantees based on workload needs:

| Consistency Model | Meaning | Typical Use |
|---|---|---|
| Linearizable | Reads see the latest committed write | Financial systems, locks, coordination |
| Sequential | Operations appear in a valid order | Some replicated systems |
| Causal | Causally related writes are preserved | Social feeds, collaborative apps |
| Eventual | Replicas converge over time | Caches, analytics, global reads |
| Snapshot isolation | Transaction sees a consistent snapshot | OLTP, reporting |
| Serializable | Equivalent to serial execution | Strong correctness requirements |

The CAP theorem summarizes a key tradeoff: during a network partition, a system must choose between **consistency** and **availability**. PACELC extends this: even without partitions, systems trade **latency** against **consistency**.

## 2. Replication

Replication stores copies of data on multiple nodes. It is one of the most important mechanisms for availability, durability, locality, and performance.

---

### 2.1 Why Replicate?

Replication provides:

1. **High availability**
   - If one node fails, another can serve requests.

2. **Fault tolerance**
   - Data survives disk, node, rack, or datacenter failures.

3. **Read scalability**
   - Reads can be served from multiple replicas.

4. **Geographic locality**
   - Users can read data from a nearby region, reducing latency.

5. **Durability**
   - Multiple copies reduce the chance of data loss.

6. **Load balancing**
   - Read traffic can be distributed across replicas.

---

### 2.2 Replication Strategies

#### 2.2.1 Synchronous Replication

The leader waits for replicas to acknowledge the write before returning success.

Example:

```text
Client → Leader
Leader → Replica 1
Leader → Replica 2
Replicas acknowledge
Leader → Client: success
```

Advantages:

- Strong durability.
- No data loss if leader fails after commit.
- Easier to reason about consistency.

Disadvantages:

- Higher write latency.
- Write availability depends on replica availability.
- Slow replicas can slow the entire system.

Performance impact:

- Write latency increases by at least one network round trip.
- Throughput may be limited by the slowest required replica.
- Tail latency can be high if any replica is slow.

Synchronous replication is common in systems requiring strong consistency, such as financial databases or consensus-based systems.

---

#### 2.2.2 Asynchronous Replication

The leader commits locally and returns success before replicas apply the write.

Example:

```text
Client → Leader
Leader commits locally
Leader → Client: success
Leader → Replica asynchronously
```

Advantages:

- Lower write latency.
- Better write throughput.
- More tolerant of slow or distant replicas.

Disadvantages:

- Replicas may lag.
- If the leader fails before replication, data may be lost.
- Reads from replicas may be stale.

Performance impact:

- Faster writes.
- Better scalability.
- Risk of replication lag and stale reads.

Asynchronous replication is common in global databases, analytics systems, and systems prioritizing availability and write latency.

---

#### 2.2.3 Semi-Synchronous Replication

The leader waits for at least one replica to acknowledge receipt of the log, but not necessarily full application.

Advantages:

- Better durability than fully asynchronous.
- Lower latency than fully synchronous.

Disadvantages:

- More complex failure handling.
- Still vulnerable to some edge cases.

---

### 2.3 Leader-Follower Replication

One node is the leader and accepts writes. Followers replicate the leader’s log.

Example:

```text
Writes:
Client → Leader → Followers

Reads:
Client → Leader or Followers
```

Advantages:

- Simple write ordering.
- Easy conflict avoidance.
- Strong consistency if reads go to leader.

Disadvantages:

- Leader can become a bottleneck.
- Leader failure requires election.
- Followers may lag.

Performance tuning:

- Use multiple leader groups for different shards.
- Route reads to nearby followers.
- Use lease-based leader election.
- Monitor replication lag.
- Avoid hot leaders by balancing shards.

---

### 2.4 Leaderless Replication

Any replica can accept writes. Coordination is done through quorums or conflict resolution.

Example:

```text
Client → Replica A, Replica B, Replica C
Write succeeds if quorum acknowledges
```

Advantages:

- No single leader bottleneck.
- High availability.
- Good for geographically distributed systems.

Disadvantages:

- Conflict resolution is complex.
- Strong consistency is harder.
- Read repair and anti-entropy are required.

Common in Dynamo-style systems.

---

### 2.5 Quorum Replication

A system uses:

- `N`: number of replicas
- `W`: number of replicas that must acknowledge a write
- `R`: number of replicas that must be read

A common rule is:

```text
R + W > N
```

This ensures overlap between reads and writes, providing strong consistency under normal conditions.

Example:

```text
N = 3
W = 2
R = 2

R + W = 4 > 3
```

Advantages:

- Tunable consistency.
- Fault tolerance.
- Can tolerate some replica failures.

Disadvantages:

- Higher latency if `W` or `R` is large.
- More complex failure handling.
- Network partitions can reduce availability.

Performance impact:

- Increasing `W` improves durability but increases write latency.
- Increasing `R` improves consistency but increases read latency.
- Choosing `R + W > N` trades latency for consistency.

---

### 2.6 Consensus-Based Replication

Systems such as Raft and Paxos use consensus to ensure that all nodes agree on the order of committed operations.

Example:

```text
Leader proposes log entry
Majority acknowledges
Entry is committed
Followers apply entry
```

Advantages:

- Strong consistency.
- Safe leader election.
- Survives majority failures.

Disadvantages:

- Requires majority availability.
- Higher latency due to coordination.
- Complex implementation.

Performance impact:

- Write latency depends on majority round trip.
- Throughput can be limited by log replication.
- Leader election can cause temporary unavailability.

---

### 2.7 Conflict Resolution

In leaderless or multi-master systems, concurrent writes can conflict.

Common strategies:

1. **Last-write-wins**
   - Uses timestamps.
   - Simple but can lose updates.

2. **Vector clocks**
   - Track causality.
   - Detect concurrent writes.

3. **CRDTs**
   - Conflict-free replicated data types.
   - Merge automatically.
   - Useful for counters, sets, maps.

4. **Application-level resolution**
   - Business rules decide the winner.
   - More correct but more complex.

5. **Single-writer per key**
   - Assign one node as owner of a key.
   - Avoids conflicts.

Performance impact:

- Conflict resolution adds CPU and storage overhead.
- CRDTs can grow metadata.
- Multi-master systems may require background reconciliation.

---

### 2.8 Replication Performance Considerations

Key performance factors:

| Factor | Effect |
|---|---|
| Replication factor | More replicas increase durability and read capacity but increase write cost |
| Network distance | Cross-region replication increases latency |
| Synchronous vs asynchronous | Synchronous improves durability but increases write latency |
| Replication lag | Causes stale reads and failover risk |
| Write amplification | Each write may be copied to multiple replicas |
| Hot shards | One shard can become a bottleneck |
| Log shipping | Can be efficient but may lag |
| Snapshot transfer | Useful for bootstrapping but expensive |

Typical write amplification:

```text
Write amplification ≈ 1 + number of replicas + number of indexes
```

For example, a write to a table with 3 replicas and 2 indexes may result in 6 logical writes.

## 3. Indexing in Distributed Databases

Indexes accelerate reads but increase write cost, storage, and coordination complexity.

---

### 3.1 Local vs Global Indexes

#### Local Index

A local index is partitioned in the same way as the base table.

Example:

```text
Table partitioned by user_id
Index also partitioned by user_id
```

Advantages:

- Simple to maintain.
- Index updates are local to the partition.
- Good for queries filtered by partition key.

Disadvantages:

- Poor for queries not including the partition key.
- May require scanning many partitions.

Performance:

- Low write overhead.
- Fast for partition-key queries.
- Slow for global queries.

---

#### Global Index

A global index is partitioned independently from the base table.

Example:

```text
Table partitioned by user_id
Index partitioned by email
```

Advantages:

- Supports queries on non-partition keys.
- Enables fast lookups by secondary attributes.

Disadvantages:

- Index updates may cross partitions.
- Requires distributed transactions or asynchronous maintenance.
- Can create hot index partitions.

Performance:

- Faster reads for secondary queries.
- Higher write latency.
- More complex consistency.

---

### 3.2 Index Maintenance Strategies

#### Synchronous Index Maintenance

The base table and index are updated atomically.

Advantages:

- Strong consistency.
- No stale index entries.

Disadvantages:

- Higher write latency.
- More distributed coordination.
- More failure handling.

Performance impact:

- Each write may require multiple partition updates.
- Cross-partition index updates may require two-phase commit or consensus.

---

#### Asynchronous Index Maintenance

The base table is updated first, and the index is updated later.

Advantages:

- Lower write latency.
- Better throughput.
- Easier to scale.

Disadvantages:

- Index may be stale.
- Queries may miss recent writes.
- Requires repair and reconciliation.

Performance impact:

- Faster writes.
- Eventually consistent reads.
- Background index builders can consume CPU and I/O.

---

### 3.3 Types of Distributed Indexes

#### Hash Index

- Maps key to partition or location.
- Good for exact-match lookups.
- Poor for range queries.

#### Range Index

- Supports range scans.
- Common in B-tree indexes.
- Can cause hot partitions if keys are sequential.

#### Composite Index

- Index on multiple columns.
- Order of columns matters.
- Useful for queries with equality and range predicates.

Example:

```sql
CREATE INDEX idx_user_status_time
ON orders(user_id, status, created_at);
```

This helps queries filtering by `user_id`, then `status`, then `created_at`.

#### Covering Index

- Contains all columns needed by a query.
- Avoids fetching the base table.
- Reduces I/O and network traffic.

Example:

```sql
SELECT user_id, status
FROM orders
WHERE user_id = 123;
```

If the index contains `user_id` and `status`, the query can be answered from the index alone.

#### Sparse Index

- Indexes only some rows.
- Useful for large tables with selective predicates.

#### Inverted Index

- Maps terms to documents or rows.
- Common in search systems.
- Can be expensive to maintain.

#### Vector Index

- Used for similarity search.
- Common in AI/ML workloads.
- Often uses approximate nearest neighbor algorithms.

---

### 3.4 Distributed Query Optimization with Indexes

A distributed query optimizer must consider:

1. **Partition pruning**
   - Avoid scanning irrelevant partitions.

2. **Predicate pushdown**
   - Send filters to storage nodes.

3. **Index selection**
   - Choose local or global indexes.

4. **Join strategy**
   - Broadcast small tables.
   - Shuffle large tables.
   - Use colocated joins when possible.

5. **Parallelism**
   - Scan multiple partitions concurrently.

6. **Data movement cost**
   - Network transfer is often more expensive than local I/O.

7. **Cardinality estimation**
   - Statistics may be distributed and stale.

Example:

```sql
SELECT *
FROM orders
WHERE user_id = 123;
```

If the table is partitioned by `user_id`, the optimizer can query only one partition.

But:

```sql
SELECT *
FROM orders
WHERE email = 'user@example.com';
```

If `email` is not the partition key, the system may need a global index or scan many partitions.

---

### 3.5 Index Performance Tradeoffs

| Benefit | Cost |
|---|---|
| Faster reads | Slower writes |
| Lower latency | More storage |
| Better query flexibility | More complexity |
| Reduced scans | More index maintenance |
| Covering indexes reduce I/O | Larger index size |

In distributed systems, indexes can become bottlenecks if they are:

- Global and synchronous.
- Skewed by hot keys.
- Too numerous.
- Not partitioned well.
- Rebuilt frequently.

## 4. Transactions in Distributed Databases

Transactions provide correctness guarantees across multiple nodes.

---

### 4.1 ACID in Distributed Systems

ACID stands for:

- **Atomicity**: all operations succeed or none do.
- **Consistency**: database moves from one valid state to another.
- **Isolation**: concurrent transactions do not interfere incorrectly.
- **Durability**: committed data survives failures.

In a distributed database, atomicity and durability are harder because data may be on multiple nodes.

---

### 4.2 Single-Partition Transactions

If all data involved in a transaction is on one partition, the transaction can be handled locally.

Advantages:

- Low latency.
- No distributed coordination.
- High throughput.

Design goal:

- Partition data so common transactions touch only one partition.

Example:

```text
Transfer between two accounts in the same shard
```

This is much faster than a cross-shard transfer.

---

### 4.3 Cross-Partition Transactions

When a transaction touches multiple partitions, coordination is required.

Common approaches:

#### Two-Phase Commit, 2PC

Phase 1: prepare

```text
Coordinator → Participant A: prepare?
Coordinator → Participant B: prepare?
Participants respond yes/no
```

Phase 2: commit or abort

```text
If all yes:
Coordinator → Participants: commit

If any no:
Coordinator → Participants: abort
```

Advantages:

- Atomic commit across participants.
- Widely understood.

Disadvantages:

- Blocking if coordinator fails.
- Participants may hold locks during prepare.
- High latency.
- Poor availability during failures.

Performance impact:

- Adds at least two coordination round trips.
- Locks may be held longer.
- Throughput can drop under contention.

---

#### Three-Phase Commit, 3PC

Attempts to reduce blocking compared to 2PC.

Advantages:

- Better theoretical availability.

Disadvantages:

- More complex.
- Still not safe under all network partitions.
- Rarely used in practice.

---

#### Consensus-Based Transactions

Systems using Raft or Paxos can commit transactions through consensus.

Advantages:

- Strong consistency.
- Better failure handling than naive 2PC.

Disadvantages:

- Requires majority availability.
- Coordination overhead.

---

#### Optimistic Concurrency Control

Transactions execute without locks and validate at commit time.

Advantages:

- Good for low-contention workloads.
- Less blocking.

Disadvantages:

- High contention causes retries.
- Validation can be expensive.

Performance impact:

- Fast when conflicts are rare.
- Slow when many transactions update the same data.

---

#### Pessimistic Concurrency Control

Transactions acquire locks before modifying data.

Advantages:

- Prevents conflicts.
- Easier to reason about.

Disadvantages:

- Locks reduce concurrency.
- Deadlocks possible.
- Lock coordination across nodes is expensive.

Performance impact:

- Better under high contention if lock management is efficient.
- Worse under long transactions or hot rows.

---

#### MVCC, Multi-Version Concurrency Control

Readers see snapshots, writers create new versions.

Advantages:

- Readers do not block writers.
- Writers do not block readers.
- Good for OLTP.

Disadvantages:

- Requires version garbage collection.
- Long transactions can cause bloat.
- Distributed snapshots require timestamp coordination.

Performance impact:

- High concurrency.
- More storage and cleanup overhead.
- Snapshot consistency depends on timestamp service.

---

### 4.4 Isolation Levels

Common isolation levels:

| Isolation Level | Guarantee | Performance |
|---|---|---|
| Read uncommitted | May read uncommitted data | Fastest, unsafe |
| Read committed | Reads only committed data | Common |
| Snapshot isolation | Consistent snapshot | Good balance |
| Serializable | Equivalent to serial execution | Strongest, slowest |

Distributed systems often implement:

- **Snapshot isolation**
- **Serializable snapshot isolation**
- **Strict serializability**
- **Linearizable transactions**

Performance impact:

- Stronger isolation usually means more coordination, more locking, or more validation.
- Serializable transactions can be expensive across partitions.

---

### 4.5 Distributed Transaction Design Strategies

#### 1. Minimize Cross-Partition Transactions

Best practice:

```text
Design schema so common transactions are local.
```

Example:

```text
Partition by customer_id
Keep customer, orders, and order_items colocated
```

#### 2. Use Idempotency

Retries are common in distributed systems.

Example:

```text
Client sends request with idempotency key
Server stores result
Duplicate request returns stored result
```

#### 3. Use Sagas for Long Workflows

A saga is a sequence of local transactions with compensating actions.

Example:

```text
Reserve inventory
Book hotel
Charge payment

If payment fails:
Cancel hotel
Release inventory
```

Advantages:

- Avoids long distributed locks.
- Better availability.

Disadvantages:

- Not isolated.
- Requires compensation logic.
- May expose intermediate states.

#### 4. Use Deterministic Ordering

Some systems assign a global order to transactions before execution.

Advantages:

- Easier replication.
- Deterministic recovery.
- Can reduce coordination.

Disadvantages:

- Requires ordering service.
- May add latency.

#### 5. Batch Transactions

Group multiple operations into one commit.

Advantages:

- Reduces coordination overhead.
- Improves throughput.

Disadvantages:

- Higher latency.
- Larger failure units.

---

### 4.6 Transaction Performance Considerations

| Factor | Effect |
|---|---|
| Number of partitions touched | More partitions means more coordination |
| Lock contention | Reduces throughput |
| Transaction duration | Longer transactions hold locks and versions longer |
| Isolation level | Stronger isolation costs more |
| Network latency | Coordination becomes slower |
| Retry rate | High contention causes wasted work |
| Timestamp service | Can become bottleneck |
| Log flush policy | Durability vs latency |

A common performance rule:

```text
Cross-partition transactions are much more expensive than local transactions.
```

Therefore, schema design and partitioning are critical.

## 5. Recovery in Distributed Databases

Recovery ensures that the database can survive failures and restore a consistent state.

---

### 5.1 Failure Types

Distributed databases must handle:

1. **Node failure**
   - A server crashes.

2. **Disk failure**
   - Storage becomes unavailable or corrupted.

3. **Network partition**
   - Nodes cannot communicate.

4. **Process failure**
   - Database process crashes but node remains alive.

5. **Site or datacenter failure**
   - Entire region becomes unavailable.

6. **Partial failure**
   - Some replicas are reachable, others are not.

---

### 5.2 Durability and Logging

Most databases use a **write-ahead log**, WAL.

Basic idea:

```text
Before modifying data pages, write the change to a durable log.
```

Example:

```text
Transaction begins
Log record written
Data page modified
Transaction commits
Log record marked committed
```

Advantages:

- Fast sequential log writes.
- Recovery can replay or undo changes.
- Replication can ship log records.

Performance impact:

- Log flush latency affects commit latency.
- `fsync` can be expensive.
- Group commit can improve throughput.

---

### 5.3 Checkpointing

A checkpoint records the database state at a point in time.

Advantages:

- Reduces recovery time.
- Allows log truncation.
- Speeds restart.

Disadvantages:

- Checkpointing consumes I/O and CPU.
- Can cause latency spikes.
- Large checkpoints may take time.

Performance impact:

- More frequent checkpoints reduce recovery time but increase overhead.
- Less frequent checkpoints improve throughput but increase recovery time.

---

### 5.4 Recovery Process

A typical recovery process:

1. **Detect failure**
   - Heartbeats, leases, consensus, or monitoring.

2. **Choose new leader**
   - If using leader-follower replication.

3. **Recover log**
   - Read durable log records.

4. **Redo committed transactions**
   - Reapply changes that were committed but not fully applied.

5. **Undo uncommitted transactions**
   - Roll back changes that were not committed.

6. **Restore consistency**
   - Repair replicas, truncate logs, reconcile state.

7. **Resume service**
   - Accept new transactions.

---

### 5.5 ARIES-Style Recovery

Many systems use ideas from ARIES:

- **Write-ahead logging**
- **Page LSNs**
- **Dirty page tables**
- **Fuzzy checkpoints**
- **Redo and undo phases**

Simplified recovery phases:

1. **Analysis**
   - Determine which transactions were active and which pages were dirty.

2. **Redo**
   - Reapply all logged changes up to failure.

3. **Undo**
   - Roll back uncommitted transactions.

Advantages:

- Fast recovery.
- Allows concurrent logging and checkpointing.

Disadvantages:

- Complex implementation.
- Requires careful log management.

---

### 5.6 Replication-Based Recovery

Replication helps recovery by providing copies of data.

#### Synchronous Replication Recovery

If the leader fails, a follower can take over with little or no data loss.

Advantages:

- Low RPO, recovery point objective.
- Better consistency.

Disadvantages:

- Higher write latency.
- Requires majority availability.

#### Asynchronous Replication Recovery

If the leader fails, a follower may be promoted, but some recent writes may be lost.

Advantages:

- Faster writes.
- Better availability.

Disadvantages:

- Higher RPO.
- Risk of data loss.
- May require conflict resolution.

---

### 5.7 Snapshots and Backups

Distributed databases often use:

- **Full snapshots**
- **Incremental backups**
- **Point-in-time recovery**
- **Continuous archiving**

Example:

```text
Snapshot at 00:00
WAL archived continuously
Restore to 14:32 by replaying WAL
```

Advantages:

- Protects against corruption and operator error.
- Enables disaster recovery.
- Supports testing and analytics.

Disadvantages:

- Storage cost.
- Backup bandwidth.
- Recovery time can be long.

Performance impact:

- Backups can compete with production I/O.
- Compression and encryption add CPU cost.
- Cross-region backups increase network usage.

---

### 5.8 Failure Detection and Leader Election

Fast failure detection improves availability.

Common mechanisms:

- Heartbeats
- Leases
- Consensus elections
- Gossip protocols
- Timeout-based detection

Tradeoffs:

| Detection Speed | Effect |
|---|---|
| Fast detection | Faster failover |
| Too fast | False positives during network delays |
| Slow detection | Longer outage |

Performance impact:

- Aggressive timeouts can cause unnecessary leader elections.
- Leader elections can pause writes.
- Network jitter can destabilize the system.

---

### 5.9 Recovery Performance Metrics

Important metrics:

| Metric | Meaning |
|---|---|
| RPO | Maximum data loss allowed |
| RTO | Maximum time to restore service |
| Recovery time | Time to restart and become consistent |
| Replication lag | How far behind replicas are |
| Log size | Amount of log to replay |
| Checkpoint interval | Frequency of checkpoints |
| Failover time | Time to detect failure and promote leader |

Design goals:

- Minimize RPO and RTO.
- Keep recovery time predictable.
- Avoid recovery storms.
- Ensure backups are tested.

---

## 6. Performance Design of Distributed Databases

Performance in distributed databases is dominated by coordination, data movement, and contention.

---

### 6.1 Main Performance Bottlenecks

#### Network Latency

Cross-node operations require network round trips.

Example:

```text
Local write: microseconds
Same datacenter write: hundreds of microseconds
Cross-region write: milliseconds
```

Design response:

- Colocate frequently accessed data.
- Use regional replicas.
- Batch operations.
- Cache hot data.

---

#### Network Bandwidth

Large scans, joins, and replication can saturate links.

Design response:

- Partition data to reduce cross-node traffic.
- Push down filters.
- Use columnar storage.
- Compress data.
- Use bloom filters and semi-joins.

---

#### Hot Partitions

One shard receives disproportionate traffic.

Example:

```text
A celebrity user receives millions of reads
```

Design response:

- Better partition keys.
- Split hot partitions.
- Use caching.
- Use request coalescing.
- Use approximate counters.

---

#### Lock Contention

Many transactions update the same row or range.

Design response:

- Short transactions.
- Fine-grained locks.
- Optimistic concurrency.
- Queue updates.
- Partition hot objects.

---

#### Index Maintenance

Too many indexes slow writes.

Design response:

- Remove unused indexes.
- Use asynchronous indexes when acceptable.
- Use covering indexes to reduce reads.
- Partition indexes to avoid hotspots.

---

#### Log Flush Latency

Durability requires log writes to stable storage.

Design response:

- Group commit.
- SSDs or NVMe.
- Battery-backed write cache.
- Batching.
- Careful fsync policy.

---

#### Garbage Collection

MVCC versions and tombstones accumulate.

Design response:

- Tune GC.
- Avoid long transactions.
- Compact LSM trees.
- Monitor version retention.

---

### 6.2 Scalability

Distributed databases scale in two ways:

#### Vertical Scaling

Increase resources on one node.

Advantages:

- Simple.

Disadvantages:

- Limited.
- Expensive.

#### Horizontal Scaling

Add more nodes.

Advantages:

- Better scalability.
- More fault tolerance.

Disadvantages:

- More complexity.
- Coordination overhead.

Good distributed design aims for horizontal scaling, but coordination can limit linear scalability.

---

### 6.3 Throughput vs Latency

There is often a tradeoff:

```text
Batching improves throughput but increases latency.
```

Example:

```text
Commit every write immediately: low latency, lower throughput
Commit every 10 ms: higher throughput, higher latency
```

Design response:

- Use adaptive batching.
- Separate latency-sensitive and throughput-sensitive workloads.
- Use priority queues.

---

### 6.4 Tail Latency

Distributed systems often suffer from high tail latency because a request may depend on multiple nodes.

Example:

```text
If one replica is slow, a quorum read may be delayed.
```

Techniques to reduce tail latency:

- Hedge requests.
- Use multiple replicas.
- Use leader leases.
- Avoid synchronous cross-region writes.
- Use request timeouts.
- Monitor p99 and p999 latency.

---

## 7. Putting It All Together: Example Design

Consider a globally distributed OLTP database.

### Design

- Data is partitioned by `customer_id`.
- Each partition is replicated using Raft with 3 replicas.
- Writes go to the leader of each partition.
- Reads can go to followers for stale reads or leader for strong reads.
- Global secondary indexes are maintained asynchronously.
- Transactions are local when possible.
- Cross-partition transactions use two-phase commit or deterministic ordering.
- MVCC provides snapshot isolation.
- WAL is used for durability and replication.
- Snapshots and continuous WAL archiving support recovery.

### Performance Characteristics

- Local transactions are fast.
- Cross-partition transactions are slower.
- Strong reads from leader have higher latency than follower reads.
- Global indexes improve secondary queries but increase write cost.
- Cross-region replication increases write latency.
- Hot partitions can limit throughput.
- Recovery time depends on log size and checkpoint frequency.

## 8. Key Tradeoffs

### Replication Tradeoffs

| Choice | Benefit | Cost |
|---|---|---|
| Synchronous replication | Durability, consistency | Latency, availability |
| Asynchronous replication | Speed, availability | Stale reads, data loss risk |
| High replication factor | Fault tolerance | Write amplification |
| Quorum reads/writes | Tunable consistency | Latency |
| Leaderless | Availability | Conflict complexity |

---

### Indexing Tradeoffs

| Choice | Benefit | Cost |
|---|---|---|
| Local indexes | Simple, fast writes | Limited query flexibility |
| Global indexes | Flexible queries | Distributed coordination |
| Synchronous indexes | Consistency | Write latency |
| Asynchronous indexes | Speed | Stale reads |
| Many indexes | Fast reads | Slow writes, more storage |

---

### Transaction Tradeoffs

| Choice | Benefit | Cost |
|---|---|---|
| Local transactions | Fast, simple | Requires good partitioning |
| Cross-partition transactions | Flexible | Slow, coordination-heavy |
| Strong isolation | Correctness | Lower concurrency |
| Optimistic concurrency | Low contention | Retries under contention |
| Pessimistic concurrency | Prevents conflicts | Locks, deadlocks |
| Sagas | Availability | Complexity, intermediate states |

---

### Recovery Tradeoffs

| Choice | Benefit | Cost |
|---|---|---|
| Synchronous replication | Low data loss | Higher latency |
| Asynchronous replication | Faster writes | Higher RPO |
| Frequent checkpoints | Faster recovery | More overhead |
| Infrequent checkpoints | Better throughput | Longer recovery |
| Continuous archiving | Point-in-time recovery | Storage and management cost |

---

## 9. Practical Design Guidelines

1. **Partition around common transactions**
   - Keep frequently updated related data together.

2. **Avoid hot partitions**
   - Choose partition keys with good cardinality and access patterns.

3. **Minimize cross-partition transactions**
   - They are the most expensive operations.

4. **Use replication deliberately**
   - Match replication mode to durability and latency requirements.

5. **Monitor replication lag**
   - Lag affects stale reads and failover safety.

6. **Use global indexes only when needed**
   - They can become distributed bottlenecks.

7. **Keep transactions short**
   - Long transactions increase locks, versions, and recovery work.

8. **Design for partial failure**
   - Network partitions and slow nodes are normal.

9. **Test recovery regularly**
   - Untested backups are not backups.

10. **Measure tail latency**
   - p99 and p999 matter more than average latency.

## 10. Summary

A distributed database is designed to provide scalable, available, and durable data management across multiple machines. Its performance depends heavily on how data is distributed and coordinated.

- **Replication** improves availability, durability, and read scalability, but adds write latency, replication lag, and consistency complexity.
- **Indexing** improves read performance, but increases write cost, storage, and distributed coordination, especially for global indexes.
- **Transactions** provide correctness across nodes, but distributed transactions require coordination, which can reduce throughput and availability.
- **Recovery** ensures the system can survive failures using logs, checkpoints, snapshots, replication, and failover mechanisms, but recovery design affects latency, durability, and operational complexity.

The best distributed database design aligns data partitioning, replication strategy, indexing, transaction model, and recovery mechanisms with the application’s consistency, latency, throughput, and fault-tolerance requirements.

# Design and Performance of a Distributed Database

## Introduction

A **distributed database** is a database system in which data is stored across multiple computers or sites connected by a network, but users perceive it as a single logical database. The main goals of a distributed database are to provide **scalability, availability, fault tolerance, reliability, and improved performance**.

However, because data is spread across multiple nodes, the system must handle issues such as **network latency, data consistency, replication, distributed transactions, and recovery**. Therefore, the design of a distributed database must carefully balance **performance, consistency, availability, and complexity**.

---

## 1. Design of a Distributed Database

The design of a distributed database involves several important decisions.

### 1.1 Data Fragmentation

Data is divided into smaller logical units called fragments.

Common types of fragmentation are:

1. **Horizontal fragmentation**
   - The table is divided by rows.
   - Example: customers from different regions stored on different nodes.

2. **Vertical fragmentation**
   - The table is divided by columns.
   - Example: customer personal details stored on one node and transaction history on another.

3. **Derived fragmentation**
   - Fragments are created based on relationships between tables.
   - Example: orders and customers stored together based on customer ID.

Fragmentation helps improve performance by allowing data to be stored close to the users who access it most often.

---

### 1.2 Data Allocation

After fragmentation, fragments are assigned to different sites.

Possible allocation strategies include:

1. **Centralized allocation**
   - All data is stored at one site.

2. **Partitioned allocation**
   - Each site stores a different part of the database.

3. **Replicated allocation**
   - Each site stores a copy of the data.

4. **Hybrid allocation**
   - Some data is partitioned, while other data is replicated.

Good allocation improves performance by reducing network traffic and improving access time.

---

### 1.3 Transparency

A distributed database should provide transparency so that users do not need to know the physical distribution of data.

Important types of transparency include:

1. **Location transparency**
   - Users do not need to know where data is stored.

2. **Fragmentation transparency**
   - Users do not need to know how data is divided.

3. **Replication transparency**
   - Users do not need to know how many copies exist.

4. **Failure transparency**
   - The system continues to operate despite node failures.

Transparency makes the distributed database easier to use and manage.

---

### 1.4 Consistency Model

A distributed database must decide how consistent the data should be across nodes.

Common consistency models include:

1. **Strong consistency**
   - All nodes see the same data at the same time.
   - Better correctness but higher latency.

2. **Eventual consistency**
   - Nodes may temporarily differ but eventually become consistent.
   - Better availability and performance but weaker guarantees.

3. **Causal consistency**
   - Related updates are seen in the same order.

4. **Snapshot consistency**
   - Transactions see a consistent view of the database at a point in time.

The choice of consistency model directly affects performance and availability.

---

## 2. Performance of a Distributed Database

The performance of a distributed database depends on several factors.

### 2.1 Network Latency

Since data is distributed, operations may require communication between nodes.

Network latency can significantly affect performance, especially for:

- distributed transactions,
- synchronous replication,
- cross-site queries,
- distributed joins.

To reduce latency, designers often use:

- data colocation,
- caching,
- local replicas,
- asynchronous replication,
- query optimization.

---

### 2.2 Network Bandwidth

Large queries and replication can consume network bandwidth.

Performance can be improved by:

- reducing data transfer,
- using indexes,
- pushing filters to storage nodes,
- using compression,
- using partition pruning.

---

### 2.3 Data Placement

Poor data placement can cause excessive network traffic.

For example, if related data is stored on different nodes, queries may require many remote accesses.

Good design places frequently accessed data together to reduce communication cost.

---

### 2.4 Load Balancing

If one node receives more requests than others, it becomes a bottleneck.

Performance improves when workload is balanced across nodes.

Techniques include:

- partitioning by hash,
- dynamic load balancing,
- replica selection,
- request routing.

---

### 2.5 Hotspots

A hotspot occurs when one partition or node receives disproportionate traffic.

Example:

- one popular user account receives millions of requests.

Hotspots reduce scalability and increase latency.

They can be reduced by:

- better partition keys,
- splitting hot partitions,
- caching,
- request batching.

---

## 3. Replication

## 3.1 Meaning of Replication

**Replication** means storing copies of data on multiple nodes.

Replication is one of the most important features of a distributed database.

---

## 3.2 Purpose of Replication

Replication is used to:

1. improve **availability**,
2. improve **fault tolerance**,
3. increase **read performance**,
4. reduce **access latency**,
5. support **disaster recovery**,
6. provide **data durability**.

---

## 3.3 Types of Replication

### 3.3.1 Synchronous Replication

In synchronous replication, a write is considered successful only after all required replicas acknowledge it.

Example:

```text
Client → Leader
Leader → Replica 1
Leader → Replica 2
Replicas acknowledge
Leader → Client: success
```

Advantages:

- strong durability,
- less risk of data loss,
- easier consistency.

Disadvantages:

- higher write latency,
- lower availability if replicas are unreachable.

Performance impact:

- slower writes,
- better safety.

---

### 3.3.2 Asynchronous Replication

In asynchronous replication, the leader commits the write and returns success before replicas apply it.

Advantages:

- faster writes,
- better throughput,
- more tolerant of slow replicas.

Disadvantages:

- replicas may lag,
- stale reads possible,
- data loss possible if leader fails.

Performance impact:

- faster performance,
- weaker durability guarantees.

---

### 3.3.3 Leader-Follower Replication

One node is the leader and handles writes. Other nodes are followers and replicate the leader’s log.

Advantages:

- simple design,
- avoids write conflicts,
- easy to implement strong consistency.

Disadvantages:

- leader can become a bottleneck,
- leader failure requires election.

Performance impact:

- good for write ordering,
- may limit write scalability.

---

### 3.3.4 Leaderless Replication

Any node can accept writes.

Advantages:

- no single leader bottleneck,
- high availability.

Disadvantages:

- complex conflict resolution,
- harder to guarantee strong consistency.

Performance impact:

- better availability,
- more complexity.

---

## 3.4 Quorum-Based Replication

In quorum-based replication, the system uses:

- `N` = number of replicas,
- `W` = number of replicas that must acknowledge a write,
- `R` = number of replicas that must be read.

A common rule is:

```text
R + W > N
```

This ensures that reads and writes overlap, providing stronger consistency.

Example:

```text
N = 3
W = 2
R = 2
```

Advantages:

- tunable consistency,
- fault tolerance.

Disadvantages:

- higher latency if `W` or `R` is large.

---

## 3.5 Performance Issues in Replication

Replication improves availability and read performance, but it also introduces costs:

| Issue | Effect |
|---|---|
| Write amplification | Each write may be copied to multiple nodes |
| Replication lag | Reads may return stale data |
| Network distance | Cross-region replication increases latency |
| Synchronous mode | Improves safety but slows writes |
| Asynchronous mode | Improves speed but risks data loss |
| Hot replicas | One replica may become overloaded |

---

## 4. Indexing

## 4.1 Meaning of Indexing

An **index** is a data structure that helps the database find data faster without scanning the entire table.

In a distributed database, indexing becomes more complex because data is spread across multiple nodes.

---

## 4.2 Types of Distributed Indexes

### 4.2.1 Local Index

A local index is partitioned in the same way as the base table.

Example:

```text
Table partitioned by user_id
Index also partitioned by user_id
```

Advantages:

- easy to maintain,
- low write overhead,
- good for queries using partition key.

Disadvantages:

- poor for queries not using partition key.

---

### 4.2.2 Global Index

A global index is partitioned independently of the base table.

Example:

```text
Table partitioned by user_id
Index partitioned by email
```

Advantages:

- supports queries on non-partition keys,
- improves flexibility.

Disadvantages:

- index updates may require cross-node coordination,
- can become a bottleneck.

---

### 4.2.3 Composite Index

A composite index is created on multiple columns.

Example:

```sql
CREATE INDEX idx_user_status
ON orders(user_id, status);
```

It is useful when queries filter on multiple columns.

---

### 4.2.4 Covering Index

A covering index contains all columns needed by a query.

Advantages:

- avoids accessing the base table,
- reduces I/O and network traffic.

---

## 4.3 Index Maintenance in Distributed Systems

Indexes must be updated when data changes.

There are two main approaches:

### 4.3.1 Synchronous Index Maintenance

The table and index are updated together.

Advantages:

- consistent index,
- no stale index entries.

Disadvantages:

- slower writes,
- more coordination.

---

### 4.3.2 Asynchronous Index Maintenance

The table is updated first, and the index is updated later.

Advantages:

- faster writes,
- better throughput.

Disadvantages:

- index may be stale,
- queries may miss recent updates.

---

## 4.4 Performance Impact of Indexing

Indexes improve read performance but increase write cost.

| Benefit | Cost |
|---|---|
| Faster query execution | Slower updates |
| Reduced table scans | More storage |
| Better query flexibility | More maintenance |
| Covering indexes reduce I/O | Larger index size |

In distributed databases, global indexes can be especially expensive because they may require updates across multiple nodes.

---

## 5. Transactions

## 5.1 Meaning of a Transaction

A **transaction** is a logical unit of work that must be processed completely or not at all.

A transaction should satisfy the **ACID** properties:

1. **Atomicity**
   - Either all operations succeed, or none do.

2. **Consistency**
   - The database moves from one valid state to another.

3. **Isolation**
   - Concurrent transactions do not interfere incorrectly.

4. **Durability**
   - Once committed, changes survive failures.

---

## 5.2 Distributed Transactions

A distributed transaction is a transaction that accesses data stored on multiple nodes.

Example:

```text
Transfer money from account A on Node 1
to account B on Node 2
```

This requires coordination between nodes.

---

## 5.3 Two-Phase Commit Protocol

The most common protocol for distributed transactions is **Two-Phase Commit**, or **2PC**.

### Phase 1: Prepare

The coordinator asks all participants whether they are ready to commit.

```text
Coordinator → Participant A: prepare?
Coordinator → Participant B: prepare?
```

### Phase 2: Commit or Abort

If all participants agree, the transaction commits.

```text
Coordinator → Participants: commit
```

If any participant fails, the transaction aborts.

```text
Coordinator → Participants: abort
```

Advantages:

- ensures atomicity across nodes.

Disadvantages:

- blocking if coordinator fails,
- locks may be held for long time,
- poor availability during failures.

Performance impact:

- adds coordination overhead,
- increases latency,
- reduces throughput under contention.

---

## 5.4 Concurrency Control in Distributed Databases

Concurrency control ensures that multiple transactions can run safely.

Common methods include:

### 5.4.1 Lock-Based Concurrency Control

Transactions acquire locks before modifying data.

Advantages:

- prevents conflicts.

Disadvantages:

- reduces concurrency,
- may cause deadlocks.

---

### 5.4.2 Optimistic Concurrency Control

Transactions execute without locks and validate at commit time.

Advantages:

- good for low-contention workloads.

Disadvantages:

- many retries under high contention.

---

### 5.4.3 MVCC

**Multi-Version Concurrency Control** allows readers to see snapshots while writers create new versions.

Advantages:

- readers do not block writers,
- writers do not block readers.

Disadvantages:

- requires garbage collection,
- long transactions can cause version bloat.

---

## 5.5 Isolation Levels

Common isolation levels include:

1. **Read committed**
2. **Snapshot isolation**
3. **Serializable isolation**
4. **Strict serializability**

Stronger isolation provides better correctness but usually reduces performance.

---

## 5.6 Performance Impact of Transactions

Distributed transactions are expensive because they require coordination.

| Factor | Effect |
|---|---|
| Number of nodes involved | More coordination |
| Lock contention | Lower throughput |
| Transaction duration | Longer locks and more recovery work |
| Isolation level | Stronger isolation means more overhead |
| Network latency | Slower commit |
| Retries | Wasted work |

Best practice:

```text
Design the database so that most transactions are local to one partition.
```

## 6. Recovery

## 6.1 Meaning of Recovery

**Recovery** is the process of restoring the database to a correct state after a failure.

Failures may include:

- node failure,
- disk failure,
- network failure,
- site failure,
- process crash.

---

## 6.2 Recovery Goals

The main goals of recovery are:

1. **Durability**
   - Committed transactions must survive failures.

2. **Atomicity**
   - Incomplete transactions must be undone.

3. **Consistency**
   - The database must return to a valid state.

4. **Availability**
   - The system should recover quickly.

---

## 6.3 Write-Ahead Logging

A common recovery technique is **Write-Ahead Logging**, or **WAL**.

Before modifying data, the database writes the change to a log.

Example:

```text
Transaction begins
Log record written
Data page modified
Transaction commits
Log record marked committed
```

Advantages:

- ensures durability,
- supports undo and redo,
- helps replication.

Performance impact:

- log flushing can slow commits,
- batching can improve throughput.

---

## 6.4 Checkpointing

A **checkpoint** records the database state at a point in time.

Advantages:

- reduces recovery time,
- allows log truncation.

Disadvantages:

- consumes CPU and I/O,
- may cause latency spikes.

Performance impact:

- frequent checkpoints reduce recovery time but increase overhead,
- infrequent checkpoints improve throughput but increase recovery time.

---

## 6.5 Redo and Undo

During recovery, the system may need to:

1. **Redo**
   - Reapply committed transactions that were not fully written to disk.

2. **Undo**
   - Roll back transactions that were not committed.

This ensures that the database returns to a consistent state.

---

## 6.6 Replication-Based Recovery

Replication helps recovery by providing backup copies.

### Synchronous replication recovery

- Low data loss,
- Better consistency,
- Higher write latency.

### Asynchronous replication recovery

- Faster writes,
- Better availability,
- Possible data loss.

---

## 6.7 Snapshots and Backups

Distributed databases often use:

- full snapshots,
- incremental backups,
- continuous log archiving,
- point-in-time recovery.

Example:

```text
Snapshot at 00:00
WAL archived continuously
Restore database to 14:32
```

Advantages:

- protects against corruption,
- supports disaster recovery.

Disadvantages:

- storage cost,
- backup bandwidth,
- recovery time.

---

## 6.8 Failure Detection and Failover

The system must detect failures quickly and promote a new leader if needed.

Common mechanisms include:

- heartbeats,
- leases,
- consensus protocols,
- timeout-based detection.

Performance impact:

- too slow detection increases downtime,
- too fast detection may cause false failures.

---

## 7. Overall Performance Tradeoffs

A distributed database must balance several competing goals.

| Design Area | Benefit | Cost |
|---|---|---|
| Replication | Availability, durability | Latency, write amplification |
| Indexing | Faster reads | Slower writes, more storage |
| Transactions | Correctness | Coordination overhead |
| Recovery | Fault tolerance | Logging and checkpoint overhead |
| Strong consistency | Reliability | Lower availability and higher latency |
| Eventual consistency | Availability and speed | Stale reads |

---

## Conclusion

The design and performance of a distributed database depend on how well the system manages **data distribution, replication, indexing, transactions, and recovery**.

- **Replication** improves availability and read performance but increases write cost and consistency complexity.
- **Indexing** improves query performance but increases write overhead and storage requirements.
- **Transactions** provide correctness but require coordination, which can reduce performance.
- **Recovery** ensures fault tolerance but requires logging, checkpoints, backups, and failover mechanisms.

A well-designed distributed database chooses its replication strategy, indexing method, transaction model, and recovery mechanism based on the application’s requirements for **performance, consistency, availability, and durability**.

# Design and Performance of a Distributed Database

## Introduction

A **distributed database** is a database system in which data is stored across multiple computers or sites connected by a network, but users perceive it as a single logical database. The main goals of a distributed database are to provide **scalability, availability, fault tolerance, reliability, and improved performance**.

However, because data is spread across multiple nodes, the system must handle issues such as **network latency, data consistency, replication, distributed transactions, and recovery**. Therefore, the design of a distributed database must carefully balance **performance, consistency, availability, and complexity**.

---

## 1. Design of a Distributed Database

The design of a distributed database involves several important decisions.

### 1.1 Data Fragmentation

Data is divided into smaller logical units called fragments.

Common types of fragmentation are:

1. **Horizontal fragmentation**
   - The table is divided by rows.
   - Example: customers from different regions stored on different nodes.

2. **Vertical fragmentation**
   - The table is divided by columns.
   - Example: customer personal details stored on one node and transaction history on another.

3. **Derived fragmentation**
   - Fragments are created based on relationships between tables.
   - Example: orders and customers stored together based on customer ID.

Fragmentation helps improve performance by allowing data to be stored close to the users who access it most often.

---

### 1.2 Data Allocation

After fragmentation, fragments are assigned to different sites.

Possible allocation strategies include:

1. **Centralized allocation**
   - All data is stored at one site.

2. **Partitioned allocation**
   - Each site stores a different part of the database.

3. **Replicated allocation**
   - Each site stores a copy of the data.

4. **Hybrid allocation**
   - Some data is partitioned, while other data is replicated.

Good allocation improves performance by reducing network traffic and improving access time.

---

### 1.3 Transparency

A distributed database should provide transparency so that users do not need to know the physical distribution of data.

Important types of transparency include:

1. **Location transparency**
   - Users do not need to know where data is stored.

2. **Fragmentation transparency**
   - Users do not need to know how data is divided.

3. **Replication transparency**
   - Users do not need to know how many copies exist.

4. **Failure transparency**
   - The system continues to operate despite node failures.

Transparency makes the distributed database easier to use and manage.

---

### 1.4 Consistency Model

A distributed database must decide how consistent the data should be across nodes.

Common consistency models include:

1. **Strong consistency**
   - All nodes see the same data at the same time.
   - Better correctness but higher latency.

2. **Eventual consistency**
   - Nodes may temporarily differ but eventually become consistent.
   - Better availability and performance but weaker guarantees.

3. **Causal consistency**
   - Related updates are seen in the same order.

4. **Snapshot consistency**
   - Transactions see a consistent view of the database at a point in time.

The choice of consistency model directly affects performance and availability.

---

## 2. Performance of a Distributed Database

The performance of a distributed database depends on several factors.

### 2.1 Network Latency

Since data is distributed, operations may require communication between nodes.

Network latency can significantly affect performance, especially for:

- distributed transactions,
- synchronous replication,
- cross-site queries,
- distributed joins.

To reduce latency, designers often use:

- data colocation,
- caching,
- local replicas,
- asynchronous replication,
- query optimization.

---

### 2.2 Network Bandwidth

Large queries and replication can consume network bandwidth.

Performance can be improved by:

- reducing data transfer,
- using indexes,
- pushing filters to storage nodes,
- using compression,
- using partition pruning.

---

### 2.3 Data Placement

Poor data placement can cause excessive network traffic.

For example, if related data is stored on different nodes, queries may require many remote accesses.

Good design places frequently accessed data together to reduce communication cost.

---

### 2.4 Load Balancing

If one node receives more requests than others, it becomes a bottleneck.

Performance improves when workload is balanced across nodes.

Techniques include:

- partitioning by hash,
- dynamic load balancing,
- replica selection,
- request routing.

---

### 2.5 Hotspots

A hotspot occurs when one partition or node receives disproportionate traffic.

Example:

- one popular user account receives millions of requests.

Hotspots reduce scalability and increase latency.

They can be reduced by:

- better partition keys,
- splitting hot partitions,
- caching,
- request batching.

---

## 3. Replication

## 3.1 Meaning of Replication

**Replication** means storing copies of data on multiple nodes.

Replication is one of the most important features of a distributed database.

---

## 3.2 Purpose of Replication

Replication is used to:

1. improve **availability**,
2. improve **fault tolerance**,
3. increase **read performance**,
4. reduce **access latency**,
5. support **disaster recovery**,
6. provide **data durability**.

---

## 3.3 Types of Replication

### 3.3.1 Synchronous Replication

In synchronous replication, a write is considered successful only after all required replicas acknowledge it.

Example:

```text
Client → Leader
Leader → Replica 1
Leader → Replica 2
Replicas acknowledge
Leader → Client: success
```

Advantages:

- strong durability,
- less risk of data loss,
- easier consistency.

Disadvantages:

- higher write latency,
- lower availability if replicas are unreachable.

Performance impact:

- slower writes,
- better safety.

---

### 3.3.2 Asynchronous Replication

In asynchronous replication, the leader commits the write and returns success before replicas apply it.

Advantages:

- faster writes,
- better throughput,
- more tolerant of slow replicas.

Disadvantages:

- replicas may lag,
- stale reads possible,
- data loss possible if leader fails.

Performance impact:

- faster performance,
- weaker durability guarantees.

---

### 3.3.3 Leader-Follower Replication

One node is the leader and handles writes. Other nodes are followers and replicate the leader’s log.

Advantages:

- simple design,
- avoids write conflicts,
- easy to implement strong consistency.

Disadvantages:

- leader can become a bottleneck,
- leader failure requires election.

Performance impact:

- good for write ordering,
- may limit write scalability.

---

### 3.3.4 Leaderless Replication

Any node can accept writes.

Advantages:

- no single leader bottleneck,
- high availability.

Disadvantages:

- complex conflict resolution,
- harder to guarantee strong consistency.

Performance impact:

- better availability,
- more complexity.

---

## 3.4 Quorum-Based Replication

In quorum-based replication, the system uses:

- `N` = number of replicas,
- `W` = number of replicas that must acknowledge a write,
- `R` = number of replicas that must be read.

A common rule is:

```text
R + W > N
```

This ensures that reads and writes overlap, providing stronger consistency.

Example:

```text
N = 3
W = 2
R = 2
```

Advantages:

- tunable consistency,
- fault tolerance.

Disadvantages:

- higher latency if `W` or `R` is large.

---

## 3.5 Performance Issues in Replication

Replication improves availability and read performance, but it also introduces costs:

| Issue | Effect |
|---|---|
| Write amplification | Each write may be copied to multiple nodes |
| Replication lag | Reads may return stale data |
| Network distance | Cross-region replication increases latency |
| Synchronous mode | Improves safety but slows writes |
| Asynchronous mode | Improves speed but risks data loss |
| Hot replicas | One replica may become overloaded |

---

## 4. Indexing

## 4.1 Meaning of Indexing

An **index** is a data structure that helps the database find data faster without scanning the entire table.

In a distributed database, indexing becomes more complex because data is spread across multiple nodes.

---

## 4.2 Types of Distributed Indexes

### 4.2.1 Local Index

A local index is partitioned in the same way as the base table.

Example:

```text
Table partitioned by user_id
Index also partitioned by user_id
```

Advantages:

- easy to maintain,
- low write overhead,
- good for queries using partition key.

Disadvantages:

- poor for queries not using partition key.

---

### 4.2.2 Global Index

A global index is partitioned independently of the base table.

Example:

```text
Table partitioned by user_id
Index partitioned by email
```

Advantages:

- supports queries on non-partition keys,
- improves flexibility.

Disadvantages:

- index updates may require cross-node coordination,
- can become a bottleneck.

---

### 4.2.3 Composite Index

A composite index is created on multiple columns.

Example:

```sql
CREATE INDEX idx_user_status
ON orders(user_id, status);
```

It is useful when queries filter on multiple columns.

---

### 4.2.4 Covering Index

A covering index contains all columns needed by a query.

Advantages:

- avoids accessing the base table,
- reduces I/O and network traffic.

---

## 4.3 Index Maintenance in Distributed Systems

Indexes must be updated when data changes.

There are two main approaches:

### 4.3.1 Synchronous Index Maintenance

The table and index are updated together.

Advantages:

- consistent index,
- no stale index entries.

Disadvantages:

- slower writes,
- more coordination.

---

### 4.3.2 Asynchronous Index Maintenance

The table is updated first, and the index is updated later.

Advantages:

- faster writes,
- better throughput.

Disadvantages:

- index may be stale,
- queries may miss recent updates.

---

## 4.4 Performance Impact of Indexing

Indexes improve read performance but increase write cost.

| Benefit | Cost |
|---|---|
| Faster query execution | Slower updates |
| Reduced table scans | More storage |
| Better query flexibility | More maintenance |
| Covering indexes reduce I/O | Larger index size |

In distributed databases, global indexes can be especially expensive because they may require updates across multiple nodes.

---

## 5. Transactions

## 5.1 Meaning of a Transaction

A **transaction** is a logical unit of work that must be processed completely or not at all.

A transaction should satisfy the **ACID** properties:

1. **Atomicity**
   - Either all operations succeed, or none do.

2. **Consistency**
   - The database moves from one valid state to another.

3. **Isolation**
   - Concurrent transactions do not interfere incorrectly.

4. **Durability**
   - Once committed, changes survive failures.

---

## 5.2 Distributed Transactions

A distributed transaction is a transaction that accesses data stored on multiple nodes.

Example:

```text
Transfer money from account A on Node 1
to account B on Node 2
```

This requires coordination between nodes.

---

## 5.3 Two-Phase Commit Protocol

The most common protocol for distributed transactions is **Two-Phase Commit**, or **2PC**.

### Phase 1: Prepare

The coordinator asks all participants whether they are ready to commit.

```text
Coordinator → Participant A: prepare?
Coordinator → Participant B: prepare?
```

### Phase 2: Commit or Abort

If all participants agree, the transaction commits.

```text
Coordinator → Participants: commit
```

If any participant fails, the transaction aborts.

```text
Coordinator → Participants: abort
```

Advantages:

- ensures atomicity across nodes.

Disadvantages:

- blocking if coordinator fails,
- locks may be held for long time,
- poor availability during failures.

Performance impact:

- adds coordination overhead,
- increases latency,
- reduces throughput under contention.

---

## 5.4 Concurrency Control in Distributed Databases

Concurrency control ensures that multiple transactions can run safely.

Common methods include:

### 5.4.1 Lock-Based Concurrency Control

Transactions acquire locks before modifying data.

Advantages:

- prevents conflicts.

Disadvantages:

- reduces concurrency,
- may cause deadlocks.

---

### 5.4.2 Optimistic Concurrency Control

Advantages:

- good for low-contention workloads.

Disadvantages:

- many retries under high contention.

---

### 5.4.3 MVCC

**Multi-Version Concurrency Control** allows readers to see snapshots while writers create new versions.

Advantages:

- readers do not block writers,
- writers do not block readers.

Disadvantages:

- requires garbage collection,
- long transactions can cause version bloat.

---

## 5.5 Isolation Levels

Common isolation levels include:

1. **Read committed**
2. **Snapshot isolation**
3. **Serializable isolation**
4. **Strict serializability**

Stronger isolation provides better correctness but usually reduces performance.

---

## 5.6 Performance Impact of Transactions

Distributed transactions are expensive because they require coordination.

| Factor | Effect |
|---|---|
| Number of nodes involved | More coordination |
| Lock contention | Lower throughput |
| Transaction duration | Longer locks and more recovery work |
| Isolation level | Stronger isolation means more overhead |
| Network latency | Slower commit |
| Retries | Wasted work |

Best practice:

```text
Design the database so that most transactions are local to one partition.
```

## 6. Recovery

## 6.1 Meaning of Recovery

**Recovery** is the process of restoring the database to a correct state after a failure.

Failures may include:

- node failure,
- disk failure,
- network failure,
- site failure,
- process crash.

---

## 6.2 Recovery Goals

The main goals of recovery are:

1. **Durability**
   - Committed transactions must survive failures.

2. **Atomicity**
   - Incomplete transactions must be undone.

3. **Consistency**
   - The database must return to a valid state.

4. **Availability**
   - The system should recover quickly.

---

## 6.3 Write-Ahead Logging

A common recovery technique is **Write-Ahead Logging**, or **WAL**.

Before modifying data, the database writes the change to a log.

Example:

```text
Transaction begins
Log record written
Data page modified
Transaction commits
Log record marked committed
```

Advantages:

- ensures durability,

- helps replication.

Performance impact:

## 6.4 Checkpointing

A **checkpoint** records the database state at a point in time.

Advantages:

- reduces recovery time,

Disadvantages:

Performance impact:

- frequent checkpoints reduce recovery time but increase overhead,
- infrequent checkpoints improve throughput but increase recovery time.

## 6.5 Redo and Undo

During recovery, the system may need to:

1. **Redo**
   - Reapply committed transactions that were not fully written to disk.

2. **Undo**
   - Roll back transactions that were not committed.

This ensures that the database returns to a consistent state.

---

## 6.6 Replication-Based Recovery

Replication helps recovery by providing backup copies.

### Synchronous replication recovery

- Low data loss,
- Better consistency,
- Higher write latency.

### Asynchronous replication recovery

- Faster writes,
- Better availability,
- Possible data loss.

---

## 6.7 Snapshots and Backups

Distributed databases often use:

- full snapshots,
- incremental backups,
- continuous log archiving,
- point-in-time recovery.

Example:

```text
Snapshot at 00:00
WAL archived continuously
Restore database to 14:32
```

Advantages:

- protects against corruption,
- supports disaster recovery.

Disadvantages:

- storage cost,
- backup bandwidth,
- recovery time.

## 6.8 Failure Detection and Failover

The system must detect failures quickly and promote a new leader if needed.

Common mechanisms include:

- heartbeats,
- leases,
- consensus protocols,
- timeout-based detection.

Performance impact:

- too slow detection increases downtime,
- too fast detection may cause false failures.

## 7. Overall Performance Tradeoffs

A distributed database must balance several competing goals.

| Design Area | Benefit | Cost |
|---|---|---|
| Replication | Availability, durability | Latency, write amplification |
| Indexing | Faster reads | Slower writes, more storage |
| Transactions | Correctness | Coordination overhead |
