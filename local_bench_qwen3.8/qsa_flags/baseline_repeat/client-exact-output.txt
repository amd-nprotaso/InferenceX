A distributed database stores data across multiple machines, often in different locations, while presenting a unified logical database to applications. Its design must balance **scalability, availability, consistency, latency, throughput, and fault tolerance**. The major design areas are **replication, indexing, transactions, and recovery**, and each has direct performance consequences.

---

## 1. Overall Design of a Distributed Database

A distributed database typically involves several design decisions:

### 1.1 Data Distribution

Data can be distributed in several ways:

#### **Replication**
The same data is stored on multiple nodes.

Example:

```text
Node A: Orders table
Node B: Orders table
Node C: Orders table
```

Benefits:

- Higher availability
- Faster reads from nearby nodes
- Fault tolerance

Costs:

- Write amplification
- Synchronization overhead
- Conflict resolution complexity

---

#### **Partitioning / Sharding**
Data is split across nodes.

Example:

```text
Node A: Orders for customers in region 1
Node B: Orders for customers in region 2
Node C: Orders for customers in region 3
```

Benefits:

- Better write scalability
- Smaller local datasets
- Parallel query execution

Costs:

- Cross-node joins are expensive
- Hotspots can occur
- Rebalancing can be complex

---

#### **Hybrid Design**
Many systems combine replication and partitioning.

Example:

```text
Shard 1:
  Primary in US
  Replica in Europe
  Replica in Asia

Shard 2:
  Primary in US
  Replica in Europe
  Replica in Asia
```

This is common in large-scale systems because it supports both scalability and availability.

---

### 1.2 Transparency Goals

A good distributed database should provide:

| Transparency | Meaning |
|---|---|
| Location transparency | Users do not need to know where data is stored |
| Replication transparency | Users do not need to know how many copies exist |
| Fragmentation transparency | Users do not need to know how data is partitioned |
| Failure transparency | System continues despite node failures |
| Performance transparency | System should behave predictably despite distribution |

In practice, full transparency is difficult. Many systems expose some distribution details to improve performance.

---

### 1.3 Consistency Models

Distributed databases must choose how consistent reads and writes appear.

Common models:

| Model | Description | Performance Impact |
|---|---|---|
| Strong consistency | All nodes see the same data at the same logical time | Higher latency, lower availability during partitions |
| Eventual consistency | Replicas converge over time | Lower latency, higher availability, possible stale reads |
| Causal consistency | Preserves cause-effect relationships | Moderate complexity |
| Read-your-writes | A client sees its own writes | Useful for user sessions |
| Monotonic reads | Reads do not go backward in time | Prevents confusing behavior |
| Quorum consistency | Reads/writes require agreement from a subset of replicas | Tunable consistency and availability |

A common quorum rule is:

```text
N = number of replicas
W = number of replicas required for a write
R = number of replicas required for a read

If R + W > N, reads and writes overlap, giving strong consistency.
```

Example:

```text
N = 3
W = 2
R = 2

R + W = 4 > 3
```

This gives strong consistency with some fault tolerance.

---

## 2. Replication

Replication is one of the most important features of a distributed database. It improves availability, read performance, and fault tolerance.

---

## 2.1 Replication Architectures

### 2.1.1 Master-Slave / Primary-Replica

One node is the primary and accepts writes. Other nodes are replicas and serve reads.

```text
Client writes
    ↓
Primary
    ↓
Replica 1
Replica 2
Replica 3
```

Benefits:

- Simple conflict resolution
- Clear write ordering
- Easy to reason about consistency

Costs:

- Primary can become a bottleneck
- Write latency may increase if replication is synchronous
- Failover requires leader election

Performance considerations:

- Synchronous replication improves durability but increases write latency.
- Asynchronous replication improves write throughput but risks data loss.
- Read replicas can scale read-heavy workloads.

Example:

```text
Write latency = local write + network RTT to replicas
```

If the primary is in New York and replicas are in London and Singapore, synchronous replication may add significant latency.

---

### 2.1.2 Multi-Master / Multi-Primary

Multiple nodes can accept writes.

```text
Client A → Node 1
Client B → Node 2
Client C → Node 3
```

Benefits:

- Better write availability
- Lower latency for geographically distributed clients
- Useful for edge or mobile applications

Costs:

- Conflict resolution is complex
- Strong consistency is difficult
- Requires conflict-free data types or application-level logic

Common conflict resolution methods:

| Method | Description |
|---|---|
| Last write wins | Based on timestamp |
| Vector clocks | Track causality |
| CRDTs | Conflict-free replicated data types |
| Application merge | Application resolves conflicts |
| Quorum merge | Combine versions using rules |

Performance considerations:

- Multi-master can improve write availability but may reduce consistency guarantees.
- Conflict resolution can increase CPU and storage overhead.
- CRDTs can be efficient but may increase data size.

---

### 2.1.3 Quorum-Based Replication

Writes and reads require agreement from a subset of replicas.

Example:

```text
N = 5 replicas
W = 3
R = 3
```

A write succeeds if 3 replicas acknowledge. A read succeeds if 3 replicas respond.

Benefits:

- Tunable consistency
- Fault tolerance
- Can tolerate some node failures

Costs:

- Latency depends on slowest required replica
- Network partitions can block operations
- Requires careful replica placement

Performance considerations:

- If `W = 1`, writes are fast but may be lost.
- If `W = N`, writes are durable but slow.
- If `R = 1`, reads are fast but may be stale.
- If `R = N`, reads are consistent but slow.

---

## 2.2 Synchronous vs Asynchronous Replication

### Synchronous Replication

The primary waits for replicas to acknowledge before confirming the write.

```text
Client → Primary → Replica ACK → Client ACK
```

Benefits:

- Strong durability
- Less risk of data loss
- Easier failover

Costs:

- Higher write latency
- Throughput limited by network and replica speed
- More sensitive to slow replicas

---

### Asynchronous Replication

The primary confirms the write before replicas acknowledge.

```text
Client → Primary → Client ACK
Primary → Replica later
```

Benefits:

- Lower write latency
- Higher throughput
- Better geographic distribution

Costs:

- Replica lag
- Possible data loss if primary fails
- Reads may be stale

---

### Semi-Synchronous Replication

The primary waits for at least one replica to acknowledge.

Benefits:

- Compromise between durability and latency
- Better than fully asynchronous

Costs:

- Still depends on replica latency
- May require timeout handling

---

## 2.3 Replication and Performance

Replication affects performance in several ways:

### Read Scaling

Replicas can serve reads:

```text
Read throughput ≈ number of replicas × per-node read throughput
```

This is useful for read-heavy applications.

---

### Write Scaling

Replication does not usually increase write throughput. In fact, it can reduce it because each write may need to be sent to multiple nodes.

```text
Write cost = local write + replication fan-out
```

---

### Latency

Geographic replication introduces network latency.

Example:

```text
New York to London RTT ≈ 70 ms
New York to Singapore RTT ≈ 200 ms
```

Synchronous replication across continents can make writes slow.

---

### Hotspots

If one shard or primary receives most traffic, replication does not solve the problem.

Example:

```text
One popular product receives most writes
```

Solutions:

- Better partitioning
- Caching
- Write batching
- Splitting hot keys
- Using counters or aggregate tables

---

## 3. Indexing in Distributed Databases

Indexing is critical for query performance, but distributed indexing is more complex than single-node indexing.

---

## 3.1 Local vs Global Indexes

### Local Index

Each partition has its own index.

```text
Partition 1: Index for partition 1
Partition 2: Index for partition 2
Partition 3: Index for partition 3
```

Benefits:

- Index updates are local
- Easier to rebalance
- Better write scalability

Costs:

- Query may need to search many partitions
- Non-partition-key queries can be expensive

Example:

```sql
SELECT *
FROM orders
WHERE customer_id = 123;
```

If data is partitioned by `order_id`, but indexed locally by `customer_id`, the query may need to scan all partitions.

---

### Global Index

An index spans all partitions.

```text
Global index maps customer_id → partition/location
```

Benefits:

- Faster non-partition-key queries
- Can avoid scanning all partitions

Costs:

- Index updates may require distributed transactions
- Global index can become a bottleneck
- Rebalancing is more complex

Example:

```text
customer_id 123 → Shard 7
```

A global index can route the query directly to the correct shard.

---

## 3.2 Partitioned Indexes

Indexes can be partitioned by the same key as the data or by a different key.

### Same-key partitioning

```text
Data partitioned by customer_id
Index partitioned by customer_id
```

Benefits:

- Index updates are local
- Good for queries filtered by partition key

Costs:

- Poor for queries on other fields

---

### Different-key partitioning

```text
Data partitioned by customer_id
Index partitioned by order_date
```

Benefits:

- Better for time-range queries

Costs:

- Index updates may cross partitions
- More complex consistency

---

## 3.3 Secondary Indexes

Secondary indexes are indexes on non-primary-key columns.

Example:

```sql
CREATE INDEX idx_email ON users(email);
```

In a distributed database, secondary indexes can be implemented as:

| Approach | Description |
|---|---|
| Local secondary index | Index stored with each partition |
| Global secondary index | Separate index table across nodes |
| Search index | External search engine or inverted index |
| Materialized view | Precomputed query result |

Performance considerations:

- Local indexes are faster to update but slower for global queries.
- Global indexes are faster for queries but slower to update.
- Search indexes are good for text, geospatial, or complex predicates.

---

## 3.4 Distributed Index Structures

Common index structures include:

### B-Tree Indexes

Good for:

- Range queries
- Equality queries
- Sorted access

In distributed systems, B-tree indexes are often local to partitions.

---

### Hash Indexes

Good for:

- Equality queries
- Fast point lookups

Poor for:

- Range queries

Example:

```text
customer_id = 123
```

---

### LSM Trees

Log-structured merge trees are common in distributed key-value stores.

Benefits:

- High write throughput
- Good for append-heavy workloads

Costs:

- Background compaction
- Read amplification
- More complex maintenance

Examples:

- Cassandra
- RocksDB
- HBase
- Bigtable-style systems

---

### Inverted Indexes

Used for full-text search.

Example:

```text
"database" → documents containing "database"
```

Benefits:

- Excellent for text search
- Supports relevance ranking

Costs:

- Large index size
- Update overhead
- Requires distributed coordination

---

## 3.5 Indexing and Query Performance

Distributed query performance depends heavily on index design.

### Good Query Pattern

```sql
SELECT *
FROM orders
WHERE customer_id = 123;
```

If data is partitioned by `customer_id`, the query can go to one partition.

Performance:

```text
Low latency
Low network traffic
High throughput
```

---

### Bad Query Pattern

```sql
SELECT *
FROM orders
WHERE order_date BETWEEN '2024-01-01' AND '2024-01-31';
```

If data is partitioned by `customer_id`, this query may scan all partitions.

Performance:

```text
High latency
High network traffic
High CPU
Poor scalability
```

Solutions:

- Partition by date
- Add global index
- Use materialized view
- Use search index
- Pre-aggregate data

---

## 3.6 Covering Indexes

A covering index contains all columns needed by a query.

Example:

```sql
CREATE INDEX idx_customer_name_email
ON users(customer_id, name, email);
```

Query:

```sql
SELECT name, email
FROM users
WHERE customer_id = 123;
```

The database can answer the query from the index without accessing the main table.

Benefits:

- Fewer disk accesses
- Lower latency
- Better throughput

Costs:

- Larger index
- More write overhead

---

## 4. Transactions in Distributed Databases

Transactions must preserve ACID properties across multiple nodes.

ACID means:

| Property | Meaning |
|---|---|
| Atomicity | All-or-nothing execution |
| Consistency | Database moves from one valid state to another |
| Isolation | Concurrent transactions do not interfere incorrectly |
| Durability | Committed data survives failures |

In distributed systems, ACID is harder because nodes can fail, networks can partition, and clocks may be unsynchronized.

---

## 4.1 Distributed Transactions

A distributed transaction may touch multiple partitions or nodes.

Example:

```sql
UPDATE accounts
SET balance = balance - 100
WHERE account_id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE account_id = 2;
```

If account 1 and account 2 are on different nodes, the transaction is distributed.

---

## 4.2 Two-Phase Commit, 2PC

Two-phase commit is a classic protocol for distributed atomic commit.

### Phase 1: Prepare

Coordinator asks all participants:

```text
Can you commit?
```

Each participant writes a prepare record and replies yes or no.

### Phase 2: Commit or Abort

If all participants vote yes:

```text
Coordinator sends COMMIT
```

If any participant votes no:

```text
Coordinator sends ABORT
```

Benefits:

- Atomicity across nodes
- Widely understood

Costs:

- High latency
- Coordinator can become bottleneck
- Blocking if coordinator fails
- Poor availability during network partitions

Performance impact:

```text
Transaction latency = local execution + prepare round trip + commit round trip
```

2PC can significantly reduce throughput, especially across regions.

---

## 4.3 Three-Phase Commit, 3PC

3PC adds a pre-commit phase to reduce blocking.

Phases:

1. Can commit?
2. Pre-commit
3. Commit

Benefits:

- Less blocking than 2PC in some cases

Costs:

- More complex
- Still not safe under all network partitions
- Rarely used in practice

---

## 4.4 Paxos and Raft

Modern distributed databases often use consensus protocols such as Paxos or Raft instead of traditional 2PC.

These protocols replicate a log of operations across a majority of nodes.

Example:

```text
Leader proposes operation
Majority of replicas acknowledge
Operation is committed
```

Benefits:

- Strong consistency
- Fault tolerance
- Leader election
- Better availability than naive 2PC

Costs:

- Majority quorum required
- Write latency depends on network
- Throughput limited by leader

Examples:

- Google Spanner
- CockroachDB
- TiDB
- etcd
- MongoDB replica sets
- Cassandra lightweight transactions

---

## 4.5 Concurrency Control

Distributed databases must control concurrent access.

### Lock-Based Protocols

Transactions acquire locks on data.

Example:

```text
Transaction A locks row 1
Transaction B waits for row 1
```

Benefits:

- Strong isolation
- Easy to reason about

Costs:

- Lock contention
- Deadlocks
- Reduced throughput

---

### Optimistic Concurrency Control

Transactions execute without locks and validate at commit time.

Benefits:

- High throughput when conflicts are rare

Costs:

- Aborts when conflicts are frequent
- Validation overhead

---

### Multi-Version Concurrency Control, MVCC

Readers see snapshots of data.

Benefits:

- Readers do not block writers
- Better concurrency
- Good for analytical and transactional workloads

Costs:

- Version storage
- Garbage collection
- Snapshot isolation anomalies

---

### Isolation Levels

Common isolation levels:

| Isolation Level | Description |
|---|---|
| Read uncommitted | May read uncommitted data |
| Read committed | Reads only committed data |
| Repeatable read | Same query returns same result in transaction |
| Snapshot isolation | Transaction sees consistent snapshot |
| Serializable | Behaves as if transactions ran one at a time |

Higher isolation usually means lower performance.

---

## 4.6 Distributed Isolation and Clocks

Distributed transactions need a way to order events.

Options:

### Logical Clocks

Use counters or Lamport clocks.

Benefits:

- No hardware clock dependency

Costs:

- May not reflect real time
- Complex causality tracking

---

### TrueTime / Hybrid Logical Clocks

Systems like Spanner use hardware clocks with uncertainty bounds.

Benefits:

- Serializable transactions across regions
- Global ordering

Costs:

- Requires careful clock synchronization
- Commit latency may depend on clock uncertainty

---

## 4.7 Transaction Performance

Transaction performance depends on:

### Number of Participants

More nodes involved means more coordination.

```text
1 node: fast
2 nodes: slower
10 nodes: much slower
```

---

### Network Latency

Cross-region transactions are expensive.

Example:

```text
Same data center: 0.1–1 ms
Same region: 1–10 ms
Different continents: 50–250 ms
```

---

### Conflict Rate

High conflict rates cause:

- Lock waits
- Aborts
- Retries
- Lower throughput

---

### Transaction Size

Large transactions are harder to commit atomically.

Better design:

- Keep transactions small
- Avoid cross-region transactions
- Batch writes carefully
- Use idempotency keys

---

## 5. Recovery in Distributed Databases

Recovery ensures that committed transactions survive failures and that the database can return to a consistent state.

---

## 5.1 Logging

Most databases use write-ahead logging, WAL.

Before modifying data, the database writes a log record.

Example:

```text
BEGIN
UPDATE account 1
UPDATE account 2
COMMIT
```

Benefits:

- Durability
- Crash recovery
- Replication source
- Point-in-time recovery

Costs:

- Log writes add latency
- Log storage grows
- Requires log rotation and archiving

---

## 5.2 Checkpointing

A checkpoint records the state of the database at a point in time.

Benefits:

- Faster recovery
- Reduces amount of log to replay

Costs:

- Checkpoint overhead
- May require flushing dirty pages

---

## 5.3 Crash Recovery

After a crash, the database uses logs to recover.

Typical process:

1. Find last checkpoint.
2. Redo committed transactions.
3. Undo uncommitted transactions.

Example:

```text
Committed transactions → redo
Uncommitted transactions → undo
```

In distributed systems, recovery must also handle:

- Partially committed distributed transactions
- Missing coordinator state
- Replica divergence
- Network partitions

---

## 5.4 Distributed Recovery Challenges

### Coordinator Failure

If the transaction coordinator fails, participants may not know whether to commit or abort.

Solutions:

- Write-ahead logging
- Stable storage
- Recovery protocol
- Consensus-based commit

---

### Replica Divergence

Replicas may have different logs after failures.

Solutions:

- Consensus protocols
- Log truncation
- Snapshot transfer
- Repair processes

---

### Network Partitions

Some nodes may be unreachable.

Solutions:

- Majority quorum
- Fencing
- Leader election
- Read-only partitions
- Conflict resolution

---

## 5.5 Snapshots and Backups

Distributed databases often use snapshots.

Benefits:

- Fast restore
- Point-in-time recovery
- Disaster recovery

Costs:

- Storage overhead
- Coordination across nodes
- Consistency challenges

A consistent distributed snapshot may require:

- Pausing writes
- Using consistent transaction timestamps
- Coordinating across partitions
- Using MVCC snapshots

---

## 5.6 Point-in-Time Recovery

Point-in-time recovery allows restoring the database to a specific time.

Example:

```text
Restore to 2024-06-01 12:00:00
```

Requirements:

- Base snapshot
- Transaction logs
- Timestamp ordering
- Consistent replay

Performance impact:

- Recovery time depends on log volume
- Large logs require more replay
- Incremental backups reduce recovery time

---

## 5.7 Failure Detection and Recovery

Distributed databases need failure detection.

Common methods:

| Method | Description |
|---|---|
| Heartbeats | Nodes periodically send status |
| Lease-based membership | Nodes renew leases |
| Gossip protocols | Nodes exchange membership information |
| Consensus leader election | Majority selects leader |

Performance considerations:

- Too frequent heartbeats increase overhead.
- Too infrequent heartbeats delay failure detection.
- False positives can cause unnecessary failover.

---

## 6. Performance Analysis of Distributed Databases

Distributed database performance is usually measured by:

| Metric | Meaning |
|---|---|
| Latency | Time to complete an operation |
| Throughput | Operations per second |
| Scalability | Performance as nodes increase |
| Availability | Percentage of time system is usable |
| Durability | Probability committed data survives failure |
| Consistency | How up-to-date reads are |
| Fault tolerance | Ability to survive failures |

---

## 6.1 Latency

Latency includes:

```text
Client → Network → Coordinator → Participants → Replicas → Client
```

Major sources of latency:

- Network round trips
- Lock waits
- Replication acknowledgments
- Index lookups
- Disk I/O
- Garbage collection
- Consensus majority waits

Example:

```text
Local write: 0.1 ms
Same-region replication: 1–5 ms
Cross-region synchronous replication: 50–250 ms
```

---

## 6.2 Throughput

Throughput depends on concurrency and latency.

Approximate relationship:

```text
Throughput ≈ Concurrency / Latency
```

If latency increases, throughput decreases unless concurrency increases.

---

## 6.3 Scalability

Distributed databases can scale in two ways:

### Vertical Scaling

Add more resources to one node.

Benefits:

- Simple

Costs:

- Limited
- Expensive

---

### Horizontal Scaling

Add more nodes.

Benefits:

- Better scalability
- More fault tolerance

Costs:

- Complexity
- Coordination overhead

---

## 6.4 Read vs Write Scaling

### Reads

Reads can often scale well using:

- Replicas
- Caching
- Partitioning
- Local indexes

---

### Writes

Writes are harder to scale because of:

- Replication
- Consensus
- Locking
- Index maintenance
- Transaction coordination

---

## 6.5 Hotspots

Hotspots occur when one partition receives disproportionate traffic.

Example:

```text
One customer has millions of orders
One product is extremely popular
One timestamp bucket receives most writes
```

Solutions:

- Better partition keys
- Salting keys
- Splitting hot ranges
- Caching
- Write batching
- Aggregation tables

---

## 6.6 Network Bottlenecks

Distributed databases are often network-bound.

Common network-heavy operations:

- Replication
- Distributed joins
- Distributed transactions
- Consensus
- Cross-partition queries
- Rebalancing

Optimizations:

- Co-locate related data
- Use local indexes
- Reduce cross-node joins
- Batch network messages
- Compress data
- Use connection pooling
- Place replicas near clients

---

## 7. Design Tradeoffs

Distributed database design is full of tradeoffs.

### Consistency vs Availability

Strong consistency often reduces availability during partitions.

Eventual consistency improves availability but may return stale data.

---

### Latency vs Durability

Synchronous replication improves durability but increases latency.

Asynchronous replication improves latency but risks data loss.

---

### Read Performance vs Write Performance

More indexes improve reads but slow writes.

Replicas improve reads but add write overhead.

---

### Partitioning vs Query Flexibility

Partitioning improves scalability but makes some queries expensive.

Global indexes improve query flexibility but increase write complexity.

---

### Simplicity vs Scalability

Single-node databases are simpler.

Distributed databases are more scalable but harder to operate.

---

## 8. Example Design: E-Commerce Distributed Database

Suppose an e-commerce system needs:

- High read throughput
- High write throughput
- Strong consistency for payments
- Global availability

Possible design:

### Data Model

```text
Customers partitioned by customer_id
Orders partitioned by customer_id
Payments partitioned by payment_id
Inventory partitioned by product_id
```

### Replication

```text
Each shard has:
- 1 primary
- 2 synchronous replicas in same region
- 1 asynchronous replica in another region
```

### Indexing

```text
Local index on customer_id
Global index on order_id
Search index for product search
```

### Transactions

```text
Payment transactions use consensus-based commit
Inventory updates use optimistic concurrency
Reads use snapshot isolation
```

### Recovery

```text
Write-ahead logging
Periodic snapshots
Point-in-time recovery
Automatic failover
```

Performance result:

- Customer reads are fast
- Payment writes are consistent but slower
- Product search is scalable
- Regional failures are tolerated
- Cross-region reads may be stale

## 9. Best Practices

### 1. Choose a Partition Key Carefully

The partition key determines scalability and query performance.

Good partition keys:

- Evenly distributed
- Frequently used in queries
- Avoid hotspots

Bad partition keys:

- Sequential IDs
- Low-cardinality fields
- Fields that create hotspots

---

### 2. Prefer Local Transactions

Cross-node transactions are expensive.

Design data so related rows are on the same partition.

Example:

```text
Partition by customer_id
Store customer, orders, and addresses together
```

---

### 3. Use Replicas for Reads

Read replicas can dramatically improve read throughput.

But be aware of replica lag.

---

### 4. Avoid Synchronous Cross-Region Writes

Synchronous replication across continents can cause high latency.

Use:

- Regional primaries
- Asynchronous cross-region replicas
- Application-level eventual consistency

---

### 5. Keep Transactions Small

Large distributed transactions are slow and prone to failure.

---

### 6. Use Idempotency

Network failures can cause retries.

Idempotent operations prevent duplicate effects.

Example:

```text
payment_id = unique request ID
```

---

### 7. Monitor Latency and Replication Lag

Important metrics:

- p50, p95, p99 latency
- Replication lag
- Lock wait time
- Transaction abort rate
- Disk I/O
- Network traffic
- Leader elections
- Partition hotspots

---

## 10. Summary

A distributed database is designed to provide scalability, availability, and fault tolerance by distributing data across multiple nodes. Its performance depends heavily on how replication, indexing, transactions, and recovery are implemented.

### Replication

- Improves availability and read performance.
- Adds write overhead and latency.
- Synchronous replication is safer but slower.
- Asynchronous replication is faster but risks stale reads or data loss.
- Quorum-based systems allow tunable consistency.

### Indexing

- Local indexes are efficient for partition-key queries.
- Global indexes improve non-partition-key queries but add complexity.
- Indexes improve reads but slow writes.
- Poor indexing can force full distributed scans.

### Transactions

- Distributed transactions require coordination.
- 2PC provides atomicity but can be slow and blocking.
