## Distributed Database Design and Performance

A **distributed database** stores data across multiple physical nodes connected by a network, while presenting a unified logical database to applications. Its design must balance **scalability, availability, consistency, latency, throughput, fault tolerance, and operational complexity**. The main design areas are **replication, indexing, transactions, and recovery**.

---

## 1. Core Design Goals

A distributed database is usually designed around these goals:

| Goal | Meaning |
|---|---|
| **Scalability** | Handle more data, users, or queries by adding nodes |
| **Availability** | Continue serving requests despite node or network failures |
| **Consistency** | Ensure users see correct and predictable data |
| **Latency** | Minimize time to read/write data |
| **Throughput** | Maximize operations per second |
| **Fault tolerance** | Survive disk, node, rack, zone, or region failures |
| **Transparency** | Hide distribution complexity from applications |

A major design tension is the **CAP theorem**:

- **Consistency**: all nodes see the same data at the same time.
- **Availability**: every request receives a response, even if some nodes fail.
- **Partition tolerance**: the system continues operating despite network partitions.

In real distributed systems, partitions can happen, so the practical choice is often between **strong consistency** and **high availability** during failures.

---

## 2. Architectural Design

Distributed databases are commonly built using one or more of these techniques:

### A. Partitioning / Sharding

Data is divided into smaller units called **partitions** or **shards**.

Common partitioning strategies:

| Strategy | Description | Pros | Cons |
|---|---|---|---|
| **Hash partitioning** | Assign shard by hash of key | Even distribution | Range queries harder |
| **Range partitioning** | Assign shard by key range | Efficient range scans | Hotspots possible |
| **Directory-based** | Lookup table maps keys to shards | Flexible | Lookup overhead |
| **Geographic partitioning** | Data placed near users | Low latency | Complex consistency |

Example:

```text
User IDs 0–999      → Shard A
User IDs 1000–1999  → Shard B
User IDs 2000–2999  → Shard C
```

Partitioning improves performance by allowing parallel processing and reducing the amount of data each node must manage.

---

### B. Replication

Each shard is usually replicated across multiple nodes for fault tolerance and read scalability.

A typical design:

```text
Shard 1:
  Leader replica
  Follower replica 1
  Follower replica 2

Shard 2:
  Leader replica
  Follower replica 1
  Follower replica 2
```

The **leader** handles writes, while followers can serve reads or act as failover candidates.

---

### C. Query Processing

A distributed query engine may:

1. Parse the query.
2. Plan execution across shards.
3. Push filters/projections to nodes.
4. Execute local scans or index lookups.
5. Combine results.
6. Return final result.

Good design pushes computation close to data to reduce network transfer.

Example:

```sql
SELECT name
FROM users
WHERE country = 'India';
```

Instead of scanning all nodes, the system can use partitioning or indexes to query only relevant shards.

---

## 3. Replication

Replication is one of the most important design choices in a distributed database.

### Why Replicate?

Replication provides:

- **High availability**
- **Fault tolerance**
- **Read scalability**
- **Low-latency local reads**
- **Disaster recovery**
- **Geographic distribution**

---

## 4. Replication Models

### A. Single-Leader Replication

One node is the **leader**. All writes go to the leader. Followers replicate the leader’s write log.

```text
Client write → Leader → Followers
Client read  → Leader or Followers
```

#### Advantages

- Simple design.
- Strong ordering of writes.
- Easy conflict resolution.
- Good for transactional workloads.

#### Disadvantages

- Leader can become a bottleneck.
- Leader failure requires election.
- Followers may lag.
- Cross-region writes can be slow.

#### Performance Impact

- Write latency depends on leader location and replication mode.
- Read throughput can scale by adding followers.
- Stale reads may occur if clients read from lagging followers.

---

### B. Multi-Leader Replication

Multiple nodes can accept writes, usually in different regions.

```text
Client in Region A → Leader A
Client in Region B → Leader B
Leaders replicate changes to each other
```

#### Advantages

- Low write latency for local users.
- Better availability during network partitions.
- Useful for global applications.

#### Disadvantages

- Write conflicts are possible.
- Conflict resolution is complex.
- Strong consistency is harder.
- Causal consistency may be required.

#### Conflict Resolution Strategies

| Strategy | Description |
|---|---|
| Last-write-wins | Use timestamp; latest write wins |
| Version vectors | Track causality and detect conflicts |
| CRDTs | Mergeable data types for automatic convergence |
| Application-level merge | Application resolves conflicts |
| Manual resolution | Human intervention |

#### Performance Impact

- Better regional write latency.
- More background replication traffic.
- Higher CPU and storage overhead due to conflict detection.
- Can improve availability but may reduce consistency guarantees.

---

### C. Leaderless Replication

Any node can accept writes. The system uses quorums to coordinate reads and writes.

```text
Write to replicas R, W
Read from replicas R, W
```

A common rule:

```text
R + W > N
```

where:

- `N` = total replicas
- `W` = number of replicas that must acknowledge a write
- `R` = number of replicas consulted for a read

Example:

```text
N = 3
W = 2
R = 2
```

This ensures at least one replica overlap between reads and writes.

#### Advantages

- High availability.
- No single leader bottleneck.
- Tolerates some node failures.

#### Disadvantages

- Complex consistency.
- Stale reads possible.
- Requires anti-entropy and repair mechanisms.
- Harder to implement strong transactions.

#### Performance Impact

- Can provide low latency if clients access nearby replicas.
- May require reading multiple replicas, increasing read cost.
- Background repair consumes bandwidth and CPU.

---

## 5. Synchronous vs Asynchronous Replication

### Synchronous Replication

The leader waits for followers to acknowledge before confirming the write.

```text
Client → Leader → Followers acknowledge → Client
```

#### Pros

- Strong durability.
- Less risk of data loss.
- Better consistency.

#### Cons

- Higher write latency.
- Slower if followers are remote.
- Availability may drop if followers are unreachable.

---

### Asynchronous Replication

The leader confirms the write before followers apply it.

```text
Client → Leader → Client
Leader → Followers later
```

#### Pros

- Lower write latency.
- Better throughput.
- More available during follower failures.

#### Cons

- Followers may lag.
- Data loss possible if leader fails before replication.
- Stale reads possible.

---

### Semi-Synchronous Replication

The leader waits for at least one follower to acknowledge receipt of the log record, but not necessarily completion of apply.

This is a compromise between durability and latency.

---

## 6. Replication Performance Considerations

### Write Amplification

Each write may be sent to multiple replicas.

```text
1 logical write → multiple physical writes
```

This increases:

- Network bandwidth
- Disk I/O
- CPU usage
- Storage consumption

### Read Amplification

Leaderless or quorum systems may require multiple replicas to answer a read.

### Replication Lag

Followers may be behind the leader. This affects:

- Read-your-writes consistency
- Session consistency
- Monitoring
- Failover correctness

### Hotspots

If one shard or key receives disproportionate traffic, replication does not solve the bottleneck.

Example:

```text
Trending product ID = 1001
All users read/write same row
```

Solutions:

- Split hot keys.
- Use caching.
- Use counters with sharding.
- Use request coalescing.
- Use materialized views.

---

## 7. Indexing in Distributed Databases

Indexes are critical for performance, but in distributed systems they are more complex than in single-node databases.

### Why Indexes Matter

Without indexes, queries may require full scans across many shards.

Example:

```sql
SELECT *
FROM orders
WHERE customer_id = 42;
```

If data is partitioned by `order_id`, this query may scan all shards unless there is an index or secondary partitioning.

---

## 8. Types of Distributed Indexes

### A. Local Indexes

Each shard maintains its own index.

```text
Shard A: local index on customer_id
Shard B: local index on customer_id
Shard C: local index on customer_id
```

#### Pros

- Simple.
- Low coordination.
- Good for shard-local queries.

#### Cons

- Query may need to search all shards.
- Global uniqueness is harder.
- Cross-shard queries can be expensive.

---

### B. Global Indexes

A separate index structure maps keys to shards.

```text
Global index:
customer_id 42 → Shard B
customer_id 87 → Shard A
```

#### Pros

- Efficient point lookups.
- Can avoid scanning all shards.
- Useful for secondary keys.

#### Cons

- Index updates may require distributed transactions.
- Global index can become a bottleneck.
- More complex failure handling.

---

### C. Partitioned Global Indexes

The global index itself is partitioned across nodes.

```text
Global index shard 1: customer_id 0–999
Global index shard 2: customer_id 1000–1999
```

This improves scalability but adds complexity.

---

## 9. Index Maintenance in Distributed Systems

Every write may require updating multiple structures:

```text
Write to table
→ update primary key index
→ update secondary indexes
→ update global index
→ replicate to followers
```

This creates **write amplification**.

Example:

```text
Insert into users
Update users_pkey
Update users_email_index
Update users_country_index
Replicate to 2 followers
```

Performance impact:

- More disk writes.
- More network traffic.
- More lock contention.
- Higher latency.

---

## 10. Index Design Strategies

### Use Covering Indexes

A covering index includes all columns needed by a query.

```sql
CREATE INDEX idx_user_country_name
ON users(country, name);
```

This can avoid fetching the base table.

### Use Partial Indexes

Index only relevant rows.

```sql
CREATE INDEX idx_active_users
ON users(email)
WHERE status = 'active';
```

This reduces index size and maintenance cost.

### Use Composite Indexes Carefully

Column order matters.

```sql
CREATE INDEX idx_orders_customer_date
ON orders(customer_id, order_date);
```

This supports queries like:

```sql
WHERE customer_id = 42
AND order_date > '2024-01-01';
```

But it may not efficiently support:

```sql
WHERE order_date > '2024-01-01';
```

### Avoid Too Many Secondary Indexes

Each index increases write cost.

A common rule:

- Few indexes for write-heavy systems.
- More indexes for read-heavy systems.
- Use materialized views or search engines for complex analytics.

---

## 11. Distributed Index Performance Issues

### Cross-Shard Index Updates

If a global index is stored separately, updating it may require a distributed transaction.

```text
Update row in Shard A
Update global index in Shard X
```

This can increase latency and failure complexity.

### Index Hotspots

A global index may become a bottleneck if many writes affect the same index range.

Example:

```text
All inserts have customer_id near 1000
```

Solutions:

- Hash-partition the index.
- Split hot ranges.
- Use batching.
- Use asynchronous index maintenance if consistency allows.

### Stale Indexes

If indexes are updated asynchronously, queries may return stale results.

This is common in search engines and analytics systems.

---

## 12. Transactions in Distributed Databases

A distributed transaction involves operations across multiple nodes or shards.

Example:

```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

If account 1 and account 2 are on different shards, this is a distributed transaction.

---

## 13. ACID in Distributed Systems

Distributed databases often aim to preserve ACID properties:

| Property | Meaning |
|---|---|
| **Atomicity** | All operations succeed or none do |
| **Consistency** | Database remains in a valid state |
| **Isolation** | Concurrent transactions do not interfere incorrectly |
| **Durability** | Committed data survives failures |

In distributed systems, ACID is harder because failures can occur between nodes.

---

## 14. Two-Phase Commit

The classic protocol for distributed atomic commit is **Two-Phase Commit**, or **2PC**.

### Participants

- **Coordinator**: manages the transaction.
- **Participants**: nodes holding data involved in the transaction.

### Phase 1: Prepare

Coordinator asks participants:

```text
Can you commit?
```

Each participant:

- Locks resources.
- Writes redo/undo logs.
- Replies yes or no.

### Phase 2: Commit or Abort

If all participants vote yes:

```text
Coordinator sends COMMIT
Participants commit
```

If any participant votes no:

```text
Coordinator sends ABORT
Participants roll back
```

### Advantages

- Provides atomicity across nodes.
- Simple conceptual model.
- Used in many relational distributed databases.

### Disadvantages

- Blocking if coordinator fails.
- Participants may hold locks while waiting.
- High latency due to multiple round trips.
- Poor availability during network partitions.

---

## 15. Three-Phase Commit

Three-Phase Commit adds a pre-commit phase to reduce blocking.

Phases:

1. Can commit?
2. Pre-commit?
3. Commit?

It improves fault tolerance but is complex and still not perfect in asynchronous networks.

---

## 16. Consensus-Based Transactions

Modern distributed databases often use consensus protocols such as:

- **Paxos**
- **Raft**
- **Zab**

These protocols help replicate logs and elect leaders.

They are used for:

- Leader election
- Metadata management
- Replicated state machines
- Distributed locks
- Transaction log replication

Consensus does not automatically provide full distributed transactions, but it is a foundation for building them.

---

## 17. Concurrency Control

Distributed databases must control concurrent access.

### Lock-Based Concurrency Control

Transactions acquire locks on rows, pages, tables, or ranges.

Example:

```text
Transaction A locks row 1
Transaction B waits for row 1
```

#### Two-Phase Locking

A transaction must acquire locks before releasing any lock.

This can ensure serializability but may cause deadlocks.

#### Deadlock Handling

Methods:

- Timeout
- Wait-for graph
- Deadlock detection
- Prevention by lock ordering

### Optimistic Concurrency Control

Transactions execute without locks and validate at commit time.

Phases:

1. Read
2. Validate
3. Write

#### Pros

- Good for low-conflict workloads.
- Less lock waiting.

#### Cons

- High abort rate under contention.
- Validation can be expensive across nodes.

### Multi-Version Concurrency Control

MVCC keeps multiple versions of data.

Readers see a snapshot, writers create new versions.

#### Pros

- Readers do not block writers.
- Writers do not block readers.
- Good for mixed read/write workloads.

#### Cons

- Requires garbage collection of old versions.
- Snapshot isolation may allow anomalies.
- Distributed MVCC is complex.

---

## 18. Isolation Levels

Common isolation levels:

| Level | Description |
|---|---|
| **Read uncommitted** | May read uncommitted data |
| **Read committed** | Reads only committed data |
| **Repeatable read** | Same transaction sees same values |
| **Snapshot isolation** | Transaction sees consistent snapshot |
| **Serializable** | Transactions behave as if executed one at a time |

In distributed systems, stronger isolation usually means more coordination and higher latency.

---

## 19. Distributed Transaction Performance

Distributed transactions are expensive because they require:

- Multiple network round trips.
- Locks across nodes.
- Log flushing on multiple nodes.
- Coordination during commit.
- Failure detection and recovery.

### Latency Example

A local transaction may take:

```text
1 ms
```

A distributed transaction across regions may take:

```text
50–200 ms
```

depending on distance and protocol.

### Throughput Impact

Throughput may drop because:

- Locks are held longer.
- Coordinators become bottlenecks.
- Participants wait for votes.
- Network failures cause retries.

### Design Strategies

To improve performance:

- Keep transactions small.
- Co-locate related data.
- Use sharding keys that match transaction patterns.
- Avoid cross-shard transactions when possible.
- Use idempotent operations.
- Use asynchronous workflows for long operations.
- Use optimistic concurrency for low-conflict workloads.
- Use batched commits.

---

## 20. Recovery in Distributed Databases

Recovery ensures that committed transactions survive failures and incomplete transactions are rolled back.

Distributed recovery is harder because failures can happen:

- During transaction execution.
- During commit.
- During replication.
- During index updates.
- During leader election.
- During network partitions.

---

## 21. Write-Ahead Logging

A common recovery mechanism is **Write-Ahead Logging**, or WAL.

Rule:

```text
Log record must be durable before data changes are applied.
```

For each transaction, the log records:

- Transaction start
- Before-image
- After-image
- Commit
- Abort
- Checkpoint

### Redo and Undo

During recovery:

- **Redo**: reapply committed changes that may not be on disk.
- **Undo**: roll back uncommitted changes.

Example:

```text
T1 committed but page not flushed → redo T1
T2 not committed → undo T2
```

---

## 22. Checkpointing

Checkpointing periodically writes dirty pages to disk and records a consistent state.

Benefits:

- Reduces recovery time.
- Limits log growth.
- Provides a known consistent point.

Without checkpoints, recovery may need to scan the entire log.

---

## 23. Recovery in Replicated Systems

In replicated databases, recovery must coordinate multiple replicas.

### Leader Failure

If the leader fails:

1. Followers detect failure.
2. A new leader is elected.
3. The new leader chooses the most up-to-date log.
4. Followers align with the new leader.
5. Clients reconnect.

### Follower Failure

A follower can recover by:

- Copying the leader’s log.
- Applying missing log records.
- Rejoining the replication group.

### Network Partition

If replicas cannot communicate:

- The system may block writes to preserve consistency.
- Or it may allow writes in each partition and resolve conflicts later.

This is the CAP tradeoff.

---

## 24. Recovery and Two-Phase Commit

2PC recovery is complex because participants may be in uncertain states.

Example:

```text
Coordinator sends PREPARE
Participant votes YES
Coordinator crashes before sending COMMIT
```

The participant does not know whether to commit or abort.

### Solutions

- Write-ahead logging.
- Coordinator logging.
- Timeout and recovery protocols.
- Heuristic decisions, though risky.
- Consensus-based commit protocols.

---

## 25. Consensus and Recovery

Modern systems often use consensus to make recovery safer.

Example with Raft:

- Nodes replicate a log.
- A leader is elected.
- A majority must acknowledge log entries.
- Committed entries are durable and safe across leader changes.

This helps avoid situations where two leaders commit conflicting data.

---

## 26. Recovery Performance

Recovery performance depends on:

- Log size.
- Checkpoint frequency.
- Amount of dirty data.
- Number of transactions in flight.
- Replication lag.
- Network speed.
- Disk throughput.
- Number of failed nodes.

### Fast Recovery Design

To recover quickly:

- Use frequent checkpoints.
- Keep logs compact.
- Use fast storage.
- Limit transaction size.
- Use parallel recovery.
- Keep replicas synchronized.
- Use consensus protocols with bounded log gaps.

---

## 27. Performance Design Principles

### A. Data Locality

Place related data on the same node when possible.

Example:

```text
User profile and user settings on same shard
```

This reduces distributed transactions and network hops.

---

### B. Query Locality

Route queries to the nearest replica when consistency allows.

Example:

```text
User in Europe reads from Europe replica
```

This reduces latency.

---

### C. Parallelism

Execute independent operations in parallel.

Example:

```text
Query 10 shards in parallel
Combine results
```

This improves scan and aggregation performance.

---

### D. Pushdown Processing

Push filters, projections, and aggregations to storage nodes.

Instead of:

```text
Send all rows to query engine
```

Use:

```text
Filter rows at storage node
Send only matching rows
```

This reduces network traffic.

---

### E. Caching

Use caches for hot data.

Examples:

- In-memory cache
- Result cache
- Query plan cache
- Metadata cache

Caches improve latency but introduce invalidation complexity.

---

### F. Batching

Batch writes and reads to reduce network overhead.

Example:

```text
1000 small writes → one batched write
```

This improves throughput but may increase latency.

---

### G. Backpressure

Prevent overload by limiting requests when nodes are saturated.

Without backpressure, queues grow and latency explodes.

---

## 28. Tradeoffs in Distributed Database Design

| Design Choice | Benefit | Cost |
|---|---|---|
| More replicas | Availability, durability | Storage, write amplification |
| Synchronous replication | Consistency, durability | Latency |
| Asynchronous replication | Low latency, throughput | Stale reads, data loss risk |
| Global indexes | Fast secondary lookups | Distributed updates |
| Strong consistency | Predictable behavior | Lower availability, higher latency |
| Eventual consistency | Availability, low latency | Complex application logic |
| Sharding | Scalability | Cross-shard complexity |
| Caching | Low latency | Invalidation complexity |
| Distributed transactions | Correctness | High latency, coordination cost |

---

## 29. Example: Designing a Distributed Banking Database

Suppose we need a distributed database for bank accounts.

### Requirements

- Strong consistency.
- No lost updates.
- High availability.
- Fast account transfers.
- Survive node failure.

### Design

1. Partition accounts by `account_id`.
2. Replicate each shard with a leader and two followers.
3. Use synchronous replication within a region.
4. Use asynchronous replication to another region.
5. Use distributed transactions for transfers.
6. Use two-phase commit or consensus-based commit.
7. Use WAL and checkpoints for recovery.
8. Use indexes on `account_id`, `customer_id`, and `branch_id`.
9. Co-locate related accounts when possible.
10. Use idempotent transfer IDs to avoid duplicate transfers.

### Performance Concerns

- Transfers across shards require distributed transactions.
- Cross-region transfers may be slow.
- Hot accounts may need special handling.
- Global indexes may become bottlenecks.
- Recovery must ensure no double-spending.

---

## 30. Example: Designing a Global Social Media Database

Suppose we need a social media database with global users.

### Requirements

- Low latency worldwide.
- High availability.
- Accept eventual consistency for some data.
- Strong consistency for critical data.

### Design

1. Partition by `user_id`.
2. Use multi-leader replication across regions.
3. Use CRDTs for counters and sets.
4. Use last-write-wins for simple profile fields.
5. Use global secondary indexes for search.
6. Use asynchronous replication for followers.
7. Use strong consistency for payments or security-sensitive data.
8. Use background repair for conflict resolution.

### Performance Concerns

- Regional writes are fast.
- Conflict resolution adds complexity.
- Search indexes may lag.
- Cross-region reads may be stale.
- Hot users can create hotspots.

---

## 31. Monitoring and Performance Tuning

A distributed database needs observability.

Key metrics:

| Metric | Why It Matters |
|---|---|
| Replication lag | Detect stale followers |
| Write latency | Detect bottlenecks |
| Read latency | Detect hotspots or bad indexes |
| Lock wait time | Detect contention |
| Transaction abort rate | Detect concurrency problems |
| Network latency | Detect infrastructure issues |
| Disk I/O | Detect storage saturation |
| CPU usage | Detect compute bottlenecks |
| Queue depth | Detect overload |
| Failover events | Detect reliability issues |

Tuning areas:

- Partition keys.
- Index design.
- Replication factor.
- Consistency level.
- Cache size.
- Batch size.
- Connection pooling.
- Query plans.
- Compaction and garbage collection.

---

## 32. Summary

A distributed database is designed to scale data and workload across multiple nodes while maintaining reliability and correctness.

### Replication

Replication improves availability, durability, and read scalability. It introduces tradeoffs between consistency, latency, and complexity. Common models include single-leader, multi-leader, and leaderless replication.

### Indexing

Indexes are essential for query performance, but distributed indexes can create write amplification, cross-shard coordination, and hotspots. Local indexes are simpler; global indexes are faster for some queries but harder to maintain.

### Transactions

Distributed transactions provide atomicity across nodes but are expensive. Two-phase commit, consensus protocols, locking, MVCC, and optimistic concurrency are common techniques. Strong isolation increases correctness but reduces performance.

### Recovery

Recovery uses write-ahead logging, checkpoints, redo/undo, replication, leader election, and consensus. Distributed recovery must handle partial failures, network partitions, and uncertain transaction states.

### Performance

Performance depends on data locality, query locality, replication mode, index design, transaction size, network latency, storage speed, caching, batching, and failure handling. The best design depends on the application’s consistency requirements, workload pattern, and geographic distribution.
