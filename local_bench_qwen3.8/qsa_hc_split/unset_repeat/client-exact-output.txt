## Distributed Database Design and Performance

A **distributed database** stores data across multiple machines, often in different locations, while presenting a single logical database to users and applications. Its design must balance **scalability, availability, consistency, latency, durability, and operational complexity**. The main performance concerns are network latency, data locality, replication overhead, transaction coordination, and failure recovery.

---

## 1. Core Design Goals

A distributed database is usually designed to achieve:

1. **Scalability**
   - Scale out by adding nodes.
   - Distribute storage and compute load.

2. **Availability**
   - Continue operating despite node or network failures.
   - Use replication and failover.

3. **Reliability and Durability**
   - Survive crashes, disk failures, and network partitions.
   - Use logs, checkpoints, backups, and replication.

4. **Performance**
   - Minimize network round trips.
   - Keep data close to compute.
   - Reduce lock contention and replication lag.

5. **Transparency**
   - Users should not need to know where data is stored.
   - The system should hide fragmentation, replication, and distribution details.

---

## 2. Data Distribution Design

Distributed databases usually distribute data using **partitioning**, also called **sharding**.

### Common Partitioning Strategies

| Strategy | Description | Performance Impact |
|---|---|---|
| **Hash partitioning** | Hash the key to assign rows to shards | Good load balance, poor range queries |
| **Range partitioning** | Assign contiguous key ranges to shards | Good range scans, risk of hotspots |
| **List partitioning** | Assign values to explicit groups | Useful for geography or tenant IDs |
| **Composite partitioning** | Combine hash, range, or list strategies | Flexible but more complex |
| **Directory-based partitioning** | Lookup table maps keys to shards | Flexible, but lookup adds latency |

### Design Considerations

- **Hotspots**: If one shard receives disproportionate traffic, performance degrades.
- **Rebalancing**: Moving shards between nodes must be efficient and online.
- **Locality**: Queries should ideally access one shard rather than many.
- **Join performance**: Distributed joins are expensive if data is not co-located.

---

## 3. Replication

Replication stores copies of data on multiple nodes. It improves **availability, fault tolerance, and read scalability**, but introduces complexity around **consistency and latency**.

---

### 3.1 Replication Models

#### 1. Leader-Follower Replication

One node is the **leader** or **primary**. It accepts writes and sends changes to **followers** or **replicas**.

**Advantages**
- Simple consistency model.
- Easy to implement strong consistency.
- Followers can serve reads.

**Disadvantages**
- Leader can become a bottleneck.
- Leader failure requires failover.
- Followers may lag behind.

**Performance Notes**
- Synchronous replication increases write latency.
- Asynchronous replication improves write latency but risks data loss.

---

#### 2. Multi-Leader Replication

Multiple nodes accept writes. Each leader replicates changes to other leaders.

**Advantages**
- Better write availability.
- Useful for geographically distributed systems.
- Can tolerate network partitions better.

**Disadvantages**
- Conflict resolution is required.
- Strong consistency is harder to achieve.
- More complex operational behavior.

**Common Conflict Resolution Methods**
- Last-write-wins using timestamps.
- Vector clocks or version vectors.
- Application-level merge logic.
- CRDTs, such as counters, sets, and maps.

---

#### 3. Leaderless Replication

Any node can accept writes. Reads may contact multiple replicas and reconcile results.

**Advantages**
- High availability.
- No single leader bottleneck.
- Good for fault-tolerant workloads.

**Disadvantages**
- Consistency is more complex.
- Requires quorum reads and writes.
- May return stale or conflicting data.

**Quorum Rule**

If there are `N` replicas:

- Writes require `W` acknowledgments.
- Reads require `R` responses.
- Strong consistency is possible when:

```text
R + W > N
```

Example:

```text
N = 3
W = 2
R = 2
```

A read and a write must overlap on at least one replica, reducing the chance of stale reads.

---

### 3.2 Synchronous vs Asynchronous Replication

| Type | Behavior | Consistency | Latency | Durability |
|---|---|---|---|---|
| **Synchronous** | Write waits for replicas | Strong | Higher | High |
| **Asynchronous** | Write returns before replicas apply | Eventual | Lower | Lower |
| **Semi-synchronous** | Wait for at least one replica | Stronger than async | Moderate | Moderate |

### Performance Tradeoff

Synchronous replication improves safety but increases write latency:

```text
Write latency = local write + network RTT to replicas + replica acknowledgment
```

Asynchronous replication reduces latency but may lose recent writes if the leader crashes.

---

### 3.3 Replication Protocols

Modern distributed databases often use consensus protocols:

- **Paxos**
- **Raft**
- **Zab**
- **Multi-Paxos**
- **Viewstamped Replication**

These protocols ensure that replicas agree on the order of operations even during failures.

**Performance Impact**
- Consensus requires multiple network round trips.
- Leader election can cause temporary unavailability.
- Log replication can become a bottleneck under high write load.

---

## 4. Indexing in Distributed Databases

Indexes are critical for performance, but in distributed systems they must be designed carefully because indexes may span multiple nodes.

---

### 4.1 Local Indexes

Each shard maintains its own index for its local data.

**Advantages**
- Simple to maintain.
- Low coordination overhead.
- Good for queries that include the shard key.

**Disadvantages**
- Queries without the shard key may need to scan all shards.
- Global uniqueness is harder to enforce.

**Example**

If data is partitioned by `user_id`, a local index on `email` may require querying every shard to find a user by email.

---

### 4.2 Global Indexes

A global index spans all shards and maps values to shard locations.

**Advantages**
- Efficient queries on non-shard-key columns.
- Can enforce global uniqueness.
- Better for secondary lookups.

**Disadvantages**
- Writes may require cross-shard coordination.
- Index maintenance can become a bottleneck.
- More complex failure handling.

**Example**

A global index on `email` can quickly find the shard containing a user without scanning all shards.

---

### 4.3 Partitioned Global Indexes

A global index is itself partitioned across nodes.

**Advantages**
- Scales better than a single global index.
- Reduces hotspot risk.

**Disadvantages**
- More complex routing and rebalancing.
- Index updates may involve multiple nodes.

---

### 4.4 Index Types

| Index Type | Use Case | Distributed Consideration |
|---|---|---|
| B-tree | Range queries, equality | Often local or partitioned |
| Hash | Equality lookups | Good for sharded keys |
| Bitmap | Low-cardinality analytics | Usually local or columnar |
| Inverted index | Full-text search | Often distributed across shards |
| Spatial index | Geo queries | Partition by region or geohash |
| Vector index | Similarity search | Partition by embedding space or cluster |
| Covering index | Avoid table lookup | Can reduce network fetches |

---

### 4.5 Indexing Performance Issues

1. **Write amplification**
   - Each write may update multiple indexes.
   - In distributed systems, index updates may require network calls.

2. **Hot index shards**
   - If many writes affect one index partition, that node becomes overloaded.

3. **Cross-shard queries**
   - If an index does not include the shard key, the query may fan out to many nodes.

4. **Index staleness**
   - Asynchronous index updates can cause stale reads.

5. **Rebalancing cost**
   - Moving data requires moving or rebuilding indexes.

---

## 5. Transactions in Distributed Databases

A distributed transaction may read or write data across multiple nodes. The system must preserve **ACID** properties:

- **Atomicity**
- **Consistency**
- **Isolation**
- **Durability**

This is much harder than in a single-node database because failures and network delays can occur between nodes.

---

### 5.1 Two-Phase Commit, 2PC

Two-phase commit is the classic protocol for distributed transactions.

#### Phase 1: Prepare

The coordinator asks all participants:

```text
Can you commit this transaction?
```

Each participant writes to its log and replies:

- Yes
- No

#### Phase 2: Commit or Abort

If all participants vote yes, the coordinator sends:

```text
Commit
```

If any participant votes no, the coordinator sends:

```text
Abort
```

**Advantages**
- Provides atomic commit across nodes.
- Works well with strong consistency.

**Disadvantages**
- Coordinator can become a bottleneck.
- Participants may block while waiting for the coordinator.
- High latency due to multiple round trips.
- Poor availability during network partitions.

**Performance Impact**

A distributed transaction using 2PC may require:

```text
Prepare round trip + commit round trip + participant logging + network failures handling
```

This can significantly increase latency.

---

### 5.2 Three-Phase Commit, 3PC

Three-phase commit tries to reduce blocking compared to 2PC.

Phases:

1. Can commit?
2. Pre-commit?
3. Commit?

**Advantages**
- Reduces some blocking scenarios.

**Disadvantages**
- Still not safe under all network partitions.
- More complex.
- Rarely used in practice.

---

### 5.3 Consensus-Based Transactions

Modern systems often combine replication and transaction commit using consensus protocols such as Raft or Paxos.

Examples:

- TiDB
- CockroachDB
- Spanner
- FoundationDB
- YugabyteDB

These systems often use:

- Raft/Paxos for replication.
- MVCC for concurrency control.
- Timestamps or clocks for ordering.
- Distributed snapshots for isolation.

---

### 5.4 Concurrency Control

Distributed databases use several concurrency-control techniques.

#### Lock-Based Concurrency Control

Transactions acquire locks on data items.

**Advantages**
- Strong isolation.
- Easy to reason about.

**Disadvantages**
- Lock contention.
- Distributed deadlocks.
- Lock coordination overhead.

**Distributed Deadlock Handling**
- Wait-for graphs across nodes.
- Timeout-based detection.
- Global deadlock detectors.
- Priority-based aborts.

---

#### Optimistic Concurrency Control

Transactions execute without locks and validate at commit time.

**Advantages**
- Good for low-contention workloads.
- Less blocking.

**Disadvantages**
- High abort rate under contention.
- Validation can be expensive.

---

#### Multi-Version Concurrency Control, MVCC

MVCC keeps multiple versions of data. Readers see snapshots, while writers create new versions.

**Advantages**
- Readers do not block writers.
- Writers do not block readers.
- Good for analytical and mixed workloads.

**Disadvantages**
- Garbage collection of old versions is required.
- Snapshot isolation may allow anomalies.
- Long-running transactions can cause version bloat.

---

### 5.5 Isolation Levels

| Isolation Level | Description | Distributed Cost |
|---|---|---|
| Read Uncommitted | May read uncommitted data | Low |
| Read Committed | Reads only committed data | Moderate |
| Repeatable Read | Same transaction sees same values | Higher |
| Snapshot Isolation | Reads from a consistent snapshot | Higher |
| Serializable | Behaves as if transactions ran one at a time | Highest |

In distributed systems, stronger isolation usually means:

- More locks.
- More validation.
- More network coordination.
- More aborts.
- Higher latency.

---

### 5.6 Distributed Transaction Performance Bottlenecks

1. **Network round trips**
   - Each coordination step adds latency.

2. **Coordinator bottleneck**
   - A single transaction coordinator can limit throughput.

3. **Lock contention**
   - Cross-node locks can serialize workloads.

4. **Hot rows**
   - Frequently updated rows cause contention.

5. **Cross-shard transactions**
   - Transactions touching many shards are slower.

6. **Clock synchronization**
   - Timestamp-based systems need accurate clocks.
   - Clock skew can cause correctness or performance issues.

---

## 6. Recovery in Distributed Databases

Recovery ensures that the database can survive crashes, network failures, disk failures, and operator errors.

---

### 6.1 Failure Types

| Failure Type | Description |
|---|---|
| Node crash | A server stops running |
| Disk failure | Storage becomes unavailable |
| Network partition | Nodes cannot communicate |
| Partial failure | Some nodes work, others do not |
| Data corruption | Stored data becomes invalid |
| Operator error | Bad update, deletion, or migration |

---

### 6.2 Write-Ahead Logging, WAL

Write-ahead logging records changes before applying them to the main database.

Basic rule:

```text
Log the change before modifying the database page.
```

**Benefits**
- Crash recovery.
- Replication.
- Point-in-time recovery.
- Auditability.

**Distributed WAL**
- Logs may be replicated to multiple nodes.
- Log order must be globally consistent.
- Log truncation must be coordinated with replicas.

---

### 6.3 Checkpointing

A checkpoint records the state of the database at a point in time.

During recovery:

1. Load the latest checkpoint.
2. Replay WAL records after the checkpoint.
3. Redo committed transactions.
4. Undo incomplete transactions.

**Performance Impact**
- Checkpoints reduce recovery time.
- Too frequent checkpoints increase I/O.
- Too infrequent checkpoints increase recovery time.

---

### 6.4 Recovery with Replication

Replication provides redundancy.

#### Synchronous Replication Recovery

If the leader fails:

- A follower with the latest log becomes leader.
- No committed data is lost.
- Failover may be slower because only fully synchronized replicas are eligible.

#### Asynchronous Replication Recovery

If the leader fails:

- The newest follower may be promoted.
- Some recent writes may be lost.
- Failover is faster but less safe.

---

### 6.5 Consensus-Based Recovery

Systems using Raft or Paxos can recover automatically:

1. Detect leader failure.
2. Elect a new leader.
3. Choose the replica with the most complete log.
4. Restore majority quorum.
5. Resume serving requests.

**Important**
- A majority of replicas must be available.
- If too many replicas are down, the system may become unavailable to preserve consistency.

---

### 6.6 Backups and Point-in-Time Recovery

Distributed databases often support:

- Full snapshots.
- Incremental backups.
- Log shipping.
- Point-in-time recovery, PITR.

**PITR Process**

1. Restore the latest full backup.
2. Apply incremental backups.
3. Replay transaction logs up to a chosen timestamp.

**Use Cases**
- Accidental deletion.
- Corrupted data.
- Bad migration.
- Security incident.

---

### 6.7 Recovery Performance Considerations

1. **Recovery time objective, RTO**
   - How quickly the system must recover.

2. **Recovery point objective, RPO**
   - How much data loss is acceptable.

3. **Log volume**
   - More logs mean longer replay time.

4. **Checkpoint frequency**
   - More checkpoints reduce replay time but increase overhead.

5. **Replica lag**
   - Lagging replicas may not be safe for promotion.

6. **Backup consistency**
   - Distributed backups must capture a consistent snapshot across shards.

---

## 7. Query Processing and Performance

Distributed query performance depends heavily on data placement and query routing.

---

### 7.1 Query Routing

A query may be:

1. **Single-shard query**
   - Fast.
   - Minimal coordination.

2. **Multi-shard query**
   - Slower.
   - Requires fan-out and result merging.

3. **Cross-shard join**
   - Expensive.
   - May require data movement.

4. **Aggregation query**
   - Can be optimized by pushing aggregation down to shards.

---

### 7.2 Distributed Joins

Common strategies:

| Join Strategy | Description | Performance |
|---|---|---|
| Co-located join | Joined tables are partitioned on the same key | Fast |
| Broadcast join | Small table is sent to all shards | Good for small tables |
| Shuffle join | Data is redistributed by join key | Expensive but scalable |
| Replicated join | One table is replicated everywhere | High storage cost, fast reads |

**Best Practice**

Design schemas so that frequently joined tables are partitioned on the same key.

---

### 7.3 Network Cost

Network latency is often the dominant cost in distributed databases.

A simple latency model:

```text
Total latency = local processing + network RTT + coordination overhead + replication overhead
```

For example, if one network round trip is 1 ms and a transaction requires 5 round trips, the transaction may take at least 5 ms before considering disk I/O and lock contention.

---

## 8. Performance Tuning Guidelines

### 8.1 Data Placement

- Choose shard keys that distribute load evenly.
- Avoid hot shards.
- Co-locate frequently joined data.
- Keep hot data on fast storage.
- Use locality-aware routing.

---

### 8.2 Replication Tuning

- Use synchronous replication when durability is critical.
- Use asynchronous replication when latency is critical.
- Monitor replica lag.
- Avoid too many synchronous replicas.
- Use quorum settings appropriate for the workload.

---

### 8.3 Indexing Tuning

- Prefer indexes that include the shard key.
- Avoid global indexes on high-write tables unless necessary.
- Use covering indexes to reduce cross-node fetches.
- Monitor index write amplification.
- Rebuild or rebalance indexes after major data changes.

---

### 8.4 Transaction Tuning

- Keep transactions short.
- Avoid cross-shard transactions when possible.
- Reduce lock contention.
- Use optimistic concurrency for low-contention workloads.
- Use MVCC for read-heavy workloads.
- Monitor abort rates.

---

### 8.5 Recovery Tuning

- Take regular checkpoints.
- Monitor log growth.
- Test failover regularly.
- Keep backups consistent across shards.
- Define clear RPO and RTO targets.
- Use fencing tokens to prevent split-brain.

---

## 9. CAP and PACELC Considerations

Distributed databases must make tradeoffs during failures and normal operation.

### CAP Theorem

During a network partition, a system can choose:

- **Consistency**
- **Availability**

It cannot guarantee both.

### PACELC

Even without partitions, systems trade off:

- **Latency**
- **Consistency**

Example:

```text
If Partitioned: choose Availability or Consistency
Else: choose Latency or Consistency
```

This explains why synchronous replication improves consistency but increases latency.

---

## 10. Summary Table

| Area | Design Choices | Performance Impact |
|---|---|---|
| **Partitioning** | Hash, range, list, directory | Determines query routing and hotspots |
| **Replication** | Leader-follower, multi-leader, leaderless | Affects availability, latency, consistency |
| **Indexing** | Local, global, partitioned global | Affects read speed and write overhead |
| **Transactions** | 2PC, consensus, MVCC, locks | Affects latency, throughput, isolation |
| **Recovery** | WAL, checkpoints, backups, failover | Affects durability, RPO, RTO |
| **Query Processing** | Routing, joins, aggregation pushdown | Affects network traffic and latency |

---

## 11. Practical Design Example

Suppose a global e-commerce system stores orders.

### Design

- Partition orders by `customer_id`.
- Replicate each shard using Raft with three replicas.
- Use synchronous replication within a region.
- Use asynchronous replication across regions.
- Maintain local indexes on `order_date`.
- Maintain a global index on `order_id`.
- Use MVCC for snapshot reads.
- Use 2PC or consensus-based transactions for cross-shard updates.
- Use WAL and snapshots for recovery.

### Performance Behavior

- Reads by `customer_id` are fast because they target one shard.
- Reads by `order_id` use the global index.
- Writes have higher latency due to consensus.
- Cross-region reads may be stale if asynchronous replication is used.
- Recovery can restore from snapshots plus WAL replay.

---

## Final Conclusion

A distributed database is designed around **data distribution, replication, indexing, transactions, and recovery**. Each area involves tradeoffs:

- **Replication** improves availability and read scalability but adds write latency and consistency complexity.
- **Indexing** speeds up queries but can increase write cost and cross-node coordination.
- **Transactions** provide correctness but require coordination, which increases latency.
- **Recovery** ensures durability but requires logs, checkpoints, backups, and failover mechanisms.

The best distributed database design depends on the workload. Read-heavy analytical systems may favor partitioned local indexes and asynchronous replication. Financial transaction systems may favor strong consistency, synchronous replication, and careful transaction coordination. The key is to align data placement, consistency requirements, and recovery strategy with the application’s performance and reliability goals.

### 4.2 Global Indexes

A global index spans all shards and maps values to shard locations.

**Advantages**
- Efficient queries on non-shard-key columns.
- Can enforce global uniqueness.
- Better for secondary lookups.

**Disadvantages**
- Writes may require cross-shard coordination.
- Index maintenance can become a bottleneck.
- More complex failure handling.

**Example**

A global index on `email` can quickly find the shard containing a user without scanning all shards.

---

### 4.3 Partitioned Global Indexes

A global index is itself partitioned across nodes.

**Advantages**
- Scales better than a single global index.
- Reduces hotspot risk.

**Disadvantages**
- More complex routing and rebalancing.
- Index updates may involve multiple nodes.

---

### 4.4 Index Types

| Index Type | Use Case | Distributed Consideration |
|---|---|---|
| B-tree | Range queries, equality | Often local or partitioned |
| Hash | Equality lookups | Good for sharded keys |
| Bitmap | Low-cardinality analytics | Usually local or columnar |
| Inverted index | Full-text search | Often distributed across shards |
| Spatial index | Geo queries | Partition by region or geohash |
| Vector index | Similarity search | Partition by embedding space or cluster |
| Covering index | Avoid table lookup | Can reduce network fetches |

---

### 4.5 Indexing Performance Issues

1. **Write amplification**
   - Each write may update multiple indexes.
   - In distributed systems, index updates may require network calls.

2. **Hot index shards**
   - If many writes affect one index partition, that node becomes overloaded.

3. **Cross-shard queries**
   - If an index does not include the shard key, the query may fan out to many nodes.

4. **Index staleness**
   - Asynchronous index updates can cause stale reads.

5. **Rebalancing cost**
   - Moving data requires moving or rebuilding indexes.

---

## 5. Transactions in Distributed Databases

A distributed transaction may read or write data across multiple nodes. The system must preserve **ACID** properties:

- **Atomicity**
- **Consistency**
- **Isolation**
- **Durability**

This is much harder than in a single-node database because failures and network delays can occur between nodes.

---

### 5.1 Two-Phase Commit, 2PC

Two-phase commit is the classic protocol for distributed transactions.

#### Phase 1: Prepare

The coordinator asks all participants:

```text
Can you commit this transaction?
```

Each participant writes to its log and replies:

- Yes
- No

#### Phase 2: Commit or Abort

If all participants vote yes, the coordinator sends:

```text
Commit
```

If any participant votes no, the coordinator sends:

```text
Abort
```

**Advantages**
- Provides atomic commit across nodes.
- Works well with strong consistency.

**Disadvantages**
- Coordinator can become a bottleneck.
- Participants may block while waiting for the coordinator.
- High latency due to multiple round trips.
- Poor availability during network partitions.

**Performance Impact**

A distributed transaction using 2PC may require:

```text
Prepare round trip + commit round trip + participant logging + network failures handling
```

This can significantly increase latency.

---

### 5.2 Three-Phase Commit, 3PC

Three-phase commit tries to reduce blocking compared to 2PC.

Phases:

1. Can commit?
2. Pre-commit?
3. Commit?

**Advantages**
- Reduces some blocking scenarios.

**Disadvantages**
- Still not safe under all network partitions.
- More complex.
- Rarely used in practice.

---

### 5.3 Consensus-Based Transactions

Modern systems often combine replication and transaction commit using consensus protocols such as Raft or Paxos.

Examples:

- TiDB
- CockroachDB
- Spanner
- FoundationDB
- YugabyteDB

These systems often use:

- Raft/Paxos for replication.
- MVCC for concurrency control.
- Timestamps or clocks for ordering.
- Distributed snapshots for isolation.

---

### 5.4 Concurrency Control

Distributed databases use several concurrency-control techniques.

#### Lock-Based Concurrency Control

Transactions acquire locks on data items.

**Advantages**
- Strong isolation.
- Easy to reason about.

**Disadvantages**
- Lock contention.
- Distributed deadlocks.
- Lock coordination overhead.

**Distributed Deadlock Handling**
- Wait-for graphs across nodes.
- Timeout-based detection.
- Global deadlock detectors.
- Priority-based aborts.

---

#### Optimistic Concurrency Control

Transactions execute without locks and validate at commit time.

**Advantages**
- Good for low-contention workloads.
- Less blocking.

**Disadvantages**
- High abort rate under contention.
- Validation can be expensive.

---

#### Multi-Version Concurrency Control, MVCC

MVCC keeps multiple versions of data. Readers see snapshots, while writers create new versions.

**Advantages**
- Readers do not block writers.
- Writers do not block readers.
- Good for analytical and mixed workloads.

**Disadvantages**
- Garbage collection of old versions is required.
- Snapshot isolation may allow anomalies.
- Long-running transactions can cause version bloat.

---

### 5.5 Isolation Levels

| Isolation Level | Description | Distributed Cost |
|---|---|---|
| Read Uncommitted | May read uncommitted data | Low |
| Read Committed | Reads only committed data | Moderate |
| Repeatable Read | Same transaction sees same values | Higher |
| Snapshot Isolation | Reads from a consistent snapshot | Higher |
| Serializable | Behaves as if transactions ran one at a time | Highest |

In distributed systems, stronger isolation usually means:

- More locks.
- More validation.
- More network coordination.
- More aborts.
- Higher latency.

---

### 5.6 Distributed Transaction Performance Bottlenecks

1. **Network round trips**
   - Each coordination step adds latency.

2. **Coordinator bottleneck**
   - A single transaction coordinator can limit throughput.

3. **Lock contention**
   - Cross-node locks can serialize workloads.

4. **Hot rows**
   - Frequently updated rows cause contention.

5. **Cross-shard transactions**
   - Transactions touching many shards are slower.

6. **Clock synchronization**
   - Timestamp-based systems need accurate clocks.
   - Clock skew can cause correctness or performance issues.

---

## 6. Recovery in Distributed Databases

Recovery ensures that the database can survive crashes, network failures, disk failures, and operator errors.

---

### 6.1 Failure Types

| Failure Type | Description |
|---|---|
| Node crash | A server stops running |
| Disk failure | Storage becomes unavailable |
| Network partition | Nodes cannot communicate |
| Partial failure | Some nodes work, others do not |
| Data corruption | Stored data becomes invalid |
| Operator error | Bad update, deletion, or migration |

---

### 6.2 Write-Ahead Logging, WAL

Write-ahead logging records changes before applying them to the main database.

Basic rule:

```text
Log the change before modifying the database page.
```

**Benefits**
- Crash recovery.
- Replication.
- Point-in-time recovery.
- Auditability.

**Distributed WAL**
- Logs may be replicated to multiple nodes.
- Log order must be globally consistent.
- Log truncation must be coordinated with replicas.

---

### 6.3 Checkpointing

A checkpoint records the state of the database at a point in time.

During recovery:

1. Load the latest checkpoint.
2. Replay WAL records after the checkpoint.
3. Redo committed transactions.
4. Undo incomplete transactions.

**Performance Impact**
- Checkpoints reduce recovery time.
- Too frequent checkpoints increase I/O.
- Too infrequent checkpoints increase recovery time.

---

### 6.4 Recovery with Replication

Replication provides redundancy.

#### Synchronous Replication Recovery

If the leader fails:

- A follower with the latest log becomes leader.
- No committed data is lost.
- Failover may be slower because only fully synchronized replicas are eligible.

#### Asynchronous Replication Recovery

If the leader fails:

- The newest follower may be promoted.
- Some recent writes may be lost.
- Failover is faster but less safe.

---

### 6.5 Consensus-Based Recovery

Systems using Raft or Paxos can recover automatically:

1. Detect leader failure.
2. Elect a new leader.
3. Choose the replica with the most complete log.
4. Restore majority quorum.
5. Resume serving requests.

**Important**
- A majority of replicas must be available.
- If too many replicas are down, the system may become unavailable to preserve consistency.

---

### 6.6 Backups and Point-in-Time Recovery

Distributed databases often support:

- Full snapshots.
- Incremental backups.
- Log shipping.
- Point-in-time recovery, PITR.

**PITR Process**

1. Restore the latest full backup.
2. Apply incremental backups.
3. Replay transaction logs up to a chosen timestamp.

**Use Cases**
- Accidental deletion.
- Corrupted data.
- Bad migration.
- Security incident.

---

### 6.7 Recovery Performance Considerations

1. **Recovery time objective, RTO**
   - How quickly the system must recover.

2. **Recovery point objective, RPO**
   - How much data loss is acceptable.

3. **Log volume**
   - More logs mean longer replay time.

4. **Checkpoint frequency**
   - More checkpoints reduce replay time but increase overhead.

5. **Replica lag**
   - Lagging replicas may not be safe for promotion.

6. **Backup consistency**
   - Distributed backups must capture a consistent snapshot across shards.

---

## 7. Query Processing and Performance

Distributed query performance depends heavily on data placement and query routing.

---

### 7.1 Query Routing

A query may be:

1. **Single-shard query**
   - Fast.
   - Minimal coordination.

2. **Multi-shard query**
   - Slower.
   - Requires fan-out and result merging.

3. **Cross-shard join**
   - Expensive.
   - May require data movement.

4. **Aggregation query**
   - Can be optimized by pushing aggregation down to shards.

---

### 7.2 Distributed Joins

Common strategies:

| Join Strategy | Description | Performance |
|---|---|---|
| Co-located join | Joined tables are partitioned on the same key | Fast |
| Broadcast join | Small table is sent to all shards | Good for small tables |
| Shuffle join | Data is redistributed by join key | Expensive but scalable |
| Replicated join | One table is replicated everywhere | High storage cost, fast reads |

**Best Practice**

Design schemas so that frequently joined tables are partitioned on the same key.

---

### 7.3 Network Cost

Network latency is often the dominant cost in distributed databases.

A simple latency model:

```text
Total latency = local processing + network RTT + coordination overhead + replication overhead
```

For example, if one network round trip is 1 ms and a transaction requires 5 round trips, the transaction may take at least 5 ms before considering disk I/O and lock contention.

---

## 8. Performance Tuning Guidelines

### 8.1 Data Placement

- Choose shard keys that distribute load evenly.
- Avoid hot shards.
- Co-locate frequently joined data.
- Keep hot data on fast storage.
- Use locality-aware routing.

---

### 8.2 Replication Tuning

- Use synchronous replication when durability is critical.
- Use asynchronous replication when latency is critical.
- Monitor replica lag.
- Avoid too many synchronous replicas.
- Use quorum settings appropriate for the workload.

---

### 8.3 Indexing Tuning

- Prefer indexes that include the shard key.
- Avoid global indexes on high-write tables unless necessary.
- Use covering indexes to reduce cross-node fetches.
- Monitor index write amplification.
- Rebuild or rebalance indexes after major data changes.

---

### 8.4 Transaction Tuning

- Keep transactions short.
- Avoid cross-shard transactions when possible.
- Reduce lock contention.
- Use optimistic concurrency for low-contention workloads.
- Use MVCC for read-heavy workloads.
- Monitor abort rates.

---

### 8.5 Recovery Tuning

- Take regular checkpoints.
- Monitor log growth.
- Test failover regularly.
- Keep backups consistent across shards.
- Define clear RPO and RTO targets.
- Use fencing tokens to prevent split-brain.

---

## 9. CAP and PACELC Considerations

Distributed databases must make tradeoffs during failures and normal operation.

### CAP Theorem

During a network partition, a system can choose:

- **Consistency**
- **Availability**

It cannot guarantee both.

### PACELC

Even without partitions, systems trade off:

- **Latency**
- **Consistency**

Example:

```text
If Partitioned: choose Availability or Consistency
Else: choose Latency or Consistency
```

This explains why synchronous replication improves consistency but increases latency.

---

## 10. Summary Table

| Area | Design Choices | Performance Impact |
|---|---|---|
| **Partitioning** | Hash, range, list, directory | Determines query routing and hotspots |
| **Replication** | Leader-follower, multi-leader, leaderless | Affects availability, latency, consistency |
| **Indexing** | Local, global, partitioned global | Affects read speed and write overhead |
| **Transactions** | 2PC, consensus, MVCC, locks | Affects latency, throughput, isolation |
| **Recovery** | WAL, checkpoints, backups, failover | Affects durability, RPO, RTO |
| **Query Processing** | Routing, joins, aggregation pushdown | Affects network traffic and latency |

---

## 11. Practical Design Example

Suppose a global e-commerce system stores orders.

### Design

- Partition orders by `customer_id`.
- Replicate each shard using Raft with three replicas.
- Use synchronous replication within a region.
- Use asynchronous replication across regions.
- Maintain local indexes on `order_date`.
- Maintain a global index on `order_id`.
- Use MVCC for snapshot reads.
- Use 2PC or consensus-based transactions for cross-shard updates.
- Use WAL and snapshots for recovery.

### Performance Behavior

- Reads by `customer_id` are fast because they target one shard.
- Reads by `order_id` use the global index.
- Writes have higher latency due to consensus.
- Cross-region reads may be stale if asynchronous replication is used.
- Recovery can restore from snapshots plus WAL replay.

---

## Final Conclusion

A distributed database is designed around **data distribution, replication, indexing, transactions, and recovery**. Each area involves tradeoffs:

- **Replication** improves availability and read scalability but adds write latency and consistency complexity.
- **Indexing** speeds up queries but can increase write cost and cross-node coordination.
- **Transactions** provide correctness but require coordination, which increases latency.
- **Recovery** ensures durability but requires logs, checkpoints, backups, and failover mechanisms.

The best distributed database design depends on the workload. Read-heavy analytical systems may favor partitioned local indexes and asynchronous replication. Financial transaction systems may favor strong consistency, synchronous replication, and careful transaction coordination. The key is to align data placement, consistency requirements, and recovery strategy with the application’s performance and reliability goals.
