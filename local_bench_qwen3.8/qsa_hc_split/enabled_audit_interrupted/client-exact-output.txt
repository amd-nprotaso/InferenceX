## Distributed Database Design and Performance

A distributed database stores data across multiple machines, often in different locations, while presenting a unified logical database to applications. Its design must balance **scalability, availability, consistency, durability, latency, and operational complexity**. The major design areas are:

1. **Data distribution and partitioning**
2. **Replication**
3. **Indexing**
4. **Transactions**
5. **Recovery**

Performance depends heavily on how these mechanisms interact with network latency, node failure, data skew, and consistency requirements.

---

# 1. Core Design Concepts

## 1.1 Nodes, Partitions, and Replicas

A distributed database is usually composed of:

- **Nodes/servers**: machines that store and serve data.
- **Partitions/shards**: subsets of data distributed across nodes.
- **Replicas**: copies of partitions placed on multiple nodes.
- **Metadata/catalog**: information about partition placement, schema, indexes, and cluster state.
- **Coordinator/query layer**: routes queries to relevant nodes and merges results.
- **Storage engine**: manages local data, logs, indexes, and compaction.

A typical design question is:

> How should data be divided, copied, indexed, updated, and recovered across nodes?

---

## 1.2 Partitioning / Sharding

Partitioning spreads data across nodes to increase capacity and parallelism.

### Common partitioning strategies

| Strategy | Description | Pros | Cons |
|---|---|---|---|
| Hash partitioning | Assign partition by hash of key | Even distribution, simple | Range queries fan out |
| Range partitioning | Assign by key ranges | Efficient range scans | Hot ranges possible |
| Directory partitioning | Metadata maps keys to nodes | Flexible | Metadata lookup overhead |
| Composite partitioning | Hash or range on multiple fields | Better locality | Complex |
| Consistent hashing | Nodes and keys on hash ring | Easier rebalancing | More complex |

### Performance implications

- **Hash partitioning** gives good write scalability but poor range query performance.
- **Range partitioning** supports efficient range scans but can create hotspots.
- **Partition key choice** is critical:
  - Too coarse: hot partitions.
  - Too fine: excessive fan-out and metadata overhead.
  - Poorly chosen: uneven load and expensive rebalancing.

---

## 1.3 Consistency Models

Distributed databases cannot simultaneously provide unlimited availability, consistency, and partition tolerance. This is often discussed using **CAP** and **PACELC**.

### CAP

Under network partition:

- **C**: Consistency
- **A**: Availability
- **P**: Partition tolerance

Most distributed databases choose **CP** or **AP** behavior during partitions.

### PACELC

Even without partitions, there is a tradeoff between:

- **Latency**
- **Consistency**

For example, synchronous replication improves consistency but increases write latency.

### Common consistency models

| Model | Meaning | Typical Use |
|---|---|---|
| Strong consistency | All reads see latest committed writes | Financial systems, inventory |
| Linearizability | Operations appear atomic and ordered | Locks, coordination |
| Sequential consistency | Operations appear in some global order | Some distributed systems |
| Causal consistency | Reads see causally related writes | Social feeds, collaboration |
| Eventual consistency | Replicas converge over time | Caches, analytics |
| Bounded staleness | Reads may be stale within limits | Geo-distributed reads |

Performance and correctness depend heavily on the chosen model.

---

# 2. Replication

Replication copies data across multiple nodes for:

- **Availability**
- **Fault tolerance**
- **Read scalability**
- **Low-latency local reads**
- **Disaster recovery**

But replication introduces complexity:

- Write amplification
- Conflict resolution
- Consistency tradeoffs
- Recovery complexity
- Network overhead

---

## 2.1 Replication Topologies

### Leader-Follower / Primary-Backup

One node is the leader for a partition. Followers apply updates from the leader.

#### Synchronous leader-follower

The leader waits for followers to acknowledge before committing.

**Pros:**

- Strong consistency
- Low risk of data loss
- Simpler conflict resolution

**Cons:**

- Higher write latency
- Availability depends on follower health
- Network latency directly affects commit time

**Performance:**

Write latency is approximately:

```text
leader write + network RTT to follower + follower write + acknowledgment
```

In geographically distributed systems, synchronous replication can be expensive.

---

#### Asynchronous leader-follower

The leader commits locally and sends updates to followers later.

**Pros:**

- Low write latency
- High throughput
- Tolerates follower lag

**Cons:**

- Followers may be stale
- Data loss possible if leader fails
- Reads from followers may be inconsistent

**Performance:**

Writes are fast, but recovery and consistency are weaker.

---

#### Semi-synchronous replication

Leader waits for at least one follower to acknowledge receipt, but not necessarily durable write.

**Pros:**

- Better durability than fully asynchronous
- Lower latency than fully synchronous

**Cons:**

- Still complex
- May block if follower is slow

---

### Multi-Leader / Multi-Master

Multiple nodes can accept writes for the same data.

**Pros:**

- Low-latency writes in multiple regions
- High availability
- Useful for offline or mobile clients

**Cons:**

- Write conflicts
- Complex conflict resolution
- Harder to guarantee strong consistency

**Conflict resolution methods:**

- Last-write-wins
- Vector clocks
- Version numbers
- CRDTs
- Application-level merge logic
- Operational transforms

**Performance:**

Multi-leader can improve write locality and availability, but conflict resolution and convergence can reduce throughput and increase complexity.

---

### Leaderless / Quorum-Based Replication

Any replica can accept writes. Reads and writes use quorums.

Example: Cassandra-style replication.

#### Quorum rule

If there are `N` replicas:

- Write to `W` replicas
- Read from `R` replicas

If:

```text
R + W > N
```

then reads and writes overlap, giving strong consistency under normal conditions.

**Pros:**

- High availability
- No single leader bottleneck
- Good for write-heavy workloads

**Cons:**

- Conflict resolution required
- Read repair and anti-entropy overhead
- Harder to reason about consistency

**Performance:**

Latency depends on the slowest `W` writes or `R` reads. Quorum systems can be resilient but may suffer from tail latency.

---

## 2.2 Replication Protocols

### Raft

Raft is a consensus protocol used by many distributed databases.

It provides:

- Leader election
- Log replication
- Fault tolerance
- Strong consistency for replicated state machines

**Performance:**

- Leader-based writes are simple.
- Commit requires majority acknowledgment.
- Network partitions can reduce availability.
- Leader election can cause temporary unavailability.

---

### Paxos

Paxos is a foundational consensus protocol.

Variants include:

- Multi-Paxos
- Raft
- Zab
- Viewstamped replication

**Performance:**

Paxos-based systems can be highly consistent but may have higher coordination overhead.

---

### Two-Phase Commit

2PC is used for distributed transactions, not usually for basic replication alone.

It is discussed later in the transaction section.

---

## 2.3 Replication and Performance

### Write amplification

If each write is replicated to `N` nodes, the system performs `N` local writes.

```text
Total write cost ≈ client write + network transfer + N local writes + acknowledgments
```

High replication factor improves durability but reduces write throughput.

---

### Read scalability

Replication allows reads from multiple replicas.

**Benefits:**

- Higher read throughput
- Lower latency for geographically distributed users
- Load balancing

**Risks:**

- Stale reads
- Inconsistent results across replicas
- Need for consistency controls

---

### Tail latency

In distributed systems, the slowest node often determines response time.

For example, if a read requires 3 replicas and one is slow, the request may wait for the slow one.

Mitigations:

- Hedge requests
- Quorum reads
- Caching
- Local replicas
- Fast follower detection
- Request timeouts and retries

---

### Network locality

Performance improves when:

- Clients are near replicas
- Replicas are in the same rack or data center
- Cross-region traffic is minimized
- Reads are served locally
- Writes are batched

Geo-replication introduces high latency. Synchronous cross-region replication can be expensive.

---

## 2.4 Replication Design Choices

| Requirement | Recommended Design |
|---|---|
| Strong consistency | Synchronous leader-follower or quorum with `R + W > N` |
| High write throughput | Asynchronous replication or leaderless with careful consistency |
| Multi-region low latency | Multi-leader or local replicas with causal/eventual consistency |
| Financial correctness | Strong consistency, synchronous replication, careful transaction design |
| Analytics | Asynchronous replicas, columnar stores, batch replication |
| Mobile/offline | Multi-leader, CRDTs, conflict resolution |

---

# 3. Indexing in Distributed Databases

Indexes accelerate queries but are more complex in distributed systems because data and indexes may be partitioned and replicated.

---

## 3.1 Local vs Global Indexes

### Local indexes

Each partition maintains its own index.

Example:

```text
Partition 1: index for keys in partition 1
Partition 2: index for keys in partition 2
```

**Pros:**

- Index updates stay local to the partition
- Easier to maintain
- Good for partition-key queries
- Less cross-node coordination

**Cons:**

- Non-partition-key queries must search all partitions
- Global uniqueness may require extra coordination

**Performance:**

Local indexes are efficient for queries that include the partition key.

Example:

```sql
SELECT * FROM orders
WHERE customer_id = 123;
```

If `customer_id` is the partition key, the query can go directly to one partition.

---

### Global indexes

A global index spans multiple partitions and may be stored separately.

Example:

```text
Global index on email -> partition ID
```

**Pros:**

- Efficient for non-partition-key queries
- Supports global uniqueness constraints
- Can avoid full fan-out

**Cons:**

- Index updates may require cross-partition coordination
- Global index becomes a bottleneck
- More complex recovery and rebalancing

**Performance:**

Global indexes can improve read performance but increase write complexity.

Example:

```sql
SELECT * FROM users
WHERE email = 'user@example.com';
```

If `email` is not the partition key, a global index can avoid scanning all partitions.

---

## 3.2 Partitioned Secondary Indexes

A secondary index can be partitioned by a different key than the primary table.

Example:

```text
Table partitioned by customer_id
Index partitioned by order_date
```

**Pros:**

- Supports queries on indexed columns
- Distributes index load

**Cons:**

- Index entries may point to many partitions
- Writes may update multiple index partitions
- Rebalancing is complex

---

## 3.3 Covering Indexes

A covering index includes enough columns to answer a query without fetching the base row.

Example:

```sql
SELECT customer_id, order_date
FROM orders
WHERE status = 'paid';
```

If the index contains `status`, `customer_id`, and `order_date`, the query can be answered from the index alone.

**Performance benefit:**

- Reduces random reads
- Reduces network fan-out
- Improves throughput

In distributed systems, covering indexes are especially valuable because fetching base rows may require cross-node requests.

---

## 3.4 Index Maintenance and Write Amplification

Every write may update:

- Primary table
- Local indexes
- Global indexes
- Replicas
- Logs
- Search indexes
- Materialized views

This creates **write amplification**.

Example:

```text
One logical write may become:
1 primary write
+ 3 replica writes
+ 2 index writes
+ 1 log write
+ 1 search index update
```

**Performance impact:**

- Lower write throughput
- Higher storage cost
- More compaction and garbage collection
- More failure recovery work

---

## 3.5 Index Types

### B-tree indexes

Good for:

- Equality
- Range queries
- Sorted access
- OLTP workloads

In distributed databases, B-trees are often local to partitions.

---

### LSM-tree indexes

Used by systems like Cassandra, RocksDB, HBase.

Good for:

- High write throughput
- Append-heavy workloads
- Large datasets

Tradeoffs:

- Compaction overhead
- Read amplification
- Background resource usage

---

### Hash indexes

Good for:

- Equality lookups
- Fast point queries

Poor for:

- Range scans
- Ordering

---

### Bitmap indexes

Good for:

- Low-cardinality columns
- Analytics
- Read-heavy analytical queries

Poor for:

- High-concurrency OLTP updates

---

### Inverted indexes

Used for:

- Full-text search
- Log search
- Tag search

Often implemented in separate search systems like Elasticsearch or OpenSearch.

---

### Vector indexes

Used for:

- Similarity search
- Embeddings
- AI/ML retrieval

Common structures:

- HNSW
- IVF
- PQ
- ScaNN

Distributed vector indexes require careful partitioning because similarity search may need to query many shards.

---

## 3.6 Distributed Index Query Patterns

### Query with partition key

Fast.

```sql
SELECT * FROM events
WHERE user_id = 42;
```

If `user_id` is partition key, query one partition.

---

### Query without partition key

Slow unless global index exists.

```sql
SELECT * FROM events
WHERE event_type = 'click';
```

May fan out to all partitions.

---

### Query using global index

Moderate.

```sql
SELECT * FROM users
WHERE email = 'a@b.com';
```

Global index lookup returns partition ID, then fetch row.

---

### Range query

Depends on partitioning.

```sql
SELECT * FROM orders
WHERE order_date BETWEEN '2025-01-01' AND '2025-01-31';
```

If partitioned by date, efficient.

If partitioned by customer, may fan out.

---

## 3.7 Indexing Performance Guidelines

1. **Design indexes around query patterns.**
2. **Prefer local indexes when queries include partition key.**
3. **Use global indexes sparingly.**
4. **Avoid too many secondary indexes on write-heavy tables.**
5. **Use covering indexes to reduce fetches.**
6. **Monitor index write amplification.**
7. **Separate analytical indexes from OLTP indexes when possible.**
8. **Use search engines for complex text or vector search.**
9. **Avoid hot index partitions.**
10. **Rebalance indexes carefully during node changes.**

---

# 4. Transactions in Distributed Databases

A transaction is a sequence of operations that should behave as a single logical unit.

Classic ACID properties:

- **Atomicity**: all or nothing
- **Consistency**: database moves from one valid state to another
- **Isolation**: concurrent transactions do not interfere
- **Durability**: committed data survives failures

In distributed databases, ACID is harder because operations may touch multiple nodes.

---

## 4.1 Distributed Transaction Challenges

A distributed transaction may involve:

- Multiple partitions
- Multiple replicas
- Multiple data centers
- Multiple indexes
- Multiple services

Challenges:

- Network latency
- Partial failures
- Coordination overhead
- Deadlocks
- Lock contention
- Clock skew
- Consistency guarantees
- Recovery from coordinator failure

---

## 4.2 Two-Phase Commit

Two-phase commit is the classic protocol for distributed atomic commit.

### Phase 1: Prepare

Coordinator asks all participants:

```text
Can you commit?
```

Each participant writes a prepare record and locks resources.

### Phase 2: Commit or Abort

If all participants vote yes, coordinator sends commit.

If any participant votes no, coordinator sends abort.

**Pros:**

- Atomic commit across participants
- Simple conceptual model

**Cons:**

- Blocking
- Coordinator failure can leave participants uncertain
- High latency
- Poor availability during partitions
- Locks held during prepare phase

**Performance:**

2PC adds at least two coordination round trips.

```text
Prepare round trip + commit round trip
```

In multi-region systems, this can be expensive.

---

## 4.3 Three-Phase Commit

Three-phase commit attempts to reduce blocking compared to 2PC.

Phases:

1. Can commit?
2. Pre-commit
3. Commit

**Pros:**

- Better handling of coordinator failure in theory

**Cons:**

- More complex
- More messages
- Still not perfect under all network conditions
- Rarely used in practice

---

## 4.4 Consensus-Based Transactions

Modern distributed databases often use consensus protocols like Raft or Paxos instead of raw 2PC.

Examples:

- TiDB
- CockroachDB
- Spanner
- FoundationDB
- YugabyteDB

These systems use replicated logs and consensus to coordinate state changes.

**Pros:**

- Better fault tolerance
- Strong consistency
- Leader-based coordination
- Log-based recovery

**Cons:**

- Coordination overhead
- Leader bottlenecks
- Cross-region latency
- Complex implementation

---

## 4.5 Isolation Levels

Distributed databases support various isolation levels.

### Read Uncommitted

May read uncommitted data.

Rarely used in serious transactional systems.

---

### Read Committed

Reads see only committed data.

May see different values in repeated reads.

---

### Repeatable Read

Repeated reads within a transaction see the same values.

May still have phantom rows.

---

### Snapshot Isolation

Transaction sees a consistent snapshot of the database.

Common in MVCC systems.

**Pros:**

- Readers do not block writers
- Good concurrency

**Cons:**

- Write-write conflicts
- May not be serializable

---

### Serializable

Transactions behave as if executed one at a time.

Strongest isolation.

**Pros:**

- Prevents anomalies
- Easier reasoning

**Cons:**

- More conflicts
- More aborts
- Higher coordination cost

---

## 4.6 MVCC

Multi-Version Concurrency Control stores multiple versions of data.

Each transaction sees a snapshot based on timestamp or version.

**Benefits:**

- Readers do not block writers
- Writers do not block readers
- Better concurrency

**Costs:**

- Version storage
- Garbage collection
- Conflict detection
- Snapshot management

In distributed systems, MVCC requires consistent timestamps or logical clocks.

---

## 4.7 Timestamps and Clocks

Distributed transactions often need ordering.

### Logical clocks

Examples:

- Lamport clocks
- Vector clocks
- Hybrid Logical Clocks

Useful for causality and versioning.

---

### Physical clocks

Systems like Google Spanner use TrueTime with atomic clocks and GPS.

This allows external consistency, where transactions appear ordered by real time.

**Performance impact:**

If clocks are uncertain, transactions may wait for clock uncertainty bounds.

---

## 4.8 Optimistic vs Pessimistic Concurrency

### Pessimistic concurrency

Lock resources before modifying.

**Pros:**

- Fewer aborts
- Predictable behavior

**Cons:**

- Lock contention
- Deadlocks
- Reduced throughput

---

### Optimistic concurrency

Read data, modify locally, validate at commit.

**Pros:**

- High throughput when conflicts are rare
- No long locks

**Cons:**

- Abort storms under contention
- Retry logic required
- Harder for hot rows

---

## 4.9 Distributed Deadlocks

Deadlocks can occur when transactions on different nodes wait for each other.

Example:

```text
Transaction A locks row X on node 1, waits for row Y on node 2
Transaction B locks row Y on node 2, waits for row X on node 1
```

Mitigations:

- Timeout-based deadlock detection
- Global deadlock detector
- Lock ordering
- Retry policies
- Short transactions
- Avoid cross-partition locks when possible

---

## 4.10 Transaction Performance

### Factors affecting performance

1. **Number of partitions touched**
2. **Number of replicas involved**
3. **Consistency level**
4. **Isolation level**
5. **Lock contention**
6. **Network latency**
7. **Coordinator location**
8. **Retry rate**
9. **Write skew**
10. **Index maintenance**

---

### Single-partition transactions

Fastest.

Example:

```sql
UPDATE accounts
SET balance = balance - 100
WHERE account_id = 123;
```

If `account_id` is partition key, transaction touches one partition.

---

### Multi-partition transactions

Slower.

Example:

```sql
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
```

If accounts are on different partitions, coordination is required.

---

### Cross-region transactions

Slowest.

Network latency dominates.

Mitigations:

- Batch operations
- Reduce cross-region writes
- Use local transactions where possible
- Use asynchronous replication for non-critical data
- Design data locality around transaction boundaries

---

## 4.11 Transaction Design Guidelines

1. **Keep transactions short.**
2. **Touch as few partitions as possible.**
3. **Design partition keys around transactional locality.**
4. **Avoid hot rows.**
5. **Use idempotent operations.**
6. **Retry with backoff.**
7. **Use optimistic concurrency for low-contention workloads.**
8. **Use pessimistic locking for high-contention critical operations.**
9. **Avoid long-running transactions.**
10. **Separate analytical and transactional workloads.**

---

# 5. Recovery in Distributed Databases

Recovery ensures that committed data survives failures and that the database can return to a consistent state.

---

## 5.1 Failure Types

Distributed databases must handle:

1. **Process crash**
2. **Node crash**
3. **Disk failure**
4. **Network partition**
5. **Clock failure**
6. **Data corruption**
7. **Operator error**
8. **Region/data center outage**
9. **Replica divergence**
10. **Split-brain**

---

## 5.2 Write-Ahead Logging

A write-ahead log records changes before applying them to data pages.

Rules:

- Log record must be durable before commit.
- Data changes can be applied later.
- Recovery can redo committed changes and undo uncommitted changes.

**Benefits:**

- Crash recovery
- Replication
- Point-in-time recovery
- Auditability

**Performance impact:**

- Sequential log writes are fast.
- fsync latency can dominate.
- Log growth requires checkpointing and truncation.

---

## 5.3 Checkpoints

A checkpoint records a consistent state of the database.

During recovery:

- Start from checkpoint.
- Redo committed log records after checkpoint.
- Undo uncommitted transactions.

**Benefits:**

- Faster recovery
- Bounded log replay

**Costs:**

- Checkpoint overhead
- I/O spikes
- Complexity

---

## 5.4 Snapshots and Backups

### Logical backups

Export data in a portable format.

**Pros:**

- Human-readable
- Portable
- Useful for migration

**Cons:**

- Slow
- May not preserve exact physical state
- Harder for large datasets

---

### Physical snapshots

Copy database files or storage volumes.

**Pros:**

- Fast
- Good for large datasets
- Supports point-in-time recovery

**Cons:**

- Storage-specific
- May require consistent snapshot mechanism
- More complex restore

---

### Continuous backups

Combine snapshots with log shipping.

Example:

```text
Snapshot + WAL segments
```

Allows point-in-time recovery.

---

## 5.5 Point-in-Time Recovery

Point-in-time recovery restores the database to a specific moment.

Useful for:

- Accidental deletes
- Bad deployments
- Data corruption
- Audit recovery

Process:

1. Restore latest snapshot before target time.
2. Replay logs up to target time.
3. Stop before bad operation.

**Performance impact:**

- Recovery time depends on log volume.
- Large logs require more replay.
- Cross-region backups may be slow.

---

## 5.6 Replication-Based Recovery

Replication provides redundancy.

If one node fails, another replica can serve data.

### Synchronous replication

If leader fails, follower has latest committed data.

**Pros:**

- Low RPO
- Strong durability

**Cons:**

- Higher latency
- Availability depends on quorum

---

### Asynchronous replication

Follower may lag.

**Pros:**

- Low latency
- High throughput

**Cons:**

- Data loss possible
- Higher RPO

---

## 5.7 Quorum Recovery

In quorum-based systems, recovery depends on majority availability.

Example:

```text
N = 5
W = 3
R = 3
```

If fewer than 3 nodes are available, the system may become unavailable.

**Recovery considerations:**

- Replacing failed nodes
- Rebuilding replicas
- Repairing divergent replicas
- Handling stale nodes
- Preventing split-brain

---

## 5.8 Anti-Entropy and Repair

Replicas can diverge due to:

- Network partitions
- Partial failures
- Bugs
- Manual changes
- Disk corruption

Anti-entropy mechanisms compare replicas and repair differences.

### Merkle trees

A Merkle tree summarizes data in a partition.

Nodes compare tree hashes to find differences efficiently.

**Benefits:**

- Efficient repair
- Detects divergence
- Reduces full data transfer

**Costs:**

- Tree construction overhead
- Memory/CPU usage
- Complexity

---

### Read repair

When a read contacts multiple replicas, inconsistent replicas are repaired.

**Pros:**

- Self-healing
- Improves consistency

**Cons:**

- Adds latency to reads
- Can amplify traffic

---

### Background repair

Periodic background jobs compare replicas.

**Pros:**

- Less impact on reads
- Good for eventual consistency systems

**Cons:**

- Slower convergence
- More background load

---

## 5.9 Split-Brain and Fencing

Split-brain occurs when two nodes believe they are the leader.

This can cause data corruption.

Mitigations:

- Quorum-based leader election
- Fencing tokens
- Lease-based leadership
- STONITH
- Network isolation
- Consensus protocols
- Unique epoch numbers

A fencing token ensures that an old leader cannot write after a new leader is elected.

---

## 5.10 Recovery Performance

Recovery performance depends on:

1. **Amount of log to replay**
2. **Snapshot frequency**
3. **Replication factor**
4. **Network bandwidth**
5. **Disk speed**
6. **Data corruption extent**
7. **Repair algorithm efficiency**
8. **Cluster size**
9. **Metadata recovery**
10. **Index rebuild requirements**

---

## 5.11 RPO and RTO

### RPO: Recovery Point Objective

Maximum acceptable data loss.

Example:

```text
RPO = 0
```

Means no committed data loss.

Usually requires synchronous replication or quorum durability.

---

### RTO: Recovery Time Objective

Maximum acceptable downtime.

Example:

```text
RTO = 30 seconds
```

Means the system must recover within 30 seconds.

Usually requires:

- Fast leader election
- Warm replicas
- Small log replay
- Automated failover
- Pre-warmed caches

---

# 6. Performance Design of Distributed Databases

Performance is not just raw throughput. It includes:

- Latency
- Throughput
- Scalability
- Availability
- Durability
- Predictability
- Cost

---

## 6.1 Latency Sources

Major latency sources:

1. **Network round trips**
2. **Disk fsync**
3. **Consensus coordination**
4. **Replication acknowledgments**
5. **Lock waits**
6. **Index maintenance**
7. **Query fan-out**
8. **Garbage collection**
9. **Compaction**
10. **Retry storms**

---

## 6.2 Throughput Bottlenecks

Common bottlenecks:

- Hot partitions
- Hot rows
- Global indexes
- Coordinator nodes
- Network bandwidth
- Disk I/O
- Lock contention
- Background compaction
- Cross-region traffic
- Metadata lookups

---

## 6.3 Scalability Patterns

### Horizontal scaling

Add more nodes.

Works well when:

- Data is partitioned evenly
- Workload is parallelizable
- No single global bottleneck exists

---

### Vertical scaling

Add more CPU, RAM, or faster disks to existing nodes.

Useful but limited.

---

### Read scaling

Add read replicas.

Works well for read-heavy workloads.

---

### Write scaling

Requires partitioning and replication strategy.

Write scalability is harder because:

- Writes must be durable
- Replicas must stay consistent
- Indexes must be updated
- Transactions may coordinate

---

## 6.4 Data Skew and Hotspots

Hotspots occur when one partition or row receives disproportionate traffic.

Examples:

```text
Popular product
Frequent account
Trending hashtag
Single tenant
Date-based partition with current day
```

Mitigations:

- Better partition keys
- Composite keys
- Random prefixes
- Caching
- Batching
- Load balancing
- Splitting hot partitions
- Using counters or sharded aggregates

---

## 6.5 Caching

Caching improves performance but complicates consistency.

### Cache types

- Client cache
- Application cache
- Distributed cache
- Database block cache
- Query result cache
- Materialized views

### Consistency issues

- Stale reads
- Cache invalidation
- Write-through vs write-back
- Cache stampedes
- Thundering herd

---

## 6.6 Batching

Batching reduces network round trips and improves throughput.

Examples:

- Batch inserts
- Batch updates
- Batch index writes
- Batch replication messages
- Batch transaction commits

**Tradeoff:**

- Higher latency for individual operations
- Better overall throughput

---

## 6.7 Query Optimization

Distributed query optimization must consider:

- Partition pruning
- Index selection
- Join placement
- Data locality
- Network cost
- Replication state
- Statistics
- Skew
- Cardinality estimation

### Join strategies

| Join type | Description | Performance |
|---|---|---|
| Broadcast join | Send small table to all nodes | Good for small tables |
| Shuffle join | Repartition both tables | Expensive but scalable |
| Colocated join | Join tables partitioned by same key | Fast |
| Index join | Use index to fetch matching rows | Good for selective queries |
| Nested loop join | For each row, lookup other table | Can be slow |

---

## 6.8 Storage Engine Choice

### B-tree based

Good for:

- OLTP
- Range queries
- Low write amplification
- Predictable latency

### LSM-tree based

Good for:

- High write throughput
- Large datasets
- Append-heavy workloads

Tradeoffs:

- Compaction
- Read amplification
- Background I/O

# 7. Putting It All Together: Example Designs

## 7.1 Strongly Consistent OLTP Database

Goal:

- Financial transactions
- Strong consistency
- Low data loss

Design:

- Range or hash partitioning
- Synchronous replication with quorum
- Raft/Paxos consensus
- MVCC
- Serializable or snapshot isolation
- Local indexes
- Short transactions
- WAL + snapshots + PITR

Performance characteristics:

- Write latency higher
- Strong correctness
- Sensitive to cross-region latency
- Requires careful partitioning

---

## 7.2 High-Throughput Event Store

Goal:

- Massive writes
- Analytics
- Tolerate eventual consistency

Design:

- Hash partitioning by event ID or tenant
- Leaderless or asynchronous replication
- LSM storage
- Local indexes
- Batch writes
- Background compaction
- Search index for analytics

Performance characteristics:

- High write throughput
- Lower read consistency
- Good scalability
- Background repair and compaction important

---

## 7.3 Multi-Region Application Database

Goal:

- Low latency for global users
- High availability
- Some consistency tradeoffs

Design:

- Multi-leader or regional replicas
- Causal consistency
- CRDTs or conflict resolution
- Local reads
- Asynchronous cross-region replication
- Regional transaction boundaries

Performance characteristics:

- Low local latency
- High availability
- Complex conflict resolution
- Not ideal for global strong consistency

---

## 7.4 Analytics Warehouse

Goal:

- Large scans
- Aggregations
- Columnar storage

Design:

- Partition by date or tenant
- Columnar storage
- Sort keys
- Materialized views
- Broadcast/shuffle joins
- Separate from OLTP
- Batch ingestion

Performance characteristics:

- High analytical throughput
- Not optimized for frequent small updates
- Cost depends on scan volume

# 8. Common Performance Problems and Fixes

| Problem | Cause | Fix |
|---|---|---|
| High write latency | Synchronous replication, cross-region writes | Local replicas, batching, async replication |
| Slow reads | Fan-out, missing indexes, cold cache | Covering indexes, caching, partition pruning |
| Hot partition | Poor partition key | Better key, split partition, random prefix |
| Lock contention | Hot rows, long transactions | Short transactions, optimistic concurrency, sharding counters |
| High abort rate | Serializable conflicts | Retry, reduce transaction scope, lower isolation if safe |
| Slow recovery | Large logs, infrequent checkpoints | More checkpoints, snapshots, faster disks |
| Replica divergence | Network partitions, bugs | Anti-entropy, Merkle trees, fencing |
| Index write bottleneck | Too many global indexes | Reduce indexes, local indexes, async search index |
| Cross-region latency | Global transactions | Regional transactions, async replication |
| Compaction spikes | LSM background work | Tune compaction, separate resources, rate limiting |

# 10. Summary

A distributed database is designed around tradeoffs.

## Replication

Replication improves availability, durability, and read scalability, but adds write latency, complexity, and consistency challenges.

Key choices:

- Synchronous vs asynchronous
- Leader-follower vs multi-leader vs leaderless
- Quorum size
- Conflict resolution
- Consistency model

## Indexing

Indexes improve query performance but increase write cost and coordination.

Key choices:

- Local vs global indexes
- Partitioned indexes
- Covering indexes
- Index type
- Write amplification
- Query fan-out

## Transactions

Distributed transactions provide correctness but are expensive.

Key choices:

- 2PC vs consensus-based commit
- Isolation level
- MVCC
- Optimistic vs pessimistic concurrency
- Transaction scope
- Partition locality

## Recovery

Recovery ensures durability and availability after failures.

Key mechanisms:

- WAL
- Checkpoints
- Snapshots
- Log shipping
- PITR
- Quorum recovery
- Anti-entropy
- Fencing
- Backup testing

## Performance

Performance depends on:

- Network latency
- Partitioning
- Replication factor
- Index maintenance
- Transaction coordination
- Data skew
- Storage engine
- Caching
- Background operations

The best distributed database design aligns the data model, workload, consistency requirements, and failure expectations. Strong consistency and global transactions are powerful but costly. High scalability and low latency often require careful partitioning, local transactions, and relaxed consistency where appropriate.
