A distributed database is a database system in which data and processing are spread across multiple machines, often across multiple data centers or cloud regions. Its design must balance scalability, availability, consistency, latency, fault tolerance, and operational complexity. The major design areas are data distribution, replication, indexing, transactions, and recovery.

## 1. Overall Design of a Distributed Database

A distributed database typically consists of multiple nodes that store data, process queries, coordinate transactions, and participate in failure detection and recovery.

### Core design goals

1. **Scalability**
   - The system should handle more data, more users, and more queries by adding nodes.
   - Horizontal scaling is preferred over vertical scaling.

2. **Availability**
   - The system should continue operating despite node, network, or data-center failures.
   - This often requires replication and automatic failover.

3. **Consistency**
   - Users should see correct and predictable data.
   - Strong consistency is easier to reason about but can reduce availability and performance.
   - Eventual consistency improves availability and latency but can produce stale reads.

4. **Low latency**
   - Queries should be served close to users when possible.
   - Network distance, cross-region coordination, and distributed joins can increase latency.

5. **Fault tolerance**
   - The system should survive disk failures, process crashes, network partitions, and data-center outages.

6. **Operational simplicity**
   - The system should be easy to deploy, monitor, upgrade, and repair.

### Common architectural components

A distributed database usually includes:

- **Storage nodes**: store data partitions or shards.
- **Compute/query nodes**: parse, optimize, and execute queries.
- **Metadata service**: tracks schema, partition placement, replication state, and cluster membership.
- **Transaction coordinator**: manages distributed commits and isolation.
- **Replication manager**: propagates writes between replicas.
- **Failure detector**: monitors node health and triggers failover.
- **Backup and recovery service**: stores snapshots, logs, and point-in-time recovery data.

### Data distribution models

Distributed databases distribute data using one or more of the following:

#### 1. Sharding / partitioning

Data is divided into partitions, often called shards.

Common partitioning strategies:

- **Hash partitioning**
  - Example: shard = hash(customer_id) % number_of_shards
  - Pros: even data distribution.
  - Cons: range queries are expensive.

- **Range partitioning**
  - Example: shard 1 stores customer IDs 1–1000, shard 2 stores 1001–2000.
  - Pros: efficient range scans.
  - Cons: hot ranges can become overloaded.

- **Directory partitioning**
  - A lookup service maps keys to shards.
  - Pros: flexible placement.
  - Cons: directory can become a bottleneck.

- **Geographic partitioning**
  - Data is placed near users or according to legal requirements.
  - Pros: low latency and compliance.
  - Cons: complex consistency and routing.

#### 2. Replication

Each shard may have multiple replicas on different nodes or regions.

Replication improves:

- Availability
- Read scalability
- Disaster recovery
- Locality

But it introduces:

- Write amplification
- Consistency complexity
- Conflict resolution
- Recovery complexity

## 2. Replication

Replication is the process of storing copies of data on multiple nodes.

### Why replication is used

Replication provides:

1. **High availability**
   - If one replica fails, another can serve requests.

2. **Read scalability**
   - Reads can be distributed across replicas.

3. **Disaster recovery**
   - Data survives data-center or region failures.

4. **Low-latency reads**
   - Users can read from a nearby replica.

5. **Load balancing**
   - Traffic can be spread across multiple nodes.

### Replication models

#### 1. Primary-backup replication

One node is the primary or leader. It accepts writes. Other nodes are backups or followers.

Flow:

1. Client writes to primary.
2. Primary writes locally.
3. Primary sends log records to backups.
4. Backups apply changes.
5. Depending on configuration, primary waits for acknowledgments before responding.

Variants:

- **Synchronous replication**
  - Primary waits for backup acknowledgment before committing.
  - Pros: strong durability, low risk of data loss.
  - Cons: higher write latency.

- **Asynchronous replication**
  - Primary commits without waiting for backups.
  - Pros: low write latency.
  - Cons: backups may lag; failover can lose recent writes.

- **Semi-synchronous replication**
  - Primary waits for at least one backup acknowledgment.
  - Balances durability and latency.

Primary-backup is common in systems such as PostgreSQL streaming replication, MySQL replication, MongoDB replica sets, and many SQL databases.

#### 2. Quorum-based replication

Writes and reads require agreement from a majority of replicas.

Example:

- 5 replicas
- Write requires 3 acknowledgments
- Read requires 3 replicas

If:

```text
W + R > N
```

then reads and writes overlap, providing strong consistency.

Example:

```text
N = 5
W = 3
R = 3
3 + 3 > 5
```

This guarantees that a read sees the latest committed write, assuming no failures violate the quorum assumptions.

Pros:

- Strong consistency possible.
- Tolerates some failures.

Cons:

- Higher latency.
- Reduced availability during partitions.

#### 3. Multi-primary / multi-master replication

Multiple nodes accept writes.

Pros:

- High write availability.
- Useful for geographically distributed workloads.

Cons:

- Conflict resolution is difficult.
- Strong consistency is hard.
- Requires conflict-free data types, version vectors, CRDTs, or application-level conflict handling.

Examples:

- Cassandra with LWW or custom conflict resolution
- DynamoDB global tables
- CockroachDB with distributed SQL and transactional guarantees
- Spanner with globally distributed transactions

#### 4. Leaderless replication

Any replica can accept writes.

Pros:

- High availability.
- No single write bottleneck.

Cons:

- Complex consistency.
- Requires read repair, hinted handoff, anti-entropy, and conflict resolution.

Used in systems inspired by Dynamo-style architectures.

### Replication consistency models

#### Strong consistency

All replicas agree on the same value before a write is considered committed.

Pros:

- Simple application semantics.
- No stale reads.

Cons:

- Higher latency.
- Less available during partitions.

#### Eventual consistency

Replicas may temporarily diverge but eventually converge.

Pros:

- High availability.
- Low latency.

Cons:

- Stale reads.
- Application must tolerate conflicts.

#### Causal consistency

Writes that causally depend on previous writes are seen in the same order.

Pros:

- Stronger than eventual consistency.
- More available than linearizability.

Cons:

- More complex implementation.

### CAP theorem and distributed databases

CAP says a distributed system cannot simultaneously guarantee:

- **Consistency**
- **Availability**
- **Partition tolerance**

In real distributed systems, partitions are unavoidable, so the choice is usually between consistency and availability during partitions.

PACELC extends this:

- If there is a Partition, choose Consistency or Availability.
- Else, if there is no Partition, choose Latency or Consistency.

This is important for performance:

- Strong consistency often increases latency.
- Low latency often requires weaker consistency.

## 3. Indexing in Distributed Databases

Indexes accelerate queries but are harder to design in distributed systems because data is partitioned and replicated.

### Types of distributed indexes

#### 1. Local indexes

Each shard maintains its own index over its local data.

Example:

```text
Shard A: index over rows in shard A
Shard B: index over rows in shard B
```

Pros:

- Simple.
- Low coordination.
- Good for queries that include the partition key.

Cons:

- Queries without partition key must scan all shards.
- Global uniqueness constraints are difficult.

#### 2. Global indexes

An index spans multiple shards and maps values to the shards containing matching rows.

Example:

```text
email -> shard 7
email -> shard 12
```

Pros:

- Efficient queries on non-partition keys.
- Can enforce global uniqueness.

Cons:

- More complex.
- Index updates may require cross-shard coordination.
- Can become a bottleneck.

#### 3. Secondary indexes

Secondary indexes are built on non-primary columns.

Example:

```text
PRIMARY KEY: customer_id
SECONDARY INDEX: city
```

In a distributed database, a secondary index may be:

- Local to each shard
- Global across shards
- Replicated
- Partitioned by indexed value

#### 4. Covering indexes

A covering index contains all columns needed by a query, avoiding access to the base table.

Example:

```text
INDEX (city, name)
```

For query:

```sql
SELECT name FROM customers WHERE city = 'Berlin';
```

The index can answer the query without fetching the full row.

Pros:

- Reduces I/O.
- Reduces network fetches.

Cons:

- Larger index size.
- More write overhead.

#### 5. Composite indexes

Indexes on multiple columns.

Example:

```text
INDEX (tenant_id, created_at)
```

Useful for multi-tenant systems.

Important rule:

```text
WHERE tenant_id = ? AND created_at > ?
```

can use the composite index efficiently.

But:

```text
WHERE created_at > ?
```

may not use it efficiently unless the index is designed differently.

#### 6. Inverted indexes

Used for full-text search.

Example:

```text
"database" -> documents 10, 25, 42
```

In distributed systems, inverted indexes are often sharded by term or document ID.

Pros:

- Excellent for search.

Cons:

- Expensive to update.
- Requires coordination for global term statistics.

#### 7. Vector indexes

Used for similarity search and embeddings.

Example:

```text
ANN index over embedding vectors
```

In distributed systems, vector indexes may be sharded and searched in parallel.

Pros:

- Useful for recommendation and semantic search.

Cons:

- High memory and CPU cost.
- Approximate results may be returned.

### Index design principles

#### 1. Include partition key in hot queries

If queries include the partition key, the database can route directly to the correct shard.

Good:

```sql
SELECT * FROM orders WHERE customer_id = 123;
```

Bad:

```sql
SELECT * FROM orders WHERE status = 'pending';
```

If `status` is not indexed globally, the query may fan out to all shards.

#### 2. Avoid hot indexes

If many writes update the same index entry, that index can become a bottleneck.

Example:

```text
INDEX (counter_name)
```

with frequent updates to the same counter.

#### 3. Prefer local indexes when possible

Local indexes reduce cross-shard coordination.

#### 4. Use global indexes carefully

Global indexes improve query flexibility but increase write cost.

#### 5. Consider index replication

If indexes are replicated, reads can be served locally, but writes must update multiple copies.

#### 6. Watch write amplification

Every index adds work to writes.

If a table has 5 indexes, one insert may require:

```text
1 base table write
+ 5 index writes
```

In a distributed system, each index write may also require replication.

### Index performance issues

#### Cross-shard scans

Queries without partition keys may need to contact many shards.

Example:

```sql
SELECT * FROM logs WHERE message LIKE '%error%';
```

This may require scanning all shards.

#### Distributed joins

Joins across shards can be expensive.

Example:

```sql
SELECT *
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id;
```

If orders and customers are partitioned differently, the database may need to:

- Broadcast one table
- Shuffle data
- Fetch rows from many shards
- Use a global index

#### Index maintenance during rebalancing

When shards move between nodes, indexes may need to be rebuilt or migrated.

#### Index skew

Some index ranges may receive disproportionate traffic.

Example:

```text
city = 'New York'
```

may have many more rows than smaller cities.

## 4. Transactions in Distributed Databases

A transaction is a logical unit of work that must satisfy ACID properties:

- **Atomicity**: all or nothing.
- **Consistency**: database moves from one valid state to another.
- **Isolation**: concurrent transactions do not interfere incorrectly.
- **Durability**: committed changes survive failures.

Distributed transactions are harder because data may be on multiple nodes.

### Distributed transaction challenges

A transaction may involve:

- Multiple shards
- Multiple replicas
- Multiple data centers
- Multiple indexes
- Multiple services

The system must ensure that either all participants commit or all abort.

### Two-phase commit

Two-phase commit, or 2PC, is the classic protocol for distributed transactions.

#### Phase 1: Prepare

Coordinator asks all participants:

```text
Can you commit?
```

Each participant:

1. Writes transaction log records.
2. Locks required resources.
3. Responds yes or no.

#### Phase 2: Commit or abort

If all participants vote yes:

```text
Coordinator sends COMMIT
Participants commit
```

If any participant votes no:

```text
Coordinator sends ABORT
Participants roll back
```

Pros:

- Provides atomic commit across nodes.

Cons:

- Coordinator can become a bottleneck.
- Participants may block while waiting for coordinator.
- High latency.
- Poor availability during network partitions.

### Three-phase commit

Three-phase commit attempts to reduce blocking in 2PC.

Phases:

1. Can commit?
2. Pre-commit?
3. Commit?

Pros:

- Less blocking than 2PC in some failure scenarios.

Cons:

- More complex.
- Still not fully safe under all network partitions.
- Rarely used in practice.

### Optimistic concurrency control

Transactions execute without locking and validate at commit time.

Flow:

1. Read data.
2. Perform local work.
3. At commit, check whether dependencies changed.
4. If conflict detected, abort and retry.

Pros:

- Good for low-contention workloads.
- Low locking overhead.

Cons:

- High retry rate under contention.
- Requires versioning or validation.

### Pessimistic concurrency control

Transactions acquire locks before modifying data.

Example:

```text
SELECT ... FOR UPDATE
```

Pros:

- Prevents conflicts early.
- Easier to reason about.

Cons:

- Lock waits.
- Deadlocks.
- Reduced throughput under contention.

### Isolation levels

Common isolation levels:

#### Read uncommitted

Transactions may see uncommitted changes.

Pros:

- High performance.

Cons:

- Dirty reads.
- Rarely acceptable.

#### Read committed

Transactions see only committed data.

Pros:

- Avoids dirty reads.

Cons:

- Non-repeatable reads.
- Phantom reads.

#### Repeatable read

A transaction sees the same values throughout its duration.

Pros:

- Avoids non-repeatable reads.

Cons:

- May still allow phantom reads depending on implementation.

#### Serializable

Transactions behave as if executed one at a time.

Pros:

- Strongest correctness.

Cons:

- Highest overhead.
- May require locking, snapshot isolation, or conflict detection.

#### Snapshot isolation

Each transaction sees a consistent snapshot of the database.

Pros:

- Good performance.
- Avoids many anomalies.

Cons:

- Write skew anomalies possible.

### Distributed transaction performance

Distributed transactions are expensive because they require coordination.

Costs include:

- Network round trips
- Lock coordination
- Log flushing
- Replication acknowledgments
- Conflict detection
- Retry overhead

### Reducing distributed transaction cost

#### 1. Co-locate related data

Partition related rows together.

Example:

```text
Partition by customer_id
```

Then orders and order items for the same customer can be updated locally.

#### 2. Avoid cross-shard transactions

Design schema so most transactions touch one shard.

#### 3. Use idempotent operations

If a transaction may be retried, operations should be safe to repeat.

#### 4. Use optimistic concurrency

Use version numbers or timestamps.

Example:

```sql
UPDATE accounts
SET balance = balance - 100, version = version + 1
WHERE account_id = 42 AND version = 7;
```

If zero rows are updated, retry.

#### 5. Use batched commits

Group multiple operations into one transaction when safe.

#### 6. Use asynchronous processing

For non-critical updates, use queues or event sourcing.

#### 7. Use saga pattern

For long-running business transactions, break work into local transactions with compensating actions.

Example:

```text
reserve inventory
charge payment
ship order
```

If shipping fails, compensate by refunding payment and releasing inventory.

## 5. Recovery in Distributed Databases

Recovery is the process of restoring correct database state after failures.

Failures can include:

- Process crash
- Disk failure
- Node failure
- Network partition
- Data-center outage
- Corrupted data
- Accidental deletion
- Software bug

### Recovery mechanisms

#### 1. Write-ahead logging

Write-ahead logging, or WAL, records changes before applying them to data pages.

Rules:

1. Log record is written before data modification.
2. Log record is flushed before commit.
3. Recovery can redo committed transactions and undo uncommitted transactions.

Pros:

- Enables crash recovery.
- Supports replication and point-in-time recovery.

Cons:

- Log writes add latency.
- Requires log management and retention.

#### 2. Checkpoints

A checkpoint records a consistent database state.

During recovery:

1. Load latest checkpoint.
2. Replay log records after checkpoint.

Pros:

- Reduces recovery time.

Cons:

- Checkpointing consumes I/O and CPU.

#### 3. Replication-based recovery

If a primary fails, a replica can be promoted.

Requirements:

- Replicas must be sufficiently up to date.
- Failover must avoid split-brain.
- New leader must know committed transactions.

#### 4. Quorum-based recovery

In quorum systems, recovery may require contacting a majority of replicas.

Example:

```text
5 replicas
majority = 3
```

A new leader may need to read from at least 3 replicas to determine committed state.

#### 5. Consensus protocols

Modern distributed databases often use consensus protocols such as:

- Raft
- Paxos
- Multi-Paxos
- Raft variants

Consensus ensures:

- Only one leader is elected.
- Committed log entries are not lost.
- Replicas agree on ordering.

Raft is widely used because it is easier to understand than Paxos.

### Failure scenarios

#### 1. Single node failure

If one replica fails:

- Reads can be served by other replicas.
- Writes may continue if quorum is available.
- Failed node rejoins and catches up from logs.

#### 2. Leader failure

If the leader fails:

1. Followers detect missing heartbeats.
2. Election begins.
3. New leader is elected.
4. Clients reconnect to new leader.

Performance impact:

- Temporary write unavailability.
- Client retries.
- Possible latency spike.

#### 3. Network partition

A network partition may separate nodes into groups.

The system must choose:

- **CP**: remain consistent, reject some requests.
- **AP**: remain available, allow divergence.

Example:

```text
Region A has 3 replicas
Region B has 2 replicas
```

If partitioned, Region A may continue because it has quorum. Region B may become unavailable for writes.

#### 4. Data loss

If a replica loses data:

- It must be rebuilt from snapshots and logs.
- It may be removed temporarily to avoid serving stale data.

#### 5. Corrupted data

Recovery may require:

- Checksums
- Scrubbing
- Rebuilding from healthy replicas
- Restoring from backup

### Backup and point-in-time recovery

Distributed databases often support:

- Full snapshots
- Incremental backups
- Log backups
- Point-in-time recovery

Point-in-time recovery allows restoring to a specific timestamp.

Example:

```text
Restore database to 2026-01-01 10:15:00
```

This is useful for:

- Accidental deletion
- Bad migration
- Application bug
- Data corruption

### Recovery performance considerations

Recovery should be fast and predictable.

Important factors:

1. **Recovery time objective**
   - How quickly must the system recover?

2. **Recovery point objective**
   - How much data loss is acceptable?

3. **Log retention**
   - More logs allow better point-in-time recovery but consume storage.

4. **Snapshot frequency**
   - Frequent snapshots reduce replay time.

5. **Replica lag**
   - Lagging replicas may not be safe to promote.

6. **Failover automation**
   - Manual failover is slow.
   - Automatic failover improves availability but must be carefully designed.

7. **Client retry behavior**
   - Clients must handle transient failures and retries.

## 6. Performance of Distributed Databases

Performance depends on many interacting factors.

### Main performance factors

#### 1. Network latency

Network latency is often the dominant cost.

Examples:

- Same rack: low latency
- Same data center: moderate latency
- Cross-region: high latency
- Cross-continent: very high latency

Strong consistency across regions can be slow because commits require acknowledgments from distant replicas.

#### 2. Network bandwidth

Large scans, joins, and index rebuilds can consume bandwidth.

#### 3. Data locality

Queries are faster when data is stored near compute nodes or users.

#### 4. Partitioning strategy

Poor partitioning causes:

- Hot shards
- Cross-shard queries
- Skewed load
- Expensive rebalancing

#### 5. Replication factor

More replicas improve availability and read capacity but increase write cost.

#### 6. Consistency level

Strong consistency requires coordination and increases latency.

#### 7. Index design

Good indexes reduce scans.

Bad indexes increase write cost and memory usage.

#### 8. Transaction scope

Large transactions touching many shards are expensive.

#### 9. Lock contention

Hot rows or hot index entries can serialize updates.

#### 10. Garbage collection and compaction

Many distributed storage engines use LSM trees.

LSM trees optimize writes but require background compaction.

Compaction can cause:

- CPU spikes
- I/O spikes
- Latency jitter

#### 11. Failure detection and recovery

Aggressive failure detection can cause unnecessary failovers.

Slow failure detection can cause long outages.

### Read performance

Read performance improves with:

- Local replicas
- Caching
- Covering indexes
- Partition-key queries
- Read quorums that avoid coordination
- Materialized views
- Denormalization

Read performance suffers from:

- Cross-shard scans
- Distributed joins
- Stale index data
- Too many replicas to read
- Poor cache hit rates

### Write performance

Write performance improves with:

- Local writes
- Asynchronous replication
- Batched commits
- Few indexes
- Good partitioning
- Low contention

Write performance suffers from:

- Synchronous cross-region replication
- Global indexes
- Distributed transactions
- Hot partitions
- Frequent compaction
- Large transaction logs

### Query performance

Distributed query optimization must consider:

- Partition pruning
- Index selection
- Join order
- Data movement
- Network cost
- Replication state
- Consistency requirements

A good distributed query plan often avoids:

- Full cluster scans
- Large cross-shard joins
- Cross-region coordination
- Repeated index lookups across shards

## 7. Design Tradeoffs

### Strong consistency vs availability

Strong consistency is easier for applications but reduces availability during failures.

Availability is useful for user-facing systems but can produce stale or conflicting data.

### Low latency vs durability

Waiting for disk flush and replica acknowledgment improves durability but increases latency.

### Read scalability vs write scalability

Replicas help reads but increase write cost.

### Global indexes vs local indexes

Global indexes improve query flexibility but increase write coordination.

### Sharding by user vs sharding by time

Sharding by user can keep related data together.

Sharding by time can help logs and analytics but may create hot recent shards.

### Synchronous vs asynchronous replication

Synchronous replication reduces data loss risk but increases latency.

Asynchronous replication improves latency but can lose recent writes during failover.

---

## 8. Practical Design Guidelines

### For data modeling

1. Choose a partition key that spreads load evenly.
2. Co-locate data that is frequently updated together.
3. Avoid large cross-shard transactions.
4. Denormalize when read performance matters more than update complexity.
5. Use tenant or customer IDs in indexes for multi-tenant workloads.

### For replication

1. Use synchronous or quorum replication for critical data.
2. Use asynchronous replication for analytics or non-critical reads.
3. Monitor replica lag.
4. Avoid promoting lagging replicas.
5. Use consensus protocols for leader election.

### For indexing

1. Prefer local indexes when queries include partition keys.
2. Use global indexes only when necessary.
3. Avoid indexes with high write amplification.
4. Use covering indexes for hot read paths.
5. Monitor index skew and hot index entries.

### For transactions

1. Keep transactions short.
2. Avoid cross-shard transactions when possible.
3. Use optimistic concurrency for low-contention workloads.
4. Use pessimistic locking for high-contention critical updates.
5. Use idempotency keys for retries.
6. Use sagas for long-running workflows.

### For recovery

1. Use write-ahead logging.
2. Take regular snapshots.
3. Retain logs for point-in-time recovery.
4. Test failover regularly.
5. Define RPO and RTO clearly.
6. Monitor replication lag and node health.
7. Avoid split-brain with fencing or consensus.

## 9. Example: Designing a Distributed E-Commerce Database

Suppose we design a distributed database for an e-commerce system.

### Workload

- Customers browse products.
- Customers place orders.
- Inventory must be updated accurately.
- Orders must not be lost.
- Read traffic is much higher than write traffic.
- Users are distributed globally.

### Design choices

#### Partitioning

Partition orders by `customer_id`.

```text
orders partitioned by customer_id
order_items partitioned by customer_id
```

This allows a customer’s order history to be queried from one shard.

#### Replication

Use three replicas per shard.

- One leader
- Two followers

For critical writes:

```text
W = 2
R = 2
N = 3
```

This provides strong consistency for order writes.

#### Indexing

Use local indexes:

```text
(customer_id, created_at)
```

Use a global index for:

```text
order_id
```

because support staff may search by order ID without knowing the customer.

#### Transactions

Order creation updates:

- orders
- order_items
- inventory

If inventory is partitioned by product ID, the transaction may cross shards.

To reduce cost:

- Reserve inventory asynchronously.
- Use optimistic concurrency on inventory rows.
- Use idempotency keys to prevent duplicate orders.

#### Recovery

Use:

- WAL
- Snapshots
- Log backups
- Automatic leader election
- Point-in-time recovery

## 10. Summary

A distributed database is designed to scale across multiple machines while maintaining reliability and correctness. Its performance depends heavily on how data is partitioned, replicated, indexed, and coordinated.

### Replication

Replication improves availability, read scalability, and disaster recovery. It introduces consistency and write-performance tradeoffs. Synchronous replication is safer but slower; asynchronous replication is faster but can lose data.

### Indexing

Indexes reduce query latency but increase write cost. In distributed systems, local indexes are simpler, while global indexes provide flexibility at the cost of coordination.

### Transactions

Distributed transactions require coordination across nodes. Two-phase commit provides atomicity but can be slow and blocking. Optimistic concurrency, co-location, idempotency, and sagas can reduce distributed transaction overhead.

### Recovery

Recovery relies on logs, checkpoints, replication, consensus, and backups. The system must handle node failures, network partitions, data loss, and corruption while meeting recovery time and data-loss objectives.

### Performance

The main performance drivers are network latency, data locality, partitioning, replication factor, consistency level, index design, transaction scope, and background maintenance such as compaction and recovery. Good distributed database design minimizes cross-node coordination and keeps hot workloads local whenever possible.
